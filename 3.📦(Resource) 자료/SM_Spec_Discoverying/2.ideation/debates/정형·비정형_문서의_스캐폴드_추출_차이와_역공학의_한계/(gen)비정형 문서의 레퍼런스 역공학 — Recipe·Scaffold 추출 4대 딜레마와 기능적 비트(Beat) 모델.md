# 비정형 문서의 레퍼런스 역공학 — Recipe·Scaffold 추출 4대 딜레마와 기능적 비트(Beat) 모델

> **핵심 테제**:  
> 정형 문서는 외재적 서식(Explicit Template: 목차, 번호, 표)을 복제하면 끝나지만, 블로그·유튜브 스크립트·테크 아티클 같은 비정형 문서는 겉으로 드러난 목차가 없다.  
> 비정형 글의 역공학은 표면적 문단 분해가 아니라, **"독자의 인지적 주의력을 통제하는 보이지 않는 심층 구조(Invisible Architecture)와 기능적 비트(Functional Beat)"**를 발라내는 작업이어야 한다.

---

## 1. 문제의 배경: 정형 문서 vs 비정형 문서의 역공학 격차

스캐폴드 매니저(Scaffold Manager)의 핵심 엔진인 `Dynamic Schema Extraction`이 레퍼런스 문서를 입력받아 `Recipe(지침·원칙)`와 `Scaffold(뼈대·슬롯)`로 디컴파일할 때, 문서의 성격에 따라 난이도의 불연속적 도약이 발생한다.

| 구분 | 정형 문서 (공문서, 특허, 규격 사업계획서) | 비정형 문서 (블로그, 유튜브 스크립트, 테크 분석글) |
| :--- | :--- | :--- |
| **외재적 구조** | 목차 번호(1.1, 1.2), 표 양식, 공식 서식 명확 | 자연스러운 줄글 흐름, 명시적 목차 결여 |
| **목적 함수** | 공개된 평가지표 및 규격 요건 (외부화됨) | 독자의 체류 시간, 주의력 유지, 설득 (암묵화됨) |
| **추출 대상** | 텍스트 박스 빈칸(Slot)과 고정 보일러플레이트 | 독자의 뇌를 공략하는 텐션의 호흡과 인지적 기능 |
| **역공학 난이도** | **낮음** (구조와 내용이 이미 시각적으로 분리됨) | **극도로 높음** (소재와 작법이 화학적으로 결합됨) |

---

## 2. 비정형 레퍼런스 ➔ Recipe & Scaffold 추출의 4대 본질적 딜레마

### 2.1. 내용(Content)과 그릇(Form)의 박리 불가능성 (De-contenting의 딜레마)
* **현상**: 비정형 글의 구조는 필자의 개인적 일화, 독창적 비유, 수사적 질문, 통계 데이터와 한 몸으로 결합되어 있다.
* **추출 엔진의 진퇴양난**:
  1. **과도한 탈색(Over-abstraction)**: 레퍼런스의 구체적 소재와 팩트를 털어내면 *"도입부에서 흥미를 유발한다"* 같은 **맹탕 요약**만 남아 실제 글을 쓸 때 아무런 와꾸 효용을 주지 못함.
  2. **과도한 결속(Over-fitting)**: 구체성을 살리려 하면 레퍼런스 원문의 고유 명사와 사례까지 스키마에 박혀버려, **새로운 주제를 부었을 때 틀이 부러지는 기형적 스캐폴드**가 도출됨.
* **핵심 질문**: *"원문의 소재(Fact)는 완벽히 증발시키면서도, 저자가 설계한 '논리적 긴장감의 골격'만 순수하게 추출하는 경계선은 어디인가?"*

---

### 2.2. 호흡과 템포(Rhythm/Beat)의 분류 경계 증발 (지침 vs 블록의 중첩)
* **현상**: 비정형 글의 승부처는 줄거리(Plot)가 아니라 독자의 도파민과 집중력을 끌고 가는 **'시간 축 위의 전개 템포'**다.
  * *예: "초반 15초(3문장) 안에 상식을 깨는 질문으로 멱살을 잡고 ➔ 1분대에 내 실패 경험으로 무장해제를 시킨 뒤 ➔ 3분대에 프레임워크 3단계를 제시한다."*
* **사양의 모호함**:
  * 이것은 글 전체를 관통하는 작법 원리이므로 **Recipe**인가?
  * 아니면 타임라인 순서대로 배치되어 데이터를 채워 넣어야 할 **Scaffold(Outline & Segment)**인가?
* 비정형 글에서는 **"지침(How to write)이 곧 시간순 블록(Where to put)"**이 되므로, Recipe와 Scaffold가 분리되지 않고 동일한 실체의 양면으로 겹쳐버린다.

---

### 2.3. 스키마 입도(Granularity)의 딜레마 (헐렁함 vs 경직성)
레퍼런스를 어느 층위의 단위 블록으로 잘라낼 것인가에 대한 추상화 계층의 충돌이다.

```text
[Macro Level: 헐렁함]  ➔  도입  ➔  문제 제기  ➔  해결책  ➔  결론
                         (누구나 아는 교과서적 구조 ➔ 빈 화면의 막막함 해결 불가)

[Micro Level: 경직성]  ➔  1문장: 도발  ➔  2문장: 통계  ➔  3문장: 반전  ➔  4문장: 결론
                         (문장 단위 강제 분해 ➔ 새 소재 투입 시 틀 파괴, 집필 질식)
```

* **Sweet Spot의 부재**: 레퍼런스의 '맛(Voice & Persuasion)'을 온전히 보존하면서도, 상이한 데이터를 유연하게 수용할 수 있는 최적의 중간 입도(Medium Granularity) 스키마 정의가 극히 까다롭다.

---

### 2.4. 암묵적 목적 함수(Implicit Objective / Angling) 역산의 한계
* **현상**: 정형 문서는 채점표가 바깥에 공개되어 있지만, 비정형 글은 **"독자의 결핍을 어떤 각도로 관통할 것인가(Angling: 타깃 독자, 페인 포인트, 반직관적 관점, 독자 획득 가치)"**가 저자의 직관(암묵지) 속에만 존재한다.
* **추론의 비약**: 겉으로 드러난 텍스트 결과물만 보고 *"저자가 왜 이 시점에 통계를 들이밀었고, 왜 이 타이밍에 예시를 끊고 반전을 주었는가"*라는 저자의 집필 전략(Recipe의 핵심 엔진)을 LLM이 자의적 왜곡 없이 역공학하기 어렵다.

---

## 3. 해결 프레임워크: "기능적 비트(Functional Beat)와 제약(Constraint)"

비정형 문서의 모호함을 해소하기 위해, 문단을 텍스트 단위로 보지 않고 **인지 공학적 '기능(Role)' 단위**로 재정의한다.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                          Functional Beat Model                         │
├───────────────┬──────────────────────────────────┬─────────────────────┤
│  단위 구분    │            Recipe 측면           │   Scaffold 측면     │
│   (Beats)     │       (How / Constraint / Role)  │   (What / Container)│
├───────────────┼──────────────────────────────────┼─────────────────────┤
│ Beat 1: Hook  │ • 통념 부정 / 손실 회피 자극    │ • [도발 질문 슬롯]  │
│               │ • 3문장 이내 압축 (제약)         │ • [충격 통계 앵커]  │
├───────────────┼──────────────────────────────────┼─────────────────────┤
│ Beat 2: Agitate│ • 독자의 실패 경험 거울치기     │ • [페인 공감 단락]  │
│               │ • 필자의 취약성 노출 (Voice)     │ • [경험 서사 슬롯]  │
├───────────────┼──────────────────────────────────┼─────────────────────┤
│ Beat 3: Pivot │ • 기존 해결책의 한계 폭로        │ • [대조 분석표]     │
│               │ • 패러다임 전환 선언             │ • [새 명제 칩]      │
├───────────────┼──────────────────────────────────┼─────────────────────┤
│ Beat 4: Model │ • 3대 핵심 기둥 구조화           │ • [프레임워크 3단]  │
│               │ • 병렬 구조 및 직관적 넘버링     │ • [단계별 실행 슬롯]│
└───────────────┴──────────────────────────────────┴─────────────────────┘
```

1. **Recipe의 재정의**: 단순 스타일 가이드가 아니라, 각 비트가 달성해야 하는 **"심리적 역할(Role)과 통과 제약식(Constraint)"**.
2. **Scaffold의 재정의**: 단순 빈칸이 아니라, 해당 비트의 역할을 완수하기 위해 요구되는 **"기능적 소켓(Functional Socket)"**.

---

## 4. Scaffold Manager 엔진 설계를 위한 시사점

1. **'목차 파서'에서 '텐션/비트 파서'로의 진화**:  
   비정형 레퍼런스를 분해할 때는 H1/H2 파싱을 버리고, 텍스트의 감정 곡선·논리 전환점·증거 제시 구간을 탐지하는 **비트 시퀀스 추출기(Beat Sequence Extractor)**가 선행되어야 한다.
2. **소재 박리 필터(De-fact Filter)의 정립**:  
   레퍼런스에서 고유 명사, 특정 수치, 고유 서사를 변수화(`$VARIABLE`)하고, 그 자리를 차지하고 있던 **논리적 관계식(대조, 인과, 귀납, 반증)**만 뼈대로 남기는 프롬프트 하네스 구축이 필수적이다.
3. **Recipe와 Scaffold의 결합형 데이터 모델**:  
   비정형 글에서는 Recipe와 Scaffold를 물리적으로 분리된 별개 파일로 다루기보다, **"슬롯마다 자체 Recipe(역할·제약)를 내장하는 컴포넌트 소켓(Socket Specification)"** 형태로 통합하는 것이 자연스럽다.
