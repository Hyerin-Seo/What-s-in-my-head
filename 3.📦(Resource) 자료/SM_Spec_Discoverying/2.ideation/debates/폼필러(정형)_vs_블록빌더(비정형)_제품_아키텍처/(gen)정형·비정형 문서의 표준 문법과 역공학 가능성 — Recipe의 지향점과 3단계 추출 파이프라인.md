# 정형·비정형 문서의 표준 문법과 역공학 가능성 — Recipe의 지향점과 3단계 추출 파이프라인

> **핵심 테제**:  
> Recipe가 지향하는 궁극적 본질은  
> **"이 글의 목적과 유형, 거기에 따른 이쪽 작업에서 보편화되고 표준화된 문법은 무엇인가"**를 규정하는 것이다.  
> 정형과 비정형의 차이는 문법이 표 양식으로 겉에 드러나 있느냐, 줄글 속에 암묵적으로 숨겨져 있느냐의 차이일 뿐, **장르의 보편적 표준 문법을 복원하는 역공학은 100% 가능하며 지극히 유효하다.**

---

## 1. 정형 문서 vs 비정형 문서의 구조적 대조

| 비교 축 | 정형 문서 (사업계획서, 특허, 기술 보고서) | 비정형 문서 (맛집, 여행, 기술 블로그) |
| :--- | :--- | :--- |
| **공통점 1: 목적 지향성** | 심사위원 통과, 자금 유치, 규격 준수 | 독자의 방문 의사결정, 트러블슈팅, 지식 습득 |
| **공통점 2: 보편적 표준 문법** | [문제 ➔ 솔루션 ➔ 시장 ➔ BM ➔ 팀]의 **업계 표준** | [위치/주차 ➔ 메뉴/가격 ➔ 실물 ➔ 팁]의 **장르 표준** |
| **공통점 3: 팩트와 틀의 분리** | 양식 껍데기와 내 데이터(기업명, 수치)가 분리됨 | 시선의 동선(와꾸)과 내 미디어(사진, 코드)가 분리됨 |
| **차이점 1: 문법의 가시성** | **외재적 (Explicit)**: 번호(1.1, 1.2), 표 칸막이로 명시 | **내재적 (Implicit)**: 줄글과 사진 배치 속에 관습으로 숨겨짐 |
| **차이점 2: 규칙 위반의 페널티** | **서류 탈락**: 필수 항목 누락 시 심사 불합격 | **독자 이탈**: 필수 정보(주차, diff 코드) 누락 시 뒤로 가기 |
| **차이점 3: 형태의 가소성** | **경직됨 (Rigid)**: 양식 칸의 크기와 순서 변경 불가 | **탄력적 (Elastic)**: 내 팩트의 양에 따라 블록 크기 유연 조절 |

## 2. 역공학의 가능성 판정: "무엇을 역공학하는가?"

"비정형 문서의 역공학은 불가능한가?"라는 질문의 답은 역공학의 대상을 어디에 두느냐에 따라 갈린다.

### 2.1. 불가능한 역공학 (픽션 날조의 함정)
* 남의 글의 **'1회성 특수한 개인 서사'**(토스닥터의 10개 비트, 토큰 터진 이야기, E1~E5 복구 로그)를 뼈대로 강제하려는 역공학.
* 내 프로젝트에는 해당 사항이 없으므로, 글의 틀을 맞추기 위해 **거짓말(소설)을 지어내야 하는 치명적 오류**에 도달한다.

### 2.2. 완전히 가능한 역공학 (Recipe의 진짜 영역)
* 레퍼런스에서 고유 사실(흑돼지, Appium 에러)은 완벽히 휘발시키고, 다음 3가지를 복원하는 역공학:
  1. **목적과 유형 식별**: "이 글은 '장애 해결 중심의 기술 블로그'다."
  2. **보편적 표준 문법 추출**: "이 장르에서 독자가 기대하는 필수 의무 블록은 [에러 증상 ➔ 원인 분석 ➔ 해결 diff ➔ 주의점]이다."
  3. **시선의 동선 추출**: "독자가 스크롤을 내릴 때 가장 편안한 배치는 [에러 화면을 상단에 박고, 해결 코드를 가운데 배치]하는 흐름이다."
* 이 3가지를 발라내는 작업은 **정형이든 비정형이든 100% 가능하며, AI가 가장 압도적인 성능을 발휘하는 영역**이다.

## 3. Scaffold Manager 역공학 엔진의 3단계 실행 파이프라인

Scaffold Manager는 남의 줄거리를 흉내 내는 것이 아니라, 레퍼런스로부터 **"그 장르의 보편적 표준 문법(Recipe)"**을 복원하여 사용자에게 깨끗한 작업 공간(Scaffold)을 제공해야 한다.

```text
┌────────────────────────────────────────────────────────────────────────┐
│             Scaffold Manager Dynamic Extraction Pipeline               │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
 [Input] 임의의 레퍼런스 투입 (예: 토스닥터 글 or 성수동 맛집 글)
                                   │
                                   ▼
 [Step 1: 목적·유형 추론]
    • 문서의 지향 목적과 장르 카테고리 판별
    • "이 글은 '실전 기술 문제 해결기' 유형이다."
                                   │
                                   ▼
 [Step 2: 보편적 표준 문법(Recipe) 복원]
    • 장르가 요구하는 필수 의무 블록(Must-Have Blocks) 도출
      - Block 1: [에러 증상] 터미널 에러 로그 / 스택 트레이스
      - Block 2: [원인 규명] 공식 문서 근거 및 아키텍처 다이어그램
      - Block 3: [해결 코드] 최종 설정 diff (`-`, `+`)
      - Block 4: [주의점/교훈] 버전 호환성 및 부작용 체크리스트
                                   │
                                   ▼
 [Step 3: 빈 와꾸(Scaffold) 자동 직조 & 소켓 렌더링]
    • 각 블록의 '역할(Role)'이 라벨링된 빈 소켓들을 시선 순서대로 화면에 배치
    • 사용자는 백지 공포 없이, 각 소켓에 자신의 진짜 사실(Fact)만 꽂아 넣음!
```

## 4. 최종 결론

1. **Recipe의 정체성 확립**:  
   Recipe는 특정 개인의 일회성 작법 가이드가 아니라, **"그 목적과 유형에서 통용되는 '보편화된 표준 문법(Standard Syntax)'"**이다.
2. **역공학의 현실화**:  
   비정형 문서의 역공학은 남의 서사를 베끼는 게 아니라, **"줄글 속에 숨겨진 표준 문법과 시선 동선을 발라내어 사용자에게 맞춤형 빈 뼈대(Scaffold)를 깔아주는 것"**이다.
3. **진실성과 생산성의 공존**:  
   사용자는 표준 문법이라는 든든한 뼈대 위에서, 겪지도 않은 거짓말(Fiction)을 지어낼 필요 없이 **오직 자신의 진짜 팩트(Fact)만을 투입하여 최고 품질의 글을 완성**할 수 있다.
