# 블로그 레퍼런스 차용의 본질 — 장르별 필수 정보 블록(중심)과 고유 사실(가변)

> **핵심 테제**:  
> 우리가 일상에서 맛집·여행·기술 블로그를 북마크해 두고 "이 글을 레퍼런스로 삼아야겠다"고 할 때,  
> 훔쳐 오려는 것은 글의 내용(고기 맛, 특정 에러 코드)이 아니다.  
> 독자가 그 장르에서 기대하는 **[필수 정보 블록]**과 **[시선이 편안한 배치 순서(와꾸)]**를 빌려와, 그 틀 안에 **[내 진짜 사진과 팩트]**를 쏟아붓는 행위다.

---

## 1. 일상에서 마주치는 장르별 '공통의 상' (독자의 뇌 속 기본 기대치)

사람들은 특정 장르의 글을 클릭할 때 이미 무의식적으로 **"이 내용들이 나와야 한다"**는 필수 부품 목록을 상식처럼 갖고 있다.

| 장르 | 독자가 반사적으로 기대하는 필수 장면 (공통 블록) | 빠졌을 때 독자의 반응 |
| :--- | :--- | :--- |
| **맛집 블로그** | • 가게 외관/간판<br>• **지도, 영업시간, 브레이크타임, 주차 정보 박스**<br>• 메뉴판 및 가격대<br>• 음식 전체 샷 ➔ 클로즈업 젓가락 샷<br>• **웨이팅 팁 및 총평 (재방문 의사, 동행 추천)** | *"위치랑 주차 정보도 없네? 낚시글이네"* ➔ 즉시 이탈 |
| **여행 블로그** | • 공항/티켓 출발 샷<br>• 1일차 동선 타임라인<br>• 숙소 룸 컨디션 및 창밖 뷰<br>• 주요 명소 인증샷 및 식사<br>• **총 경비 정산표 (비용) 및 준비물 꿀팁** | *"일정 코스랑 비용 정보가 없어서 쓸모없다"* ➔ 실용성 상실 |
| **기술 블로그** | • **터미널 에러 로그 / 스택 트레이스 캡처**<br>• 흔한 구글링 해결책의 실패 언급<br>• **핵심 원인 분석 (공식 문서 근거 / 다이어그램)**<br>• **최종 해결 코드 및 설정 diff (`-`, `+`)**<br>• 성공 실행 로그 및 주의점/교훈 | *"코드랑 에러 메시지도 안 보여주고 말만 하네"* ➔ 뒤로 가기 |

## 2. 레퍼런스 차용의 이원화 구조: [중심(척추)] vs [가변(치환)]

우리가 레퍼런스를 볼 때 취사선택하는 경계선은 명확하다.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Reference Deconstruction                        │
├──────────────────────────────────┬─────────────────────────────────────┤
│         중심 (척추 / 불변)        │          가변 (유동적 / 치환)        │
│   "레퍼런스에서 훔쳐 오는 것"    │        "100% 내 것으로 채우는 것"   │
├──────────────────────────────────┼─────────────────────────────────────┤
│ 1. 장르별 필수 의무 정보 블록     │ 1. 내 고유의 사실 데이터 (Facts)   │
│    (기본 정보 박스, 메뉴판, diff) │    (내 식당 위치, 내 에러 메시지)  │
├──────────────────────────────────┼─────────────────────────────────────┤
│ 2. 독자의 시선이 편안한 배치 순서│ 2. 내 주관적 감상과 현장 에피소드    │
│    (외관 ➔ 정보 ➔ 실물 ➔ 총평)   │    (바질 향이 좋았다, 평일 낮 방문) │
├──────────────────────────────────┼─────────────────────────────────────┤
│ 3. 독자의 의사결정을 돕는 기준선 │ 3. 블록별 세부 수량과 크기          │
│    (가성비, 웨이팅 난이도, 주의점)│    (사진 3장 vs 10장, 코드 줄 수)   │
└──────────────────────────────────┴─────────────────────────────────────┘
```

### 2.1. 중심 (척추 / 불변): 레퍼런스에서 훔쳐 오는 것
1. **장르별 필수 의무 블록 (Must-Have Information Blocks)**:
   * "메뉴판은 음식 사진 나오기 전에 보여준다", "주차 정보는 본문 상단 박스로 뺀다", "기술 글은 에러 메시지를 전면에 박고 시작한다"는 **정보의 완전성 규칙**.
2. **독자의 시선이 편안한 배치 동선 (Information Flow)**:
   * 독자가 스크롤을 내릴 때 인지적 저항 없이 자연스럽게 정보를 소비할 수 있도록 설계된 **배치 순서(와꾸)**.
3. **의사결정을 돕는 평가 기준선 (Evaluation Criteria)**:
   * 단순 일기를 넘어 남에게 유용한 정보가 되게 만드는 기준 (예: 맛집의 '동행 대상 추천', 기술 글의 '도입 시 주의할 부작용').

### 2.2. 가변 (유동적 / 치환): 100% 내 것으로 채우는 것
1. **내 고유의 사실과 미디어 (My Facts & Media)**:
   * 레퍼런스는 제주 흑돼지였지만 내 글은 성수동 파스타이고, 레퍼런스는 Appium 에러였지만 내 글은 Redis OOM이다. 
   * 사진, 수치, 코드, 위치는 100% 내 현실의 데이터로 치환된다.
2. **개인의 주관적 감상과 현장 에피소드 (Personal Voice)**:
   * 필자의 고유한 취향, 현장에서 겪은 소소한 사건, 솔직한 느낌.
3. **블록의 세부 수량과 비중 (Local Tuning)**:
   * 내 팩트의 양에 따라 사진이 3장일 수도, 코드가 50줄일 수도 있다.

## 3. Scaffold Manager 제품 설계를 향한 핵심 시사점

1. **'통짜 비트 강제'가 아니라 '장르별 필수 블록 프리셋' 제공**:  
   Scaffold Manager는 복잡한 코드가 아니라, 사용자가 "맛집 리뷰", "장애 해결 기술 블로그"를 고르면 **그 장르의 필수 의무 블록들(기본 정보 박스, 에러 로그 칸, 해결 diff 칸 등)이 자연스러운 시선 순서로 배치된 와꾸**를 기본 제공해야 한다.
2. **블록의 역할은 안내하고, 데이터는 사용자가 부어 넣는다**:  
   * 블록(Scaffold)은 "이 자리는 메뉴판과 가격대를 짚어주는 자리입니다"라고 역할만 정의하고,  
   * 사용자는 그 자리에 자신의 진짜 사진과 가격 팩트를 드래그앤드롭하여 채워 넣는다.
3. **레퍼런스는 '시선의 동선 템플릿'으로 기능한다**:  
   사용자가 레퍼런스 URL이나 아티클을 넣었을 때, 시스템이 뽑아내야 할 진짜 가치는 **"이 레퍼런스가 어떤 필수 블록들을 어떤 순서로 배치했는가(시선의 흐름)"**여야 한다.
