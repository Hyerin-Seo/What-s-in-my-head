# 문서 스캐폴딩의 두 갈래 길 — 정형(폼 필러) vs 비정형(웹사이트 블록 빌더) 비교와 1단계 정형 집중 전략

> **핵심 테제**:  
> **"정형 문서는 '빈칸 채우기(Form-Filling)'다."**  
> **"비정형 문서는 '웹사이트 빌더(Block Assembly)'에 가깝다."**  
> 겉보기엔 같은 문서 도구처럼 보이지만, 둘은 사용자의 인터랙션 모델과 시스템 아키텍처가 완전히 다른 두 개의 제품이다.  
> 1개월 타임박스 내에 'Cursor의 효용'을 실측하기 위해서는 **비정형 문서를 과감히 배제하고, 정형 문서의 빈칸 채우기 모델에 올인하는 단계적 쐐기(Wedge) 전략**이 필수적이다.

---

## 1. 2대 제품 아키텍처 본질 비교

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Product Fork in the Road                        │
├──────────────────────────────────┬─────────────────────────────────────┤
│      방법 A: 정형 문서 모델      │       방법 B: 비정형 문서 모델      │
│     (스마트 폼 필러 엔진)        │      (비주얼 블록 빌더 엔진)        │
├──────────────────────────────────┼─────────────────────────────────────┤
│ • 대표: PandaDoc, 특허/지원사업기│ • 대표: Framer, Webflow, Notion     │
│ • 방식: 고정된 빈칸 채우기       │ • 방식: 레고 블록 조립 및 재배치    │
│ • 틀(Scaffold): 불변의 고정 양식 │ • 틀(Scaffold): 가변적 모듈 블록    │
│ • 개발 난이도: 낮음 (스키마 중심)│ • 개발 난이도: 극도로 높음 (웹빌더) │
│ • 1개월 내 검증: 압도적 가능     │ • 1개월 내 검증: 공수 폭발로 불가   │
└──────────────────────────────────┴─────────────────────────────────────┘
```

### 1.1. 방법 A: 정형 문서 모델 ("빈칸 채우기")
* **작업 대상**: 정부 지원사업 계획서, 연구보고서, 회사 표준 품의서, 특허 문서 등.
* **사용자 행동**: 
  * 이미 목차(H1, H2)와 표 양식이 정해져 있음.
  * 와꾸를 고민할 필요 없이, **"각 칸에 들어갈 최적의 팩트와 수치를 던지고 AI와 함께 채우는 작업"**.
* **기술적 장점**:
  * 복잡한 블록 조립 UI/UX가 불필요함.
  * 백엔드 엔진(`packages/scaffold-engine`)에서 슬롯 매핑과 토큰 바인딩만 탄탄하게 구현하면 즉시 "10배 빠른 문서 작성" 효용을 입증 가능.

### 1.2. 방법 B: 비정형 문서 모델 ("웹사이트식 블록 조립")
* **작업 대상**: 맛집·여행·기술 블로그, 유튜브 스크립트, 뉴스레터, 랜딩페이지 등.
* **사용자 행동**:
  * 고정된 빈칸이 없음.
  * `[헤더 블록] ➔ [인용구 카드] ➔ [에러 로그 블록] ➔ [3단 대조표] ➔ [요약 칩]`처럼 **블록을 레고처럼 끼워 맞추고 순서를 바꾸는 작업**.
* **기술적 리스크**:
  * 사실상 **'웹사이트 빌더(Website Builder)' 수준의 프론트엔드 에디터 엔진**이 필요함.
  * 캔버스 드래그앤드롭, 블록별 반응형 조판, 블록 재정렬 상태 관리 등 개발 범위가 기하급수적으로 팽창하여, 이번 스프린트 내에 검증이 불가능해짐.

## 2. 전략적 선택의 기로 (Strategic Decision)

### 선택지 1: 비정형(블로그)은 과감히 버리고, '정형 문서'에만 올인한다 (권장)
* **결단**: 블로그나 자유 글쓰기는 이번 스프린트 범위에서 일체 배제.
* **효과**: 
  * 스펙이 극도로 단순해져 팀의 자원을 분산시키지 않음.
  * [Decision 03 (Scaffold Manager 단일 집중 및 규격 문서 한정)]의 헌법과 100% 일치.
  * 10월 30일 마일스톤 내에 비문학 규격 문서 작업자 대상 WTS/WTP 가치 검증(Value Risk)을 단숨에 돌파 가능.

### 선택지 2: 정형 문서를 버리고, '비정형 블록 빌더'로 피벗한다
* **결단**: 규격 문서를 포기하고 블로그/웹 콘텐츠 빌더로 전면 전환.
* **문제점**: 1개월 타임박스 내 완성이 불가능하며, 노션·프레이머와의 전면전에 노출되어 차별성을 잃고 좌초할 위험이 큼.

## 3. 추천 실행 로드맵: 단계적 쐐기 (Wedge) 전략

```text
[Phase 1: 10월 스프린트] ➔ 정형 문서 올인 (Wedge)
  • 타깃: 사업계획서, 기술 보고서, 특허 등 규격 문서
  • 메커니즘: '스마트 폼 필러' (빈칸 채우기)
  • 목표: 복잡한 프론트 없이 백엔드 하네스 기반 "Cursor의 압도적 속도" 입증
       │
       ▼ (Value Risk 검증 성공 후)
       │
[Phase 2: 상용 확장 단계] ➔ 비정형 블록 빌더로 진화 (Scale)
  • 타깃: 블로그, 아티클, 크리에이터 콘텐츠
  • 메커니즘: '웹사이트 빌더' (서랍/블록 조립 인터페이스 결합)
  • 목표: 검증된 백엔드 엔진 위에 모듈식 블록 UI를 얹어 대중 시장으로 확장
```

## 4. 최종 결론

지금 시점에서 팀이 취해야 할 가장 현명한 태도는 **"우리가 풀려는 문제가 지금 당장은 '웹사이트 빌더'가 아니라 '스마트 폼 필러'임을 인정하는 것"**이다.  
비정형 문서의 블록 조립 사양을 탐색하며 얻은 통찰은 아카이브해 두고, **현재의 실행은 정형 문서의 빈칸 채우기 엔진을 완벽하게 벼리는 데에만 100% 집중**해야 한다.
