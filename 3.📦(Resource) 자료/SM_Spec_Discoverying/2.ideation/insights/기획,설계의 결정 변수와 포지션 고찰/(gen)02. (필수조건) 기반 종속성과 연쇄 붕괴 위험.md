기획과 설계를 '하면 좋은 선택 사항'에서 **'무조건 해야만 하는 절대적 생존 조건'**으로 전환시키는 단 하나의 기준은 바로 **'기반 종속성(Foundation Dependency)'**입니다.

> 🛑 **"내가 만드는 결과물이 다른 작업(또는 타자)이 딛고 올라설 '발판(Foundation & Contract)'이 되는가?"**

---

### 1. 말단(Leaf Node) vs 기반(Foundation & Contract)의 본질적 차이

우리가 기획과 설계를 건너뛰고 '즉시 실행'할 수 있는 유일한 이유는 그 작업이 **'말단(Leaf Node)'**이기 때문입니다.

* **말단 작업 (Leaf)**:
  * 버튼 색상, UI 여백, 문장 윤문, 독립된 계산 유틸 함수.
  * 망가져도 **그 지점 하나만 뚝 떼어내어 5초 만에 고치면 끝**납니다. 연쇄 반응이 없습니다.
* **기반 작업 (Foundation & Contract)**:
  * 데이터 스키마(Flat 맵 vs 계층 트리), 상태 머신 전이 규칙, 글의 코어 메시지, API 인터페이스 규격.
  * 그 위에 다른 사람, 후속 작업, AI 에이전트의 산출물이 겹겹이 쌓여 올라갑니다.
  * **여기서 1도 틀어지면 상위의 모든 산출물이 도미노처럼 와르르 연쇄 붕괴(Cascading Failure)**됩니다.

---

### 2. 왜 기반 작업에서는 기획과 설계가 100% 강제되는가?

1. **실패 비용의 곱셈 법칙**:  
   말단에서의 실수는 덧셈으로 복구되지만, 기반에서의 실수는 상위에 연결된 모든 모듈과 문서에 **곱셈(Cascade)**으로 터집니다. 1,000줄의 코드와 10개의 챕터가 통째로 폐기됩니다.
2. **타자와의 약속 (Contract)**:  
   나 혼자 머릿속으로 때우는 작업이 아니라 타인이나 AI 에이전트가 이어서 작업해야 하는 인터페이스를 정의할 때, 기획(Why)과 설계(How)가 문서화되지 않으면 후속 작업자는 100% 환각을 일으키거나 산으로 갑니다.

### ⚖️ 판별 매트릭스

| 구분 | 🍃 말단 작업 (Leaf Node) | 🧱 기반 작업 (Foundation & Contract) |
| :--- | :--- | :--- |
| **파괴 반경** | 실패 시 국소 수정 (연쇄 반응 0) | **실패 시 상위 작업 와르르 연쇄 붕괴** |
| **의존성** | 누구도 이 작업에 기대지 않음 | **후속 작업, 타인, AI 에이전트가 의존** |
| **실전 예시** | 버튼 색상, UI 여백, 문장 윤문 | 데이터 스키마, 상태 머신, 글의 코어 메시지 |
| **진입 규칙** | ⚡ **기획·설계 선택 (즉시 실행)** | 🛑 **기획·설계 100% 필수 (생존 조건)** |

> 💡 **단 하나의 절대 원칙**  
> **"내가 만드는 결과물이 다른 작업이 딛고 올라설 '발판'이 되는 순간, 기획과 설계는 선택이 아닌 유일한 생존 조건이다."**
