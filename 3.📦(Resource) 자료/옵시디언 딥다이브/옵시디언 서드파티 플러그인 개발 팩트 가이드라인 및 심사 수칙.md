# 옵시디언 서드파티 플러그인 개발 팩트 가이드라인 및 심사 수칙

본 문서는 옵시디언(Obsidian) 공식 개발자 문서([docs.obsidian.md](https://docs.obsidian.md))에 명시된 **공식 개발자 정책(Developer Policies)** 및 **플러그인 리뷰 가이드라인(Plugin Guidelines)** 원문을 기반으로, 서드파티 플러그인 개발자가 반드시 지켜야 하는 필수 기술 규격과 심사(Review) 통과 기준을 100% Fact 기반으로 교차 검증하여 정리한 기술 카드입니다.

---

## 1. 공식 개발자 정책: 절대 금지 행위 (Prohibited Behaviors)

> 🔗 **공식 출처**: [Obsidian Developer Policies](https://docs.obsidian.md/Developer+policies)

공식 디렉터리 제출 시 위반하면 즉시 반려(Reject)되거나 퇴출되는 강제 조항입니다.

1. **난독화 금지 (No Code Obfuscation)**
   * **원문 규정**: *"Code must not be obfuscated to hide its purpose."*
   * **사유**: 옵시디언 팀과 커뮤니티가 소스 코드의 보안성과 악의적 동작 여부를 직접 검증할 수 있어야 합니다. 소스 맵이 없거나 의도적으로 난독화된 번들은 등록이 거부됩니다.
2. **동적 광고 금지 (No Ads)**
   * **원문 규정**: *"Plugins cannot include dynamic ads loaded over the internet or static ads outside of the plugin's own interface."*
   * **사유**: 외부 인터넷에서 동적으로 불러오는 광고 배너나, 플러그인 자체 설정 뷰 이외의 영역에 상업적 광고를 노출하는 행위는 엄격히 금지됩니다.
3. **클라이언트 텔레메트리 금지 (No Client-side Telemetry)**
   * **원문 규정**: *"Client-side telemetry is not allowed."*
   * **사유**: 옵시디언의 핵심 가치는 프라이버시(Local-First)입니다. 사용자의 허가 없이 클라이언트에서 사용 통계, 행동 추적, 분석 데이터를 무단 수집할 수 없습니다.
4. **자체 업데이트 및 임의 설치 금지 (No Self-Updates)**
   * **원문 규정**: *"Plugins and themes cannot install or update themselves or their dependencies."*
   * **사유**: 모든 플러그인 업데이트는 옵시디언 공식 커뮤니티 플러그인 인프라를 통해서만 배포되어야 하며, 플러그인이 외부 서버에서 임의로 바이너리를 내려받아 실행해서는 안 됩니다.

## 2. 보안 규격 (Security)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Security](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Security)

1. **`innerHTML`, `outerHTML`, `insertAdjacentHTML` 사용 회피**
   * **공식 가이드**: `Avoid innerHTML, outerHTML and insertAdjacentHTML`
   * **원문 설명**: 사용자 입력을 `${name}` 형태로 받아 `innerHTML`로 DOM을 생성하면 `<script>` 실행을 통한 임의 코드 실행(XSS) 공격에 노출됩니다.
   * **권장 대안**:
     * 순수 DOM API 또는 옵시디언 헬퍼 함수인 `createEl()`, `createDiv()`, `createSpan()`을 사용하여 프로그래밍 방식으로 생성할 것.
     * 요소 내용 초기화 시에는 `el.empty()`를 사용할 것.

---

## 3. 자원 관리 및 누수 차단 (Resource Management)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Resource+management](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Resource+management)

1. **언로드 시 모든 자원 정리 (Clean up resources when plugin unloads)**
   * **공식 가이드**: `Clean up resources when plugin unloads`
   * **원문 설명**: 플러그인이 생성한 모든 이벤트 리스너, 타이머는 플러그인이 언로드될 때 반드시 해제되어야 합니다.
   * **필수 구현**: 수동 해제 대신 `this.registerEvent()`, `this.registerDomEvent()`, `this.registerInterval()`을 사용하여 옵시디언 수명주기에 바인딩할 것.
2. **`onunload`에서 Leaf 분리 금지 (Don't detach leaves in onunload)**
   * **공식 가이드**: `Don't detach leaves in onunload`
   * **원문 설명**: 플러그인 업데이트 시 열려 있던 탭(Leaf)을 강제로 닫아버리면 사용자가 정성껏 배치해 둔 워크스페이스 레이아웃 위치 정보가 유실되므로, `onunload`에서 리프를 detach하지 말 것.

## 4. 파일 입출력 및 볼트 조작 규격 (Vault)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Vault](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Vault)

1. **활성 파일 수정 시 `Vault.modify` 대신 `Editor` API 우선 사용**
   * **공식 가이드**: `Prefer the Editor API instead of Vault.modify to the active file`
   * **사유**: 현재 열려 있는 활성 노트에 `Vault.modify()`를 호출하면 커서 위치, 선택 영역, 접힌 헤딩(Fold) 상태가 전부 리셋되는 치명적인 사용자 경험 저하가 발생합니다.
2. **백그라운드 파일 수정 시 `Vault.process` 우선 사용**
   * **공식 가이드**: `Prefer Vault.process instead of Vault.modify to modify a file in the background`
   * **사유**: `Vault.process()`는 원자적(Atomic)으로 동작하여 다른 플러그인이나 동기화 엔진과 동시에 같은 파일을 수정할 때 발생하는 레이스 컨디션(경쟁 상태) 충돌을 차단합니다.
3. **프론트매터 수정 시 `FileManager.processFrontMatter` 사용**
   * **공식 가이드**: `Prefer FileManager.processFrontMatter to modify frontmatter of a note`
   * **사유**: 정규식이나 문자열 치환 대신 원자적 API를 통해 YAML 레이아웃 무결성을 유지하고 타 플러그인과의 편집 충돌을 방지합니다.
4. **Adapter 대신 Vault API 우선 사용**
   * **공식 가이드**: `Prefer the Vault API over the Adapter API`
   * **사유**: `app.vault`는 캐싱 레이어를 통한 고속 조회와 동시 I/O 직렬화(Safety)를 보장합니다.
5. **전체 파일 순회 검색 금지 (Avoid iterating all files)**
   * **공식 가이드**: `Avoid iterating all files to find a file by its path`
   * **나쁜 예**: `this.app.vault.getFiles().find(file => file.path === filePath)`
   * **올바른 예**: `this.app.vault.getFileByPath(filePath)` 또는 `getFolderByPath()` 사용 (대용량 볼트 성능 보장).
6. **경로 정규화 필수 (Use normalizePath)**
   * **공식 가이드**: `Use normalizePath() to clean up user-defined paths`
   * **사유**: 운영체제별 슬래시(`/`, `\`) 차이, 연속 슬래시, 공백 특수문자를 크로스 플랫폼에 맞게 안전하게 정제합니다.

## 5. 작업 공간 및 커스텀 뷰 규격 (Workspace)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Workspace](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Workspace)

1. **커스텀 뷰 인스턴스 직접 보관 금지**
   * **공식 가이드**: `Avoid managing references to custom views`
   * **나쁜 예**: `this.registerView(TYPE, () => this.view = new MyCustomView())` (메모리 누수 유발)
   * **올바른 예**: `this.registerView(TYPE, () => new MyCustomView())`로 등록하고, 필요 시 `app.workspace.getActiveLeavesOfType(TYPE)`로 동적 탐색할 것.
2. **활성 뷰 탐색 시 `getActiveViewOfType` 사용**
   * **공식 가이드**: `Avoid accessing workspace.activeLeaf directly`
   * **권장**: `this.app.workspace.getActiveViewOfType(MarkdownView)` 또는 `activeEditor` 옵셔널 체이닝 사용.

## 6. 스타일링 규격 (Styling)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Styling](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Styling)

1. **하드코딩된 스타일 절대 금지 (No hardcoded styling)**
   * **공식 가이드**: `No hardcoded styling`
   * **사유**: 인라인 스타일(`style.color = 'white'`)을 주입하면 사용자의 테마나 커스텀 CSS 스니펫으로 커스터마이징할 수 없습니다.
   * **필수 요건**: CSS 클래스를 부여하고, 옵시디언 공통 CSS 변수(`var(--text-normal)`, `var(--background-modifier-error)`)를 사용하여 다양한 커뮤니티 테마와 자연스럽게 일체화시킬 것.

## 7. 명령어 및 전역 객체 규격 (Commands & General)

> 🔗 **공식 출처**: [Obsidian Plugin Guidelines #Commands](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#Commands) 및 [#General](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines#General)

1. **전역 app 인스턴스 참조 금지**
   * **공식 가이드**: `Avoid using global app instance`
   * **사유**: `window.app` 또는 전역 `app`은 디버깅 전용이며 향후 릴리즈에서 제거될 수 있으므로, 플러그인 인스턴스에 주입된 **`this.app`**만 사용할 것.
2. **명령어 기본 단축키(Default Hotkey) 강제 지정 지양**
   * **공식 가이드**: `Avoid setting a default hotkey for commands`
   * **사유**: 타 플러그인이나 사용자의 기존 단축키와 충돌을 일으키므로 단축키 할당은 사용자 자율에 맡길 것.
3. **불필요한 콘솔 로깅 금지 (Avoid unnecessary logging to console)**
   * **사유**: 기본 상태의 콘솔창은 오직 실제 에러 메시지만 출력되어야 하며, 릴리즈 빌드에 불필요한 `console.log` 디버그 출력을 남겨서는 안 됨.

---

## 8. 플랫폼 호환성 규격 (Manifest & Platform)

> 🔗 **공식 출처**: [Submission requirements for plugins](https://docs.obsidian.md/Plugins/Releasing/Submission+requirements+for+plugins)

1. **모바일 호환성 명시**
   * Node.js 또는 Electron 전용 모듈(`fs`, `child_process`, `electron`)을 사용하는 플러그인은 반드시 `manifest.json`에 **`"isDesktopOnly": true`**를 명시해야 함 (미설정 시 모바일 앱 크래시 유발로 리젝).
2. **README 고지 의무 (Required Disclosures)**
   * 결제나 계정 생성이 필요한 경우, 외부 네트워크 서버와 통신하는 경우, 볼트 외부 파일에 접근하는 경우 반드시 `README.md`에 목적과 대상을 명확히 밝혀야 함.

### 💡 한 줄 결론

서드파티 플러그인 개발의 핵심은 **"옵시디언이 제공하는 공인 API(`this.app`, `Vault.process`, `this.register*`, CSS 변수)의 울타리 안에서만 움직이고, 사용자의 데이터와 시스템 자원을 단 1바이트도 무단 오염시키지 않는 것"**입니다.
