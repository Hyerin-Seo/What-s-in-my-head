# 옵시디언 사용자 주권과 확장성의 5대 심화 설계 철학

앞선 1편([[옵시디언 컴포넌트 사양의 5대 핵심 설계 철학]])에서 '시스템 무결성과 컴포넌트 생명주기'를 다루었다면, 본 카드는 옵시디언을 '단순 메모 앱'을 넘어 **'개인 지식 생태계의 운영체제(OS)'**로 진화시킨 **사용자 주권, 인터랙션 몰입, 생태계 확장성 관점의 5대 심화 설계 철학**을 정리합니다.

---

### 1. "사용자 텍스트를 기계 식별자로 오염시키지 마라" (Human-Readable Links, No Invasive ID)

* **설계적 고민**:
  * 노션, 롬리서치, 다수의 아웃라이너는 블록 단위 관리를 편하게 하려고 데이터베이스나 텍스트 본문에 난수 식별자(`^block-9f8a12`)를 강제로 심습니다. 사용자가 10년 뒤 일반 메모장이나 타 텍스트 에디터로 그 파일을 열면 기계 쓰레기 코드가 가득합니다.
* **옵시디언의 설계 결정**:
  * **"도구가 데이터를 위해 존재하는 것이지, 기계가 관리하기 편하자고 사용자의 글을 더럽히지 않는다."**
  * 옵시디언의 링크 체계(`[[노트명]]`, `[[노트명#헤딩]]`)는 사람이 눈으로 읽을 수 있는 자연어 그대로를 유지합니다.
  * 내부 색인은 메타데이터 캐시가 감당하며, 사용자의 파일 본문에는 어떠한 인위적 메타 식별자도 강제 주입하지 않는 텍스트의 순수성을 보존합니다.

---

### 2. "모든 기능은 명령(Command)이고, 키보드로 완결된다" (Command-First & Keyboard Sovereignty)

* **설계적 고민**:
  * 마우스 클릭 위주의 UI는 만들기 쉽고 직관적이지만, 사고를 전개하는 지식 노동자의 '몰입(Flow)'을 치명적으로 끊습니다.
* **옵시디언의 설계 결정**:
  * 옵시디언 코어에는 **"커맨드 팔레트(`Ctrl/Cmd + P`)와 단축키로 호출할 수 없는 기능은 2류 기능이다"**라는 강력한 원칙이 깔려 있습니다.
  * 플러그인이 UI 버튼(리본 아이콘, 컨텍스트 메뉴 등)을 만들기 전에 반드시 독립된 `Command` 객체(`addCommand`)로 선언되도록 유도합니다.
  * 심지어 Vim 모드까지 코어에 내장되어 있어, 마우스에 손을 대지 않고 100% 키보드만으로 화면 분할, 파일 탐색, 뷰 전환이 가능하도록 컴포넌트 인터랙션을 사양화했습니다.

---

### 3. "점진적 복잡성 수용" (Progressive Disclosure: Low Floor, High Ceiling)

* **설계적 고민**:
  * 기능이 많아지면 초심자에게 진입 장벽이 너무 높고, 단순하게 만들면 파워 유저의 복잡한 워크플로우를 담아내지 못합니다.
* **옵시디언의 설계 결정**:
  * **바닥(Floor)은 극단적으로 낮게**: 설치하자마자 그냥 메모장(Notepad)처럼 줄글을 쓰면 끝납니다. 데이터베이스, 태그, 프론트매터를 몰라도 기록하는 데 아무런 지장이 없습니다.
  * **천장(Ceiling)은 무한히 높게**: 사용자가 복잡성을 원할 때에만 Dataview, Templater, 커스텀 JS 스크립트, CSS 스니펫을 하나씩 얹어 자신만의 ERP/IDE 수준으로 진화시킬 수 있습니다.
  * 컴포넌트 역시 처음부터 모든 옵션을 화면에 쏟아내지 않고, 사용자의 필요에 따라 점진적으로 드러나는 '점진적 공개(Progressive Disclosure)' 설계를 권장합니다.

---

### 4. "작업 공간 세션의 완벽한 환생" (State Serialization: getState / setState)

* **설계적 고민**:
  * 일반적인 브라우저나 웹 뷰는 새로고침하거나 창을 닫으면 스크롤 위치나 세부 조작 상태가 날아가기 쉽습니다.
* **옵시디언의 설계 결정**:
  * 옵시디언은 앱을 껐다 켜거나 기기를 동기화해도 **내가 작업하던 탭 분할 상태, 스크롤 위치, 활성 노드, 핀 고정 여부**가 1픽셀도 어긋나지 않고 그대로 복구됩니다.
  * 이를 위해 모든 `View` 컴포넌트는 반드시 **`getState()` (상태 직렬화)**와 **`setState(state)` (상태 역직렬화)** 인터페이스를 계약으로 구현해야 합니다.
  * 즉, 컴포넌트는 언제든 메모리에서 증발하더라도 **순수 JSON 상태 조각 하나만 있으면 그 자리에 그대로 환생할 수 있는 '직렬화 가능성(Serializability)'**을 사양으로 요구받습니다.

---

### 5. "비독점적 개방성과 샌드박스 없는 신뢰" (Zero Lock-in & Unsandboxed Trust)

* **설계적 고민**:
  * 대다수의 상용 소프트웨어는 데이터 무결성을 핑계로 파일을 배타적으로 잠그거나(File Lock), 익스텐션을 엄격한 샌드박스(iframe, WebWorker)에 가두어 창의성을 질식시킵니다.
* **옵시디언의 설계 결정**:
  * **파일 락 배제**: 옵시디언에서 파일을 열어둔 채로 VSCode나 터미널 Vim, 외부 자동화 스크립트로 같은 파일을 동시에 수정해도 문제없이 공존합니다.
  * **샌드박스 없는 신뢰**: 플러그인 개발자에게 Electron의 Node.js 환경, 최상위 DOM 트리, 전역 윈도우 객체 접근 권한을 무제한으로 개방합니다.
  * 보안을 위해 가능성을 억압하지 않고 개발자에게 완전한 자유도를 줌으로써, React 캔버스, Svelte 위젯, 웹소켓 서버 등 혁신적인 도구들이 탄생할 수 있는 생태계적 토양을 마련했습니다.

---

### 🧭 10대 핵심 설계 철학의 통합 매트릭스

| 영역 | 시스템 무결성 (1편) | 사용자 주권 및 확장성 (2편) |
| :--- | :--- | :--- |
| **데이터 (Data)** | **File Over App**<br>(파일 투영기 모델) | **텍스트 무오염 & 파일 락 배제**<br>(인위적 ID 배제, 외부 에디터 공존) |
| **화면 (Layout)** | **Composable Leaf Tree**<br>(화면 독점 금지, 유연한 분할) | **키보드 주권 (Command-First)**<br>(마우스 의존 탈피, 단축키 우선주의) |
| **자원 (Lifecycle)** | **Hierarchical Lifecycle**<br>(부모 종속 트리, 무누수 자동 GC) | **무제한 개방성 (Unsandboxed)**<br>(신뢰 기반 생태계, 완벽한 세션 환생) |
| **경험 (Experience)** | **MetadataCache 분리**<br>(디스크 I/O 차단, 60fps 반응성) | **점진적 복잡성 수용**<br>(낮은 바닥, 무한한 천장) |

---

### 💡 독립 지식 도구(Spine) 개발을 위한 교훈

우리가 구축하는 독자적인 지식 스캐폴딩 엔진과 캔버스 역시:
1. 독점 규격에 사용자를 가두지 않는 **데이터 중립성**,
2. 마우스와 캔버스의 화려함 뒤에 반드시 보장되어야 하는 **키보드 접근성**,
3. 언제든 직렬화되어 다시 살아날 수 있는 **무상태적 회복력(Resilience)**

을 잃지 않을 때, 비로소 단순한 토이 프로젝트를 넘어 오랜 시간 사랑받는 영속적인 도구가 될 수 있습니다.
