# 옵시디언 에디터 코어와 데이터 엔지니어링의 5대 핵심 설계

앞선 1편([[옵시디언 컴포넌트 사양의 5대 핵심 설계 철학]])의 '시스템 무결성', 2편([[옵시디언 사용자 주권과 확장성의 5대 심화 설계 철학]])의 '사용자 주권 및 인터랙션'에 이어, 옵시디언이 기술적으로 경이로운 안정성과 개방성을 갖추게 된 **에디터 코어, 지식 그래프, 데이터 엔지니어링 관점의 5대 핵심 설계**를 다룹니다.

---

### 1. CodeMirror 6 기반 'Live Preview'의 비밀 (Non-Destructive WYSIWYG)

* **설계적 딜레마**:
  * 노션이나 Tiptap 같은 전통적 위지윅(WYSIWYG) 에디터는 텍스트를 파싱하여 HTML DOM(`<h1>`, `<p>`, `<div>`) 구조로 완전히 치환합니다. 이 방식은 원본 마크다운 평문과의 괴리를 낳고 파일 무결성을 훼손합니다.
  * 반대로 순수 마크다운 에디터는 편집 모드(Edit)와 읽기 모드(Preview)를 매번 전환해야 하므로 인지 피로도가 높습니다.
* **옵시디언의 설계 결정**:
  * 에디터 코어를 **CodeMirror 6(CM6)**로 전면 재작성하며 비파괴적 **'실시간 미리보기(Live Preview)'**를 구현했습니다.
  * **핵심 메커니즘**: 디스크 파일의 평문 마크다운 문자열은 **단 1바이트도 수정하지 않습니다.** 대신 CM6의 뷰 렌더링 레이어(`Decoration.replace`, `Widget`)에서만 텍스트를 실시간으로 가리고 렌더링된 서식으로 덮어씌웁니다.
  * 커서가 해당 블록에 진입하면 평문 `# 제목`이 드러나고, 커서가 벗어나면 즉시 큰 제목 위젯으로 치환됩니다.
  * **"평문 데이터의 100% 무결성을 완벽히 보존하면서도, 위지윅의 직관성을 달성한 타협 없는 하이브리드 해법"**입니다.

---

### 2. 트리 파일 시스템 위에 얹은 '양방향 그래프 네트워크' (Implicit Inverted Index)

* **설계적 딜레마**:
  * 운영체제의 파일 시스템은 계층적 '트리(Folder > Subfolder > File)' 구조에 갇혀 있습니다. 그러나 인간의 뇌와 실제 지식은 그물망처럼 유기적으로 얽힌 '방향 그래프(Directed Graph)'입니다.
* **옵시디언의 설계 결정**:
  * 디스크의 평면적인 파일들 위에 **`[[위키링크]]`를 매개로 수학적 방향 그래프를 실시간 투영**합니다.
  * 특히 **백링크(Backlinks)와 언급되지 않은 링크(Unlinked Mentions)**를 지연 없이 처리하기 위해, 백그라운드의 `MetadataCache`가 메모리 상에 역인덱스(Inverted Index)를 O(1) 수준으로 상시 유지합니다.
  * 사용자가 억지로 폴더 구조를 복잡하게 분류하지 않아도, 링크를 맺는 행위만으로 지식이 스스로 연결망(MOC, Map of Content)을 조직하도록 만듭니다.

---

### 3. 개방형 화이트보드 표준: `JSON-Canvas` 스펙 제정

* **설계적 딜레마**:
  * 캔버스(무한 화이트보드) 기능을 도입할 때, 상용 협업 툴(Miro, FigJam 등)처럼 독점 바이너리 포맷이나 암호화된 파일 규격을 채택할 유혹이 있었습니다.
* **옵시디언의 설계 결정**:
  * 폐쇄적 독점 포맷을 일체 거부하고, **100% 개방형 표준인 `JSON-Canvas`([jsoncanvas.org](https://jsoncanvas.org)) 스펙을 제정하여 전 세계에 무료 공개**했습니다.
  * 캔버스 파일(`.canvas`)은 단순히 노드(`nodes`)와 엣지(`edges`) 배열로 구성된 순수 평문 JSON입니다.
  * 덕분에 사용자는 옵시디언 앱 없이도 Python 스크립트, 웹 브라우저, 외부 엔진으로 캔버스 데이터를 자유롭게 파싱하고 자동 생성할 수 있습니다. (Spine 엔진의 DTO 철학과 정확히 일치합니다.)

---

### 4. 오프라인 우선(Local-First)과 종단간 암호화 동기화 (E2EE Sync)

* **설계적 딜레마**:
  * 클라우드 중심 협업 도구(Notion 등)는 오프라인에서 기능이 정지되며, 중앙 서버가 사용자의 민감한 비공개 문서를 평문으로 읽어 AI 학습이나 광고에 무단 활용할 보안 리스크가 큽니다.
* **옵시디언의 설계 결정**:
  * **Complete Offline-First**: 네트워크가 1초도 연결되지 않아도 로컬 디스크 환경에서 100% 완벽하게 구동됩니다.
  * **Zero-Knowledge E2EE**: 공식 유료 동기화(Obsidian Sync)조차 사용자의 암호 키로 클라이언트에서 암호화된 바이너리 청크만 중계 서버로 전송합니다. 개발사 서버조차 사용자의 노트 내용을 볼 수 없습니다.
  * 오프라인 작업 후 네트워크 재연결 시 라인 기반 스마트 Diff 병합으로 충돌을 최소화합니다.

---

### 5. 데이터와 시스템의 완전한 격리 (`.obsidian/` 은닉 폴더)

* **설계적 딜레마**:
  * 사용자의 순수 텍스트 문서와 앱의 런타임 환경 설정(단축키, 테마, 플러그인, 세션 상태)이 뒤섞이면 백업이나 Git 버전 관리가 오염됩니다.
* **옵시디언의 설계 결정**:
  * 사용자의 모든 순수 지식 자산(MD, 이미지, PDF)은 볼트 루트에 깨끗한 디스크 파일로 배치됩니다.
  * 반면 옵시디언 앱의 모든 런타임 설정과 플러그인 코드는 최상위 숨김 폴더인 **`.obsidian/`** 하나에 완벽히 격리됩니다.
  * 사용자는 볼트 전체를 Git 저장소로 운용할 때, `.obsidian/workspace.json` 등 휘발성 파일만 가볍게 무시(.gitignore)함으로써 완벽한 개인 지식 형상관리를 달성할 수 있습니다.
