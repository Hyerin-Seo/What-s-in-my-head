# 옵시디언 컴포넌트 사양의 5대 핵심 설계 철학

옵시디언(Obsidian) 개발팀(Shida Li, Licia He)이 컴포넌트(`Component`, `View`, `WorkspaceLeaf`, `Vault`)의 기본 사양을 정의할 때, 결코 타협하지 않고 밑바닥에 깔아둔 **5대 근본 설계 철학(Architectural Invariants)**을 분석·정리한 기술 카드입니다.

---

### 1. "파일이 앱보다 오래 살아남아야 한다" (File Over App & Projection 모델)

* **설계적 고민**:
  * *"사용자가 10년 뒤 옵시디언이 사라져도 로컬 데이터를 완전히 열어볼 수 있어야 한다. 그렇다면 컴포넌트는 데이터를 어떻게 보관해야 하는가?"*
* **컴포넌트 사양 결정**:
  * **컴포넌트는 데이터의 소유자(Owner)가 아니라 '투영기(Projection)'여야 한다.**
  * 컴포넌트(`View`)가 메모리 안에 자체 데이터베이스나 독점 상태를 가두는 순간 File-Over-App 원칙은 파괴됩니다.
  * 따라서 모든 에디터 컴포넌트는 `TextFileView`처럼 **[디스크 평문 파일 ➔ 화면 렌더링 ➔ 수정 시 즉시 파일로 환원]**이라는 엄격한 파이프라인 규격을 따르도록 강제했습니다.
  * 에디터가 갑자기 강제 종료되거나 플러그인이 크래시되어도, 디스크의 파일만 온전하면 언제든 동일한 상태로 즉시 재투영될 수 있는 무상태성(Stateless)에 가까운 복원력을 보장합니다.

---

### 2. "어떤 컴포넌트도 화면 전체를 독점할 수 없다" (Composable Leaf Tree)

* **설계적 고민**:
  * *"사용자는 화면을 상하좌우로 쪼개고, 탭을 이동하고, 사이드바에 넣고, 팝아웃(별도 OS 창)으로 분리한다. 컴포넌트는 이 유동적인 레이아웃 환경을 어떻게 견디는가?"*
* **컴포넌트 사양 결정**:
  * 옵시디언의 레이아웃은 단일 브라우저 뷰가 아니라 고도로 추상화된 **'분할 트리(Split Tree)'** 구조입니다. 그 트리의 말단 잎사귀가 바로 `WorkspaceLeaf`입니다.
  * 컴포넌트에게 고정된 크기나 절대 좌표를 허용하지 않습니다.
  * 좌측 사이드바(폭 200px)에 꽂히든, 메인 창(폭 1200px)에 꽂히든, 별도 분리 창에 꽂히든 컴포넌트는 **자신이 배치된 `Leaf`의 컨테이너 크기와 리사이즈 이벤트에 100% 종속**되어야 합니다.

---

### 3. "서드파티 플러그인이 앱 전체를 죽여서는 안 된다" (Hierarchical Lifecycle & Zero Leak)

* **설계적 고민**:
  * *"수십, 수백 개의 외부 플러그인이 동시에 돌아가는 Electron 환경에서, 개발자가 DOM 이벤트 리스너나 타이머를 해제하지 않으면 메모리 누수로 앱이 멈춘다. 이를 프레임워크 차원에서 어떻게 막을 것인가?"*
* **컴포넌트 사양 결정**:
  * 옵시디언의 모든 UI 및 컨트롤 요소는 기본 클래스인 `Component`를 상속받습니다.
  * `Component`는 **계층적(트리형) 수명주기 헬퍼**를 강제합니다:
    * `this.registerEvent(...)` : 옵시디언 내부 이벤트 자동 해제
    * `this.registerDomEvent(...)` : 순수 DOM 이벤트 리스너 자동 제거
    * `this.registerInterval(...)` : 타이머 인터벌 자동 정리
  * 개발자가 `removeEventListener`를 일일이 수동 호출하지 않아도, 해당 컴포넌트나 플러그인이 언로드(`onunload`)되는 순간 **등록된 모든 자원을 트리 단위로 가비지 컬렉션(GC)**하여 메모리 누수를 원천 차단합니다.

---

### 4. "디스크 I/O와 UI 렌더링의 철저한 분리" (MetadataCache & Reactive Event Loop)

* **설계적 고민**:
  * *"수만 개의 파일과 수십만 개의 링크가 얽혀 있는 대형 볼트에서, 컴포넌트가 화면을 그릴 때마다 디스크를 긁어오면 싱글 스레드(JS)가 멈춰버린다. 어떻게 즉각적인 60fps 반응 속도를 유지하는가?"*
* **컴포넌트 사양 결정**:
  * **물리적 디스크(`Vault`)**와 **메모리 내 색인 엔진(`MetadataCache`)**을 철저히 분리했습니다.
  * 컴포넌트 작성 원칙: *"화면을 렌더링할 때는 절대 디스크 파일을 직접 긁지 말고, 항상 `metadataCache`에서 O(1)로 캐시된 메타데이터(YAML, 태그, 위키링크)를 꺼내 써라."*
  * 외부(Git, 동기화 툴, 외부 에디터)에서 파일이 변경되면 옵시디언 코어가 백그라운드에서 캐시를 갱신하고, 컴포넌트는 `vault.on('modify')` 이벤트를 구독하여 변경된 부분만 리액티브하게 다시 그립니다.

---

### 5. "테마 불가지론(Theme-Agnostic)과 시맨틱 디자인 토큰"

* **설계적 고민**:
  * *"사용자들은 수백 가지의 커뮤니티 테마(Minimal, Dracula, Solarized 등)를 취향대로 적용한다. 플러그인이 하드코딩된 색상을 사용하면 화면이 흉측하게 깨진다."*
* **컴포넌트 사양 결정**:
  * 컴포넌트는 절대로 고정된 색상 코드(예: `#ffffff`, `black`)를 직접 사용하지 못하도록 규정했습니다.
  * 모든 UI는 옵시디언이 제공하는 공통 CSS 변수(시맨틱 디자인 토큰)를 통해서만 스타일링해야 합니다:
    * `--background-primary` : 에디터 및 작업 영역 기본 배경
    * `--text-normal` : 표준 본문 텍스트 색상
    * `--interactive-accent` : 활성 포커스 및 브랜드 강조 색상
    * `--font-text` / `--font-interface` : 통일된 서체 패밀리
  * 이를 통해 어떤 기괴하거나 극단적인 테마가 적용되어도, 새로 얹힌 서드파티 컴포넌트가 원래 옵시디언 내장 기능이었던 것처럼 완벽하게 일체화됩니다.

---

### 💡 한 줄 요약 및 시사점

옵시디언의 컴포넌트 사양은 결국:
1. 언제든 앱이 사라져도 데이터는 디스크에 남는 **투영성 (Local-First File Projection)**
2. 어디에 꽂혀도 유연하게 적응하는 **합성성 (Composable Leaf Tree)**
3. 닫히는 순간 흔적도 없이 정리되는 **안전성 (Hierarchical Zero-Leak Lifecycle)**

이라는 3대 안전장치를 소프트웨어 레벨에서 기계적으로 보장하기 위한 아키텍처적 결과물입니다.
