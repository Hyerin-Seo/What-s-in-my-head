## 좋은 시스템 지시의 조건

좋은 시스템 지시는 헌법처럼 짧고 강해야 한다. 세부 업무를 모두 넣으면 오히려 지시가 무거워진다.

좋은 시스템 지시의 조건은 다음과 같다.

|조건|설명|
|---|---|
|안정성|모든 작업에 적용되는 원칙만 담는다|
|짧음|모델이 매번 기억할 수 있을 정도로 간결하다|
|우선순위|충돌 시 무엇이 우선인지 분명하다|
|금지 범위|하면 안 되는 행동을 명확히 한다|
|검증 습관|완료 전 확인을 요구한다|

## 나쁜 지시: 너무 길고, 모호하고, 낡은 지시

OpenAI의 하네스 엔지니어링 글은 `AGENTS.md`를 거대한 백과사전으로 만들지 말고, 더 깊은 문서를 가리키는 지도처럼 쓰라고 설명한다. 너무 긴 지시는 모델이 핵심을 놓치게 할 수 있고, 오래된 규칙의 무덤이 될 수 있다.

회사에서도 마찬가지다. 사내 규정집이 500쪽인데 아무도 업데이트하지 않는다면, 직원은 결국 주변 사람에게 물어본다. AI도 낡은 문서가 많으면 잘못된 규칙을 따를 수 있다. 하네스는 문서를 많이 쌓는 일이 아니라, **필요한 문서를 찾기 쉽게 유지하는 일**이다.

## 컨텍스트는 왜 희소 자원인가
개발자가 아닌 사람에게도 실무적으로 중요한 원칙은 이렇다. AI에게 긴 자료를 줄 때는 “전부 읽고 알아서 해”보다 “먼저 목차를 보고, 필요한 섹션만 읽고, 읽은 섹션명을 답변에 남겨라”가 훨씬 낫다.

여기서 프롬프트, 컨텍스트, 하네스의 관계를 한 번 더 구분해 두면 좋다. **프롬프트 엔지니어링**은 모델에게 어떤 지시를 줄지 다룬다. **컨텍스트 엔지니어링**은 모델이 무엇을 언제 보게 할지 다룬다. **하네스 엔지니어링**은 이 둘을 포함해 도구 실행, 권한, 상태, 오류 복구, 검증, 기록까지 전체 작업 환경을 다룬다.

|구분|핵심 질문|일상 비유|
|---|---|---|
|프롬프트 엔지니어링|어떻게 말할 것인가?|업무 지시서 쓰기|
|컨텍스트 엔지니어링|무엇을 보여 줄 것인가?|책상 위 자료 정리|
|하네스 엔지니어링|어떤 환경에서 일하게 할 것인가?|사무실, 도구, 승인, 검사 체계 만들기|

컨텍스트 엔지니어링을 더 구체적으로 보면, 모델의 책상 위에는 보통 여섯 가지 재료가 올라간다. 중요한 것은 이 여섯 가지를 모두 많이 넣는 일이 아니라, 지금 작업에 맞는 순서와 양으로 조립하는 일이다.

![[Pasted image 20260810140700.png]]첫 번째는 **시스템 지시**다. 시스템 지시는 모델이 어떤 역할로 행동해야 하는지, 어떤 원칙을 우선해야 하는지 알려 주는 기본 규칙이다. 회사로 치면 업무 매뉴얼이나 사내 규정에 가깝다. 너무 길면 매번 읽기 어렵고, 너무 짧으면 판단 기준이 부족하다.

두 번째는 **사용자 요청**이다. 사용자가 지금 맡긴 일, 질문, 목표가 여기에 해당한다. 같은 자료를 보더라도 “요약해줘”, “위험을 찾아줘”, “실행 계획으로 바꿔줘”는 서로 다른 작업이다. 그래서 사용자 요청은 현재 업무의 방향을 정한다.

세 번째는 **검색과 RAG**다. 모든 지식을 미리 컨텍스트에 넣는 대신, 필요한 순간에 관련 문서만 찾아오는 방식이다. 도서관에서 모든 책을 책상에 쌓아 두지 않고, 사서가 지금 필요한 책과 페이지만 찾아 주는 것과 같다.

네 번째는 **장기 메모리**다. 이전 세션의 배움, 사용자의 선호, 프로젝트의 반복 규칙이 여기에 해당한다. 단골 카페가 손님의 취향을 기억하듯이, 좋은 메모리는 반복 설명을 줄인다. 하지만 잘못된 메모리가 저장되면 같은 실수를 반복할 수 있으므로 관리 기준이 필요하다.

다섯 번째는 **사용 가능한 도구**다. 검색, 파일 읽기, 코드 실행, 캘린더 등록, API 호출처럼 모델이 실제 행동으로 이어갈 수 있는 수단이다. 도구 설명도 컨텍스트의 일부다. 도구 이름과 설명이 모호하면 모델은 잘못된 버튼을 누르기 쉽다.

여섯 번째는 **출력 형식**이다. 출력 형식은 엄밀히 말하면 “자료”라기보다 결과를 담는 틀이다. 하지만 모델이 답변을 만들 때 따라야 하는 양식이므로 컨텍스트 설계에서 중요하다. 보고서 양식, 체크리스트, JSON 스키마, 표 형식이 여기에 해당한다. OpenAI의 Structured Outputs처럼 출력 구조를 스키마로 강하게 제한하는 기능도 이 계층과 연결된다.

**수많은 설정과 맥락을 유지하며 창작을 이어나가는 '웹소설 집필'** 같은 복잡한 작업에서 훨씬 더 찰떡같이 맞아떨어집니다.

1. **시스템 지시:** "너는 웹소설 작가의 아이디어를 구체화하는 공동 집필자야. 문체는 장황하지 않게, 빠르고 건조한 하드보일드 스타일을 유지해."
    
2. **사용자 요청:** "이번 화에서 퇴역 군인 출신 주인공이 뒷골목에서 함정에 빠져 적들과 싸우는 도입부 액션 씬을 1000자 정도로 묘사해 줘."
    
3. **검색과 RAG:** AI가 작가의 작업 공간(예: 설정집이나 바이블 문서)에서 주인공의 '주력 무기', '사용 가능한 특수 스킬', '뒷골목 배경 묘사'에 대한 문서만 딱 찾아서(검색) 책상 위에 올려둡니다. 엉뚱한 마법 주문을 쓰지 않게 막아주죠.
    
4. **장기 메모리:** AI가 과거 세션의 대화나 과업 정리표를 기억합니다. _"맞다, 주인공이 3화 전에 오른쪽 어깨에 관통상을 입어서 아직 안 나았지."_ 이 기억을 바탕으로 전투 씬에서 오른쪽 어깨 때문에 고전하는 디테일을 스스로 추가합니다.
    
5. **사용 가능한 도구:** 다 쓴 원고의 맞춤법을 검사하는 '문법 검사기', 특정 단어의 어원을 찾는 '웹 검색 도구', 작성된 원고를 저장하는 '파일 쓰기 도구'.
    
6. **출력 형식:** "최종 결과물은 반드시 Markdown 형식으로 작성하고, 대화체는 겹따옴표(`""`), 주인공의 독백은 홑따옴표(`''`)로 엄격하게 구분해서 출력해."
    

**💡 왜 이 예시가 더 적절할까요?** CS 예시는 매번 새로운 고객을 상대하는 '단발성' 성격이 강하지만, 웹소설 집필 같은 장기 프로젝트는 과거의 설정(메모리)을 잃지 않고, **방대한 세계관(RAG)** 안에서 벗어나지 않으며, 작가만의 고유한 문장 스타일(출력 형식)을 일관되게 유지해야 하기 때문에 6가지 컨텍스트 요소가 하나라도 빠지면 퀄리티가 확 떨어지기 때문입니다.

|재료|핵심 질문|잘못 설계했을 때|
|---|---|---|
|시스템 지시|어떤 원칙으로 일해야 하는가?|규칙이 너무 길거나 충돌한다|
|사용자 요청|지금 무엇을 해야 하는가?|목표가 모호해 결과가 흔들린다|
|검색/RAG|어떤 문서를 찾아와야 하는가?|관련 없는 문서가 섞이거나 중요한 문서를 놓친다|
|장기 메모리|무엇을 다음에도 기억해야 하는가?|잘못된 기억이 반복 오류를 만든다|
|사용 가능한 도구|어떤 행동을 할 수 있는가?|도구가 많거나 설명이 모호해 잘못 호출한다|
|출력 형식|어떤 모양으로 결과를 내야 하는가?|답변은 맞아도 검토하거나 재사용하기 어렵다|

좋은 프롬프트는 중요하지만, 좋은 프롬프트만으로는 제품급 에이전트가 되지 않는다. 지시가 아무리 좋아도 필요한 문서가 없고, 도구 권한이 엉망이며, 결과를 확인하는 기준이 없다면 AI는 안정적으로 일하기 어렵다.

## 문서, 검색, 메모리, 도구 결과의 우선순위

컨텍스트에는 여러 종류가 있다.

|종류|예시|위험|
|---|---|---|
|지시|시스템 지시, AGENTS.md, CLAUDE.md|너무 길면 무시됨|
|문서|제품 설명서, 정책 문서|오래되면 잘못된 기준이 됨|
|검색 결과|웹 검색, 사내 검색|출처 신뢰도 차이|
|메모리|이전 세션의 배움|잘못 저장되면 반복 오류|
|도구 결과|API 응답, 테스트 결과|불완전하거나 지연될 수 있음|

잘 설계된 하네스는 우선순위를 정한다. 예를 들어 “회사 정책 문서가 사용자 말보다 우선한다”, “테스트 결과가 모델의 자기 확신보다 우선한다”, “외부 웹페이지는 신뢰하지 않는 입력으로 취급한다” 같은 규칙이 필요하다.

## AGENTS.md와 CLAUDE.md

`AGENTS.md`는 Codex와 여러 코딩 에이전트가 프로젝트별 지시를 읽기 위한 파일이다. OpenAI Codex 문서는 Codex가 작업 전에 `AGENTS.md` 파일을 읽고, 전역 지시와 프로젝트별 override를 조합할 수 있다고 설명한다. `CLAUDE.md`는 Claude Code에서 프로젝트 메모리와 지시 파일 역할을 한다.

두 파일의 정신은 비슷하다. AI에게 “이 프로젝트에서는 이렇게 일해라”라고 말하는 README다.

초보자용 템플릿:

```md
# AGENTS.md 또는 CLAUDE.md

## 프로젝트 목표
이 프로젝트는 고객 문의를 빠르고 정확하게 분류하는 AI 도우미를 만든다.

## 작업 전 읽을 문서
- docs/product.md
- docs/policy.md
- docs/faq.md

## 반드시 지킬 규칙
- 문서에 없는 내용은 추측하지 않는다.
- 고객 개인정보를 답변에 노출하지 않는다.
- 변경 후 checklist.md를 확인한다.

## 완료 기준
- 결과 요약 작성
- 불확실한 항목 표시
- 다음 작업 제안
```

## “목차형 지시 파일”과 “기록 시스템형 docs/”

OpenAI의 하네스 글은 짧은 `AGENTS.md`가 맵 역할을 하고, 더 깊은 지식은 구조화된 `docs/` 디렉터리에 둔다고 설명한다. 이 패턴은 개발 업무가 아닌 일에도 매우 유용하다.

예를 들어 마케팅 팀은 다음처럼 만들 수 있다.

```text
marketing-ai-harness/
├── AGENTS.md
└── docs/
    ├── brand-voice.md
    ├── campaign-history.md
    ├── customer-personas.md
    ├── legal-review-rules.md
    └── examples/
        ├── good-copy.md
        └── bad-copy.md
```

`AGENTS.md`에는 “어디를 읽어라”만 적고, 상세 내용은 docs에 둔다. 이것이 오래 유지되는 하네스의 기본이다.

### 컨텍스트 부패와 Lost in the Middle
. LLM도 비슷한 현상을 보인다. “Lost in the Middle” 연구는 관련 정보의 위치가 바뀌면 성능이 크게 떨어질 수 있고, 특히 시작이나 끝에 있을 때보다 중간에 있을 때 성능이 저하된다고 보고했다.

그래서 하네스는 책상 정리 담당자처럼 행동해야 한다. 모델에게 모든 서류를 한꺼번에 쌓아 주는 것이 아니라, 지금 필요한 서류를 잘 보이는 위치에 둔다. 다음 네 가지 전략이 실무에서 자주 쓰인다.

|전략|설명|일상 비유|
|---|---|---|
|압축(compaction)|오래된 대화를 요약해 공간을 확보한다|회의록 요약본 만들기|
|관찰 마스킹|과거 도구 결과 전문은 숨기고 호출 기록만 남긴다|영수증 원본 대신 지출 요약표 보기|
|JIT 검색|전체 파일을 넣지 않고 필요할 때 grep/head/search로 읽는다|창고 전체가 아니라 필요한 상자만 꺼내기|
|구조화 메모|progress.md, feature_list.json처럼 정리된 파일로 남긴다|인수인계 문서 작성|

ACON 연구처럼 장시간 에이전트의 컨텍스트를 압축하는 방법도 등장하고 있다. 이 연구는 환경 관찰과 상호작용 이력을 더 짧고 유용한 형태로 압축해 peak token을 줄이면서 성능을 유지하는 방향을 제시한다. 처음 접하는 사람은 복잡한 압축 알고리즘을 직접 구현하지 않아도 된다. 먼저 `progress.md`, `decision_log.md`, `feature_list.json`처럼 사람이 읽어도 명확한 구조화 메모를 만드는 것만으로도 큰 효과가 있다.
