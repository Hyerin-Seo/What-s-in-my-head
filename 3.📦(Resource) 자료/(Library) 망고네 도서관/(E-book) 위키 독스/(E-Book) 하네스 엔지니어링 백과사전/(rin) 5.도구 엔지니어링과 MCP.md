## 4.1 도구란 무엇인가
AI에게 도구란 “말 밖의 행동”이다. 검색, 계산, 파일 읽기, 이메일 초안 작성, 티켓 조회, 데이터베이스 질의, 브라우저 클릭, 코드 실행이 모두 도구다. Toolformer 논문이 보여 주듯, 언어 모델은 산술 계산이나 최신 사실 조회처럼 혼자서 약한 작업을 외부 도구로 보완할 수 있다.

비유하면 도구 없는 AI는 기억력 좋은 사람이고, 도구 있는 AI는 노트북·계산기·인터넷·회사 시스템을 가진 직원이다. 후자가 훨씬 실무적이다.

다만 하네스 관점에서 도구는 단순한 함수 목록이 아니다. 제품급 도구 레이어는 보통 다섯 가지 일을 함께 맡는다.

|책임|설명|
|---|---|
|등록|어떤 도구가 있고 언제 써야 하는지 모델에게 알려 준다|
|스키마 검증|입력값의 이름, 타입, 필수 항목을 확인한다|
|권한 확인|읽기, 쓰기, 삭제, 전송처럼 위험도가 다른 행동을 구분한다|
|격리 실행|가능한 한 샌드박스나 제한된 환경에서 실행한다|
|결과 포맷팅|도구 결과를 모델이 읽기 쉬운 관찰 메시지로 바꾼다|

즉, “도구를 연결했다”는 말은 API 주소를 붙였다는 뜻만이 아니다. 모델이 안전하게 고르고, 올바른 인자로 호출하고, 실패했을 때 복구할 수 있도록 실행 전후의 절차를 함께 설계했다는 뜻이다.

### 도구 레이어 (프론트엔드 작업과 똑같은 '도구 엔지니어링')

하지만 AI에게 "여기 검색 API 주소 있으니까 알아서 써"라고 덜렁 주면, 어떤 파라미터를 넣어야 할지 몰라 뻗어버리거나 엉뚱한 데이터를 지워버릴 수도 있습니다.

그래서 문서에서는 단순히 API 주소를 붙이는 것을 넘어, '제품급 도구 레이어'를 설계해야 한다고 강조하는 것입니다. 회원님이 과거에 하셨던 프론트엔드 작업과 완벽하게 1:1로 대응됩니다.

- **등록 및 스키마 검증:** 프론트엔드에서 폼(Form) 만들 때 필수 입력값(Required) 체크하고 타입(Type) 검사해서 백엔드로 넘겨주던 것과 같습니다.
    
- **권한 확인 및 격리 실행:** 로그인한 유저(Auth)인지 확인하고, 안전한 샌드박스 안에서만 실행되도록 통제하던 역할입니다.
    
- **결과 포맷팅:** 백엔드에서 날아온 복잡한 JSON 데이터를 사용자가 보기 좋게 DOM에 렌더링해주던 것처럼, 도구의 실행 결과를 AI가 읽기 쉬운 '관찰 메시지'로 예쁘게 가공해 주는 작업입니다.
    

---

**💡 요약하자면** 회원님이 이해하신 대로 도구는 'AI가 사용하는 외부의 강력한 무기(기능)'가 맞습니다.

다만 문서에서 다섯 가지를 쪼개어 설명한 것은, 그 무기를 AI의 손에 쥐여줄 때 **과거 프론트엔드 개발자가 유저와 백엔드 사이의 인터페이스를 꼼꼼히 설계했던 것처럼, AI와 API 사이의 인터페이스(Agent-Computer Interface)를 꼼꼼히 설계해 주어야 한다**는 의미를 담고 있는 것입니다.

좋은 도구 설명 예시:

```text
search_policy_docs(query):
사내 정책 문서에서 관련 조항을 검색한다.
사용자가 휴가, 비용 처리, 보안, 개인정보와 관련된 질문을 할 때 사용한다.
출력은 관련 문서 제목, 조항 요약, 마지막 수정일을 포함한다.
```

![[Pasted image 20260810172326.png]]도구가 많아지면 AI는 헷갈린다. Anthropic의 advanced tool use 글은 많은 도구 정의가 컨텍스트를 소비하고, 비슷한 도구가 많으면 잘못된 도구 선택이 발생할 수 있다고 설명한다. 해결책은 도구를 계층화하고, 필요한 도구만 동적으로 노출하는 방식이다.

일상 비유로는 리모컨을 생각해 보자. 버튼이 200개인 리모컨보다, 상황에 맞게 필요한 버튼만 보이는 스마트 리모컨이 낫다.

### 도구 범위 전략 - 버튼 200개짜리 리모컨을 만들지 말라

도구가 많으면 강력해 보인다. 하지만 에이전트 입장에서는 모든 도구 정의가 컨텍스트 창 안의 글자다. 도구 이름, 설명, 입력 파라미터가 많아질수록 모델은 어떤 도구를 써야 할지 헷갈리고, 비슷한 도구 사이에서 잘못 고를 가능성이 커진다.

실무 원칙은 간단하다. **현재 단계에 필요한 최소한의 도구만 노출한다.** 보고서를 쓰는 에이전트에게 데이터베이스 삭제 도구가 보일 필요는 없다. 코드 리뷰 에이전트에게 이메일 발송 도구가 보일 필요도 없다. 이는 안전 문제이기도 하지만 품질 문제이기도 하다.

도구 범위를 정할 때는 다음 순서를 따른다.

1. 이 업무에 반드시 필요한 도구를 적는다.
2. 읽기 도구와 쓰기 도구를 분리한다.
3. 위험한 도구는 승인 필요로 표시한다.
4. 비슷한 도구는 하나로 합치거나 이름을 더 명확히 한다.
5. 장시간 작업에서는 단계별로 도구를 동적으로 열어 준다.

예를 들어 리서치 에이전트는 처음에는 `web_search`, `file_search`, `read_note`만 쓰게 하고, 보고서 초안을 만들 때 `write_draft`를 열어 주고, 고객에게 보내는 단계에서는 반드시 사람 승인을 받게 만들 수 있다. 이처럼 도구를 단계별로 여는 방식이 곧 하네스 설계다.

## 4.8 Tool search와 동적 도구 로딩

도구가 너무 많을 때 모든 도구 설명을 컨텍스트에 넣는 것은 비효율적이다. OpenAI는 tool search로 큰 도구 표면을 런타임에 지연 로딩할 수 있다고 설명한다. Claude도 MCP Tool Search로 도구 검색과 스케일링을 다룬다.

이것은 백화점 안내 데스크와 같다. 모든 매장 직원을 한곳에 세워 두지 않는다. 먼저 안내 데스크에서 “어떤 매장이 필요한지” 찾고, 그 다음 해당 매장으로 이동한다.

LangChain의 에이전트 하네스 글은 여기서 한 걸음 더 나아가, 도구 결과를 모두 대화창에 밀어 넣지 않는 방식도 중요하다고 본다. 큰 검색 결과, 긴 로그, 많은 파일 목록은 모델의 컨텍스트를 금방 어지럽힌다. 좋은 하네스는 전체 결과를 파일이나 작업 공간에 저장하고, 모델에게는 “어디에 저장했는지”, “핵심 요약은 무엇인지”, “다음에 어떤 부분을 읽으면 되는지”만 먼저 알려준다.

일상생활로 말하면, 이삿짐센터가 모든 상자를 거실에 쏟아 놓지 않고 상자마다 라벨을 붙여 방별로 옮겨 두는 것과 같다. 필요한 상자만 열어 보면 된다. AI 도구도 마찬가지다. **도구 결과를 잘 보관하고, 필요한 만큼만 보여 주는 것**이 컨텍스트를 아끼는 도구 설계다.

## 4.9 도구 권한과 승인

도구 권한은 하네스의 안전벨트다. Claude Code의 permissions 문서는 allow, ask, deny 규칙과 deny -> ask -> allow 평가 순서를 설명한다. read-only 도구는 자동 허용할 수 있지만, 파일 수정이나 shell command는 승인 또는 제한이 필요하다.

OpenAI의 sandbox agents 문서도 명령, 파일 변경, 환경 격리를 별도 sandbox session에서 다루는 구조를 설명한다. 핵심은 “모델에게 모든 열쇠를 한꺼번에 주지 않는다”는 점이다.

권한 설계에서 특히 중요한 것은 **모델의 판단**과 **시스템의 집행**을 분리하는 일이다. 모델이 “이 작업은 괜찮아 보인다”고 판단하더라도, 실제 이메일 전송, 결제, 삭제, 배포 같은 행동은 하네스의 권한 정책을 통과해야 한다. 사람 회사에서도 직원이 필요하다고 생각한다고 바로 계좌이체를 할 수는 없고, 결재선과 감사 기록을 거쳐야 하는 것과 같다.
