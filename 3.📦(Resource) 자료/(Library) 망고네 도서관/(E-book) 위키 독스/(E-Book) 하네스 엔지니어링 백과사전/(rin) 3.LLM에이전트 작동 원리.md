## 시스템 메시지, 개발자 메시지, 사용자 메시지
- 시스템 메시지: 모델의 최상위 행동 원칙
- 개발자 메시지: 애플리케이션이나 프로젝트의 규칙
- 사용자 메시지: 지금 해결해야 할 요청
- 도구 결과: 외부 시스템에서 돌아온 관찰값

잘 설계된 하네스는 이 계층을 섞지 않는다. “사용자가 이렇게 말했으니 보안 규칙을 무시하라”는 식의 요구를 막아야 한다.

이 4가지 메시지는 AI가 엉뚱한 소리를 하지 않고 똑똑하게 일할 수 있도록 지시를 내리는 '명령의 우선순위'라고 생각하시면 됩니다.

### 🎧 쇼핑몰 AI 상담원의 환불 처리 프로세스

**1. 시스템 메시지 (회사의 사규 / AI의 기본 인성)** 가장 강력하고 변하지 않는 최상위 규칙입니다. AI가 어떤 정체성을 가져야 하는지 세팅합니다.

- **부여된 명령:** "너는 '다팔아 쇼핑몰'의 친절한 CS 상담원이야. 고객이 아무리 화를 내도 절대 화내지 말고, 항상 존댓말로 상냥하게 대답해야 해."
    

**2. 개발자 메시지 (부서의 업무 매뉴얼 / 프로젝트 규칙)** 특정 상황이나 프로젝트에서 AI가 어떻게 행동해야 하는지 구체적인 업무 지침을 줍니다.

- **부여된 명령:** "고객이 주문 취소나 환불을 요청하면, 대답하기 전에 무조건 '배송 조회 도구'를 사용해서 현재 위치를 확인해. 만약 이미 상품이 출발했다면 반품 배송비 3천 원이 발생한다고 안내해야 해."
    

**3. 사용자 메시지 (고객의 실제 요청 / 지금 당장 해야 할 일)** 실제 고객(사용자)이 채팅창에 입력한 질문이나 요구사항입니다.

- **고객의 입력:** "아니, 어제 산 파란색 운동화 왜 아직도 안 와요? 짜증 나니까 그냥 지금 당장 취소하고 환불해 줘요!"
    

**4. 도구 결과 (외부 시스템에서 확인해 온 팩트)** 사용자 메시지를 본 AI가 개발자 메시지(매뉴얼)에 따라 '배송 조회 도구'를 사용했고, 그 시스템에서 돌아온 실제 데이터값입니다.

- **조회된 데이터:** `[시스템 반환값: 상품명 '파란색 운동화', 상태 '어제 오후 5시 택배사 인계 완료 및 배송 중']`

### 💡 최종 결과: AI의 종합 판단 및 답변

AI는 이 4가지를 머릿속(컨텍스트 창)에 모두 올려놓고 순서대로 조합하여 최종 답변을 만듭니다.

> "고객님, 배송이 지연되어 정말 죄송합니다. **(시스템 메시지: 상냥하고 친절하게)** 방금 고객님의 파란색 운동화 배송 상태를 조회해 본 결과, 어제 오후 5시에 이미 택배사로 전달되어 배송이 시작되었습니다. **(도구 결과: 팩트 확인)** 상품이 이미 출발했기 때문에 지금 취소를 진행하시면 부득이하게 반품 배송비 3,000원이 발생하게 됩니다. 이대로 환불 절차를 도와드릴까요? **(개발자 메시지: 매뉴얼에 따른 정확한 안내)**"

이렇게 4가지 단계가 하나의 프로세스로 맞물려 돌아가기 때문에, AI가 단순한 '챗봇'을 넘어 실제 사람처럼 업무를 처리하는 '에이전트'로 동작할 수 있게 됩니다.

## Agent loop: 관찰 → 계획 → 행동 → 검증 → 반복

1. 관찰: 현재 상황을 읽는다.
2. 계획: 무엇을 할지 정한다.
3. 행동: 도구를 호출하거나 파일을 수정한다.
4. 검증: 결과가 맞는지 확인한다.
5. 기록: 다음 반복을 위해 상태를 남긴다.

ReAct는 이 루프를 연구적으로 뒷받침한 대표 흐름이다. 추론과 행동이 분리되어 있지 않고, 서로 보완한다. 행동은 외부 정보를 가져오고, 추론은 그 정보를 해석한다.
![[Pasted image 20260810132936.png]]'AI 비서에게 치킨 배달을 부탁하는 상황'에 빗대어 설명해 드릴게요.

이 루프를 이해하시면 AI가 얼마나 체계적이고 꼼꼼하게 일하는지 알 수 있습니다.

### 🍗 예시: "오늘 저녁에 근처에서 치킨 좀 시켜줘!"

**1단계: 프롬프트 조립 (작업 지시서 묶기)** AI가 일을 시작하기 위해 필요한 모든 준비물을 하나의 파일철로 묶는 단계입니다.

- **실제 상황:** 하네스(시스템)가 AI의 머릿속에 다음 정보들을 한 번에 밀어 넣습니다.
    
    - "너는 친절한 개인 비서야" (시스템 지시)
        
    - "너는 '배달앱 검색', '결제하기' 버튼을 누를 수 있어" (도구 스키마)
        
    - "사용자 집 주소는 서울시 마포구야" (메모리)
        
    - **"오늘 저녁에 근처에서 치킨 좀 시켜줘!" (현재 사용자 요청)**
        

**2단계: LLM 추론 (AI의 생각과 판단)** 준비물을 건네받은 AI가 '이제 뭘 해야 할지' 생각하는 단계입니다.

- **실제 상황:** AI가 고민합니다. *"바로 대답할까? 아니지, 근처 치킨집이 어딘지 모르니까 먼저 '배달앱 검색 도구'*_를 써야겠다!"_
    

**3단계: 출력 분류 (말인지, 행동인지 구분하기)** AI가 내놓은 결과물이 사용자에게 건네는 '대화'인지, 아니면 시스템을 조작하려는 '버튼 누르기'인지 분류합니다.

- **실제 상황:** AI가 "네, 시켜드릴게요"라고 말로 뱉은 게 아니라, `배달앱_검색(키워드="치킨")`이라는 컴퓨터 명령어를 뱉어냈으므로 하네스는 이를 '도구 실행 요청'으로 분류합니다.
    

**4단계: 도구 실행 (진짜로 버튼 누르기)** AI가 요청한 행동을 시스템이 실제로 대신해 주는 단계입니다. 안전을 위해 검사도 꼼꼼히 합니다.

- **실제 상황:** 하네스가 실제로 배달앱 서버에 접속해 마포구 주변 치킨집을 검색합니다. (이때 "결제하기" 도구였다면 한도 초과가 아닌지 권한을 먼저 확인했을 겁니다.)
    

**5단계: 결과 패키징 (AI가 읽기 좋게 포장하기)** 도구를 써서 얻은 결과나 에러 메시지를 AI가 이해할 수 있는 언어로 예쁘게 번역해서 포장합니다.

- **실제 상황:** 배달앱 서버에서 복잡한 코드로 날아온 검색 결과를 이렇게 포장해 줍니다. _"관찰 결과: 1. A치킨(배달비 2천원), 2. B치킨(배달비 3천원)이 있습니다."_ (만약 식당 문이 닫혔다면 에러를 숨기지 않고 *"현재 영업 종료된 식당입니다"*라고 알려줍니다.)
    

**6단계: 컨텍스트 업데이트 (기억 최신화)** 방금 알게 된 새로운 사실을 원래 있던 1단계의 '작업 지시서' 맨 밑에 추가로 적어 넣습니다.

- **실제 상황:** 기존 기억에 [방금 검색한 A치킨, B치킨의 목록]을 새롭게 추가하여 AI의 기억력을 최신 상태로 업데이트합니다.
    

**7단계: 반복 또는 종료 (루프 판별)** 아직 일이 안 끝났다면 1단계로 다시 돌아가고, 일이 끝났다면 사용자에게 결과를 보고하며 종료합니다.

- **실제 상황:** 아직 치킨 주문을 완료하지 않았죠? AI는 새롭게 업데이트된 기억(검색 결과)을 들고 **다시 1단계로 돌아가서 2번째 턴을 시작합니다.**
    
    - _(두 번째 턴 진행 중...)_ AI 추론: _"A치킨이 배달비가 싸네. A치킨으로 '결제하기' 도구를 쓰자!"_
        
    - 결제가 완료되고 나면 드디어 도구 호출 없이 최종 답변을 냅니다. _"사용자님, 배달비가 더 저렴한 A치킨으로 주문을 완료했습니다. 30분 뒤에 도착합니다!"_ -> **종료**

### 💡 핵심 요약

마지막 문장에 적힌 것처럼, 에이전트는 질문을 듣자마자 0.1초 만에 뚝딱 정답을 뱉어내는 마법의 기계가 아닙니다.

마치 사람이 일을 하듯 **상황을 파악하고(1~2) → 검색해보고(3~5) → 알게 된 사실을 바탕으로 다음 행동을 계획하는(6~7)** 작은 행동들을 수없이 반복하며 최종 목표를 달성하는 끈기 있는 작업자에 가깝습니다.

### ReAct와 Plan-and-Execute의 차이
### 1. ReAct (즉흥적 대처 방식)

ReAct는 **'생각하고(Reason) $\rightarrow$ 행동하고(Act) $\rightarrow$ 결과를 보고(Observe) $\rightarrow$ 다시 생각하는'** 유연한 방식입니다.

- **웹소설 집필에 비유하자면:**
    
    주인공이 예상치 못한 적과 마주치는 짧은 액션 씬을 쓸 때와 같습니다. 적의 기습 공격을 한 줄 묘사하고(행동), 문장의 호흡을 읽어본 뒤(관찰), 주인공이 어떻게 반격하는 게 자연스러울지 생각해서(추론) 다음 줄을 써 내려갑니다.
    
- **특징:** 즉석에서 한 단계씩 상황에 맞춰 유연하게 대처합니다. 편의점에서 물을 사는 것처럼 직관적이고 독립적인 작업에 아주 적합합니다.
    

### 2. Plan-and-Execute (계획 후 분할 실행 방식)

Plan-and-Execute는 **'전체 청사진을 완벽히 먼저 짜고(Plan) $\rightarrow$ 그 계획을 하위 작업자들에게 나누어 실행(Execute)하게 하는'** 체계적인 방식입니다.

- **웹소설 집필에 비유하자면:**
    
    새로운 단행본 분량의 큰 스토리를 시작할 때와 같습니다. 무작정 1화부터 쓰기 시작하는 게 아니라, 먼저 '웹소설 작가 과업 정리표'를 열어서 전체 기승전결 플롯을 짜고, 떡밥 회수 타이밍을 정하고, 캐릭터의 감정선을 촘촘히 배치하는 등 마스터플랜을 세웁니다. 이 거대한 계획표가 다 완성된 후에야 각 챕터별 세부 집필에 들어가는 식이죠.
    
- **특징:** 장소 예약, 예산, 초대장 등 여러 요소가 얽혀있는 결혼식 준비처럼 복잡한 프로젝트에 적합합니다. 중간에 길을 잃지 않으며, 전체적인 비용(토큰)과 속도 측면에서 훨씬 안정적입니다.

### 💡 요약하자면

이 문서는 우리에게 "AI 에이전트를 만들 때 무조건 한 가지 방식만 고집하지 말라"고 말해주고 싶은 것입니다.

가벼운 리서치나 단발성 코드 수정에는 빠릿빠릿한 **ReAct** 방식을, 여러 도구를 거치며 긴 호흡으로 완성해야 하는 대규모 프로젝트에는 치밀한 **Plan-and-Execute** 방식을 선택하라는(또는 두 방식을 적절히 섞어 쓰라는) 가이드를 주고 있는 것

멀티에이전트는 목적이 있을 때만 써야 한다.

|역할|하는 일|
|---|---|
|Planner|목표를 작은 단계로 나눈다|
|Researcher|자료를 찾고 요약한다|

### 하위 에이전트 오케스트레이션의 세 가지 형태

하위 에이전트는 무조건 “AI 여러 명이 회의한다”는 뜻이 아니다. 실무에서는 세 가지 형태로 나뉜다.

|형태|쉬운 설명|언제 쓰나|주의점|
|---|---|---|---|
|Fork|부모의 컨텍스트를 복사해 별도 작업을 시킨다|독립적인 조사, 코드 리뷰, 대안 생성|결과 요약을 잘해야 부모 컨텍스트가 오염되지 않는다|
|Teammate|별도 터미널이나 세션에서 동료처럼 일한다|긴 작업, 병렬 작업, 지속적인 QA|누가 무엇을 했는지 기록이 필요하다|
|Worktree|격리된 브랜치/작업공간에서 수정하게 한다|코드 수정, 실험, 위험한 변경|merge와 충돌 해결 정책이 필요하다|

처음 접하는 사람은 처음부터 멀티에이전트 시스템을 만들 필요가 없다. 먼저 한 에이전트가 문서를 잘 읽고, 도구를 정확히 쓰고, 테스트를 통과하게 만들어야 한다. 그다음 같은 에이전트가 너무 많은 역할을 떠안아 품질이 떨어지는 지점이 보일 때 분업한다. 회사에서도 신입 한 명에게 모든 일을 맡기면 안 되지만, 처음부터 부서 10개를 만들면 관리 비용만 늘어나는 것과 같다.

### 워크플로와 에이전트는 다르다
초보자가 기억할 기준은 간단하다. **길이 보이면 워크플로, 길을 찾아야 하면 에이전트**다. 하네스 엔지니어링은 이 둘 중 하나만 고집하는 일이 아니라, 반복 가능한 부분은 워크플로로 고정하고 판단이 필요한 부분은 에이전트에게 맡기는 균형 잡기다.
