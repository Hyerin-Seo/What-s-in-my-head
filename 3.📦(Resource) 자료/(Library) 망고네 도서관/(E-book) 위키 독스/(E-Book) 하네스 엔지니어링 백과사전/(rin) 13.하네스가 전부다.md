**이 장에서 기억할 문장**  
**모델은 생각하는 엔진이다. 하네스는 그 엔진이 무엇을 보고, 무엇을 만지고, 어디서 멈추고, 어떻게 다시 시작하는지를 결정한다.**

이 장은 여러 공개 사례를 하나의 강한 문제의식으로 묶는다. 제1장에서 하네스의 정의를 배웠고, 제3장에서 컨텍스트 관리, 제8장에서 장시간 에이전트, 제11장에서 12가지 실전 패턴, 제12장에서 7가지 설계 결정을 다뤘다. 이제는 이 지식들을 실제 사례 위에 얹어 볼 차례다.

핵심 질문은 단순하다. **왜 같은 모델을 써도 어떤 팀은 안정적으로 결과를 내고, 어떤 팀은 계속 같은 실수에 막히는가?**

> **하네스는 보조 장치가 아니다. 하네스는 모델이 세상을 경험하는 방식이다.**

이 장에서는 하네스가 실제 제품과 작업 환경에서 어떻게 성능 차이를 만드는지 다섯 가지 큰 흐름으로 본다.

1. SWE-agent가 보여 준 **Agent-Computer Interface(ACI)**의 힘
2. Anthropic이 보여 준 **장시간 에이전트의 세션 인계 문제**
3. OpenAI가 보여 준 **에이전트-퍼스트 소프트웨어 엔지니어링**
4. UI/UX 관점에서 보는 **사람·에이전트·운영자 인터페이스**
5. Awesome Agent Harness 생태계가 보여 주는 **하네스 스택의 분화**

![[Pasted image 20260814174236.png]]이 장의 목적은 단순하다.

> **모델의 성능을 묻기 전에, 모델이 어떤 환경에서 일하고 있는지 묻는 법을 배우는 것.**

이 질문이 생기면 AI를 보는 눈이 달라진다. “왜 모델이 틀렸지?”에서 멈추지 않고, “어떤 정보가 빠졌지?”, “어떤 도구가 잘못 연결됐지?”, “검증 루프가 있었나?”, “상태가 이어졌나?”, “사람 승인이 필요한 지점이 있었나?”를 묻게 된다.

그때부터 AI 활용은 프롬프트 작성이 아니라 **시스템 설계**가 된다.

하지만 하네스 관점에서는 질문이 더 구체적으로 바뀐다.

|문제가 보이는 방식|하네스 관점의 질문|
|---|---|
|모델이 회사 정책을 반영하지 못했다|정책 문서가 컨텍스트에 있었는가? 최신 문서였는가?|
|도구를 잘못 사용했다|도구 설명이 명확했는가? 너무 많은 도구가 노출되었는가?|
|이전 작업을 잊었다|상태 기록이나 progress 파일이 있었는가?|
|테스트 없이 완료했다고 말했다|검증 루프나 자동 테스트 실행이 하네스에 있었는가?|
|위험한 행동을 시도했다|권한, 승인, 샌드박스가 설계되어 있었는가?|
|답변이 매번 달랐다|출력 형식, 평가 기준, 예시가 충분히 고정되어 있었는가?|

이 표가 보여 주는 점은 중요하다. 하네스 관점은 문제를 “모델이 멍청하다”로 끝내지 않는다. 대신 고칠 수 있는 구조를 찾게 만든다.

모델이 필요한 문서를 보지 못했다면 문맥 관리의 문제다. 도구를 잘못 골랐다면 도구 설계의 문제다. 위험한 행동을 했다면 권한과 승인 흐름의 문제다. 이전 작업을 잊었다면 상태와 메모리의 문제다. 결과가 검증되지 않았다면 평가 루프의 문제다.

이렇게 문제를 나누어 보면 AI 시스템은 훨씬 다루기 쉬워진다.

여기서 중요한 결론이 나온다. **하네스는 제품의 주변 장식이 아니라 제품 경험 그 자체에 가깝다.** 같은 모델을 써도 한 제품은 파일을 안전하게 읽고, 필요한 도구만 열고, 실패를 기록하고, 다음 세션으로 이어 간다. 다른 제품은 같은 모델을 쓰면서도 문서를 못 찾고, 도구를 잘못 고르고, 테스트 없이 완료했다고 말한다. 사용자가 느끼는 차이는 “모델 이름”보다 “하네스가 얼마나 잘 설계되었는가”에서 더 크게 나타날 수 있다.

그래서 에이전트 제품을 평가할 때는 모델만 보지 말고 다음을 함께 보아야 한다.

|질문|의미|
|---|---|
|어떤 컨텍스트를 언제 읽는가?|모델이 판단할 근거를 안정적으로 받는가|
|도구 호출은 어떻게 검증되는가?|행동이 안전하고 재현 가능한가|
|실패는 어디에 기록되는가?|같은 실패를 다음에 줄일 수 있는가|
|사용자는 어디서 승인하는가?|위험한 행동이 모델 판단만으로 실행되지 않는가|
|세션이 바뀌어도 이어지는가?|제품이 장기 작업을 감당할 수 있는가|

이 관점에서 보면 하네스는 “모델을 감싸는 얇은 껍질”이 아니라, 모델이 실제 세계와 만나는 인터페이스이자 운영체제다.

### 모델은 요리사, 하네스는 주방이다
하네스를 이해하는 가장 쉬운 비유 중 하나는 주방이다.

뛰어난 요리사가 있다고 해보자. 이 요리사는 맛을 이해하고, 재료를 다루고, 훌륭한 요리를 만들 수 있다. 하지만 주방이 엉망이면 결과는 흔들린다.

냉장고에 라벨이 없다. 칼이 무뎌 있다. 주문서가 뒤섞여 있다. 조리대가 지저분하다. 위생 기준이 없다. 완성된 음식의 품질을 확인하는 절차도 없다.

이런 주방에서는 뛰어난 요리사도 실수한다.

반대로 주방이 잘 정리되어 있다고 해보자. 재료는 라벨링되어 있고, 조리 도구는 제자리에 있으며, 레시피와 주문서가 명확하고, 완성된 음식은 나가기 전에 검사된다. 같은 요리사라도 훨씬 안정적으로 일할 수 있다.

모델은 요리사다. 하네스는 주방이다.

|주방|하네스|
|---|---|
|재료 창고|파일시스템, 문서 저장소, 장기 메모리|
|조리대|현재 컨텍스트|
|레시피|시스템 지시, 스킬, 업무 절차|
|조리 도구|검색, 브라우저, 코드 실행, API|
|위생 규칙|권한, 가드레일, 샌드박스|
|주문서|사용자 요청, 목표 문서|
|품질 검사|테스트, 평가, 리뷰 루프|
|주방 동선|오케스트레이션 로직|

좋은 요리는 요리사의 능력만으로 나오지 않는다. 좋은 주방이 있어야 능력이 안정적으로 결과로 바뀐다.

AI 에이전트도 마찬가지다. 좋은 모델은 필요하다. 하지만 좋은 모델만으로는 충분하지 않다. 모델이 일할 수 있는 주방, 즉 하네스가 필요하다.

아침 루틴으로 바꾸어도 같은 원리가 보인다. 같은 사람이 같은 의지를 가지고 있어도, 알람이 침대 옆에 있는지 방 반대편에 있는지, 전날 가방을 싸 두었는지, 현관 앞 체크리스트가 있는지에 따라 아침 결과는 달라진다. 사람의 능력이 갑자기 달라진 것이 아니라, 행동을 둘러싼 환경이 달라진 것이다.

|아침 루틴 요소|하네스 요소|의미|
|---|---|---|
|알람 위치|트리거와 시작 조건|일을 언제 시작하게 할지 정한다.|
|전날 챙긴 가방|미리 준비된 컨텍스트|필요한 정보를 제때 볼 수 있게 한다.|
|현관 체크리스트|검증 루프|빠뜨린 것이 없는지 나가기 전에 확인한다.|
|가족에게 확인받기|사람 승인|중요한 행동은 혼자 결정하지 않고 멈춰 묻는다.|
|늦은 이유 기록|피드백 기록|다음 날 같은 실수를 줄인다.|

### 하네스는 모델이 할 수 없는 일을 맡는다

LangChain 글은 모델이 기본적으로 할 수 없는 일을 하네스가 맡는다고 설명한다. 모델은 대체로 입력을 받아 출력을 생성한다. 하지만 우리가 에이전트에게 기대하는 일은 그보다 훨씬 많다. 에이전트는 상태를 유지하고, 코드를 실행하고, 최신 정보를 찾고, 작업 환경을 구성하고, 결과를 검증해야 한다. 이런 기능은 모델 자체가 아니라 하네스 차원에서 만들어진다.

예를 들어 채팅도 사실 아주 작은 하네스다.

모델은 한 번에 입력을 받고 출력을 생성한다. 그런데 우리는 AI와 “대화가 이어진다”고 느낀다. 왜 그럴까? 하네스가 이전 메시지를 보관하고, 새 요청에 다시 붙이고, 대화 흐름을 유지하기 때문이다. 모델은 매번 새 입력을 처리하지만, 하네스가 대화 기록을 이어주기 때문에 사용자는 연속적인 대화를 경험한다.

이 작은 예시만 봐도 하네스의 역할이 보인다.

“기억해”라고 말하는 것과 실제로 기억을 저장하는 구조를 만드는 것은 다르다. “테스트해”라고 말하는 것과 실제로 테스트를 실행하고 실패 결과를 모델에게 돌려주는 것은 다르다. “위험한 행동은 하지 마”라고 말하는 것과 실제로 삭제·배포·결제 같은 행동 앞에 승인 절차를 두는 것은 다르다.

프롬프트는 말이다. 하네스는 구조다.

말은 중요하다. 하지만 구조가 있어야 반복 가능해진다.

**이 절에서 기억할 문장**  
**모델은 가능성을 만든다. 하네스는 그 가능성을 반복 가능한 업무 성과로 바꾼다.**

### 인터페이스는 에이전트의 작업 습관을 만든다

인터페이스는 단순한 화면 모양이 아니다. 인터페이스는 에이전트의 작업 습관을 만든다.

검색 도구가 너무 많은 결과를 반환하면 에이전트는 잡음 속에서 헤맨다. 파일 뷰어가 위치 정보를 분명히 보여주지 않으면 에이전트는 수정할 지점을 헷갈린다. 편집 후 바로 오류를 알려 주지 않으면 에이전트는 잘못된 수정 위에 또 다른 수정을 쌓는다. 테스트 결과가 명확하지 않으면 실패 원인을 엉뚱하게 추측한다.

반대로 인터페이스가 잘 설계되어 있으면 에이전트의 행동도 달라진다.

|나쁜 인터페이스|좋은 인터페이스|
|---|---|
|검색 결과가 너무 많이 쏟아진다|필요한 범위만 좁혀서 보여 준다|
|파일 전체를 무작정 읽게 한다|필요한 위치와 주변 맥락을 보여 준다|
|수정 후 오류를 늦게 발견한다|수정 직후 오류를 알려 준다|
|테스트 실패 원인이 불분명하다|실패 위치와 원인을 읽기 쉽게 제공한다|
|이전 행동의 결과가 흐릿하다|현재 상태와 다음 행동을 분명히 보여 준다|

이 표는 하네스 엔지니어링의 핵심을 잘 보여 준다. 에이전트의 성능은 모델 내부의 지능만으로 결정되지 않는다. 모델이 무엇을 보고, 어떤 피드백을 받고, 어떻게 다시 행동할 수 있는지에 따라 달라진다.

## 13.4 UI/UX에서 하네스를 적용하는 법: 사람, 에이전트, 운영자를 함께 설계하기

UI/UX 디자이너, 제품 기획자, 화면 문구를 쓰는 사람, 화면을 구현하는 개발자에게 하네스 엔지니어링은 처음에는 조금 멀게 들릴 수 있다. 화면은 사람이 보는 영역이고, 하네스는 화면 뒤에서 움직이는 시스템처럼 보이기 때문이다. 그래서 “하네스는 화면보다 뒤쪽 시스템 이야기 아닌가?”라고 생각하기 쉽다. 하지만 에이전트가 제품 안으로 들어오는 순간 UI/UX는 하네스의 중심부가 된다.

여기서 말하는 UI/UX 설계자는 디자이너만 뜻하지 않는다. 사용 흐름을 정하는 기획자, 버튼과 안내 문구를 다듬는 사람, 프론트엔드를 구현하는 개발자까지 포함한다. AI 제품에서는 화면의 모양, 버튼 이름, 상태 표시, 오류 문구, 승인 흐름이 모두 하네스의 일부가 되기 때문이다.

왜냐하면 에이전트 제품은 세 관점에서 함께 설계해야 하기 때문이다. 같은 화면이라도 누가 보느냐에 따라 필요한 정보가 달라진다.

첫 번째는 제품을 쓰는 사람의 관점이다. 고객, 직원, 수강생처럼 실제로 제품을 쓰는 사람은 에이전트에게 일을 맡기고, 진행 상태를 이해하고, 위험한 행동을 승인하거나 중단해야 한다.

두 번째는 에이전트의 관점이다. 에이전트는 화면, 화면의 뼈대, 버튼 이름, 오류 메시지, 작업 기록, 서버가 돌려준 응답, 테스트 결과를 읽고 다음 행동을 정한다.

세 번째는 운영자의 관점이다. 운영자는 여러 에이전트가 지금 무엇을 하고 있는지, 어디서 막혔는지, 비용이 얼마나 들었는지, 어떤 승인 대기와 실패가 있는지 봐야 한다.

일상으로 바꾸면 카페 운영과 비슷하다. 손님에게는 보기 좋은 메뉴판이 필요하다. 직원에게는 제조 레시피와 주문표가 필요하다. 점장에게는 재고표, 매출표, 컴플레인 기록, 마감 체크리스트가 필요하다. 같은 카페라도 보는 사람에 따라 필요한 인터페이스가 다르다. AI 제품도 같다. 사람에게 예쁜 화면만으로는 부족하다. 에이전트가 읽기 쉬운 구조와 운영자가 관리하기 쉬운 계기판까지 함께 있어야 한다.

이 절 아래에서 별도 설명 없이 “사용자”라고 하면 기본적으로 **제품을 쓰는 사람**을 뜻한다. 에이전트와 운영자는 필요한 곳에서 따로 이름을 붙여 부른다.

이 절에서 나오는 기술 용어는 다음 정도로만 이해해도 충분하다.

|어려운 말|쉽게 말하면|
|---|---|
|UI/UX|화면 모양과 사용 흐름|
|프론트엔드|사람이 직접 보는 화면을 만드는 영역|
|백엔드|화면 뒤에서 데이터, 권한, 규칙을 처리하는 영역|
|화면 구조, DOM|화면을 이루는 제목, 버튼, 입력칸 같은 뼈대|
|도구·서버 응답, API 응답|서버나 도구가 돌려주는 결과|
|로그|누가 언제 무엇을 했는지 남긴 작업 기록|
|작업 동선 기록, trace|여러 단계의 작업 흐름을 따라볼 수 있는 기록|
|변경 차이, diff|바뀌기 전과 바뀐 뒤의 차이|

### 왜 UI/UX에 하네스를 적용해야 하는가

전통적인 UI/UX는 주로 사람이 화면을 보고 판단하는 경험을 설계했다. 버튼이 보이는가, 문구가 이해되는가, 흐름이 자연스러운가, 실수했을 때 되돌릴 수 있는가를 본다. 에이전트 시대에도 이 원칙은 여전히 중요하다. 다만 질문이 더 늘어난다.

사람은 지금 에이전트가 무엇을 하고 있는지 알 수 있는가? 에이전트는 지금 화면에서 무엇을 해야 하는지 읽을 수 있는가? 위험한 행동은 승인 없이 실행되지 않는가? 실패했을 때 사람과 에이전트가 같은 원인을 볼 수 있는가? 결과를 믿어도 되는 근거가 화면이나 기록으로 남는가?

하네스가 없는 AI UI는 “똑똑한 자동 버튼”처럼 보이지만, 실제로는 블랙박스가 되기 쉽다. 제품을 쓰는 사람은 에이전트가 생각 중인지, 실행 중인지, 멈췄는지, 실패했는지 모른다. 에이전트는 화면의 시각적 배치만 보고 의미를 추측한다. 운영자는 실패가 난 뒤에야 로그를 뒤진다.

좋은 UI/UX 하네스는 이 문제를 줄인다. 사람에게는 상태와 통제권을 주고, 에이전트에게는 읽기 쉬운 구조를 주며, 운영자에게는 관찰 가능한 기록을 준다.

![[Pasted image 20260814180942.png]]

**UI/UX에서 하네스를 설계할 때는 한 화면만 보지 말고 세 가지 화면을 함께 봐야 한다.

|관점|일상 비유|설계해야 할 것|
|---|---|---|
|Human UX, 사람의 경험|손님용 메뉴판|제품을 쓰는 사람이 요청, 검토, 승인, 취소, 수정할 수 있는 경험|
|Agent Experience, 에이전트의 경험|직원용 레시피와 주문표|에이전트가 상태, 의미, 다음 행동, 오류를 읽을 수 있는 구조|
|Operator UX, 운영자의 경험|점장용 대시보드|실행 상태, 비용, 실패, 승인 대기, 작업 기록, 결과물을 관리하는 화면|

사람의 경험만 좋으면 제품을 쓰는 사람은 처음에 편하다고 느낀다. 하지만 에이전트가 화면을 잘못 읽으면 결과가 흔들린다. 에이전트의 경험만 좋으면 에이전트는 일을 잘할 수 있지만, 사람은 불안해진다. 운영자의 경험이 없으면 문제가 커진 뒤에야 원인을 알게 된다.

하네스 엔지니어링 관점의 UI/UX는 이 세 가지를 동시에 맞추는 일이다.

### 화면 설계와 구현에서는 무엇을 적용해야 하는가

화면을 설계하거나 구현하는 사람은 에이전트가 읽고 조작할 수 있는 화면을 만들어야 한다. 이것은 접근성과도 깊게 연결된다. 접근성은 눈이 불편한 사람, 키보드만 쓰는 사람, 보조기기를 쓰는 사람도 화면을 이해하고 사용할 수 있게 만드는 일이다. 스크린리더가 읽을 수 있는 구조는 대체로 에이전트에게도 읽기 쉽다. 반대로 사람 눈에는 예뻐 보여도 의미가 이름 없는 상자와 아이콘 안에만 숨어 있으면 에이전트는 추측해야 한다.

실무에서 바로 적용할 수 있는 원칙은 다음과 같다.

|적용 지점|하네스 관점의 의미|
|---|---|
|명확한 버튼 이름|“확인”, “처리”보다 “예약 확정”, “환불 요청 보내기”처럼 행동을 드러낸다.|
|안정적인 상태 표시|로딩, 실행 중, 승인 대기, 실패, 완료 상태를 화면과 코드 양쪽에서 분명히 둔다.|
|의미 있는 오류 메시지|“오류 발생”이 아니라 무엇이 실패했고 제품을 쓰는 사람이 무엇을 할 수 있는지 알려 준다.|
|접근성 라벨과 의미 있는 HTML|버튼, 제목, 입력칸의 의미를 에이전트와 보조기술이 읽을 수 있게 한다.|
|테스트 가능한 흐름|사람이 클릭하는 과정을 자동으로 따라 해 보는 브라우저 테스트로 주요 행동을 반복 확인한다.|
|작업 기록 연결|화면에서 한 행동, 서버 응답, 에이전트 행동이 한 흐름으로 이어지게 한다.|
|되돌리기와 초안 상태|에이전트가 만든 결과를 바로 실행하지 않고 검토 가능한 상태로 둔다.|

예를 들어 “메일 보내기” 버튼 하나를 생각해 보자. 사람에게는 버튼 모양이 중요하다. 에이전트에게는 이 버튼이 초안 저장인지, 내부 검토 요청인지, 실제 외부 발송인지가 중요하다. 운영자에게는 누가 언제 어떤 내용을 발송했는지 기록이 필요하다. 그래서 좋은 UI는 버튼 하나에도 의미, 권한, 기록, 되돌리기를 함께 설계한다.**

### 사용 경험에서는 무엇을 설계해야 하는가

사용 경험을 설계하는 사람의 역할도 커진다. 에이전트 UI에서 디자인은 예쁜 채팅창을 만드는 일이 아니다. 제품을 쓰는 사람이 AI의 행동을 적절히 신뢰하고, 필요한 순간에 개입하고, 실패를 복구할 수 있도록 경험을 설계하는 일이다.

특히 다음 질문이 중요하다.

|질문|디자인에서 다룰 것|
|---|---|
|제품을 쓰는 사람은 에이전트가 지금 무엇을 하는지 아는가?|진행 상태, 단계 표시, 실행 로그 요약|
|제품을 쓰는 사람은 어디서 멈출 수 있는가?|중단, 되돌리기, 초안 저장, 재시도 버튼|
|제품을 쓰는 사람은 무엇을 승인해야 하는가?|결제, 외부 발송, 삭제, 권한 상승 같은 고위험 행동|
|제품을 쓰는 사람은 결과를 왜 믿을 수 있는가?|근거 문서, 테스트 결과, 변경 전후 차이, 출처, 검증 상태|
|제품을 쓰는 사람은 실패 후 무엇을 할 수 있는가?|수정 요청, 이전 상태 복구, 다른 방식으로 재실행|
|제품을 쓰는 사람은 AI의 한계를 알고 있는가?|가능한 일과 불가능한 일, 불확실한 상태의 표현|

여기서 중요한 것은 모든 내부 추론을 길게 보여 주는 것이 아니다. 제품을 쓰는 사람은 모델의 긴 생각을 보고 싶은 것이 아니라, **지금 어떤 단계이고, 무엇을 근거로 했고, 어디서 내가 결정해야 하는지**를 알고 싶다. 좋은 디자인은 정보를 많이 보여 주는 것이 아니라, 사람이 개입해야 하는 지점을 정확히 보여 준다.

### 연구와 가이드에서 확인되는 기준

이 절은 “그럴듯한 디자인 조언”을 만들기 위한 것이 아니다. UI/UX 하네스는 이미 사람과 AI가 함께 일하는 방식을 연구한 Human-AI Interaction과 HCI 연구에서 확인된 원칙 위에 세워야 한다. HCI는 사람과 컴퓨터의 상호작용을 연구하는 분야다. 이 책에서는 그 자료들을 하네스 관점으로 다시 읽는다.

|자료에서 확인되는 내용|하네스 관점으로 옮기면|
|---|---|
|Amershi 등의 Human-AI Interaction 가이드라인은 AI 시스템이 무엇을 할 수 있고, 얼마나 잘할 수 있는지 제품을 쓰는 사람이 알 수 있어야 한다고 제시한다.|AI 기능을 넣을 때는 “무엇을 해줄 수 있는지”와 “어디서 틀릴 수 있는지”를 화면에 드러내야 한다.|
|같은 가이드라인은 AI 서비스가 제품을 쓰는 사람의 현재 작업과 환경에 맞는 시점에 개입해야 한다고 본다.|에이전트가 아무 때나 끼어드는 것이 아니라, 제품을 쓰는 사람이 도움을 받을 준비가 된 지점에서 제안해야 한다.|
|AI가 틀렸을 때 제품을 쓰는 사람이 쉽게 무시하고, 수정하고, 복구할 수 있어야 한다는 원칙도 제시된다.|승인, 중단, 되돌리기, 재시도, 초안 모드는 부가 기능이 아니라 하네스의 안전장치다.|
|Agent Experience 연구는 GenAI 에이전트가 사람과 다르게 화면의 코드 구조, 서버 응답, 접근성 이름, 이미지 설명, 정리된 데이터에 의존한다고 설명한다.|사람 눈에 보기 좋은 화면뿐 아니라, 에이전트가 읽을 수 있는 코드 구조와 상태 이름도 함께 설계해야 한다.|
|UXAgent 연구는 LLM 에이전트로 웹 사용성 테스트 설계를 미리 점검하고, 상호작용 기록과 사후 설문 같은 데이터를 볼 수 있게 한다고 설명한다.|에이전트는 사람 대상 사용자 조사를 대체하는 존재라기보다, 실제 사람 테스트 전에 흐름과 질문지를 점검하는 하네스가 될 수 있다.|

이 표에서 중요한 것은 “AI가 디자인을 대신한다”가 아니다. 오히려 반대에 가깝다. AI 기능이 들어오면 제품 경험을 설계하는 사람이 다뤄야 할 대상이 늘어난다. 제품을 쓰는 사람의 기대, AI의 한계, 에이전트가 읽는 구조, 운영자가 보는 기록을 함께 설계해야 한다.

### UI/UX 설계자가 하네스로부터 얻는 것

UI/UX 설계자가 하네스 엔지니어링에서 얻을 수 있는 가장 큰 이점은 “AI 기능을 화면 요소가 아니라 운영 흐름으로 보는 눈”이다.

예전에는 “AI 추천 버튼을 어디에 둘까?”가 질문이었다면, 하네스 관점에서는 질문이 이렇게 바뀐다.

|기존 질문|하네스 관점의 질문|
|---|---|
|AI 버튼을 어디에 둘까?|제품을 쓰는 사람이 언제 AI를 호출하고, 언제 무시하고, 언제 수정할 수 있어야 할까?|
|결과 카드를 어떻게 예쁘게 보여줄까?|결과의 근거, 불확실성, 검증 상태를 어디까지 보여줘야 할까?|
|로딩 화면을 어떻게 만들까?|에이전트가 지금 검색 중인지, 작성 중인지, 승인 대기인지 구분되는가?|
|오류 문구를 어떻게 쓸까?|실패 원인과 제품을 쓰는 사람이 취할 다음 행동이 분명한가?|
|관리자 화면은 나중에 만들까?|실패, 승인 대기, 비용, 재시도 기록을 운영자가 볼 수 있는가?|

이 변화는 작지 않다. UI/UX 설계자는 더 이상 “AI가 만든 결과를 담는 그릇”만 설계하지 않는다. AI가 언제 시작하고, 어디서 멈추고, 무엇을 근거로 보여 주고, 실패하면 어떻게 돌아오는지까지 설계한다.

### AI 기능의 상태 모델을 먼저 그린다

AI UI를 설계할 때 가장 먼저 해야 할 일 중 하나는 상태 모델을 그리는 것이다. 이것은 연구 자료의 원칙과도 연결된다. 제품을 쓰는 사람은 AI가 무엇을 할 수 있는지, 현재 무엇을 하는지, 틀렸을 때 어떻게 고칠 수 있는지 알아야 한다. 에이전트 역시 현재 상태와 오류를 구조적으로 읽을 수 있어야 한다.

최소 상태는 다음처럼 잡을 수 있다.

|상태|제품을 쓰는 사람에게 보여줄 것|에이전트와 시스템에 남길 것|
|---|---|---|
|대기|무엇을 요청할 수 있는지, 예시 요청은 무엇인지|가능한 작업 목록, 입력 조건|
|이해 중|요청을 해석하고 있음을 짧게 표시|원본 요청, 분류된 의도|
|실행 중|검색, 작성, 계산, 도구 사용 중 어느 단계인지|도구 사용 기록, 서버 응답, 실행 기록|
|승인 대기|어떤 행동이 왜 승인이 필요한지|위험도, 승인 대상, 요청 주체|
|검증 중|결과를 확인하고 있음을 표시|테스트 결과, 출처 확인, 변경 전후 차이|
|실패|무엇이 실패했고 제품을 쓰는 사람이 무엇을 할 수 있는지|오류 코드, 실패 단계, 재시도 조건|
|완료|결과, 근거, 다음 행동을 보여줌|산출물, 검증 상태, 작업 기록|
|수정 가능|제품을 쓰는 사람이 어디를 고칠 수 있는지 표시|사람의 수정 피드백, 수정 이력|

이 상태 모델은 모든 제품에 그대로 쓰라는 템플릿이 아니다. 핵심은 AI 기능을 “입력하면 결과가 나오는 상자”로 보지 않는 것이다. AI 기능은 요청, 해석, 실행, 관찰, 검증, 승인, 복구를 거치는 흐름이다. 그 흐름이 화면과 코드에 모두 표현되어야 한다.

### 디자인 산출물도 하네스가 된다

하네스는 개발자가 만드는 실행 코드만 뜻하지 않는다. AI 제품에서는 디자인 산출물도 하네스의 일부가 된다. 왜냐하면 디자인 산출물이 제품을 쓰는 사람의 기대, 승인 지점, 실패 복구, 결과 검토 방식을 정하기 때문이다.

|디자인 산출물|하네스에서의 역할|
|---|---|
|사람 여정 지도|사람이 언제 AI에게 맡기고, 언제 직접 판단하는지 정한다.|
|에이전트 여정 지도|에이전트가 어떤 정보를 읽고, 어떤 도구를 쓰고, 어떤 검증을 거치는지 정한다.|
|상태표|대기, 실행, 승인 대기, 실패, 완료 같은 상태를 일관되게 만든다.|
|승인 플로우|고위험 행동을 사람 검토 없이 실행하지 않게 한다.|
|오류와 복구 문구|실패했을 때 제품을 쓰는 사람이 다음 행동을 알 수 있게 한다.|
|결과 검토 화면|근거, 출처, 변경 전후 차이, 테스트 결과를 확인할 수 있게 한다.|
|접근성·의미 구조 명세|사람과 에이전트가 같은 의미를 읽도록 돕는다.|
|사용성 테스트 시나리오|실제 사람 대상 테스트 전후로 흐름과 질문을 검증한다.|

그래서 UI/UX 설계자가 하네스 엔지니어링을 배운다는 것은 코드를 직접 짜는 법을 배우는 일이 아니다. 자신이 만드는 화면, 문구, 흐름, 문서가 에이전트 실행 환경의 일부가 된다는 사실을 이해하는 일이다.

### AI UX 패턴을 하네스 관점으로 본다

AI 제품에서 자주 보이는 패턴도 하네스 관점으로 다시 볼 수 있다.

|UX 패턴|제품을 쓰는 사람이 얻는 것|하네스가 얻는 것|
|---|---|---|
|예시 프롬프트|무엇을 요청할 수 있는지 이해한다.|입력 범위가 안정된다.|
|초안 모드|결과를 바로 실행하지 않고 검토한다.|위험 행동을 승인 전 단계에 묶는다.|
|근거 보기|결과를 왜 믿을 수 있는지 확인한다.|출처와 작업 동선 기록이 남는다.|
|실행 단계 표시|AI가 멈췄는지 일하는 중인지 안다.|작업 상태가 구조화된다.|
|승인 모달|중요한 행동을 직접 판단한다.|권한 경계가 명확해진다.|
|중단과 되돌리기|원하지 않는 자동화를 멈춘다.|복구 가능한 실행 흐름이 된다.|
|재시도와 수정 요청|틀린 결과를 다시 다듬는다.|피드백 루프가 생긴다.|
|불확실성 표시|AI 결과를 과신하지 않는다.|모델 한계가 제품 경험 안에 반영된다.|

이 패턴들은 장식이 아니다. 사람과 AI의 상호작용 가이드라인에서 말하는 능력과 한계의 전달, 적절한 개입 시점, 효율적인 무시와 수정, 행동 이유 설명을 제품 화면으로 옮긴 것이다.

### 실제 적용 순서

UI/UX 하네스를 적용할 때는 다음 순서로 시작하면 좋다.

1. **사람 여정과 에이전트 여정을 나란히 그린다.** 제품을 쓰는 사람은 “자료 조사 요청”이라고 느끼지만, 에이전트는 검색, 문서 읽기, 요약, 검증, 출처 정리, 보고서 작성 단계를 거친다. 두 여정을 나란히 그리면 어떤 상태를 화면에 보여야 하는지 보인다.
    
2. **위험 행동 지도를 만든다.** 삭제, 결제, 외부 발송, 개인정보 조회, 배포, 권한 변경처럼 반드시 사람 승인이 필요한 지점을 표시한다. 이것이 승인 UX의 기준이 된다.
    
3. **에이전트가 읽을 수 있는 의미 계층을 만든다.** 화면의 문구, 버튼 이름, 입력칸 이름, 페이지 주소, 서버 응답, 오류 메시지, 작업 기록이 서로 같은 의미를 갖게 한다. 사람에게는 “보이는 구조”가 필요하고, 에이전트에게는 “읽히는 구조”가 필요하다.
    
4. **검증 가능한 완료 기준을 둔다.** “보고서 작성 완료”가 아니라 “출처 5개 이상, 반대 근거 1개 이상, 요약 800자 이하, 중복 문장 없음”처럼 확인 가능한 기준을 둔다. UI 작업이라면 “주요 버튼 클릭 가능, 모바일에서 겹침 없음, 접근성 이름 존재, 스크린샷 비교 통과”처럼 쓴다.
    
5. **운영자 화면을 늦게 만들지 않는다.** 처음부터 거대한 관리자 화면은 필요 없다. 하지만 최소한 실행 중, 승인 대기, 실패, 완료, 비용, 최근 오류, 재시도 횟수 정도는 볼 수 있어야 한다.
    
6. **실패를 제품 경험의 일부로 설계한다.** 에이전트가 실패하지 않는다고 가정하지 않는다. 실패했을 때 제품을 쓰는 사람이 무엇을 보고, 무엇을 누르고, 어떤 정보를 수정해 다시 실행할지까지 설계한다.
    

### 자주 생기는 문제

UI/UX에서 하네스를 적용하지 않으면 비슷한 문제가 반복된다.

|문제|왜 생기는가|하네스식 대응|
|---|---|---|
|에이전트가 화면을 잘못 이해한다|버튼과 상태의 의미가 시각적으로만 표현된다|의미 있는 HTML, 접근성 라벨, 명확한 상태 이름을 둔다|
|제품을 쓰는 사람이 불안해한다|에이전트가 무엇을 하는지 보이지 않는다|단계 표시, 실행 요약, 승인 대기 화면을 둔다|
|위험한 행동이 너무 쉽게 실행된다|모든 행동을 같은 버튼 흐름으로 처리한다|위험도별 승인 UX와 권한 경계를 둔다|
|실패 원인을 모른다|화면 행동과 에이전트 작업 기록이 연결되지 않는다|사람의 화면 행동, 도구 사용, 오류, 결과를 한 흐름으로 기록한다|
|결과를 믿기 어렵다|근거와 검증 상태가 보이지 않는다|출처, 테스트, 변경 전후 차이, 검토 상태를 함께 보여 준다|
|화면은 예쁜데 자동화가 어렵다|디자인 시스템이 사람 눈 중심으로만 설계된다|화면 부품의 상태와 의미를 에이전트가 읽을 수 있게 표준화한다|
|제품을 쓰는 사람이 너무 많은 정보를 본다|투명성을 “모든 로그 공개”로 오해한다|요약, 상세 펼치기, 위험 지점 중심으로 점진적 공개를 한다|

이 문제들은 “디자인이 부족해서”가 아니라, 에이전트 시대에는 한 화면을 보는 관점이 여러 개로 늘어나기 때문에 생긴다. 사람만 보는 제품에서 사람과 에이전트가 함께 쓰는 제품으로 바뀌었기 때문이다.

### UI/UX 하네스 점검 질문

UI/UX 디자이너, 제품 기획자, 화면을 구현하는 개발자는 다음 질문으로 자신의 제품을 점검할 수 있다.

|질문|확인할 것|
|---|---|
|제품을 쓰는 사람은 에이전트가 현재 어느 단계에 있는지 아는가?|상태 표시, 진행 단계, 최근 행동 요약|
|제품을 쓰는 사람은 에이전트를 멈추거나 되돌릴 수 있는가?|취소, 중단, 되돌리기, 초안 저장|
|고위험 행동은 사람 승인 없이 실행되지 않는가?|결제, 삭제, 외부 발송, 배포, 권한 변경|
|에이전트는 화면의 주요 버튼과 상태를 의미로 읽을 수 있는가?|라벨, 의미 있는 HTML, 접근성 이름, 테스트용 이름|
|에이전트가 실패했을 때 원인을 읽을 수 있는가?|오류 메시지, 작업 기록, 작업 동선 기록, 재시도 정보|
|결과가 맞는지 확인할 근거가 보이는가?|출처, 테스트 결과, 변경 전후 차이, 평가 기준|
|운영자는 여러 실행을 한눈에 볼 수 있는가?|실행 목록, 실패 목록, 승인 대기, 비용, 시간|
|같은 시나리오를 반복 테스트할 수 있는가?|브라우저 테스트, 시나리오 프롬프트, 회귀 테스트|
|화면 문구와 서버 상태 이름이 서로 충돌하지 않는가?|디자인 시스템과 코드 상태명의 일관성|
|접근성 개선이 에이전트 경험 개선으로도 이어지는가?|스크린리더 친화 구조, 명확한 폼 라벨, 키보드 흐름|

이 질문들은 디자이너, 기획자, 화면을 구현하는 개발자 모두에게 중요하다. 에이전트 시대의 UI/UX는 화면 구성만이 아니라 **행동의 안전성, 관찰 가능성, 복구 가능성**을 함께 다루기 때문이다.

### 이 절의 정리

UI/UX에 하네스를 적용한다는 것은 채팅창을 하나 더 붙이는 일이 아니다. 사람에게는 이해와 통제권을 주고, 에이전트에게는 읽기 쉬운 작업 표면을 주며, 운영자에게는 관찰 가능한 대시보드를 주는 일이다.

좋은 AI 제품은 “AI가 대신 해 줍니다”라고 말하는 데서 끝나지 않는다. 제품을 쓰는 사람이 언제 맡기고, 언제 멈추고, 언제 승인하고, 어떻게 결과를 믿을 수 있는지까지 설계한다. 그리고 에이전트가 화면과 시스템을 추측하지 않고 읽을 수 있게 만든다.

결국 UI/UX 하네스의 핵심은 이 문장으로 정리된다.

> **사람에게 보기 좋은 화면, 에이전트에게 읽기 좋은 구조, 운영자에게 관리하기 좋은 기록이 함께 있어야 에이전트 제품은 안정적으로 작동한다.**

## 13.12 반복해서 나타나는 다섯 가지 설계 패턴

여러 공개 사례를 종합하면 반복해서 나타나는 설계 패턴이 보인다. 이 책에서는 이를 다음 다섯 가지로 압축한다.

### 1. 점진적 공개

처음부터 모든 문서, 모든 도구, 모든 로그를 보여 주지 않는다. 작은 지도와 필요한 곳으로 이동하는 링크를 준다. SWE-agent의 제한된 검색 결과, OpenAI의 짧은 `AGENTS.md`, Anthropic의 progress file 읽기 순서가 모두 이 패턴이다.

LangChain의 관점으로 보면 Skill도 이 패턴에 속한다. Skill은 모든 업무 매뉴얼을 처음부터 모델에게 들이붓지 않는다. 먼저 이름과 설명만 보이고, 필요한 순간에 본문과 참고 자료를 읽게 한다. 이것은 컨텍스트를 아끼는 기능이면서 동시에 컨텍스트가 낡은 정보와 불필요한 세부사항으로 오염되는 것을 막는 장치다.

가정으로 비유하면, 집안 모든 설명서를 거실 바닥에 펼쳐 두지 않는 것과 같다. 세탁기를 고칠 때는 세탁기 설명서만, 공유기를 설정할 때는 공유기 설명서만 꺼내야 한다.

### 2. 작업 공간 격리

에이전트마다 독립된 브랜치, worktree, sandbox를 제공한다. 이것은 여러 사람이 같은 문서 한 장을 동시에 고치다 충돌하는 상황을 막는 것과 같다. Cursor Background Agents와 OpenAI Codex의 cloud sandbox 사례도 같은 방향이다.

### 3. 저장소가 진실의 원천

정책, 스펙, 완료 기준, 아키텍처 원칙이 저장소에 있어야 한다. 에이전트가 읽지 못하는 지식은 존재하지 않는다.

### 4. 기계적 아키텍처 강제

“이렇게 해 주세요”라고만 말하지 않는다. 린터, 구조 테스트, CI, 권한 정책으로 강제한다. 중요한 규칙은 기억이 아니라 시스템에 넣는다.

### 5. 통합 피드백 루프

실수를 늦게 발견할수록 비싸다. 편집 직후 린터, 변경 직후 테스트, UI 작업 직후 브라우저 검증, 운영 문제에는 로그와 트레이스가 필요하다. 잘 설계된 하네스는 결과를 기다렸다가 사람이 보는 것이 아니라, 에이전트가 스스로 볼 수 있게 만든다.

## 13.13 최소 하네스: 거창하게 시작하지 않아도 된다

이 장의 결론이 “OpenAI처럼 거대한 시스템을 만들라”는 뜻은 아니다. 작은 팀이나 개인도 바로 시작할 수 있다. 최소 하네스는 다음 네 가지면 된다.

![[Pasted image 20260814182601.png]]

1. **progress.md**: 매 세션 시작 때 읽고, 끝날 때 업데이트한다.
2. **feature_list.json**: 완료 기준을 검증 가능한 항목으로 나눈다.
3. **git commit**: 세션 종료 시 깨끗한 상태로 커밋한다.
4. **테스트/린터/브라우저 검증**: 에이전트가 결과를 직접 확인하게 한다.

이 네 가지가 있으면 에이전트는 훨씬 덜 길을 잃는다. 이것은 개발 업무가 아니어도 마찬가지다. 리서치 에이전트라면 progress file은 조사 일지, feature list는 보고서 목차와 검증 질문, git commit은 버전 기록, 테스트/린터는 출처 검증과 논리 점검이 된다.

Anthropic의 “Building effective agents” 글도 같은 결론을 다른 표현으로 말한다. LLM 애플리케이션을 만들 때는 가능한 한 가장 단순한 해법을 먼저 찾고, 필요할 때만 복잡성을 높여야 한다. 많은 경우에는 retrieval과 in-context example을 붙인 단일 LLM 호출만으로도 충분하다. 워크플로나 자율 에이전트는 예측 가능한 경로만으로 부족하고, 모델이 여러 턴에 걸쳐 판단해야 할 때 선택하는 다음 단계다.

그래서 최소 하네스의 목표는 작아 보이지만 가볍지 않다. `progress.md`, `feature_list.json`, 버전 기록, 검증 루프는 에이전트가 환경에서 ground truth를 얻고, 어디까지 했는지 알고, 필요할 때 사람에게 멈춰 물어볼 수 있게 만든다. 복잡한 에이전트 프레임워크보다 먼저 필요한 것은 이런 기본 작업 환경이다.

## 13.14 환경 감사 질문

이미 에이전트를 쓰고 있는데 결과가 불안정하다면 모델부터 바꾸지 말고 다음 질문을 던져 보자.

|질문|하네스 개선 방향|
|---|---|
|에이전트가 알아야 하는데 읽을 수 없는 정보가 있는가?|문서화, 저장소화, 검색 도구 추가|
|에이전트가 자주 막히는 지점은 어디인가?|전용 도구, 더 좋은 출력 형식, 진행 파일 추가|
|실수가 너무 늦게 발견되는가?|테스트, 린터, 브라우저 검증, 로그 도구 추가|
|컨텍스트가 잡음으로 가득 차는가?|결과 제한, 요약, 파일 뷰어, progressive disclosure|
|위험한 행동을 모델 판단에만 맡기는가?|권한 정책, 승인 단계, 샌드박스|
|세션이 바뀔 때마다 처음부터 다시 시작하는가?|progress file, feature list, git log, init script|
|제품을 쓰는 사람과 에이전트가 같은 화면을 서로 다르게 오해하는가?|UI 상태, 접근성 라벨, trace, 승인 UX, 운영자 대시보드|

이 질문의 목적은 비난이 아니다. 실패는 하네스가 어디를 보강해야 하는지 알려 주는 신호다.

![[Pasted image 20260814182632.png]]

> **하네스는 모델을 보조하는 껍데기가 아니라, 모델이 세상을 경험하고 행동하는 운영체제다.**

처음 접하는 사람은 먼저 모델을 바꾸고 싶어진다. 실무자는 프롬프트를 고치고 싶어진다. 그러나 하네스 엔지니어는 한 단계 더 들어간다.

- 모델이 보는 정보의 형식은 적절한가?
- 도구 출력은 너무 많거나 너무 적지 않은가?
- 실수는 바로 보이는가?
- 세션이 바뀌어도 일이 이어지는가?
- 완료 기준은 추측이 아니라 파일로 존재하는가?
- 위험한 행동은 시스템으로 막히는가?
- 처리량이 늘어날 때 낡은 문서와 임시 구조를 정리하는 루프가 있는가?

이 질문들을 던지는 순간, 우리는 더 이상 “AI를 잘 쓰는 사람”에 머물지 않는다. 우리는 **AI가 일할 수 있는 환경을 설계하는 사람**이 된다.
