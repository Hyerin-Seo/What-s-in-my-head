## 8.1 Long-running agent 문제

짧은 대화에서는 AI가 잘해 보인다. 하지만 여러 시간, 여러 날 이어지는 작업에서는 문제가 생긴다. 대화가 길어지고, 컨텍스트가 복잡해지고, 이전 결정이 잊히고, AI가 완료되지 않은 일을 완료했다고 착각한다.

Anthropic의 “Effective harnesses for long-running agents” 글은 장시간 작업에서 각 새 세션이 이전 작업 상태를 모른다는 문제를 강조한다. 이것을 사람 업무로 비유하면 교대근무 문제다. 야간 근무자가 아무 인수인계 없이 출근하면, 낮 근무자가 무엇을 했는지 다시 조사해야 한다.

## 8.2 Context window 한계

컨텍스트 창이 커져도 무한하지 않다. 게다가 정보가 많아질수록 중요한 사실이 묻힐 수 있다. 장시간 에이전트는 대화를 계속 이어 붙이는 방식보다, 핵심 상태를 구조화된 파일로 남기는 방식이 낫다.

## 8.3 Compaction의 장단점

Compaction은 긴 대화를 요약해 컨텍스트를 줄이는 기술이다. 장점은 대화를 계속 이어 갈 수 있다는 점이다. 단점은 요약 과정에서 중요한 디테일이 빠질 수 있다는 점이다.

그래서 하네스는 compaction에만 의존하면 안 된다. 사람이 회의록만 믿고 원본 계약서를 버리지 않는 것처럼, AI도 progress file, feature list, git history 같은 원천 기록을 함께 가져야 한다.

Anthropic의 harness design 글은 장시간 앱 개발에서 **context anxiety**라는 현상도 설명한다. 컨텍스트 창이 거의 찼다고 느끼면 에이전트가 남은 일을 충분히 확인하지 않고 “이 정도면 끝났다”고 서둘러 마무리하려는 경향이 생긴다는 뜻이다. 사람도 회의 종료 시간이 다가오면 어려운 쟁점을 “다음에 보죠” 하고 넘기고 싶어진다. 그래서 장시간 하네스는 모델에게 오래 버티라고만 하지 않고, 적절한 시점에 새 세션으로 넘길 수 있는 인수인계 문서를 준비해야 한다.

## 8.4 Context reset

Context reset은 새 세션을 시작하는 일이다. 처음 들으면 위험해 보이지만, 잘 설계하면 오히려 강력하다. 새 세션은 오래된 잡음을 제거하고, 구조화된 인계 문서만 읽고 출발한다.

좋은 reset 조건:

- 한 기능 단위가 끝났을 때
- 대화가 너무 길어졌을 때
- 모델이 반복해서 혼란스러워할 때
- 새로운 역할의 에이전트가 필요할 때

## 8.5 Handoff artifact

Handoff artifact는 인수인계 문서다. Anthropic의 long-running harness 글은 `claude-progress.txt`, feature list, git history를 사용해 새 agent가 현재 상태를 파악하게 하는 접근을 설명한다.

좋은 handoff artifact는 다음을 포함한다.

```md
# Handoff

## 목표
현재 프로젝트가 달성하려는 것

## 완료된 일
검증된 완료 항목

## 진행 중인 일
아직 끝나지 않은 항목

## 다음 행동
다음 세션이 가장 먼저 해야 할 일

## 주의점
실패했던 접근, 위험한 파일, 남은 질문
```

## 8.6 Feature list와 progress file

Feature list는 전체 완료 기준이고, progress file은 시간순 작업 기록이다.

|파일|역할|
|---|---|
|feature_list.json|무엇이 남았는지 구조화|
|progress.md|지금까지 무엇을 했는지 설명|
|git history|실제 변경 이력|
|test report|무엇이 검증되었는지 증거|

Feature list가 없으면 AI는 “많이 한 것 같다”를 “끝났다”고 착각할 수 있다.

Anthropic 글에서 특히 실전적인 점은 feature list를 단순한 할 일 목록이 아니라 **검증 대장**처럼 다룬다는 데 있다. 처음에는 모든 항목을 `passes: false`로 둔다. 에이전트는 기능 설명이나 테스트 조건을 마음대로 바꾸지 못하고, 실제로 구현하고 확인한 뒤에만 `passes` 값을 `true`로 바꿀 수 있어야 한다.

예를 들어 다음처럼 생각하면 쉽다.

```json
[
  {
    "feature": "여행 보험 가입 확인",
    "check": "보험 증권 PDF가 저장되어 있고, 보장 기간이 여행 기간 전체를 포함한다.",
    "passes": false
  },
  {
    "feature": "공항 이동 방법 확정",
    "check": "출발 시간, 이동 수단, 예상 소요 시간, 대체 경로가 기록되어 있다.",
    "passes": false
  }
]
```

장기 여행 체크리스트에서도 “보험 알아보기”라고만 적으면 완료 기준이 흐릿하다. 하지만 “보험 증권 PDF가 있고, 날짜가 맞고, 가족 구성원이 모두 포함되어 있다”라고 적으면 확인할 수 있다. AI 작업도 마찬가지다. 좋은 feature list는 할 일을 적는 문서가 아니라, **완료라고 말하기 전에 무엇을 증명해야 하는지 적는 문서**다.

### Ralph Loop - 여러 세션을 이어 주는 근무 교대 시스템
![[Pasted image 20260814140920.png]]장시간 에이전트의 가장 큰 문제는 “다음 근무자가 어제 무슨 일이 있었는지 모른다”는 점이다. Anthropic의 long-running harness 연구는 이를 해결하기 위해 초기화 에이전트와 코딩 에이전트를 나누었다. 일부 커뮤니티 자료는 이 흐름을 Ralph Loop라고 부르는 표현과 함께 소개한다.

구조는 단순하다.

1. **Initializer Agent**가 처음에 환경을 만든다. `init.sh`, `progress.md`, `feature_list.json`, 첫 git commit을 준비한다.
2. **Coding Agent**는 매 세션마다 git log, progress file, feature list를 읽고 현재 상태를 파악한다.
3. 미완료 기능 중 하나를 고른다.
4. 구현하거나 수정한다.
5. 테스트하고, 통과한 경우에만 feature list의 상태를 바꾼다.
6. git commit과 progress update를 남긴다.
7. 다음 세션은 이 흔적을 읽고 이어 간다.

비유하자면 24시간 운영되는 병원의 교대근무다. 의사가 아무리 유능해도 인수인계 차트가 없으면 환자의 상태를 놓친다. 장시간 에이전트의 `progress.md`와 `feature_list.json`은 바로 그 차트다.

이때 파일 시스템은 단순한 저장 공간이 아니라 **컨텍스트 창 사이를 이어 주는 기억 장치**가 된다. 대화창 안의 내용은 길어지면 압축되거나 사라질 수 있지만, `progress.md`, `feature_list.json`, git history, test report는 다음 세션이 다시 읽을 수 있다. 그래서 장시간 하네스에서는 “모델이 기억한다”보다 “다음 모델도 읽을 수 있게 남긴다”가 더 안전한 원칙이다.

```text
새 세션 시작
→ pwd 확인
→ progress.md 읽기
→ git log 읽기
→ feature_list.json에서 미완료 항목 선택
→ init.sh 또는 smoke test 실행
→ 한 기능만 작업
→ 테스트 후 상태 업데이트
→ commit + progress 기록
```

처음 배우는 사람이 바로 적용할 수 있는 핵심 규칙은 하나다. **AI에게 “계속해”라고만 하지 말고, 계속할 수 있는 흔적을 파일로 남기게 하라.**

LangChain의 에이전트 하네스 글에서 배울 수 있는 또 하나의 포인트는 “끝내려는 순간을 하네스가 한 번 더 붙잡는다”는 점이다. 긴 작업에서 에이전트는 컨텍스트가 복잡해지면 스스로 “이제 마무리하겠습니다”라고 판단할 수 있다. 이때 하네스가 바로 종료시키지 않고, 새롭고 깨끗한 세션을 열어 원래 목표, 진행 파일, 남은 기능 목록을 다시 읽게 만들 수 있다.

이것은 병원 교대근무에서 퇴근하려는 의사에게 “잠깐, 인수인계 차트에 빠진 환자는 없는지 확인하고 다음 근무자에게 넘기자”라고 말하는 것과 같다. 핵심은 에이전트를 오래 붙잡아 두는 데 있지 않다. **낡고 복잡해진 대화창을 새 작업자에게 안전하게 넘기는 구조**를 만드는 데 있다.

## 8.7 Git history를 상태 기억으로 쓰기

Git은 개발자 도구지만, 하네스 관점에서는 상태 기억 장치다. 어떤 파일이 언제 왜 바뀌었는지 기록한다. AI가 장시간 작업을 할 때 git commit은 “작업 일지” 역할을 한다.

개발 업무가 아닌 일에서도 유사한 구조를 만들 수 있다. 문서 버전 기록, 변경 로그, 승인 이력, 작업 완료표가 모두 git history와 같은 역할을 한다.

## 8.8 Init script와 smoke test

Init script는 새 세션이 시작될 때 환경을 준비하는 스크립트다. Smoke test는 기본 기능이 크게 깨지지 않았는지 빠르게 확인하는 테스트다.

식당 비유로는 개점 체크리스트다. 가스 밸브, 냉장고 온도, 카드 단말기, 예약 목록을 확인한 뒤 영업을 시작한다. AI 작업도 마찬가지다.

## 8.9 브라우저 검증: 실제로 써 보기

장시간 작업에서 또 하나 중요한 점은 에이전트가 “테스트가 일부 통과했다”를 “사용자가 쓸 수 있다”로 착각할 수 있다는 점이다. Anthropic 글에서도 에이전트가 단위 테스트나 `curl` 확인만으로 기능을 완료 처리하는 문제가 있었다고 설명한다. 그래서 실제 사용 흐름을 브라우저 자동화로 확인하게 하는 방식이 중요해졌다.

일상 비유로는 여행 가방을 다 쌌다고 말하는 것과 비슷하다. 체크리스트에 “충전기”라고 적고 체크했다고 끝이 아니다. 실제로 콘센트에 꽂아 충전이 되는지, 해외 어댑터가 맞는지, 보조배터리가 기내 반입 가능한지까지 확인해야 한다.

AI 작업에서도 마찬가지다.

|완료 주장|실제 검증|
|---|---|
|로그인 화면을 만들었다|브라우저에서 이메일과 비밀번호를 입력해 로그인 흐름을 끝까지 확인한다|
|검색 기능을 만들었다|실제 검색어를 넣고 결과, 빈 결과, 오류 상태를 확인한다|
|결제 버튼을 연결했다|샌드박스 환경에서 승인, 취소, 실패 흐름을 확인한다|
|보고서를 완성했다|출처 링크, 빠진 항목, 중복 문장, 출력 형식을 확인한다|

즉, 장시간 하네스의 완료 기준은 “코드가 있다”가 아니라 “사용 흐름이 통과했다”에 가까워야 한다. 개발 업무에서는 브라우저 테스트, 스크린샷, 로그, 테스트 리포트가 그 증거가 되고, 일상 업무에서는 예약번호, 영수증, 확인 메일, 최종 체크리스트가 그 증거가 된다.

## 8.10 Clean state의 의미

Clean state는 작업 환경이 예측 가능한 상태라는 뜻이다. 테스트가 실패한 채로 방치되어 있거나, 임시 파일이 쌓여 있거나, 진행 기록이 업데이트되지 않았으면 다음 세션이 혼란스러워진다.

잘 설계된 하네스는 각 세션 종료 시 다음을 요구한다.

- 변경 요약
- 실행한 테스트
- 실패한 테스트
- 남은 작업
- 다음 추천 작업

## 8.11 장시간 작업에서 자주 생기는 실패

Anthropic 글의 사례를 일상 언어로 바꾸면, 장시간 에이전트의 실패는 대체로 아래 네 가지로 모인다.

|실패 모습|왜 위험한가|하네스 보완|
|---|---|---|
|너무 일찍 “전체 완료”라고 말한다|일부 기능만 만들고 프로젝트가 끝났다고 착각한다|feature list에서 남은 항목을 먼저 읽게 한다|
|버그가 있는 상태로 다음 세션에 넘긴다|다음 세션이 실패 원인을 다시 찾아야 한다|실패 테스트와 오류 로그를 progress file에 남긴다|
|실제 사용 흐름을 확인하지 않는다|겉보기에는 만들어졌지만 사용자는 막힌다|브라우저 검증, 스크린샷, 시나리오 테스트를 요구한다|
|매번 실행 방법을 다시 찾는다|시작할 때마다 시간이 낭비되고 실수가 반복된다|`init.sh`와 smoke test로 시작 절차를 고정한다|

이 표는 병원 교대근무로도 이해할 수 있다. “환자 상태 좋음”이라고만 쓰면 다음 의사는 무엇이 좋은지 모른다. 체온, 혈압, 투약 여부, 다음 검사 시간처럼 확인 가능한 항목이 있어야 한다. 장시간 에이전트도 “완료”라는 말보다 **무엇을 확인했고 무엇이 남았는지**가 더 중요하다.
