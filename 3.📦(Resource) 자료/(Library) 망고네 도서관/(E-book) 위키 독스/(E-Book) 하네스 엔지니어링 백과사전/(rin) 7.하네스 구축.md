## 6.6 Agents SDK

OpenAI Agents SDK는 agent, tools, handoffs, guardrails, tracing, sessions 같은 요소를 코드로 조립하게 해 준다. 개발자에게는 프레임워크이고, 개발자가 아닌 사람에게는 “AI 업무팀을 구성하는 설계도”라고 이해하면 된다.

예시 구조:

```text
Customer Support Agent
├── Policy Search Tool
├── Order Lookup Tool
├── Refund Specialist Agent
├── Safety Guardrail
└── Trace Dashboard
```

이 구조를 개인 비서 업무로 다시 보면 다음과 같다.
  
|OpenAI 구성요소|개인 비서 사무실에서의 모습|
|---|---|
|Responses API|모든 요청이 처음 들어오는 접수 창구|
|Function calling|캘린더, 메일, 예약 앱을 실제로 여는 행동|
|Built-in tools|검색, 파일 찾기, 계산처럼 자주 쓰는 기본 도구|
|Handoff|법무, 회계, 여행 예약처럼 전문 담당자에게 넘기는 일|
|Guardrail|결제, 외부 발송, 민감한 정보 처리 전에 멈추는 확인 규칙|
|Tracing|누가 어떤 도구를 썼고 어떤 결과가 나왔는지 남기는 업무 일지|
|Eval|비서 업무가 정확했는지 주기적으로 확인하는 점검표|

## 6.7 Handoffs, guardrails, tracing

Handoff는 전문 에이전트에게 넘기는 방식이고, guardrail은 위험하거나 잘못된 요청을 걸러내는 장치이며, tracing은 에이전트가 무엇을 했는지 기록하는 일이다. OpenAI Agents SDK 문서는 tracing이 LLM generation, tool call, handoff, guardrail, custom event를 기록한다고 설명한다.

회사 업무로 비유하면 다음과 같다.

|기능|회사 비유|
|---|---|
|Handoff|상담원이 전문 부서로 연결|
|Guardrail|결재 규정, 법무 검토, 보안 승인|
|Tracing|업무 로그, 결재 이력, 감사 기록|

## 6.8 에이전트가 읽기 쉬운 애플리케이션

OpenAI의 하네스 엔지니어링 글에서 눈여겨볼 부분은 “에이전트가 코드를 많이 썼다”가 아니라, **에이전트가 스스로 관찰하고 수정할 수 있는 환경을 만들었다**는 점이다. 사람에게 좋은 화면이 항상 에이전트에게 좋은 화면은 아니다. 에이전트에게는 화면뿐 아니라 로그, 테스트 결과, trace, 오류 메시지, 파일 구조, 실행 명령이 모두 인터페이스가 된다.

일상으로 비유하면, 신입 직원에게 “매장을 잘 운영해 봐”라고만 말하는 것과 다르다. 좋은 매장에는 재고표, 매출표, 고객 문의 기록, 체크리스트, CCTV, 마감 점검표가 있다. 직원은 이 자료를 보고 어디가 문제인지 찾고, 다음 행동을 정한다. AI 에이전트도 마찬가지다. 결과 화면만 보는 것이 아니라, 실패 원인과 다음 행동을 읽을 수 있어야 한다.

|에이전트가 보기 어려운 환경|에이전트가 읽기 쉬운 환경|
|---|---|
|오류가 화면에만 흐릿하게 보인다|오류 메시지와 로그가 파일이나 trace로 남는다|
|테스트 실패 이유가 길고 산만하다|실패 위치, 기대값, 실제값이 분명하다|
|앱 상태를 사람 눈으로만 확인한다|브라우저 검증, 스크린샷, 접근성 정보로 확인한다|
|문서와 규칙이 여러 채팅방에 흩어져 있다|저장소 안의 짧은 지도와 `docs/` 구조로 정리한다|
|수정 후 무엇이 바뀌었는지 알기 어렵다|`git diff`, 테스트 결과, 리뷰 체크리스트가 남는다|

OpenAI 하네스를 설계할 때는 모델 호출 코드만 보지 말아야 한다. 에이전트가 “보고, 실행하고, 실패를 읽고, 다시 고칠 수 있는가”를 함께 봐야 한다. 이것이 제13장에서 다루는 ACI와도 연결된다.

## 6.9 에이전트가 만드는 것은 코드만이 아니다

OpenAI 사례는 에이전트의 산출물을 코드로만 보지 않는다. 에이전트는 제품 코드뿐 아니라 테스트, 문서, 릴리스 도구, 평가 케이스, 리뷰 응답, 대시보드 정의, 운영 스크립트까지 만들 수 있다. 이 관점이 중요하다. “AI가 코드를 써준다”로만 이해하면 하네스의 절반만 보는 셈이다.

하네스 엔지니어링에서는 산출물을 더 넓게 본다.

|산출물|하네스 관점|
|---|---|
|제품 코드|사용자가 직접 만나는 기능|
|테스트 코드|다음 변경에서도 기능이 깨지지 않게 하는 안전망|
|문서|다음 에이전트와 사람이 읽을 수 있는 업무 기억|
|릴리스/배포 도구|반복 배포를 사람이 매번 손으로 하지 않게 하는 절차|
|eval 케이스|하네스가 좋아졌는지 비교하는 시험지|
|trace와 대시보드|어디서 실패했는지 찾는 계기판|
|리뷰 응답|의사결정과 수정 이유를 남기는 작업 기록|

회사 일로 바꾸면 더 쉽다. 좋은 직원은 보고서만 쓰는 사람이 아니다. 보고서 양식도 정리하고, 다음 사람이 쓸 체크리스트도 남기고, 실수한 지점을 기록해서 다음 달 업무 방식도 고친다. AI 에이전트도 잘 설계된 하네스 안에서는 결과물 하나만 만들고 끝나지 않는다. **다음 실행이 더 나아지도록 주변 구조까지 함께 남긴다.**

### 🧑‍💻 사람의 방식 vs 🤖 에이전트의 방식

사람과 AI는 정보를 받아들이는 방식(인터페이스)이 완전히 다릅니다.

- **사람 (시각과 직관 의존):** 예쁜 UI, 팝업창, 색상 변화 등으로 상황을 파악합니다. 앱에 빨간색 경고창이 뜨면 사람은 즉시 "오류가 났네"라고 시각적으로 인지합니다.
    
- **에이전트 (텍스트와 구조 의존):** AI는 기본적으로 텍스트(코드, 로그, 데이터)를 읽고 해석하는 모델입니다. 화면에 아무리 예쁜 빨간 팝업창이 떠도, 텍스트 형태의 '시스템 로그(Log)'나 명확한 '오류 메시지 코드'로 백단에 남겨주지 않으면 에이전트는 무슨 일이 일어났는지 제대로 파악하기 어렵습니다.
### 🎯 요약하자면

작가는 "사람 눈에 예쁘고 직관적인 그래픽 화면(GUI)에만 집중하다 보면, 정작 코드를 짜고 판단을 내려야 하는 에이전트에게는 필수적인 데이터(텍스트 로그, 명확한 에러 값)가 차단될 수 있다"는 점을 지적한 것입니다. 즉, AI가 일을 잘하게 하려면 사람이 보는 화면 뒤편에 '에이전트 전용 텍스트 계기판(명확한 로그, 구조화된 폴더, 테스트 결과표)'을 반드시 마련해 주어야 한다는 뜻입니다.

문서에서 설명한 개인 비서 및 회사의 비유를 활용해 GTD의 각 단계를 에이전트의 기능으로 분류해 드릴게요.

### 1. 수집함 (Inbox) ➔ 🚪 Responses API

- **GTD 단계:** 모든 일거리와 아이디어가 처음 쏟아져 들어오는 곳입니다.
    
- **에이전트 기능:** Responses API (접수 창구)가 이 역할을 합니다. 모든 사용자의 요청이 처음 들어와 "이건 바로 답할 일인가, 도구를 쓸 일인가"를 1차로 마주하는 관문입니다.
    

### 2. 명료화 후 "행동이 필요 없는 일" 처리

- 🗑️ **휴지통 (Trash) ➔ Guardrail (가드레일)**
    
    - **에이전트 기능:** 결제, 외부 발송, 보안 위반 등 회사 규정에 어긋나거나 수행하면 안 되는 위험한 요청을 걸러내고 차단(버림)하는 확인 규칙입니다.
        
- 🗂️ **참고자료 (Reference) ➔ File search (파일 검색) / AGENTS.md**
    
    - **에이전트 기능:** 당장 행동할 건 아니지만, 에이전트가 나중에 꺼내 읽어야 하는 사내 매뉴얼이나 프로젝트 규칙(AGENTS.md)입니다. 에이전트가 '읽기 쉬운 환경'을 위해 문서(docs/) 구조로 정리해둡니다.
        
- 💭 **언젠가/아마도 (Someday/Maybe) ➔ Tracing (업무 일지)**
    
    - **에이전트 기능:** 당장 실행하지는 않아도, 누가 어떤 도구를 썼고 어떤 결과나 오류가 났는지 로그(Trace)로 남겨두는 기능입니다. 에이전트나 사람은 이 기록을 보고 다음 행동을 고치거나 미래의 작업을 계획합니다.
        

### 3. "행동이 필요한 일" 처리 (다음 행동)

- ⚡ **실행한다 (Do it) ➔ Function calling / Built-in tools**
    
    - **에이전트 기능:** 2분 안에 끝낼 수 있는 명확한 일이라면, 에이전트가 직접 도구(웹 검색, 코드 실행, 메일 초안 작성 등)를 호출하여 즉각적으로 업무를 처리(실행)합니다.
        
- 🤝 **위임한다 (Delegate) ➔ Handoff / Subagent**
    
    - **에이전트 기능:** 내 권한 밖이거나 너무 무거운 일은 Handoff(넘기기)를 통해 법무, 회계, 여행 예약 등을 담당하는 다른 전문 에이전트(Subagent)나 사람에게 넘깁니다.
        
- 🗓️ **연기한다 (Defer) ➔ Hook / Codex agent loop의 대기**
    
    - **에이전트 기능:** 특정 시점에 실행해야 하는 일은 자동으로 켜지는 센서등인 **Hook**에 맡기거나, 에이전트 루프 안에서 우선순위를 미뤄두었다가 나중에 다시 관찰하고 판단하게 만듭니다.

요약하자면, GTD에서 사람이 뇌를 비우고 시스템에 맡기듯, AI 에이전트도 도구(실행), 핸드오프(위임), 가드레일(휴지통)이라는 명확한 구조(하네스) 안에서 일해야 엉뚱한 거짓말 없이 깔끔하게 업무를 쳐낼 수 있습니다.

![[Pasted image 20260814133545.png]]Codex 관련 문서를 하네스 관점으로 읽으면 각각의 기능이 하나의 부품처럼 보인다. 기능 이름을 외우는 것보다, 이 기능이 에이전트의 어떤 문제를 해결하는지 보는 편이 훨씬 쉽다.

| Codex 구성요소  | 일상생활 비유             | 하네스에서 하는 일                               |
| ----------- | ------------------- | ---------------------------------------- |
| `AGENTS.md` | 매장 운영 수칙            | 프로젝트 규칙, 실행 명령, 주의사항을 에이전트가 작업 전에 읽게 한다. |
| Skill       | 반복 업무 레시피 카드        | 자주 하는 작업의 절차, 참고자료, 스크립트를 재사용 가능하게 묶는다.  |
| Subagent    | 따로 보낸 조사 담당자        | 독립적으로 처리할 일을 병렬로 맡기고 결과만 회수한다.           |
| Worktree    | 별도 작업대              | 같은 프로젝트에서 여러 작업을 서로 방해하지 않고 진행하게 한다.     |
| Hook        | 자동으로 켜지는 센서등        | 특정 시점에 검사, 기록, 승인, 요약 같은 절차를 자동 실행한다.    |
| App Server  | 매장 시스템과 주문 앱의 연결 통로 | Codex를 제품이나 클라이언트 안에 깊게 연결할 때 쓰는 인터페이스다. |
Codex agent loop 설명에서 중요한 말은 “loop”다. 에이전트는 한 번 생각하고 끝나는 것이 아니라, 사용자의 요청을 받고, 모델이 다음 행동을 정하고, 도구를 실행하고, 결과를 관찰하고, 다시 판단한다. 이 반복이 끝났다고 판단할 때 비로소 사용자에게 “무엇을 했다”고 보고한다.

일상으로 바꾸면 출장 수리 기사와 비슷하다. 고객이 “세탁기가 멈췄어요”라고 말하면, 수리 기사는 바로 부품을 갈지 않는다. 먼저 증상을 듣고, 전원을 확인하고, 배수구를 보고, 테스트 버튼을 눌러 보고, 결과를 보면서 다음 행동을 정한다. 마지막에는 “배수 필터를 청소했고, 정상 동작을 확인했습니다”라고 보고한다. 이 전체 흐름이 agent loop다.

|Codex loop 단계|출장 수리 기사 비유|하네스 관점|
|---|---|---|
|사용자 요청|고객이 문제를 설명한다.|목표와 제약이 들어온다.|
|모델 추론|수리 기사가 어디를 볼지 판단한다.|다음 행동, 도구, 검증 방법을 고른다.|
|도구 실행|전원, 배수구, 부품을 실제로 확인한다.|파일 읽기, 명령 실행, 코드 수정, 테스트를 수행한다.|
|관찰|검사 결과를 보고 원인을 좁힌다.|stdout, 오류 메시지, diff, 테스트 결과를 읽는다.|
|반복|필요하면 다른 부위를 다시 본다.|새 관찰을 바탕으로 다음 행동을 정한다.|
|종료 보고|고친 내용과 확인 결과를 고객에게 말한다.|작업 산출물과 검증 결과를 요약한다.|

여기서 하네스는 수리 기사의 손목을 잡고 조종하는 장치가 아니다. 어떤 공구를 쓸 수 있는지, 위험한 전기 작업은 언제 멈춰야 하는지, 작업 기록을 어디에 남길지, 수리 후 어떤 테스트를 해야 하는지 정하는 운영 환경이다. 그래서 Codex를 볼 때도 “모델이 코드를 잘 쓰는가”만 보면 부족하다. **루프가 어떤 관찰을 받고, 어떤 도구를 쓰고, 어디서 멈추는지**를 함께 봐야 한다.

실무에서는 다음 순서로 시작하면 된다.

1. 자주 들어오는 실제 요청 20개를 모은다.
2. 기대 결과를 사람이 정한다.
3. 모델 출력과 기대 결과를 비교한다.

# CLAUDE.md

## 대화 방식
- 불필요한 인사말 없이 바로 답한다.
- 확실하지 않은 사실, 날짜, 수치, 출처는 먼저 불확실하다고 말한다.
- 간단한 질문은 짧게, 복잡한 작업은 충분히 자세히 답한다.

## 변경 통제
- 사용자가 요청하지 않은 파일, 문단, 구조는 바꾸지 않는다.
- 큰 변경, 삭제, 덮어쓰기, 외부 전송은 먼저 무엇을 바꿀지 설명하고 확인을 받는다.
- 작업이 끝나면 변경한 내용과 확인이 필요한 점을 짧게 정리한다.

## 사용자와 프로젝트 맥락
- 대상 사용자: [예: 하네스 엔지니어링을 처음 접하는 사람]
- 선호 톤: [예: 친절하고 차분하지만 장황하지 않게]
- 피할 것: [예: 검증되지 않은 수치, 과장된 표현, 불필요한 전문용어]

## 기억과 연속성
- 중요한 결정은 `MEMORY.md`에 남긴다.
- 세션을 끝낼 때 완료한 일, 진행 중인 일, 다음 할 일을 요약한다.

## 개발 작업 안전
- 현재 요청과 직접 관련된 파일과 코드만 수정한다.
- 기술 스택과 테스트 명령은 프로젝트 규칙을 따른다.

## 고위험 행동 차단
- 배포, DB 변경, 외부 전송, 삭제처럼 되돌리기 어려운 행동은 먼저 확인을 받는다.

![[Pasted image 20260814135103.png]]둘을 구분하는 이유는 간단하다. 팀 규칙과 개인 취향이 섞이면 나중에 관리가 어려워진다. 회사 냉장고에 모두가 먹을 반찬과 내 개인 간식을 뒤섞어 두면 헷갈리는 것과 같다. 프로젝트 공용 설정은 함께 쓰는 기준이고, 개인 설정은 내 작업 방식을 편하게 만드는 보조 장치다.

여기서 중요한 것은 모든 파일명을 외우는 것이 아니다. **규칙은 `CLAUDE.md`, 반복 업무는 `skills`, 역할은 `agents`, 강제 제어는 `settings`와 `hooks`로 나누어 생각하는 것**이다. 이 감각이 생기면 Claude Code는 낯선 폴더 묶음이 아니라, AI가 일하는 작은 사무실처럼 보이기 시작한다.

|---|---|---|---|

이 다섯 층은 “전부 켜야 하는 체크리스트”가 아니다. Claude Code 공식 문서도 처음부터 모든 확장을 설정하라고 말하지 않는다. 반복되는 문제가 생길 때마다 그 문제에 맞는 층을 하나씩 추가하는 방식이 더 자연스럽다. Claude가 같은 규칙을 두 번 놓치면 `CLAUDE.md`에 적고, 같은 절차를 세 번째로 붙여 넣고 있다면 Skill로 빼고, 반드시 매번 실행되어야 하는 검사는 Hook으로 옮기고, 한 작업이 대화를 너무 어지럽히면 Subagent에게 맡기는 식이다.

#### 처음에는 어떤 순서로 익히면 좋을까

처음 Claude Code를 배우는 사람은 모든 기능을 한 번에 이해하려고 하지 않아도 된다. 아래 순서로 익히면 자연스럽다.

|순서|먼저 해볼 일|익히는 감각|
|---|---|---|
|1|프로젝트 루트에 짧은 `CLAUDE.md`를 만든다.|AI에게 매번 다시 말하지 않아도 되는 기본 규칙을 만든다.|
|2|반복해서 붙여 넣는 절차를 Skill로 만든다.|긴 프롬프트를 재사용 가능한 매뉴얼로 바꾼다.|
|3|꼭 실행해야 하는 검사를 Hook으로 옮긴다.|부탁이 아니라 자동 점검으로 바꾼다.|
|4|긴 조사나 독립 검토를 Subagent에게 맡긴다.|주 대화의 책상 위를 깨끗하게 유지한다.|
|5|여러 프로젝트에서 쓰는 구성을 Plugin으로 묶는다.|개인 설정을 팀과 조직의 운영 패키지로 확장한다.|

결국 판단 기준은 간단하다.

|질문|어울리는 위치|
|---|---|
|항상 알아야 하는 규칙인가?|`CLAUDE.md` 또는 `.claude/rules/`|
|가끔 필요한 긴 절차인가?|Skill|
|반드시 자동으로 실행되어야 하는 검사인가?|Hook|
|별도 담당자에게 맡겨도 되는 독립 작업인가?|Subagent|
|여러 프로젝트와 팀에 배포할 것인가?|Plugin|
|외부 도구나 데이터에 연결해야 하는가?|MCP|

이렇게 보면 Claude Code는 단순한 채팅 도구가 아니다. `CLAUDE.md`는 기억과 규칙을 제공하고, Skill은 반복 업무를 절차화하며, Hook은 빠뜨리면 안 되는 일을 자동화하고, Subagent는 일을 나누고, Plugin은 그 구성을 다른 곳으로 옮긴다. MCP는 외부 세계와 연결되는 통로가 된다. 이 전체가 모여 Claude Code의 하네스를 이룬다.

![[Pasted image 20260814135407.png]]![[Pasted image 20260814135415.png|700]]

|기능|하네스 위치|쉬운 비유|핵심 질문|
|---|---|---|---|
|`CLAUDE.md`|1층 기억과 규칙|사무실 벽에 붙은 기본 규칙|Claude가 매번 알아야 하는 원칙인가?|
|Permissions|3층 권한과 안전|출입카드와 잠금장치|읽기, 쓰기, 실행 권한을 어디까지 줄 것인가?|
|Skills|2층 업무 매뉴얼|반복 업무 레시피|같은 절차를 계속 설명하고 있는가?|
|Hooks|3층 자동 점검|가스 차단기와 마감 알림|사람이 자주 빼먹는 검사를 자동화할 수 있는가?|
|Slash Commands|운영 버튼|자주 쓰는 단축 버튼|긴 요청을 짧은 명령으로 바꿀 수 있는가?|
|Plan Mode|실행 전 승인|공사 전 설계도 확인|바로 실행하기 전에 계획을 봐야 하는가?|
|Checkpoints|복구 안전망|저장 지점과 되돌리기|문제가 생겼을 때 어디로 돌아갈 것인가?|
|Compaction|문맥 정리|긴 회의록 요약|대화가 길어져 핵심이 묻히고 있는가?|
|Context Control|1층 문맥 관리|책상 위 자료 고르기|Claude가 지금 무엇을 보고 일해야 하는가?|
|MCP|외부 연결 통로|외부 창고와 연결된 전선|어떤 도구나 데이터에 연결해야 하는가?|
|Subagents|4층 전문 담당자|역할을 나눈 팀원|독립 담당자에게 맡기면 더 깨끗한 작업인가?|
|Headless Mode|자동화 실행|무인 접수 창구|사람이 붙어 있지 않아도 반복 실행할 일인가?|

이 표에서 중요한 점은 12가지를 모두 같은 깊이로 외우는 것이 아니다. 처음에는 `CLAUDE.md`, permissions, Plan Mode, checkpoints처럼 작업을 안전하게 만드는 기능부터 익히면 된다. 반복 작업이 늘어나면 Skills와 slash commands로 표준화하고, 반드시 지켜야 하는 검사는 Hooks로 옮긴다. 외부 도구가 필요해지면 MCP를 연결하고, 작업이 복잡해지면 Subagents로 나눈다. 마지막으로 CI나 반복 보고처럼 사람이 매번 붙어 있지 않아도 되는 일은 headless mode로 자동화한다.

### 잘 작동하는 Skill의 5가지 구성요소
![[Pasted image 20260814135628.png]]![[Pasted image 20260814135755.png]]![[Pasted image 20260814135857.png]]
### 1. 에이전트를 통제하는 '5계층 하네스 구조' (7.3절)

에이전트에게 일을 시킬 때 모든 지시사항을 프롬프트 하나에 욱여넣으면 반드시 고장이 납니다. 문서는 이를 5가지 층으로 분리하라고 조언하는데, 이는 어떤 도구를 쓰든 똑같이 적용되는 진리입니다.

- **1층 (기본 규칙):** 매번 말하지 않아도 항상 지켜야 하는 절대 원칙 (예: 말투, 프로젝트 배경)
    **벽에 붙인 포스터):** "항상 손을 씻고, 존댓말을 써라." 매번 말하지 않아도 AI가 항상 지켜야 하는 기본 배경입니다.
- **2층 (업무 매뉴얼):** 특정 상황에만 꺼내보는 절차서 (예: 제안서 작성법)
    **서랍 속 레시피 북):** "파스타 만드는 법." 평소엔 안 보다가, 손님이 파스타를 주문할 때만 서랍에서 꺼내 읽게 하는 구체적인 절차입니다.
- **3층 (자동 점검):** 사고를 치기 전에 무조건 멈추게 하는 가스 차단기 같은 권한 제어
    **가스 차단기):** "냄비가 타면 무조건 가스를 차단하라." AI가 멋대로 메일을 발송하거나 파일을 지우기 전에 강제로 멈추게 하는 안전장치입니다.
- **4층 (전문 담당자):** 일을 섞지 않고 쪼개서 맡기는 하위 에이전트 (Subagent)
    **재료 손질 알바생):** 양파 까는 일만 전문으로 하는 하위 AI(Subagent)를 둡니다. 메인 셰프(메인 AI)가 요리(핵심 업무)에 집중하도록 일을 쪼개는 겁니다.
- **5층 (외부 도구):** 외부 DB나 API와 연결하는 플러그인
    **배달 앱 연동):** 완성된 음식을 라이더에게 넘기듯, 외부 DB나 메일 시스템과 연결하는 플러그인입니다.

### 2. 에이전트의 실패를 진단하는 '5가지 유형' (7.4절)

프롬프트나 지시를 내렸을 때 AI가 엉뚱하게 행동하는 패턴을 아주 날카롭게 분류해 두었습니다. 내가 만든 AI가 이상한 짓을 할 때, 어디를 고쳐야 할지 알려주는 훌륭한 진단표입니다.

- **침묵하는 스킬:** 써야 할 때 안 씀 (트리거가 모호함)
    **(작동 안 함):** 먼지가 쌓였는데 청소를 안 합니다. ➔ **해결:** 먼지를 인식하는 센서(작동 조건)를 더 명확하게 설정해 줘야 합니다.
- **하이재커:** 엉뚱한 상황에 끼어듦 (하지 말아야 할 조건이 없음)
    **(급발진):** 거실만 닦으라니까 강아지 밥그릇까지 밀어버립니다. ➔ **해결:** "강아지 집 근처는 절대 가지 마(금지 조건)"라는 규칙을 추가해야 합니다.
- **표류하는 스킬:** 결과가 매번 다름 (출력 기준이 없음)
    **(오락가락):** 어제는 지그재그로 청소하더니 오늘은 빙글빙글 돕니다. ➔ **해결:** 결과물에 대한 명확한 양식(결과물 가이드라인)을 쥐어줘야 합니다.
- **유리 멘탈 스킬:** 예외 상황이 오면 고장 남 (엣지 케이스 고려 안 함)
    **(작은 변수에 고장):** 바닥에 양말 한 짝이 있다고 오류를 내며 멈춥니다. ➔ **해결:** "장애물이 있으면 피해 가라"는 예외 상황 대처법을 알려줘야 합니다.
- **과한 의욕:** 시키지도 않은 말을 덧붙임 (출력 범위 제한이 없음)
    **(투머치토커):** 바닥 청소를 끝내고서 굳이 안 해도 될 화장실 청소까지 하려다 물에 빠집니다. ➔ **해결:** "딱 바닥만 닦고 끝내라"고 업무의 종료 지점을 칼같이 그어줘야 합니다.

### 3. 업무의 성격을 나누는 '역량형 vs 선호형' (7.5절)

AI에게 일을 가르칠 때 이 기준을 명확히 하면 유지보수가 엄청나게 쉬워집니다.

- **역량형 (모델의 한계 보완):** AI가 아직 엑셀 변환 같은 걸 잘 못해서 내가 규칙을 촘촘히 짜준 경우. 나중에 AI 모델이 더 똑똑하게 업데이트되면 이 규칙은 미련 없이 버리면 됩니다.
    - _예시:_ 지금 쓰는 AI가 표(Table)를 예쁘게 못 그려서, "1열은 굵게 하고, 2열은 가운데 정렬해"라고 아주 복잡하게 10줄짜리 팁을 적어뒀습니다.
    - _미래:_ 나중에 엄청 똑똑한 AI 모델(GPT-6 등)이 나오면 이 규칙은 **미련 없이 버려야 합니다.** 알아서 잘할 테니까요.
- **선호형 (우리의 규칙):** 우리 회사의 보고서 톤, 금칙어 등. 이건 AI가 아무리 똑똑해져도 '우리의 선택'이므로 평생 유지하고 관리해야 하는 규칙입니다.
    - _예시:_ "고객에게 보내는 모든 메일 마지막에는 항상 [감사합니다. 플레이그라운드 드림] 이라고 서명을 넣어라."
    - _미래:_ 이건 AI가 아무리 천재가 되어도 **우리가 알려주지 않으면 절대 모릅니다.** 평생 유지하고 관리해야 하는 소중한 규칙입니다.

### 4. Subagent의 진짜 목적은 '협업'이 아니라 '격리'다 (7.9절)

에이전트를 여러 개 만들면 서로 똑똑하게 회의를 할 것 같지만, 실무에서는 그렇게 쓰면 안 된다고 경고합니다. Subagent의 핵심은 **문맥을 격리하는 것**입니다. 메인 에이전트의 머리가 복잡해지지 않게, "너는 저기 가서 이 문서만 읽고 요약만 딱 가져와"라고 독립된 방에서 일을 시키는 용도로 써야 깔끔하다는 통찰입니다.
