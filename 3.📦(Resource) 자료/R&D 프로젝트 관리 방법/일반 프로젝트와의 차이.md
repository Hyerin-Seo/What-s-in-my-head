일반적인 프로젝트 관리가 '이미 아는 문제를 효율적이고 예측 가능하게 구현하는 것(Delivery)'에 초점을 맞춘다면, ==R&D 성격의 프로젝트는 '불확실성을 체계적으로 줄여나가며 기술적·사업적 실현 가능성을 입증하는 것(Discovery)'이 핵심==입니다.
이러한 특성 때문에 기존에 사용하던 지라, 노션, 미로의 운영 방식과 프레임워크를 그대로 대입하면 관리가 겉돌거나 팀의 피로도가 급격히 높아집니다.

## 1. 핵심 관리 패러다임의 차이

### 가설 중심의 완료 정의 (DoD: Definition of Done)

- **일반 프로젝트:** "기획서 요구사항에 맞춰 기능 구현 및 QA 완료"가 태스크의 종료 조건입니다.
- **R&D 프로젝트:** 태스크의 단위가 '기능'이 아니라 '가설(Hypothesis)'이 됩니다. 연구 결과가 실패(가설 기각)로 끝나더라도, 명확한 데이터와 원인 분석이 남았다면 해당 태스크는 성공적으로 완료된 것입니다.

### 일정 추정과 진척도 관리 (Timeboxing vs. Velocity)

- **일반 프로젝트:** 스토리 포인트와 스프린트 속도(Velocity)를 바탕으로 릴리즈 일정을 선형적으로 예측할 수 있습니다.
- **R&D 프로젝트:** "이 기술이 구현 가능한가?"를 파악하는 작업은 2시간이 걸릴 수도, 2주가 걸릴 수도 있습니다.
- 스토리 포인트 추정 대신 **타임박스(Timebox, 예: 3일간 집중 탐색 후 Go/No-Go 판정)** 기반의 **스파이크(Spike)** 기법을 적용해야 일정이 무한정 늘어지는 것을 막을 수 있습니다.

### 음의 지식(Negative Knowledge)의 자산화
- **일반 프로젝트:** 배포된 코드와 사용자 가이드 등 '성공한 결과물' 위주로 문서화합니다.
- **R&D 프로젝트:** "어떤 접근 방식이 왜 작동하지 않았는가"를 남기는 것이 핵심 자산입니다. 이를 기록하지 않으면 몇 달 뒤 다른 담당자가 같은 실패를 반복하게 됩니다.

## 2. 일반 프로젝트 vs R&D 프로젝트 관리 비교

|**구분**|**일반 프로젝트 (Delivery 중심)**|**R&D 프로젝트 (Exploration 중심)**|
|---|---|---|
|**관리 단위**|유저 스토리, 기능 티켓|가설 검증 티켓, 연구 스파이크(Spike)|
|**완료 기준 (DoD)**|요구사항 부합 및 배포|가설 채택/기각 여부 판정과 근거 데이터 확보|
|**진척도 측정**|스프린트 번다운, 기능 진척률|불확실성 감소율, Go/No-Go 마일스톤 달성|
|**실패의 정의**|일정 지연, 결함 발생, 규격 미달|검증 데이터 없이 시간만 소진된 탐색|
|**팀 운영 구조**|단일 스트림 (스프린트 주기 일정)|듀얼 트랙 (R&D 선행 탐색 + 양산/적용 파이프라인)|

## 3. 기존 도구(Jira, Notion, Miro) 적용 방식의 변화

기존 도구를 버리고 새 도구를 도입하기보다는, 도구의 데이터 구조와 템플릿을 R&D 사이클에 맞게 변형해야 합니다.
### Jira: '스파이크'와 '가설 검증' 이슈 타입 신설

- 스프린트 백로그에 일반 개발 티켓과 R&D 티켓을 무작정 섞으면 번다운 차트가 무너집니다.
- 이슈 타입을 **`Research Spike`** 또는 `Hypothesis`로 별도 지정하고, 상한선(Time-limit)을 티켓에 명시합니다.
- 티켓 템플릿에 **검증 대상 가설**, **검증 방법**, 성공 기준(판정 지표)을 필수로 기입하도록 필드를 구성합니다.

### Notion: '실험 일지(Lab Notebook)' DB 구축

- 일반적인 회의록이나 작업 리스트 대신 **실험 로그(Experiment Log)** 데이터베이스를 구축합니다.
- 속성(Property) 설계: `가설`, `사용한 방법론/라이브러리`, `실험 파라미터`, `결과 데이터`, `판정(Adopt / Pivot / Drop)`
- 실패한 시도 태그(`Failed Attempt`)를 별도로 관리하여 나중에 히스토리를 쉽게 검색할 수 있도록 만듭니다.

### Miro: 가설 트리(Hypothesis Tree)와 기술 리스크 매핑

- 일반적인 플로우차트나 와이어프레임 대신 불확실성 매트릭스(영향도 대비 기술적 난이도)를 시각화합니다.
- 하나의 큰 기술 목표를 하위 가설들로 분해하는 '가설 트리'를 그려두고, 팀원들과 함께 어떤 가설부터 검증할지 우선순위를 시각적으로 합의하는 용도로 활용합니다.
