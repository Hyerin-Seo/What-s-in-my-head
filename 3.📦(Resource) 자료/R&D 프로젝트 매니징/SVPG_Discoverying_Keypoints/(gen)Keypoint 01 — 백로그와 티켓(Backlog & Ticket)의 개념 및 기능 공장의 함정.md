# Keypoint 01 — 백로그와 티켓(Backlog & Ticket)의 개념 및 기능 공장의 함정

> **핵심 한 줄 요약**:  
> **백로그(Backlog)**는 '할 일 대기 창고', **티켓(Ticket)**은 '개별 작업 카드 1장'이며, SVPG는 엔지니어가 이유도 모른 채 티켓만 쳐내는 **'기능 공장(Feature Factory)'**으로 전락하는 것을 가장 엄격히 경계합니다.

---

## 1. 용어의 기본 개념과 실생활 비유

### ① 백로그 (Backlog) = "주문 대기열 (밀려 있는 일거리 목록)"
* **실생활 비유**: 식당 주방에 가면 요리사가 순서대로 조리하기 위해 꽂아두는 **'주문서 꽂이'**와 같습니다.
* **소프트웨어 개발에서**: 개발팀이 앞으로 만들어야 할 기능, 개선사항, 버그 수정, 기술 조사 과제들을 모아둔 **'전체 작업 대기 저장소'**를 의미합니다.

### ② 티켓 (Ticket / Issue) = "개별 작업 쪽지 (작업 카드 1장)"
* **실생활 비유**: 놀이공원 이용권이나 식당의 **'개별 주문 영수증 1장'**과 같습니다.
* **소프트웨어 개발에서**: Jira(지라), GitHub Issues, Linear 같은 협업 도구에서 할 일 하나를 등록하면 고유 번호(예: `[ENG-101]`)가 붙은 카드(쪽지)가 생성되는데, 이를 업계에서는 **'티켓'** 또는 **'이슈'**라고 부릅니다.

> 💡 **옵시디언 볼트(`What-s-in-my-head`)와의 1:1 매핑**:
> * `📋 프로젝트 보드`의 `to do` 열에 쌓여 있는 상태 = **백로그 (Backlog)**
> * 그 안에 들어있는 **`유형: 할일` 개별 노트 1장** = **티켓 (Ticket)**

---

## 2. '백로그 티켓'이라는 표현이 쓰이는 실무 맥락

소프트웨어 팀은 보통 1~2주 단위의 개발 주기인 **스프린트(Sprint)**를 운영합니다.

```text
[전체 백로그 창고 (Backlog)]
├── 🎟️ 티켓 01: 검색창 자동완성
├── 🎟️ 티켓 02: 캔버스 줌 버그 수정
├── 🎟️ 티켓 03: DB 인덱스 튜닝
├── 🎟️ 티켓 04: 사용자 탈퇴 API
└── ... (수십~수백 개 대기 중)
           │
           │ [스프린트 플래닝: 이번 주에 할 것 선별]
           ▼
[이번 주 스프린트 보드 (In-Progress)]
├── 🎟️ 티켓 01 ➔ 철수 개발 착수
└── 🎟️ 티켓 02 ➔ 영희 디자인 착수
```

즉, **'백로그 티켓'**이란 **"아직 개발에 착수하지 않고 대기 창고(Backlog)에 꽂혀 자기 차례를 기다리는 개별 일거리 쪽지"**를 뜻합니다.

## 3. SVPG의 핵심 경계: 기능 공장(Feature Factory)의 함정

마티 케이건(Marty Cagan)과 SVPG는 역할 규격이나 아티클에서 *"엔지니어는 단순 백로그 티켓 처리자가 아니다"*, *"PM은 티켓을 일방적으로 뿌리지 마라"*라고 끊임없이 경고합니다. 그 이유는 소프트웨어 조직이 가장 빠지기 쉬운 **'기능 공장'** 안티패턴 때문입니다.

### ❌ 낡은 방식 : 기능 공장 (Feature Factory)
1. 기획자나 경영진이 회의실에서 "버튼 A 만들어라", "DB 테이블 B 설계해라" 같은 **수단(Output/Feature) 중심의 티켓을 100개 만들어 백로그에 쌓아둡니다.**
2. 그리고 개발자에게 "자, 이번 주는 이 티켓 5개 코드 짜서 해치워!"라고 하향식으로 던집니다.
3. **문제점**:
   * 개발자는 **"이 기능을 고객이 왜 쓰는지, 진짜 문제가 해결되는지"**를 전혀 모릅니다.
   * 마치 컨베이어 벨트 조립 노동자처럼 **티켓에 적힌 대로 기계처럼 코딩하고 티켓을 닫아버리는(Done/Close) 하청 노동자**로 전락합니다.
   * 결과적으로 코드는 완벽히 배포되었지만 고객의 고통은 전혀 줄어들지 않는 비극이 발생합니다.

### 🟢 SVPG 정본 방식 : 임파워드 팀 (Empowered Product Team)
1. PM은 개발자에게 기능 티켓을 하달하지 않고, **"지금 사용자가 출처를 검증하느라 5분이나 헤매고 있어(Outcome: 검증 시간 90% 단축)"**라는 **'문제와 목표'**를 함께 공유합니다.
2. 뛰어난 엔지니어는 단순 하청이 아니라 **제품의 공동 설계자(Co-creator)**로 참여합니다.
3. 엔지니어가 스스로 **"아, 그렇다면 뻔한 버튼 만들지 말고, 제가 AI 인라인 앵커링 스파이크를 하루 만에 짜서 검증해볼게요!"**라며 최선의 기술적 티켓을 역발의합니다.

## 4. 요약 비교표

| 구분 | ❌ 기능 공장 (Feature Factory) | 🟢 SVPG 임파워드 팀 (Empowered Team) |
| :--- | :--- | :--- |
| **팀에게 주어지는 것** | 상위에서 정해진 **백로그 티켓(기능 목록)** | 해결해야 할 **Outcome(문제 및 목표 성과)** |
| **엔지니어의 역할** | 티켓에 적힌 대로 코딩하는 **단순 처리자** | 기술적 가능성을 제시하는 **디스커버리 파트너** |
| **성공의 기준** | "이번 주에 티켓 몇 개 쳐냈는가? (Output)" | "고객의 문제가 실제로 해결되었는가? (Outcome)" |
| **백로그의 성격** | 경영진/기획자의 요구사항 쓰레기통 | 가설 검증을 통과한 엄선된 수직 슬라이스 목록 |
