# 린 캔버스 01 v2 — 핵심 문제와 기존 대안 (핵심 북극성과 제품 컨셉)

> **"We must be brutal about truth. Never solve a lukewarm problem, and never fall in love with a specific UI solution before proving the core value."**

---

## 1. 핵심 북극성 (The North Star)

### 🧭 궁극의 아키텍처 질문 (North Star Inquiry)
> **"복잡한 자료를 기반으로 문서를 작성하는 전문가가, 에이전트를 통해 자신의 인지 부하(Cognitive Load)를 극복하고 진정한 인지 증강(Cognitive Augmentation)을 달성하려면, 작업 공간(Workspace)은 어떤 본질적 구조를 가져야 하는가?"**

### 🎯 타깃 유저 (Target User Profile)
* **대상**: 10~50장 이상의 사업계획서, 연구개발계획서, 제안요청서(RFP) 대응 문서, 전략 기획서 등 **다수의 레퍼런스와 엄격한 규격을 바탕으로 논리를 전개해야 하는 전문 문서 작성자**.
* **상황**: 머릿속에 기획 의도와 뼈대는 있으나, 방대한 백데이터 대조와 엄격한 서식 규격 준수로 인해 극심한 인지 피로와 시간 낭비를 겪고 있음.

### 🚨 해결해야 할 본질적 3대 고통 (The 3 Core Pains)
1. **Concept Drift (맥락 붕괴)**: 새 참고 자료를 추가할 때마다 에이전트가 기존 문서의 상위 뼈대와 기획 컨셉을 잊어버리고 제멋대로 엉뚱한 방향으로 리셋하는 문제.
2. **The Correction Loop (교정 지옥)**: 원하는 양식 규격, 톤, 목차를 지키게 하려고 매 턴마다 *"아니 그게 아니라"*며 멱살을 잡고 다그치는 데 모든 에너지를 소모하는 문제.
3. **Verification Hell (환각 검증 지옥)**: 에이전트가 그럴듯하게 채워 넣은 문장과 수치의 사실 여부를 확인하기 위해 수많은 원본 자료를 일일이 열어 `Ctrl + F`로 대조하느라 본작성보다 더 많은 시간을 탕진하는 문제.

## 2. 제품 컨셉 (Core Concept)

### 💡 컨셉 정의: “전문 문서 작성자를 위한 지능형 스캐폴딩 & 검증 엔진”
> 코딩에서 Cursor가 프로젝트 전체 코드베이스 맥락과 Linter 규칙에 구속되어 정밀하게 작동하듯,  
> **문서 작업에서도 에이전트가 사용자의 확립된 아웃라인과 원문 규격에 엄격히 구속(Harnessed)되어 작동하는 인지 증강 작업 공간.**

### 🏛️ 3대 핵심 아키텍처 기둥 (The 3 Pillars)

| 기둥 (Pillar) | 핵심 메커니즘 | 달성하는 사용자 경험 |
| :--- | :--- | :--- |
| **1. Unshakable Concept Anchor<br>(불변의 컨셉 닻)** | • 상위 아웃라인(H1~H3)과 챕터별 핵심 명제의 **물리적 잠금(Lock)**.<br>• 슬롯 단위 격리 실행(Isolated Slot Execution)으로 자료 추가 시에도 컨셉 오염 방지. | 새 자료를 1개를 넣든 100개를 넣든 기획 컨셉과 목차가 흔들림 없이 유지됨. |
| **2. Silent Scaffolding Execution<br>(무언의 스캐폴딩 강제)** | • 과거 통과된 레퍼런스 문서나 공식 양식(RFP 필수항목, 서식, 표 구조)을 엔진이 자동 역공학.<br>• 프롬프트 잔소리 없이도 슬롯별 작성 규칙을 시스템 수준에서 강제. | 에이전트에게 양식과 서식을 설명하고 다그치는 비용을 최소화하고 첫 시도부터 규격 내 안착. |
| **3. Instant Fact Verification<br>(원문 1:1 결속 검증)** | • 생성된 모든 문장·정량 수치와 원본 백데이터(페이지/문단) 간 **양방향 앵커 결속(1:1 Anchor Binding)**.<br>• 본문 클릭 시 원본 근거 위치로 즉각 연결되어 확인 및 인라인 정정 지원. | 에이전트의 환각을 의심하고 원본을 뒤적거리는 검증 시간을 획기적으로 단축. |

## 3. 솔루션 중립성 원칙 (Solution Neutrality)

* **특정 UI 형태(2D Canvas 등)를 전제하지 않음**:
  * 2D 캔버스, 분할 화면(Split View), 에디터 인라인 임베디드, 워드 플러그인 중 **“사용자의 기존 업무 전환 비용을 가장 낮추고, 오류율과 검수 시간을 가장 크게 줄여주는 형태”**가 무엇인지 프로토타입 비교 실험을 통해 결정함.
* **가치 검증 기준선**:
  * “신기한 UI인가?”가 아니라, **“기존 Word/ChatGPT 조합 대비 실제 규격 문서 완성 시간과 검수 피로도를 유의미하게 줄여주는가?”**만을 유일한 성공 기준으로 삼음.
