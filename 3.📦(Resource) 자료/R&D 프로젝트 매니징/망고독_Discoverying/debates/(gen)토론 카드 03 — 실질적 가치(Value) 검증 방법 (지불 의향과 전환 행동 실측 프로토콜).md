# (gen)토론 카드 03 — 실질적 가치(Value) 검증 방법 (지불 의향과 전환 행동 실측 프로토콜)

> **SVPG 정본 헌법 (Marty Cagan Verbatim)**:  
> *"Customers don't know what's possible, and they don't know what they want until they see a solution."*  
> *(고객은 기술로 무엇이 가능한지 알지 못하며, 구체적인 솔루션(프로토타입)을 눈으로 보기 전까지는 자신이 무엇을 원하는지조차 알지 못한다.)*  
> *(출처: Marty Cagan, Discovery – Problem vs. Solution)*  
> 
> *"The primary purpose of prototyping is to help discover a successful solution... before you proceed to building the actual product."*  
> *(프로토타입의 제1 목적은 실제 제품을 만들기 전에, 성공적인 솔루션을 발견하고 리스크를 검증하는 것이다.)*  
> *(출처: Marty Cagan, The Purpose of Prototypes)*

---

## 1. 토론의 출발점: 핵심 딜레마 (The Core Question)

우리는 앞서 4대 리스크 중 최우선 과제로 **`Risk 01: Value Risk`**를 설정했다. 그러나 기획과 엔지니어링 사이에서 가장 첨예하게 부딪히는 본질적 의문이 제기되었다:

```text
[핵심 질문]
"완성적인 프로토타입이 나오기 전에 어떻게 Value(가치) 검증을 따로 구성한단 말인가?
 SVPG에서는 대체 뭐라고 하는가?
 결국 Value 검증은 코딩으로 프로토타입을 '다 만들고 나서' 해야 되는 것 아닌가?"
```

이 질문에 대해 마티 케이건(Marty Cagan)의 SVPG 정본 원칙은 **"무엇이 맞고, 무엇이 치명적인 함정인지"**를 명확하게 가르고 있다.

---

## 2. SVPG 헌법의 판정: 무엇이 맞고 무엇이 함정인가?

```
[사용자의 직관 (100% 정답)]
"프로토타입 없이 말(구두)로만 가치를 검증하는 것은 불가능하다."
➔ 고객은 만져볼 수 있는 구체적 솔루션을 보지 못하면 자신이 살지, 갈아탈지 알 수 없다.

[흔히 빠지는 치명적 함정 (안티패턴)]
"그렇다면 프로토타입을 '코딩으로 다 만들고 나서(풀스택 웹 앱)' 검증해야 한다."
➔ React, FastAPI, DB를 연결해 2~3개월간 상용 소프트웨어(Build to Earn)를 다 짜고 나서
   고객을 만나는 순간, 이미 시간과 자본이 전액 매몰되어 피봇이 불가능해진다 (망하는 지름길).
```

### SVPG가 정의하는 '프로토타입'의 실체:
* SVPG가 말하는 프로토타입은 **"코딩이 단 1줄도 들어가지 않은 2~3일짜리 가짜 인터랙티브 껍데기(User Prototype / Figma)"**이다.
* 마티 케이건의 실제 디스커버리 일지(*Product Discovery Diary*)를 보면, **화요일 오후에 기획해서 수요일 오전에 바로 1차 프로토타입을 뽑아 목요일에 고객에게 들이민다 (단 2일 소요).**
* 즉, **"완성된 소프트웨어는 전혀 없지만, 고객 눈에는 100% 완성된 것처럼 완벽하게 작동을 흉내 내는 시뮬레이션(Figma / Smoke Page)"**을 들고 가치 검증을 수행하는 것이 정본이다.

---

## 3. 가치 검증 신호의 3대 위계 (Hierarchy of Value Evidence)

마티 케이건과 알베르토 사보이아(Alberto Savoia, *The Right It*)가 공통으로 규정한 '가치 검증의 진실성 사다리':

```
▲ [Level 3] 비가역적 전환 (Irreversible Switching) : Word 창을 끄고 다음 문서도 스스로 직조
│ [Level 2] 실질적 화폐 결속 (Skin in the Game)    : 환불 불가 계약금 / 사전 결제 승인
▼ [Level 1] 구두 칭찬 및 설문 (Opinion / Compliment) : "정말 좋네요, 출시되면 꼭 살게요" ➔ [쓰레기 신호]
```

* **Level 1 (의견/칭찬) ➔ 100% 무효 판정**: 인터뷰나 설문조사에서 나온 모든 호평("유용하네요", "멋져요")은 기각한다.
* **Level 2 (화폐적 베팅) ➔ 최소 유효 신호**: 고객이 신용카드 번호를 입력하거나, 사전 예약 보증금을 실제로 지불해야 한다.
* **Level 3 (행동적 대체) ➔ 궁극적 정본 신호**: 생성된 30장을 실제로 정부/투자처에 공식 제출하고, 기존 Word+ChatGPT 복붙 창을 영구히 닫아야 한다.

---

## 4. 소프트웨어 완성 전, 2~3일 만에 실행하는 3대 Value 검증 프로토콜

코드를 한 줄도 짜지 않고, 시장의 진짜 지불 의향(Level 2)과 전환 의향(Level 3)을 뽑아내는 SVPG 정본 기법:

### 프로토콜 A: 정성적 가치 테스팅 (Qualitative Value Testing with Figma User Prototype)
* **준비물**: 백엔드 연결 없는 **Figma 초고해상도 인터랙티브 프로토타입 (제작 소요: 2일)**.
  - 좌측 `@Reference` 뷰어, 우측 `Composer` 프롬프트 입력창, 중앙 `Document` 실시간 직조 뷰가 마치 실제로 작동하는 것처럼 클릭 인터랙션 설계.
* **실행 절차**:
  1. 2주 뒤 마감 과제를 쥔 실제 창업가/연구원에게 Figma 화면을 넘겨준다.
  2. 고객의 실제 백데이터 주제에 맞추어, 프로토타입 상에서 30장 제안서가 팩트 앵커와 함께 직조되는 시뮬레이션을 직접 조작하게 한다.
* **승패 판정 (The Decisive Questions)**:
  - 조작 후 "어떠세요?"라고 묻지 않는다. 다음 2가지 질문으로 행동을 강제한다:
    1. *"이 제품이 다음 주 화요일에 오픈합니다. **지금 쓰시던 Word 창을 끄고, 다음 주 마감 과제를 진짜로 이걸로 작성하시겠습니까?**"* (WTS 검증)
    2. *"오늘 사전 예약하시는 분들께만 첫 6개월을 50% 할인(월 19,000원)해 드립니다. **지금 카드 번호를 등록하시겠습니까?**"* (WTP 검증)
  - **합격**: 고객이 눈을 빛내며 *"언제 나오나요? 당장 결제할 테니 1호로 열어주세요"*라고 카드를 꺼낼 때.
  - **사망**: *"신기하긴 한데, 글쎄요...", "나중에 정식 출시되면 볼게요"*라고 미룰 때.

### 프로토콜 B: 정량적 수요 검증 (Quantitative Fake Door / Smoke Test)
* **준비물**: 단 1페이지짜리 티저 랜딩페이지 (노션/Framer/간이 웹).
  - 헤드카피: *"백데이터 100쪽을 30초 만에 인덱싱하여 30장 완제품 제안서를 직조하는 MangoDoc"*.
  - 실제 작동 데모 영상 (Figma 화면 녹화본 30초).
  - **[월 39,000원 결제하고 바로 시작하기]** 실제 결제 버튼 배치.
* **실행 절차**:
  - 실제 스타트업 커뮤니티(디스콰이엇, 단톡방 등)에 링크를 배포.
  - 사용자가 결제 버튼을 누르면: *"현재 비공개 알파 30명 정원이 마감되었습니다. 이메일을 남겨주시면 1호 알림과 함께 1개월 무료 쿠폰을 드립니다."* 안내.
* **승패 판정**:
  - **방문자 대비 결제 버튼 클릭률(Conversion Rate) 실측**:
    - **클릭률 5% 이상**: 시장의 지불 의향 검증 완료 (Pass).
    - **클릭률 1% 미만**: 제품 콘셉트 또는 가격 정책 재수립 (Fail).

### 프로토콜 C: B2B 사전 구매 의향서 (Letter of Intent, LOI)
* **준비물**: Figma 프로토타입 데모 + 1장짜리 사전 도입 협약서(LOI).
* **실행 절차**:
  - 제안서/과제 작성이 빈번한 중소기업/스타트업 대표를 만남.
  - *"우리가 11월에 이 제품을 완성해 올 테니, 완성되면 월 5만 원(연 60만 원)에 1년간 전사 도입한다는 조건으로 오늘 사전 구매 의향서(LOI)에 서명해 주시겠습니까?"*
* **승패 판정**:
  - 도장을 찍거나 서명을 완료하면 B2B 가치 검증 통과. 말로만 "좋네요" 하면 실패.

## 5. 결론: 개발 순서와 1주일 디스커버리 로드맵

```text
[Day 1~2: Figma User Prototype]
2D 캔버스 없는 3단 레이아웃 (Reference - Document - Composer) 초고해상도 클릭 목업 제작

[Day 3~4: 병렬 스파이크 가동]
├─ Track 1 (Value)       : 타깃 빌더 3명 대면 Figma 시뮬레이션 & 선결제 카드 등록 유도
└─ Track 2 (Feasibility) : 터미널 파이썬 스크립트(scratch/)로 1:1 팩트 앵커링 정합성 계측

[Day 5: 사망 판정 (Kill Criteria Evaluation)]
고객의 실제 결제 의향(WTP)과 백엔드 물리적 실현성(Feasibility)이 입증되었는가?
├─ YES ➔ 비로소 상용 엔지니어링 본 코딩(Build to Earn) 착수
└─ NO  ➔ 상용 코드 1줄도 안 짰으므로 매몰비용 0원 상태에서 즉각 피봇
```

> **단언적 결론:**  
> **"우리는 프로토타입 없이 Value를 검증하려는 것이 아닙니다.  
> 2개월짜리 상용 소프트웨어 코딩을 하는 대신, 2일짜리 Figma 인터랙티브 프로토타입으로 고객의 지불 의향을 먼저 뽑아내려는 것입니다."**
