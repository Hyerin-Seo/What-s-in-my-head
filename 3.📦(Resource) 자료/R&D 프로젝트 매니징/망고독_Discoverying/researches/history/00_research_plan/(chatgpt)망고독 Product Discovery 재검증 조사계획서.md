# 망고독 Product Discovery 재검증 조사계획서

> **문서 상태: 계획서.** 조사 전에는 어떤 문제·솔루션·시장 수요도 검증된 것으로 표기하지 않는다.
> `researches/history/`의 이전 카드는 증거가 아니라, 출처를 다시 확인하거나 기각할 **주장 목록**이다.
> 웹·문서·서비스 표본틀은 [[(chatgpt)소스 범위·필수 서비스·수집 기준]]을 따른다. 그 기준을 채우기 전에는 데스크 리서치 종합을 작성하지 않는다.

## 1P 요약

**북극성 질문**: “우리가 생각한 제품을 어떻게 증명할 것인가?”가 아니라, **“어떤 증거가 나오면 지금 생각한 제품을 버릴 것인가?”**

이번 조사는 `2D Canvas`의 선호도를 묻지 않는다. 여러 참고자료와 기존 형식에 맞춰 규격 문서를 작성·검토·제출하는 사람이 실제로 어떤 일을 하고, 어디서 비용을 치르며, 현재 무엇으로 해결하고, 대가를 치르면서도 바꿀 이유가 있는지를 확인한다.

| 단계 | 확인할 것 | 방법 | 남겨야 할 증거 |
| --- | --- | --- | --- |
| 0 | 기존 주장이 사실인가 | Evidence Audit | 주장-출처 매트릭스 |
| 1 | 문제가 실제 존재하는가 | 인터뷰 + 실제 작업물 회고 | 녹취·비식별 문서·화면 |
| 2 | 문제가 얼마나 심각한가 | Workflow 관찰 | 시간·빈도·실패·우회 비용 |
| 3 | 현재 어떻게 해결하는가 | 대안 조사 | 실제 Tool Stack·선택 이유 |
| 4 | 어떤 해결방식이 먹히는가 | Concept Test | 대안별 행동·반대 증거 |
| 5 | 실제 사용할 수 있는가 | Prototype Test | 핵심 과업 성공·중단·도움 요청 |
| 6 | 돈을 낼 가치가 있는가 | Commitment Test | 파일럿·후속 일정·유료 약정 |
| 7 | 만들 수 있는가 | Technical Spike | 구현 비용·성능·한계·실패 사례 |

## 1. 조사 대상 Job과 범위

> **최근 또는 임박한 마감의 규격 문서를, 여러 근거 자료와 기존 형식에 맞춰 완성·검토·제출해야 할 때, 작성자는 어떤 자료를 오가며 어디서 시간을 잃고 무엇으로 문제를 우회하는가?**

- 규격 문서는 외부 또는 조직 내부의 검토·승인이 필요하고, 과거 문서·양식 또는 명시적 형식 제약이 있으며, 근거 자료가 3개 이상인 문서로 한정한다.
- 사업계획서 하나만을 대표 사례로 삼지 않는다.
- AI 일반 의견만 있는 사람, 최근 실제 사례를 보여 줄 수 없는 사람, 비밀 자료를 안전하게 비식별할 수 없는 사람은 이번 조사 대상에서 제외한다.

## 2. 운영 원칙

1. **문제와 솔루션을 분리한다.** 2D Canvas·레퍼런스 추출·좌표 연결은 모두 후보 해법이며, 인터뷰 초반에는 언급하지 않는다.
2. **의견보다 최근 행동을 우선한다.** “좋다/쓸 것 같다”보다 마지막 실제 업무의 문서·도구·수정·우회 행동을 확인한다.
3. **원자료가 없는 인용은 증거로 쓰지 않는다.** 모든 핵심 주장은 `Claim → Participant/Source → Raw Evidence → Observation → Interpretation → Confidence → Decision`으로 연결한다.
4. **반대 증거를 같은 무게로 기록한다.** 기존 Word/Notion/템플릿만으로 충분한 사례는 실패가 아니라 중요한 발견이다.
5. **표본을 시장 추정에 쓰지 않는다.** 초기 12명 내외의 목적은 반복 패턴과 반증을 찾는 것이지 비율을 일반화하는 것이 아니다.

## 3. 표본과 책임

| 코호트 | 목표 | 모집 조건 |
| --- | ---: | --- |
| 외부 심사·승인 문서 작성자 | 4명 | 제안서·지원서·입찰·규제 문서처럼 형식 오류 비용이 큰 최근 사례 |
| 조직 내 전략·리서치 문서 작성자 | 4명 | 여러 출처를 결합해 의사결정 문서를 만든 최근 사례 |
| AI 워크플로우 파워 유저 | 4명 | 자동화·AI 서비스를 이미 적극적으로 사용한 최근 사례 |

조사 착수 전에 PM·디자이너·엔지니어가 각자 어떤 리스크를 관찰하고 어떤 결과면 가설을 버릴지 합의한다. 참가자의 실명·동의·원문 자료는 접근 제한된 저장소에 두며, 이 볼트에는 참가자 ID와 비식별 근거만 남긴다.

## 3.1 소스 범위 게이트

- **서비스 지형**: 필수 서비스 18종마다 기능·도움말/API·가격/보안/내보내기 문서 3건 이상을 수집한다. 총 54건 이상의 1차 출처가 필요하다.
- **실제 사용자 행동**: 참가자 12명 내외의 원자료와 별개로, 최소 60건의 공개 행동 증거를 12개 이상 도메인에서 수집한다. 한 도메인은 10건을 넘지 않는다.
- **실제 문서 과업**: 최소 12개 과업 팩을 만든다. 각 팩에는 공개된 형식/레퍼런스 문서 1건, 근거 문서 3건 이상, 성공 조건 1건이 있어야 한다.
- **판정 제한**: 서비스 기능은 공식 문서로, 실제 마찰은 참가자·공개 사용 기록으로, 문서 형식은 공개 원문으로 확인한다. 한 종류의 출처만으로 결론 내리지 않는다.

## 4. 단계별 실행

- **Stage 0 — 증거 감사**: 이전 카드의 주장마다 원문 URL, 원문 위치, 작성자·게시일, 수집일, 해석자를 붙인다. 원문이 없거나 인용이 맞지 않으면 `미검증`이다.
- **Stage 1–3 — 문제·강도·대안 발견**: 최근 실제 문서 한 건을 시간선으로 복기한다. 언제 무엇을 열고, 복사하고, 확인하고, 수정했는지와 기존 도구·사람·템플릿에 쓴 비용을 기록한다.
- **Stage 4 — 해결안 탐색**: 발견된 하나의 Job에 대해 기존 작업 흐름, 에디터 내 기능, 분할 화면, 2D Workspace를 동등한 후보로 보여 준다.
- **Stage 5 — 프로토타입 과업**: 실제와 유사한 비식별 과업을 수행하게 하고 완료·중단·도움 요청·오류·다음 업무 선택을 관찰한다.
- **Stage 6 — 행동 기반 가치 검증**: 다음 실제 업무 제시, 파일럿 일정 확정, 자료 제공, 유료/보증금 파일럿 수락 순으로 행동 강도를 기록한다. 단순 WTP 답변은 보조 자료다.
- **Stage 7 — 기술 스파이크**: 살아남은 해결안만, 고정된 문서 세트·모델 버전·프롬프트·반복 횟수·평가 기준으로 시험한다.

## 5. 의사결정 규칙

| 결과 | 의미 | 다음 행동 |
| --- | --- | --- |
| Supported | 원자료가 연결된 실제 행동이 서로 다른 코호트에서 반복됨 | 다음 리스크 실험으로 진행 |
| Mixed | 문제·대안·고객군에 따라 결과가 갈림 | 고객군 또는 Job을 좁혀 재실험 |
| Not supported | 현재 대안이 충분하거나, 관찰된 행동이 가설과 반대 | 해당 솔루션 가설 중단 또는 피벗 |
| Insufficient evidence | 원자료·표본·관찰이 부족함 | 결론을 보류하고 증거 보강 |

독립 Workspace는 참가자가 대안과 비교한 뒤 자신의 다음 실제 업무에 선택하고, 기존 도구보다 과업을 더 잘 끝낸다는 관찰이 있을 때만 다음 단계로 간다. 반대로 에디터 내 기능이나 업무 절차가 충분하다면 그 방향으로 피벗한다.

## 6. 조사 종료 산출물

- [[(chatgpt)가설·리스크·판정기준]]의 가설별 상태와 근거 ID
- [[(chatgpt)소스 범위·필수 서비스·수집 기준]]의 충족 현황과 빠진 표본
- [[(chatgpt)Evidence Matrix]]의 주장-원자료 연결
- 원자료와 분리된 종합 메모 및 실패 사례
- [[(chatgpt)Continue-Pivot-Stop Decision]]의 사람 검토용 결정안

예쁜 종합 리포트가 아니라, 다른 사람이 원자료까지 역추적하고 결론에 반대할 수 있는 기록을 완료 조건으로 삼는다.
