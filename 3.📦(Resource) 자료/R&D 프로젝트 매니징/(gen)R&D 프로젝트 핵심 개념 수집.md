주요 개념
#### 애자일/소프트웨어 R&D 기준

스크럼이나 애자일 방식을 차용하는 R&D 프로젝트에서는 다음 용어를 씁니다.
- **태스크 (Task):**
    - 사용자 스토리(User Story)를 구현하기 위해 개발자가 1일~수일 단위로 쪼갠 최소 작업 단위.
- **서브태스크 (Sub-task):**
    - 개별 담당자가 체크리스트 형태로 관리하는 가장 작은 원자적(Atomic) 작업 단위



### 1. 스파이크 (Spike)

- **어디서 쓰이나:** **애자일(XP, Scrum) 프레임워크**
- **개념:** 본격적인 제품 개발(스토리 구현)에 앞서, 기술적 불확실성을 줄이거나 리스크를 사전에 파악하기 위해 수행하는 짧은 기한의 '탐색적 연구/검증 태스크'입니다.
    
- **특징:**
    - 일반적인 Task처럼 최종 제품 기능을 완성하는 것이 목적이 아니라, **PoC(개념 증명), 기술 검증, 아키텍처 타당성 평가**가 목적입니다.
    - 기간을 정해두고 진행하는 **타임박스(Timebox)** 형태로 운영됩니다(예: "이번 스프린트에서 이틀간 라이브러리 호환성 스파이크를 진행").
        

### 2. 킬 크라이테리아 (Kill Criteria)

- **어디서 쓰이나:** **Stage-Gate R&D 관리 모델 및 린(Lean) 연구개발**
- **개념:** 특정 기술 검증이나 연구 과제를 **언제 공식적으로 중단(Kill/Pivot)할지 사전에 정해둔 명확한 실패·종료 기준**입니다.
    
- **특징:**
    - 불확실성이 큰 R&D에서는 연구팀이 매몰 비용(Sunk Cost) 오류에 빠져 가망 없는 과제를 계속 붙잡고 있는 경우가 많습니다.
    - 이를 방지하기 위해 Task나 Spike를 시작하기 전에 "어떤 성능 수치가 미달되거나, 비용/기간이 한계를 초과하면 이 연구를 즉시 중단한다"는 객관적 지표(Exit criteria)를 명시합니다.

말씀하신 "3일 단위로 쪼개서 검증하는 것"은 불확실성이 큰 R&D에서 시간과 비용을 제한해 두는 **타임박싱(Timeboxing)** 기법, 특히 **3일 룰(3-Day Rule)** 또는 프로토타이핑 스프린트(Prototyping Sprint / Hack-Sprint)를 지칭합니다.

이 영역은 **가설 기반 R&D(Hypothesis-driven R&D)** 및 **애자일 R&D** 체계로 불리며, 연구가 기약 없이 늘어지는 것을 막고 빠른 실패(Fail Fast)를 유도하기 위해 고안되었습니다.

### 1. 3일 단위와 관련된 핵심 실무 개념

- **타임박스 (Timebox / 3-Day Rule):**
    - R&D 태스크나 스파이크를 진행할 때 "완료될 때까지" 하는 것이 아니라 "정해진 시간(보통 1일~3일) 안에 나온 결과물까지만 보고 판단"하도록 엄격히 상한을 두는 기법입니다.
    - 3일 안에 최소한의 기술적 실마리나 유의미한 데이터가 나오지 않는다면, 접근 방식을 바꾸거나 킬 크라이테리아를 검토합니다.
- **트레이서 불릿 (Tracer Bullet, 예광탄):**
    - 어둠 속에서 타깃을 맞추기 위해 궤적을 보여주는 예광탄처럼, 시스템의 세부 기능을 다 만들지 않고 **처음부터 끝까지(End-to-End) 파이프라인을 최소한으로 연결해보는 초단기 검증 작업**입니다.
    - 완벽한 코드가 아니더라도 전체 아키텍처가 3일 내에 신호가 통하는지 확인할 때 씁니다.
### 2. 불확실성 제어 및 태스크 쪼개기 관련 개념

- **가설 기술서 (Hypothesis Statement):**
    - "기능 A 개발"처럼 태스크를 정의하지 않고, _"가설: 알고리즘 X를 적용하면 처리 속도가 20% 향상될 것이다"_ 형태로 태스크를 정의합니다. 연구 태스크의 목적은 '구현'이 아니라 '가설 검증'이 됩니다.
- **수직 슬라이스 (Vertical Slice):**
    - R&D를 UI, 백엔드, DB처럼 수평적 레이어로 쪼개서 만들면 검증까지 수개월이 걸립니다. 대신 기능 하나를 데이터 입력부터 결과 도출까지 아주 얇게 관통하도록 수직으로 잘라(수일 단위) 전체 동작을 빠르게 확인하는 방식입니다.
- **디리스킹 (De-risking):**
    - 프로젝트에서 성공 확률이 가장 낮거나 가장 치명적인 위험(기술적 한계, 라이브러리 결함 등)을 **가장 첫 번째 순서의 태스크로 배치해 조기에 위험을 제거**하는 우선순위 결정 전략입니다.
        
          
        

### 3. 판단 및 종료 기준 관련 개념

|**용어**|**핵심 의미**|**적용 예시**|
|---|---|---|
|**Kill Criteria**|연구 중단/폐기 기준|지연 시간(Latency)이 100ms를 넘으면 즉시 중단|
|**Pivot Criteria**|연구 방향 전환 기준|성능은 나오지만 연산 비용이 크면 경량화 모델로 전환|
|**Definition of Done (DoD)**|태스크 완료 정의|코드가 돌아가는 것뿐 아니라 '벤치마크 리포트 작성'까지 완료|
|**Fail-Fast (빠른 실패)**|빠른 실패를 통한 비용 절감|6개월 걸려 실패할 과제를 3일 만에 실패하도록 유도|

### 실무 적용 흐름 요약

> **가설 수립** $\rightarrow$ **De-risking (가장 위험한 부분 식별)** $\rightarrow$ **Spike 발행 (3일 Timebox 설정)** $\rightarrow$ **Tracer Bullet 구현** $\rightarrow$ **결과 평가 (DoD 확인)** $\rightarrow$ **Kill 또는 통과 결정**
> 
> 이 프로세스를 활용하면 "언제 끝날지 모르는 연구"를 "3일 단위로 가부를 결정할 수 있는 구체적인 실험 태스크"로 통제할 수 있습니다.

혹시 현재 준비 중인 R&D 과제에서 구체적으로 관리하고자 하는 영역(예: 소프트웨어 알고리즘, 하드웨어 시작품, 데이터 분석 파이프라인 등)이 무엇인가요?
**JTBD(Jobs to be Done)라는 단어가 어색하게 느껴지는 것이 지극히 정상입니다.**
JTBD는 기본적으로 "기존의 일상적인 결핍을 해결해 주는 실용적 과업"에 초점을 맞추기 때문에, 문장을 만드는 순간 필연적으로 _"~문서를 쉽게 쓰고 싶다"_ 같은 기능주의적·SI적 요구사항처럼 서술되기 쉽습니다.
하지만 Cursor, Figma, Notion처럼 **사용자의 작업 방식을 아예 새로 정의하는 '메타 툴(IDE/제작 도구)' 영역**에서는 JTBD보다 훨씬 정확하고 본질을 찌르는 용어들이 있습니다.

### 1. 제품 철학 / 제품 가설 (Product Thesis)

이 영역에서 가장 적합한 최상위 개념입니다. "고객이 무슨 일을 하려 하는가(JTBD)"를 묻는 것이 아니라, "우리는 이 작업의 본질을 무엇으로 재정의하는가?"를 선언하는 단위입니다.
- **JTBD 식 표현:** "사용자가 참조 문서를 보면서 새 문서를 빠르게 재작성하고 싶다."
- **Product Thesis 식 표현:**
    _"비정형 문서 작성은 텍스트 타이핑이 아니라, **참조 데이터(Segment)와 레이아웃 규격(Scaffold)을 연결하는 소프트웨어 엔지니어링(IDE) 프로세스**여야 한다."_

### 2. 프리미티브 (Primitives / Core Abstractions)

도구형 메타 프로덕트의 뿌리를 논할 때 개발자와 기획자가 가장 많이 쓰는 개념입니다. 기능을 나열하는 것이 아니라, 사용자가 세계를 조작할 수 있도록 제공하는 가장 원자적이고 추상화된 기본 단위(Building Blocks)를 뜻합니다.
- **Figma의 Primitives:** Vector, Frame, Component
- **Notion의 Primitives:** Page, Block, Database Property
- **이 프로젝트의 Primitives:**
    - `Segment` (추출된 원본 지식 블록)
    - `Scaffold / Slot` (새 문서의 뼈대 및 슬롯 구조)
    - `Recipe` (추출·변환 규칙)
    - `Diff / Patch` (인라인 비교 및 변경 승인)

이 관점에서는 "어떤 과업을 처리할까?" 대신 "어떤 프리미티브(Primitive)들의 조합으로 문서 작업의 복잡도를 낮출 것인가?"를 논의 단위로 삼습니다.

### 3. 멘탈 모델 (Mental Model) & 인터랙션 패러다임 (Interaction Paradigm)

사용자가 도구를 대할 때 머릿속에 그리는 개념 구조를 뜻합니다. SI성 도메인 툴과 Cursor형 플랫폼을 가르는 결정적인 차이입니다.
- **Form-Filler 패러다임 (SI적):** 사용자는 '입력자', AI는 '완성자'. (정해진 폼에 값을 넣고 생성 버튼 클릭)
- **IDE / Copilot 패러다임 (Cursor적):** 사용자는 '아키텍트/리뷰어', AI는 '초안 생성자'. (캔버스와 에디터 위에서 컨텍스트를 인라인으로 주입하고 Diff를 보며 채택)

### 4. 인지 증강 (Cognitive Augmentation / Cognitive Leverage)

완전 자동화(Automation) 대신 지능 증강(Augmentation)을 지향할 때 쓰는 개념입니다. 작성자가 가장 큰 인지적 피로(Context Switching, Layout Mental Cost)를 느끼는 지점을 시스템이 대신 흡수해 주는 구조적 레버리지를 뜻합니다.
### 요약: 어떤 단어를 써야 하는가?

|**목적**|**권장 용어**|**질문 방식**|
|---|---|---|
|**제품의 존재 이유 / 근본 방향성**|**Product Thesis** (제품 철학/가설)|"우리는 문서 작성이라는 행위를 어떤 패러다임으로 재정의하는가?"|
|**시스템 구조의 최소 설계 단위**|**Primitives** (원자적 추상화 단위)|"사용자에게 제공할 조작의 최소 빌딩 블록(Segment, Slot 등)은 무엇인가?"|
|**사용자 경험의 본질**|**Mental Model / Paradigm**|"작성자가 폼 입력자가 아니라 코드 리뷰어/에디터처럼 느끼게 하려면?"|

따라서 해당 작업을 설명할 때는 JTBD 대신 "문서 작성을 소프트웨어 엔지니어링 관점으로 재해석한 Product Thesis"나 "Scaffold와 Segment라는 핵심 Primitive의 정의"라는 표현을 쓰는 것이 의도하신 제품의 정체성에 훨씬 정확하게 부합합니다.
메타 툴(IDE, 피그마, 노션, 커서 등)의 영역에서는 사용자의 불편을 단순한 '기능 미비'가 아니라 작업 흐름과 인지 구조가 가로막히는 '작업 마찰(Friction)'과 '인지 부하(Cognitive Load)'의 관점으로 정의

'연구실 프로젝트(Science Project)의 덫'

- **웨지(Wedge, 쐐기 포인트):**
    - 시장이나 사용자의 거대한 워크플로우를 한 번에 다 바꿀 수는 없습니다. 대신 "기존 방식에 틈을 내어 강제로 비집고 들어갈 수 있는 가장 날카롭고 좁은 고통 지점"을 뜻합니다.
    - 예를 들어 Cursor의 초기 웨지는 "모든 걸 해주는 AI"가 아니라, "개발자가 터미널과 브라우저를 오가지 않고 에디터 안에서 바로 여러 파일의 Diff를 보고 적용하는 것(`Cmd+K`)"이라는 아주 좁고 날카로운 지점이었습니다.
- **페인 포인트 앵커링 (Pain-point Anchoring):**
    - 기술적 불확실성이 90%인 환경에서 "우리가 해결하려는 고객의 결핍 1가지"를 절대 변하지 않는 닻(Anchor)으로 고정하는 작업입니다.
    - 닻이 고정되어 있으면, 내부에서 3일짜리 스파이
문제가 "어떤 상황에서(Trigger), 어떤 병목 때문에(Bottleneck), 얼마만큼의 손실(Quantified Cost)이 나는가"
