# 예시 후보 2 — 오류도 알림도 없이 아홉 장

> **한 줄**: 노트 아홉 장에 속성이 한 글자도 안 써졌다. 오류도 알림도 없었고 git 에도 안 보였다. 아홉 장 모두 에이전트의 스크립트가 그날 쓴 것이었다.

## 실제 재료 (버그 리포트와 고친 커밋 `160b843` 그대로, 2026-09-16)

```diff
- if (!data.startsWith("---\n")) return data;
+ const nl = eolOf(data);
+ const text = toLf(data);
+ if (!text.startsWith("---\n")) return data;
```

CRLF 파일은 `---\r\n` 으로 시작해서, 고치기 전 코드는 원본을 그대로 돌려줬다.

그때 `CLAUDE.md` 에 더한 줄 (커밋 `e974cc4`, 지금은 `docs/properties.md`):

```markdown
## 줄끝은 **LF** 입니다 — CRLF 면 속성이 조용히 안 써집니다

| 어디서 CRLF 가 들어오나 | 막는 법 |
| --- | --- |
| 파이썬 `write_text` — 윈도우에서 `\n` 을 `\r\n` 으로 바꿉니다 | `newline=""` 를 꼭 넘기세요 |

- 노트를 스크립트로 고칠 때는 **반드시** `newline=""`. 안 그러면 조용히 망가집니다.
```

에이전트가 쓰는 코드의 Before / After:

```python
# Before — 윈도우에서 줄끝이 \r\n 이 됨
path.write_text(text, encoding="utf-8")

# After — 규칙을 읽은 뒤
open(path, "w", encoding="utf-8", newline="").write(text)
```

⚠ Before 의 파이썬 줄은 그날 스크립트가 남아 있지 않아 리포트의 설명("파이썬 `write_text` 로 노트를 고친다")에서 옮긴 모양입니다. After 는 `skills/meeting-notes/SKILL.md` 9절에 적힌 모양입니다.

- 파이썬 `write_text` 는 윈도우에서 `\n` 을 `\r\n` 으로 바꾼다.
- git 은 못 봤다. `core.autocrlf` 가 커밋할 때 LF 로 바꿔서 diff 가 비어 있었다.
- 고침 세 겹: 아홉 장을 LF 로 · `.gitattributes` 에 `eol=lf` · 코드가 CRLF 를 견디게.
- 남은 규칙: `CLAUDE.md` 의 "줄끝은 LF. 파이썬으로 쓸 때는 `newline=""`."

## 글에서 이렇게 보인다

> 상태 칩을 눌러도 값이 안 바뀌었습니다. 오류는 없었습니다. git diff 도 비어 있었습니다.
> 원인은 줄끝 한 글자였고, 그 아홉 장은 전부 그날 에이전트가 파이썬으로 고친 노트였습니다.
> 그래서 입구에 한 줄이 생겼습니다 — "줄끝은 LF."

## 뼈대의 어느 칸에

- **지킨 기준** 의 첫 줄 "틀려도 오류가 안 나고 조용히 깨지는 것만 입구에 둔다" 의 근거로 딱 맞습니다.
- **Before / After** 로도 됩니다 — 규칙이 없을 때 에이전트가 쓴 파일 ↔ 규칙을 읽고 쓴 파일.

## 왜 괜찮은가

- "에이전트가 망가뜨린 것이 규칙이 됐다" 는 하네스의 정의 그 자체입니다.
- 코드 한 줄, 원인 한 글자. 개발자 독자가 바로 알아봅니다.

## 약점 · 확인할 것

- 윈도우 · 파이썬 사정이라 맥 사용자에게는 남의 일입니다.
