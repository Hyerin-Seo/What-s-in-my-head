# 하네스 엔지니어링(harness engineering)으로 사람과 에이전트가 같이 쓰는 옵시디언 볼트 만들기 — 1편

## 개요 (← 개요)

사람 둘과 에이전트 여럿(Claude · Codex · Gemini)이 옵시디언 볼트 하나를 같이 씁니다. 에이전트가 바뀔 때마다 볼트의 약속을 처음부터 다시 설명해야 했습니다.

"할 일 노트 하나 만들어 줘" 한마디에도 매번 이런 말을 덧붙였습니다.

> 속성은 열세 개를 전부 넣고
> 위키링크는 따옴표로 감싸고
> `제목` 속성은 만들지 않습니다

〔그림 1 — 쉬어 가는 삽화〕

그래서 물었습니다. '에이전트가 볼트의 약속을 처음부터 알고 시작하게 할 수 없을까?'

이것을 하네스 엔지니어링이라고 부릅니다. 이 글은 옵시디언 볼트에 규칙과 스킬로 하네스를 짜고, 1,404줄이던 설명서를 입구 147줄로 줄인 과정을 다룹니다. 여섯 편 가운데 첫 편입니다.

## 볼트 지도 — 규칙과 스킬 (← Rules / Skills)

볼트 맨 위에 에이전트가 읽는 것이 이렇게 놓여 있습니다.

〔트리 — `CLAUDE.md` · `docs/` · `skills/` 세 줄〕

〔표 — 규칙(`CLAUDE.md` · `docs/`): 볼트의 약속을 알려 줌 / 스킬(`skills/`): 순서가 있는 일을 맡김〕

## 규칙 (← Rules)

규칙은 에이전트에게 볼트의 약속을 알려 줍니다. 개요에서 매번 덧붙이던 세 줄을 규칙으로 적으면 이렇게 됩니다.

〔코드 — `docs/properties.md` 의 YAML 규칙 한 토막 (속성 13종 · 따옴표 친 위키링크 · 줄끝 LF)〕

> Tip: 규칙을 전부 읽히지 않습니다. 입구(`CLAUDE.md`)의 표가 "하려는 일 → 읽을 문서" 를 짝지어 주고, 에이전트는 맞는 문서만 엽니다.

〔표 — 입구 표에서 세 줄만: 노트를 찾는다 / 새 노트를 만든다 / 속성을 고친다〕

이렇게 적어 두면 어느 에이전트가 와도 따로 설명하지 않고 볼트에 맞는 노트를 처음부터 만듭니다.

### Before / After 예시 (← Before / After 예시)

차이는 에이전트에게 부탁하는 말에서 가장 잘 보입니다. 같은 부탁 "`할머니한테 9시에 전화하기` 할 일 만들어 줘" 로 견줍니다.

**Before** — 부탁 앞에 설명 세 줄이 먼저 필요했고, 그래도 이런 노트가 나왔습니다.

〔코드 — 규칙 없이 만든 프론트매터〕
⚠ 실제로 규칙 없이 돌려서 받아야 합니다. 문서에 남은 실패 모양은 `제목` 속성 만들기, 따옴표 없는 `[[Claude]]`, `작성자` 를 한 줄로 쓰기입니다.

설명 → 생성 → 지적 → 수정이 되풀이됐습니다.

**After** — 부탁은 한 줄이고, 노트는 한 번에 맞게 나옵니다.

〔코드 — 속성 열세 개가 맞게 들어간 프론트매터〕

〔그림 2 — 쉬어 가는 삽화〕

### 규칙을 적을 때 지킨 기준 (← Rules를 작성할 때 고려했던 기준)

- **틀려도 오류가 안 나고 조용히 깨지는 것만 입구에 둡니다** — 나머지는 주제별 문서로 보냅니다. (↔ 이미 아는 내용은 넣지 않는다)
- **규칙은 한 곳에만 적습니다** — 입구에는 한 줄 요약과 문서 이름만, 순서는 스킬에만. (↔ Rules 와 Skills 는 중복하지 않는다)
- **폴더가 아니라 속성으로 찾게 적습니다** — 유형 → 구역 → 주제 순으로 좁히면 에이전트가 폴더를 뒤지지 않습니다. (↔ 구조와 패턴을 드러낸다)

### 도입 후 달라진 것 (← 도입 후 느낀 변화)

- **같은 설명을 다시 하지 않습니다** — 부탁 한 줄이면 됩니다.
- **어느 에이전트가 해도 같은 모양의 노트가 나옵니다** — `CLAUDE.md` 를 안 읽는 에이전트는 `AGENTS.md` 로 들어옵니다.
- **첫 시도에 맞는 노트가 나오는 일이 늘었습니다** ⚠ 체감입니다. 잰 숫자는 없습니다.

### 언제 규칙으로 적으면 좋은가 (← 언제 Rules를 쓰면 좋은가)

- **모든 노트에 걸리는 약속이 있을 때** — 속성 · 구역 · 분류처럼 한 장도 빠지면 안 되는 것.
- **여러 사람과 에이전트가 번갈아 쓸 때** — 시키는 방식이 달라도 결과가 같아야 할 때.

## 스킬 (← Skills)

규칙이 약속이라면 스킬은 순서입니다. 일 하나를 처음부터 끝까지 어떤 차례로 하는지를 폴더 하나에 적어 둡니다.

〔표 — 스킬 넷: 스킬 · 하는 일 · 부르는 말 (`meeting-notes` "이 회의록 정리해 줘" / `pre_meeting_agenda_preparer` / `meeting_decision_recorder` / `editor_mockup_todo_manager`)〕

회의 스킬은 속기를 읽고 끝나지 않고 이런 순서로 한 바퀴를 돕니다.

〔그림 — Pre(지난 회의 점검) → Live(속기) → Post(안건 카드 · 결정 카드) → Action(사람이 골라 프로젝트로) → Learn(스킬 고치기)〕

에이전트가 다 해 주는 것은 아닙니다. 에이전트가 70~80% 를 깔고, 고르고 다듬는 것은 사람입니다. AI 가 쓴 것은 작업 공간에만 두고 사람이 고른 것만 볼트로 올립니다.

### 언제 스킬로 만들면 좋은가 (← 언제 Skills를 쓰면 좋은가)

- **순서가 늘 같은 일일 때** — 회의 정리처럼 단계가 매번 같은 차례로 이어지는 것.
- **노트 여러 장을 한 번에 만들어야 할 때** — 기획 노트 하나를 할 일 여러 장으로 쪼개는 것.

## 입구와 속성으로 에이전트가 읽는 양 줄이기 (← 전처리 스크립트를 활용한 컨텍스트 최적화 패턴)

규칙과 스킬이 늘자 설명서가 1,404줄이 됐습니다. 에이전트는 속성 한 줄을 고치려 해도 그걸 다 읽었고, 노트를 찾을 때는 폴더를 하나씩 열었습니다.

해법은 둘입니다. 설명서를 **입구 한 장과 주제별 문서**로 쪼개고, 노트는 **프론트매터 속성으로** 찾게 했습니다.

〔그림 3 — 쉬어 가는 삽화〕

### 예시: "진행 중인 할 일을 찾아 줘" 를 받았을 때 (← 예시: API 훅 생성 Skill에 …)

**AS-IS: 통째로 읽고 폴더를 뒤진다**

〔흐름 — 부탁 → 설명서 1,404줄 전부 → 프로젝트 폴더를 하나씩 열어 봄 → 답〕

**TO-BE: 입구에서 고르고 속성으로 찾는다**

〔흐름 — 부탁 → 입구 147줄 → "노트를 찾는다" 는 입구로 충분 → 속성으로 한 번에 → 답〕

**실제로 읽는 것 비교**

〔AS-IS — 통짜 설명서의 목차 (찾는 일과 상관없는 플러그인 · 회의록 · 보드 규칙까지)〕
〔TO-BE — 입구의 `자료를 찾을 때` 한 절〕

**어떻게 만들었나**

모든 노트가 같은 속성 열세 개를 가지니, 찾는 일은 명령 한 줄이 됩니다.

〔코드 — `grep -rl '^유형: 할일' --include='*.md'` 와 주제 · 요약으로 찾는 줄〕

**[참고] 일마다 읽게 되는 줄 수**

| 일 | 예전 (통짜) | 지금 (입구 + 맞는 문서) | 줄어든 비율 |
| --- | --: | --: | --: |
| 노트를 찾는다 | 1,404줄 | 147줄 | 89.5% |
| 속성을 고친다 | 1,404줄 | 385줄 (입구 + `properties.md`) | 72.6% |
| 새 노트를 만든다 | 1,404줄 | 650줄 (입구 + `new-notes.md` + `properties.md`) | 53.7% |

> 참고: 줄 수이지 토큰이 아닙니다. 에이전트가 **읽게 되어 있는** 양이고 실제로 읽은 양을 잰 것은 아닙니다. 문서는 쪼갠 뒤에도 늘어서 지금 전부 합치면 예전보다 깁니다 (2026-10-01 에 셈).

⚠ 폴더를 뒤질 때와 속성으로 찾을 때의 차이(연 파일 수 · 호출 수)는 아직 안 쟀습니다.

## 마무리 (← 마무리)

프롬프트를 잘 쓰는 것보다, 에이전트가 일할 자리와 읽을 것을 미리 놓아 두는 것이 더 중요했습니다.

한 사람의 요령에 기대지 말고, 누가 시켜도 같은 결과가 나오는 자리를 볼트에 만들어 보시기를 권합니다.

다음 편에서는 1,404줄 설명서를 어떻게 쪼갰는지, 무엇을 입구에 남겼는지를 다룹니다.
