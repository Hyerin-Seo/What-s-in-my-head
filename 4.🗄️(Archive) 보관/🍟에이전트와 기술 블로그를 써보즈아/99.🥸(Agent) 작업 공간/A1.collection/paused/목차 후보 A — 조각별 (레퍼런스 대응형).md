# 후보 A — 조각별 (레퍼런스 대응형)

> **한 줄**: 볼트를 이루는 조각 하나가 한 편. 레퍼런스가 Rules → Skills → 전처리 스크립트로 간 순서를 시리즈로 늘린 것.

## 편 목록

| 편 | 가제 | 불편했던 장면 → 전/후 | 볼트 근거 |
| --- | --- | --- | --- |
| 1 | 총론 — 사람 둘과 에이전트 여럿이 한 볼트를 쓰기까지 | 에이전트가 바뀔 때마다 규칙을 다시 설명 → 입구 하나 읽고 시작 | 상위 카드의 11칸 표 |
| 2 | 규칙 — 1,404줄 설명서를 입구 한 장과 문서 열 장으로 | 통짜 `CLAUDE.md` → 입구 표 + `docs/` | `CLAUDE.md` · `docs/` · `AGENTS.md` |
| 3 | 속성 — 폴더를 뒤지지 않고 이름표로 찾기 | 상태 폴더와 속성이 어긋남 → 속성 하나가 정본 | `docs/properties.md` · `docs/para.md` |
| 4 | 스킬 — 회의 속기가 할 일 카드가 되기까지 | 속기만 남음 → 안건 카드 · 결정 카드 | `skills/meeting-notes` · `docs/meetings-and-skills.md` |
| 5 | 플러그인 — 조용히 깨지는 것을 코드로 막기 | 사람이 손으로 맞춤 → 만들면 속성이 붙음 | `plugins/claude` · `docs/new-notes.md` · `docs/inbox.md` |
| 6 | 협업 — 둘이 같이 쓰는 볼트의 동기화와 코멘트 | 손으로 커밋 · 병합 → 버튼 하나 | `plugins/vault-sync` · `docs/comments.md` |

## 한 편 안의 소제목 (2편을 예로)

```
개요        규칙이 길어져 에이전트가 필요 없는 것까지 다 읽었다 → 일에 맞는 것만 읽게 할 수 없을까
지도        CLAUDE.md(입구) · docs/(주제별) · AGENTS.md(다른 에이전트의 입구)
입구        무엇을 입구에 남겼나 — 실제 입구 표 한 토막
Before/After  통짜 1,404줄 → 입구 147줄 + 문서 열 장
정한 기준    틀려도 오류가 안 나고 조용히 깨지는 것만 입구에 · 규칙은 한 곳에만
달라진 점
언제 쓰면 좋은가
마무리      다음 편 — 속성
```

## 잘 맞는 경우

- 읽는 사람이 **에이전트를 쓰는 개발자**일 때. 레퍼런스와 1:1 로 견줘 읽을 수 있습니다.
- 상위 카드의 11칸 표를 1편으로 그대로 쓸 수 있습니다.

## 약점

- 설명서처럼 읽히기 쉽습니다. 왜 그렇게 됐는지(사건)가 본문 뒤로 밀립니다.
- 조각이 여섯이면 끝납니다. 계속 이어 쓰는 시리즈로는 다음 편을 붙일 자리가 없습니다.
