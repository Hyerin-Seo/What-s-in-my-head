# 구성안 — 같은 회의 예시로 Rules와 Skills 설명하기

**후속 요청으로 전문 작성 승인.** 사용자가 레퍼런스의 시각 디자인과 삽화 세 장까지 반영해 전문을 작성하라고 요청했다. 결과는 [[(최종본) 회의록을 에이전트의 기억으로 만들기 — Rules와 Skills]]에 있다. 아래 구성은 그 원고를 작성할 기준으로 보존한다.

## 가제와 독자

**회의록을 에이전트의 기억으로 만들기 — 작업 공간의 규칙과 회의 정리 스킬**

독자: 회의록을 에이전트에게 정리시키면서, 후보와 확정 기록을 구분하고 이후 대화에서도 기록을 활용하려는 사람.

가져갈 것: 작업 공간을 운영하는 규칙과 회의 정리 스킬의 차이, 각 도구가 해결하는 문제, 적용할 상황.

## 끝까지 가져갈 예시

**2026.10.01 회의 하나를 따라간다.**

“이 회의록 정리해줘.” → 175발화를 카드 후보로 정리 → 사람이 선택·보완 → 남겨 둔 기록을 다음 기획 대화에 읽혀 팀의 논의 방향을 맞춘다.

9월 29일 회의 수치나 다른 버그 사례를 중간에 끼워 주인공을 바꾸지 않는다. 회의별 수치는 본문 작성 시 원자료와 채택 기록으로 다시 확인한다.

## 두 도구가 해결하는 문제

| 도구 | 해결할 문제 | 보여 줄 것 |
| --- | --- | --- |
| Rules — 작업 공간의 규칙 | AI가 쓴 후보와 사람이 확정한 기록이 섞인다 | 어디에 쓰는지, 누가 고르는지, 무엇을 보드에서 제외하는지 |
| Skills — 회의 정리 절차 | 작업할 자리는 있어도 긴 속기에서 무엇을 어떻게 뽑을지 매번 설명해야 한다 | 속기를 분류하고 안건·결정 카드로 만드는 순서와 양식 |

폴더 자체를 Rules라고 부르지 않는다. 규칙 문서, 규칙에 따라 만든 작업 공간, 제외 설정의 관계를 보여 준다. 규칙은 작성·선택·반영의 범위를 정하고, 스킬은 그 안에서 수행할 절차를 정한다.

## 목차와 채울 내용 — 레퍼런스 11칸 대응

H2는 단원, H3는 그 안의 예시·기준·활용 상황으로 나눈다. 레퍼런스의 구간 순서와 각 구간이 하는 일을 유지하되 제목 계층은 구조 분석의 지침을 따른다.

| 순서 | 목차 | 채울 내용과 예시 |
| --- | --- | --- |
| 1 | 개요 — 회의록 정리를 맡겼는데, 결과를 다시 정리해야 했다 | AI의 후보가 회의록 보드에 섞이는 불편 → “마음껏 후보를 만들게 하면서 우리가 고른 것만 반영하려면?” → 작업 공간의 규칙과 스킬 → 같은 회의를 끝까지 따라간다는 범위. 확인한 회의 수치 한 줄을 개요로 당긴다 |
| 2 | Rules / Skills — 지켜야 할 약속과 실행할 순서 | CLAUDE.md·docs/·skills/·99 작업 공간의 관계를 짧은 트리와 역할 표로 설명. 볼트 전체 소개로 늘리지 않는다 |
| 3 | Rules — 후보를 쓰는 곳과 확정하는 곳을 나눈다 | 정의 → 실제 규칙 발췌(작업 공간에 작성, A1에 후보, A5는 사람이 선택, 프로젝트 반영은 사람이 수행) → 폴더 다섯 개 → 제외 설정의 역할과 효과 |
| 4 | Before / After — 같은 카드가 보드에 섞이지 않게 됐다 | Before: 카드의 분류·상태 때문에 초안도 보드에 표시. After: 작업 공간을 제외하고 사람이 반영한 기록만 표시. 카드 속성 예와 실제 설정을 제시하고 앞뒤에 무엇을 보는지·무엇이 달라졌는지 한 줄씩 설명 |
| 5 | 규칙을 정한 기준 — 작성·선택·반영의 책임을 구분한다 | ① 원문 보존 ② 선택은 사람이 ③ 안 고른 자료도 보존. 각각 같은 회의에서 무엇을 보호하는지 설명 |
| 6 | 도입 후 변화 — 후보를 검토하는 일이 실제 업무와 분리됐다 | 보드에서 초안을 걸러 읽는 부담, 반영 전에 수정할 수 있는 여유, 다른 에이전트가 이어받을 작업 기록. 확인된 변화만 쓰고 시간 절감 수치를 만들지 않는다 |
| 7 | 언제 Rules를 쓰면 좋은가 | 여러 에이전트가 같은 자료를 다룰 때, AI 제안과 팀 결정을 구분해야 할 때. 블로그 후보·기획 제안에 같은 원칙을 적용하는 짧은 예 |
| 8 | Skills — 같은 회의를 안건과 결정으로 정리한다 | 정의 → 스킬·역할·요청 표 → 175발화에서 안건 3장·결정 1장, 사람이 결정 1장 채택한 흐름. ‘와꾸’ 안건 카드와 결정 카드 일부, 원문 발화·시각·결정 질문을 채우는 절차. 사람이 검토·보완할 부분과 전사·인용의 한계 |
| 9 | 언제 Skills를 쓰면 좋은가 | 같은 순서로 반복 처리하는 일, 여러 결과물을 같은 양식으로 만드는 일. Rules로 작업 위치와 책임을 정해도 카드 내용은 따로 생성해야 한다는 점 연결 |
| 10 | 응용 — 정리한 회의를 다음 기획 대화에 읽혔다 | 한계: AI가 팀의 논의 방향을 모르고 기능 사양으로 흐름 → 회의 폴더를 가리킴 → 실제 캡처와 답 → 앞에서 만든 ‘와꾸’ 카드 재등장. 안 고른 카드의 쓸모, 원문·시각·링크의 역할, 스킬의 실제 카드 양식. 원문과 카드 발췌를 비교하고 화자 오류도 대조. 측정 표는 확인한 파일 크기를 쓸 경우에만 넣고 읽은 양·토큰 절감으로 해석하지 않는다 |
| 11 | 마무리 — 규칙으로 반영 범위를 정하고, 스킬로 기록을 쌓는다 | 두 도구가 같은 문제를 나눠 해결한 방식 회수 → 독자가 시작할 최소 구성 → 다음 회의 점검과 스킬 사본 튜닝으로 확장 → 참고 링크·저자 소개 |

## 분량과 문체

- Rules·Skills 설명 약 60%, 응용 약 25%, 개요·지도·마무리 약 15%.
- ‘와꾸’ 이야기만 길어져 구축 과정 설명을 잡아먹지 않게 한다.
- 우리 팀의 실제 경험을 합니다체로 쓴다. 문단 하나에 한 가지, 짧은 코드 앞뒤에는 설명 한 줄씩.
- 번역투, 추상적인 결론, 같은 효과의 반복, “혁신적인·획기적인·다양한·살펴보겠습니다”를 피한다.
- 만든 예시는 설명용이라고 표시한다. 실제 기록과 같은 질문의 전후 실험인 것처럼 섞지 않는다.

## 본문 작성 전에 확인할 것

- 10월 1일의 카드 수·채택 수와 카드 원문을 확인한다.
- 초안의 9월 23일 제외 설정은 당시 변경이고, 현재는 폴더 깊이와 무관하게 제외하는 정규식이다. 어느 시점의 설정인지 밝힌다.
- 실제 요청은 ‘와꾸의 뜻’ 질문이 아니라 ‘행위에 집중’하라는 요청이었다. 캡처의 요청과 결과를 그대로 연결한다.
- 에이전트의 정확한 탐색 경로와 읽은 양은 모른다. 링크 구조와 실제 탐색을 구분한다.
- 레퍼런스의 측정 표 모양을 맞추려고 성능·시간 절감 수치를 만들어 넣지 않는다.
