# 회의록 세컨드 브레인(second brain)으로 에이전트에게 '와꾸' 가르치기

| 레퍼런스 | 우리 |
| --- | --- |
| 끝까지 가는 예시: "user 조회 React Query 훅 만들어 줘" | 끝까지 가는 예시: "와꾸가 안 잡혔다가 무슨 뜻이야?" |
| 맞고 틀림이 보이는 곳: `fetch` 를 직접 썼나, `UserAPI` 를 썼나 | 맞고 틀림이 보이는 곳: "기준 문서가 없는 상태" 라고 답했나, "80%는 나왔는데 20%를 모르는 상태" 라고 답했나 |
| 도구 1 Rules · 도구 2 Skills · 심화 전처리 스크립트 | 도구 1 카드 · 도구 2 스킬 · 심화 전사 대신 카드 |

---

## 개요

`레퍼런스: 불편한 장면 → 매번 덧붙이던 말 (인용) → 삽화 → 질문 한 줄 → 개념 이름 → 이 글의 범위`

어느 팀에나 그 팀에서만 통하는 말이 있습니다. 우리 팀은 "와꾸" 입니다. 에이전트는 이 말을 모르고, 설명해 줘도 자기 식으로 알아듣고 엉뚱한 사양을 내놓았습니다.

원하는 답을 얻으려고 매번 이런 설명을 덧붙였습니다. 〔만듦 — 셋째 줄만 실제로 한 말〕

> 와꾸는 문서의 뼈대를 말하는 거고
> 양식이 있다고 와꾸가 잡힌 게 아니고
> 기능 말고 '행위'에 집중을 하라는 거야

〔삽화 1〕

그래서 이런 생각이 들었습니다. '에이전트가 우리 팀의 말을 처음부터 알아듣게 만들 수는 없을까?'

사람의 머리 밖에 두는 두 번째 기억을 세컨드 브레인이라고 부릅니다. 이 글은 옵시디언 볼트에서 회의를 카드와 스킬로 쌓아 에이전트가 읽는 기억으로 만들고, 읽는 양까지 줄여 본 사례입니다.

## 카드 / 스킬

`레퍼런스: 디렉터리 트리 → 역할 표 (두 줄)`

```
<프로젝트>/discussions/<회의 날짜>/     ← 카드
skills/meeting-notes/                  ← 스킬
```

| 구성 | 역할 |
| --- | --- |
| 카드 | 팀이 합의한 것 전달 |
| 스킬 | 회의를 카드로 만드는 작업 자동화 |

## 카드

`레퍼런스: 정의 → 설정 코드 → Tip 콜아웃 → 효과`

카드는 회의에서 오간 말을 안건 하나 단위로 잘라 적은 노트입니다. 개요의 "와꾸" 는 카드에 이렇게 적혀 있습니다. 〔실물〕

```markdown
# 1.1 와꾸가 안 잡힌 사람 — 첫 타겟을 어디에 그을까

> **속기 원문** (속기 46–53 · 121–125 · 148–154)
> - 발화자 2 (23:50) *… 기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?*
> - 발화자 1 (32:02) *내가 방금 기준 문서 안에서도 와꾸가 안 나오는 항목들은 왕왕 등장해.*
> - 발화자 1 (32:50) *그러니까 와꾸가 안 잡혔다라는 것은 내가 80%는 나왔는데 20%는 몰라. 그럼 왔고 안 잡힌 거야.*
```

> Tip: 주목할 것은 **시각**입니다. 카드는 뜻을 풀어 적지 않습니다. 그 말이 오간 자리를 시각과 함께 그대로 옮깁니다. 에이전트는 정의가 아니라 그 자리를 읽습니다.

이렇게 적어 두면 에이전트는 따로 설명을 듣지 않고도 팀이 그 말을 어떤 뜻으로 쓰는지 가져옵니다.

## Before / After 예시

`레퍼런스: Before (먼저 필요했던 설명 → 요청 → 틀린 결과 → 되풀이) → After (요청 한 줄 → 맞는 결과) → 삽화`

차이는 같은 질문 하나를 던져 보면 가장 잘 보입니다.

### Before (카드를 읽히기 전)

개요의 설명 세 줄을 먼저 붙이고 물어도, 에이전트는 보통 이렇게 답합니다. 〔만듦〕

```
질문: 우리 팀에서 "와꾸가 안 잡혔다" 는 게 무슨 뜻이야?

답:   양식이나 기준 문서가 없어서 문서의 틀이 잡히지 않은 백지 상태를 말합니다.
```

틀렸습니다. 기준 문서가 **있어도** 와꾸는 안 잡힐 수 있습니다.

이 오답은 그럴듯합니다. 회의에서 사람도 똑같이 알아들었습니다. 〔실물〕

```
발화자 2 (23:50)  기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?
```

결국 "아니 그게 아니라…" → 다시 설명 → 또 비슷한 답이 되풀이됩니다.

### After (카드를 읽힌 뒤)

질문은 한 줄이면 됩니다.

```
질문: discussions 폴더를 보고 답해 줘. "와꾸가 안 잡혔다" 는 게 무슨 뜻이야?

답:   80%는 양식(기준 문서)이 있어도, 20%의 모르는 칸이 나오면 와꾸가 안 잡힌 것이다. (속기 32:50)
```

〔실물 — 답의 문장은 캡처에서 가져옴. 다만 그때의 요청은 이 질문이 아니라 "'행위'에 집중해 줘" 였음. ⚠ 이 질문 그대로 돌려 본 적은 없음〕

### 나란히 놓기

| 확인할 것 | Before | After |
| --- | --- | --- |
| 뜻이 맞나 (기준 문서가 있어도 해당된다) | ✗ | ✓ |
| 팀이 실제로 한 말을 인용했나 | 0개 | 1개 |
| 인용에 시각이 붙어 있나 | 없음 | 32:50 |
| 확인하러 갈 곳이 있나 | 없음 | 회의록의 그 시각 |

〔삽화 2〕

## 카드를 만들 때 고려했던 기준

`레퍼런스: 기준 세 개 (소제목이 결론 문장)`

#### 뜻을 풀어 쓰지 않고 발화 원문과 시각을 붙인다

"와꾸 = 문서의 뼈대" 라고 정의해 뒀다면 Before 의 오답이 그대로 나왔을 것입니다. 팀의 뜻은 정의가 아니라 32:50 의 말에 있습니다.

#### 정한 것과 아직 안 정한 것은 따로 둔다

- 결정 카드 = 이미 정한 것 ("우리 도구는 시뮬레이터다")
- 안건 카드 = 아직 안 정한 것 ("와꾸가 안 잡힌 사람 — 첫 타겟을 어디에 그을까")

#### 회의마다 폴더 하나, 카드끼리는 링크로 잇는다

결정 카드에서 안건 카드로 링크가 이어져 있어, 폴더 하나만 가리켜도 "와꾸" 가 나온 자리까지 갑니다.

## 도입 후 느낀 변화

`레퍼런스: 변화 세 개`

#### "아니야 아니야" 를 덜 친다

설명을 고쳐 쓰는 대신 폴더를 가리킵니다.

#### 사람끼리 맞춘 뜻을 에이전트도 그대로 쓴다

"와꾸" 는 회의에서 사람 둘이 23:50 부터 32:50 까지 9분 동안 세 번 되물어 맞춘 말입니다. 에이전트는 그 되물음이 끝난 자리를 가져왔습니다.

#### 틀렸을 때 어디가 틀렸는지 짚을 수 있다

답에 시각이 붙어 있어서 원문을 열어 볼 수 있습니다. 실제로 열어 보니 화자 하나가 틀려 있었습니다.

## 언제 카드를 쓰면 좋은가

`레퍼런스: 경우 두 개`

#### 팀에만 통하는 말이 있는 경우

"와꾸" · "진심 펀치" 처럼 사전에 없고 정의하기도 어려운 말로 일하는 팀.

#### 회의에 없던 사람이나 에이전트가 일을 이어받는 경우

합의한 자리에 없었어도 같은 뜻에서 출발해야 할 때.

## 스킬

`레퍼런스: 정의 → 스킬 표 (스킬 · 하는 일 · 예시 요청) → 파이프라인 → 한계 인정`

카드가 기록이라면 스킬은 그 기록을 만드는 순서입니다.

| 스킬 | 하는 일 | 예시 요청 |
| --- | --- | --- |
| 회의 정리 | 속기를 읽고 안건 카드 · 결정 카드를 뽑아 작업 공간에 둠 | "이 회의록 정리해줘" |
| 안건 카드 | 아직 안 정한 것을 결정 질문 · 쟁점으로 구조화 | (회의 정리가 부름) |
| 결정 카드 | 이미 정한 것을 결정 · 기한 · 이유로 기록 | (회의 정리가 부름) |
| 지난 회의 점검 | 지난번에 하기로 한 것이 됐는지 점검표를 깖 | "지난 회의 점검해줘" |
| 다시 뽑기 | 사람이 안 고른 카드의 이유로 스킬 사본을 고쳐 다시 뽑음 | "다시 뽑아줘" |

```
녹음 · 전사
    ↓
안건 카드 · 결정 카드 뽑기
    ↓
사람이 고름
    ↓
프로젝트의 회의 날짜 폴더로
    ↓
다음 회의에서 점검
```

에이전트가 다 해 주는 것은 아닙니다. "와꾸" 가 나온 그 회의는 175발화에서 카드 넉 장이 나왔고 사람이 고른 것은 한 장입니다. "와꾸" 카드는 **안 고른 석 장** 중 하나였습니다. 지우지 않고 남겨 둔 덕에 읽혔습니다.

## 언제 스킬을 쓰면 좋은가

`레퍼런스: 경우 두 개`

#### 순서가 늘 같은 일인 경우

회의는 매번 같은 차례로 정리됩니다.

#### 노트 여러 장을 한 번에 만들어야 하는 경우

회의 하나에서 카드 여러 장이 나옵니다.

## 카드를 활용한 컨텍스트 최적화 패턴

`레퍼런스: 한계 제기 → 해법 → 삽화 → 예시 (AS-IS 흐름 · TO-BE 흐름 · 실제 전달 데이터 비교) → 어떻게 구현했나 → [참고] 측정 표 → 수치의 단서`

"전사를 통째로 읽히면 되지 않나" 에 부딪힙니다. 전사는 길고, 무엇보다 **"와꾸" 를 "와꾸" 라고 적지 않습니다.**

그래서 전사 전체가 아니라, 안건에 닿는 발화만 뽑아 한 가지 표기로 묶은 카드를 읽힙니다.

〔삽화 3〕

### 예시: 전사에서 "와꾸" 를 찾을 때

#### AS-IS: 전사를 통째로

```
"와꾸" 가 뭐야?
  → 35분 53초짜리 전사 175발화를 처음부터 읽음
  → "와꾸" 로 찾으면 절반도 안 나옴
  → 답
```

#### TO-BE: 카드로

```
"와꾸" 가 뭐야?
  → 회의 날짜 폴더의 결정 카드
  → 링크된 안건 카드 "1.1 와꾸가 안 잡힌 사람"
  → 답
```

#### 실제 전달 데이터 비교

AS-IS: 전사가 받아 적은 "와꾸" 〔실물 — 10.01 회의 속기에서 셈〕

| 전사에 적힌 글자 | 횟수 | 예 |
| --- | --: | --- |
| 와꾸 | 10 | "와꾸가 안 잡혔다라는 것은" |
| 왔고 | 8 | "왔고가 잡혔다는 거 아니야?" |
| 와코 | 2 | "와코가 잡힌 거지" |
| 와꼬 | 2 | "와꼬를 아 없는" |
| 악구 | 1 | "나는 악구가 잡힌 거라고" |

스물세 번 가운데 "와꾸" 로 적힌 것은 열 번입니다. 한 발화 안에서도 "와꾸가 안 잡혔다라는 것은 … 그럼 **왔고** 안 잡힌 거야" 로 갈립니다.

TO-BE: 카드 〔실물〕 — 카드 한 장에 "와꾸" 가 열세 번 나옵니다 (원문 인용 속의 것 포함). 제목과 결정 질문 · 분석은 "와꾸" 한 가지로 쓰고, 전사의 글자는 원문 인용 칸에만 그대로 남깁니다.

**카드는 어떻게 만드나요?**

안건 카드 스킬에 적힌 틀과 첫 단계입니다. 〔실물〕

```markdown
> **속기 원문**
> - *<회의 속기에서 발췌한 날것의 발언 원문 그대로 인용>*
```

```markdown
1. **회의 속기 원문 파싱 및 안건 분리**:
   * … 속기(`## 속기`) 내용을 한 줄씩 전수 검토하여, 논의가 필요한 핵심 안건 단위로 분리합니다.
```

**[참고] 실제 회의 두 번의 크기**

| 회의 | 전사 전체 | 프로젝트 폴더에 남은 것 | 줄어든 비율 |
| --- | --: | --: | --: |
| 09.29 (376발화) | 70,383 bytes | 16,394 bytes | 76.7% |
| 10.01 (175발화) | 35,913 bytes | 1,729 bytes | 95.2% |

"와꾸" 카드 한 장은 5,798 bytes, 전사의 16% 입니다.

> 참고: 파일 크기이지 토큰이 아닙니다 (2026-10-01 에 잼). "왔고" 여덟 번은 문맥으로 보아 "와꾸" 로 센 것입니다. 그리고 카드를 전부 합치면 줄지 않습니다 — 09.29 회의는 카드 전체가 67,390 bytes 로 전사와 거의 같습니다. 줄어드는 것은 한 번에 읽는 양입니다.

## 마무리

`레퍼런스: 관점 전환 한 문장 → 권유 → 다음에 넓힐 방향 → 참고 리소스 → 저자 소개`

예전에는 에이전트에게 우리 말을 잘 풀어 설명하는 것이 중요했다면, 지금은 그 말이 오간 자리를 가리킬 수 있게 쌓아 두는 것이 더 중요하다고 느꼈습니다.

팀의 말을 사전으로 만들려 하지 말고, 그 말이 맞춰진 회의를 남겨 보시기를 권합니다.

여기서 한 걸음 더 가면, 다음 회의 전에 지난 합의가 지켜졌는지 에이전트가 먼저 점검하고, 사람이 안 고른 카드로 스킬이 스스로 고쳐지는 데까지 넓힐 수 있습니다.
