## ⚖️ 오늘 결정할 3대 쟁점 및 외부 레퍼런스 체크포인트

---

### 쟁점 1. 완료된 할 일을 보드에서 언제 숨길 것인가?

```
[A안: 완전 즉시 숨김]  ─────────▶  체크하는 순간 보드에서 사라짐 (초깔끔 / 필요시 '완료 보드'에서 조회)
[B안: 3일 유예 후 숨김 (권장)] ──▶  3일간은 취소선으로 노출(성취감/확인용), 3일 지나면 자동 필터 아웃
```

#### 🌐 외부 레퍼런스 및 생산성 표준 (External Reference)
* **GTD (Getting Things Done - 데이비드 알렌):** 
  * *"완료된 행동은 인지 시야에서 즉각 격리되어야 한다."* 시야에 완료된 항목이 계속 머무르면 뇌는 '아직 끝내지 못한 일'과 동일한 인지 에너지(Cognitive Load)를 소비함.
* **현대 협업 툴(Linear, Asana, Jira)의 표준 처리:**
  * **Linear:** Done 상태가 된 티켓은 기본적으로 1~3일 후 'Auto-Archive'되어 활성 뷰에서 숨김 처리됨.
  * **Asana:** 완료 체크 시 시각적 인터랙션(체크표시)을 제공한 뒤, 기본 필터는 '미완료 작업만 보기'로 강제함.

#### ✅ 회의 전 스스로 확인해볼 체크포인트 (Checkpoints)
- [ ] 지난 2주간 내가 '완료된 할 일'을 다시 확인하기 위해 칸반을 뒤진 적이 실제로 있었는가?
- [ ] 완료된 카드가 눈앞에 남아있을 때의 **성취감**과 화면을 가리는 **피로도** 중 어느 쪽이 더 큰가?
- [ ] B안(3일 유예 후 숨김) 적용 시, 주간 리뷰(Weekly Review)나 업무 보고에 지장이 없는가?

### 쟁점 2. 끝난 프로젝트 폴더는 어떻게 격리할 것인가?

| 선택지 | 동작 방식 | 장점 | 주의점 |
| :--- | :--- | :--- | :--- |
| **A안 (권장)** | 폴더째로 `4.🗄️(Archive) 보관`으로 드래그 이동 | `1.project` 최상단이 항상 클린하게 유지됨 | 링크 깨짐 방지를 위해 폴더명 유지 필수 |
| **B안** | 위치는 그대로 두고 상태값만 `완료`로 변경 | 이동 작업이 없음 | 폴더 목록에는 계속 남아 시각적 노이즈 잔존 |

#### 🌐 외부 레퍼런스 및 생산성 표준 (External Reference)
* **PARA 원작 방법론 (Tiago Forte - Building a Second Brain):**
  * *"프로젝트는 마감이 지났거나 중단되는 즉시 Archive 구역으로 이동시켜야 한다."*
  * 활성 프로젝트(Projects) 폴더에는 사람이 동시에 집중할 수 있는 한계치인 **최대 10~15개 이내**만 머물러야 생산성이 유지된다고 규정함.
* **Shape Up (Basecamp의 프로젝트 관리론):**
  * 베이스캠프의 6주 사이클(Cycle)이 끝나면 해당 프로젝트는 '완료(Archived)' 상태로 동결되며, 새로운 사이클의 작업 공간과 엄격히 분리됨.

#### ✅ 회의 전 스스로 확인해볼 체크포인트 (Checkpoints)
- [ ] 현재 `1.🎯(Project)` 안에 있는 프로젝트 중 최근 2주간 손대지 않은 '사실상 멈춘 프로젝트'가 몇 개인가?
- [ ] 프로젝트를 `4.archive`로 옮겼을 때, 다른 노트에서 걸려 있는 위키링크(`[[...]]`) 검색에 문제가 생기지 않는다는 것을 알고 있는가?
- [ ] '잠시 멈춘 프로젝트(Paused)'와 '완전히 종결된 프로젝트(Closed)'를 나누는 기준(예: 1개월 이상 진척 없음)에 동의하는가?

### 쟁점 3. 에이전트 작업 공간(`99번`) 임시 히스토리 정리 주기

* **[선택 A] 30일 수명 주기 (TTL - 권장):** 생성 후 30일 지난 `history` 파일은 주기적으로 정리/폐기
* **[선택 B] 태스크 종결 시 즉시 수동 정리:** 사람이 결과물 승격 시 수동으로 정리

#### 🌐 외부 레퍼런스 및 생산성 표준 (External Reference)
* **데이터 엔지니어링 / 클라우드 수명 주기 정책 (Retention & TTL):**
  * AWS S3 및 임시 데이터 파이프라인에서는 스테이징/스크래치 데이터에 대해 **30일/90일 TTL(Time-To-Live)**을 적용하여 콜드 스토리지로 내리거나 자동 정리하는 것이 표준.
* **Git 브랜치 라이프사이클 (Branch Pruning):**
  * 피처(Feature) 브랜치가 메인(Main)에 머지되면 작업 브랜치는 삭제(Prune)하여 저장소의 인덱스 비대화를 방지하는 원칙과 동일.

#### ✅ 회의 전 스스로 확인해볼 체크포인트 (Checkpoints)
- [ ] 에이전트가 만든 중간 작업 메모(Working Memory)가 1개월 뒤에도 다시 열어볼 만한 가치가 있는가?
- [ ] 작업 공간이 정리되지 않고 파일 수백 개가 쌓일 경우, 에이전트의 검색/인덱싱 속도 저하를 감수할 수 있는가?
- [ ] 30일 후 정리할 때, '사람이 최종 컨펌하는 1분 확인 절차'가 필요한가?

## 💡 컨센서스 포인트 (Consensus Points: 사전 지식 및 배경 설명)

> *회의 중 불필요한 논쟁을 줄이고, 참석자 간 논의의 눈높이를 맞추기 위한 핵심 가이드입니다.*

### 1. "보드에서 숨긴다" vs "파일을 삭제한다"는 완전히 다릅니다
* 옵시디언의 보드(`.base`)는 엑셀 파일이 아니라 **"조건에 맞는 파일만 모아서 보여주는 렌더링 렌즈"**입니다.
* 보드에서 필터를 걸어 완료된 할 일을 숨긴다고 해서 파일이 지워지는 것이 아닙니다. 언제든 '완료 모아보기' 뷰를 켜면 그대로 다 살아 있습니다.

### 2. `4.🗄️(Archive)`는 휴지통이 아니라 '영구 도서관'입니다
* PARA 철학에서 Archive는 버리는 곳이 아닙니다. **"지금 당장 마감이 있는 일이 아니어서 책상 위에서 치워두는 서고"**입니다.
* `4.archive`로 옮겨진 프로젝트나 문서도 검색(`Ctrl+O`), 그랩(`grep`), 위키링크 연결이 완벽하게 지원됩니다.

### 3. 에이전트 샌드박스(`99번`)를 볼트 본문과 격리하는 기술적 이유
* 에이전트가 복잡한 일(멀티스텝 작업 기억, 아이데이션 스크래치)을 할 때 생기는 중간 메모리들이 `1.project`나 `0.inbox`에 직접 생기면, 볼트 자동화 플러그인이 이를 '진짜 할 일'이나 '진짜 문서'로 오인하여 보드에 마구 띄웁니다.
* 따라서 `99.🥸 작업 공간`에 `PARA정리: 끔`을 걸고 격리하는 것은 볼트의 질서를 지키기 위한 필수적인 완충 지대(방화벽)입니다.

### 4. 볼트의 절대 원칙: "삭제는 사람이 한다"
* 에이전트나 자동화 스크립트는 볼트 내 파일을 영구 삭제할 권한이 없습니다.
* 모든 정리는 '보관 구역(`4.archive`)으로 이동'하거나 '보드 필터 숨김'으로 처리되며, 최종적으로 파일 자체를 지우는 것은 사람(민규 서/Rin)이 직접 휴지통으로 보낼 때만 일어납니다.
