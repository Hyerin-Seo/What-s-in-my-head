## 9.1 자기평가 편향

사람도 자기 글을 스스로 검토하면 오타를 놓친다. AI도 자기 결과를 평가할 때 지나치게 긍정적일 수 있다. Anthropic의 2026년 harness design 글은 generator와 evaluator를 분리하는 3-agent architecture를 소개한다. Planner가 작업을 나누고, Generator가 만들고, Evaluator가 비판적으로 검사한다.

이 구조는 처음 배우는 사람에게도 직관적이다. 글을 쓰는 사람과 편집자가 다르면 품질이 올라간다. 개발자와 QA가 분리되면 버그를 더 잘 찾는다.

## 9.2 Generator agent

Generator는 만드는 역할이다. 코드, 문서, 디자인, 보고서, 이메일 초안 등 결과물을 만든다. Generator에게는 창의성과 실행력이 필요하다. 하지만 Generator에게 검증까지 모두 맡기면 놓치는 것이 많다.

좋은 Generator 지시:

```md
너는 Builder다.
이번 sprint contract 범위만 구현하라.
완료 후 변경 사항, 실행한 검증, 불확실한 점을 기록하라.
```

## 9.3 Evaluator agent

Evaluator는 검사하는 역할이다. 목표는 친절한 칭찬이 아니라 결함 발견이다. Anthropic의 harness design 글은 evaluator가 Playwright MCP로 실제 앱을 클릭하고 UI, API, DB 상태를 테스트했다고 설명한다.

좋은 Evaluator 지시:

```md
너는 Evaluator다.
Generator의 결과를 비판적으로 검토하라.
통과 기준을 충족하지 못하면 구체적 근거와 재현 절차를 작성하라.
수정하지 말고 평가만 하라.
```

## 9.4 Planner agent

Planner는 큰 목표를 작게 나눈다. 좋은 Planner는 “앱 전체 만들기”를 “로그인 화면”, “회원가입 검증”, “대시보드 카드”, “오류 상태” 같은 작은 sprint로 나눈다.

Planner가 중요한 이유는 AI가 한 번에 너무 많은 일을 하려는 경향이 있기 때문이다. 작은 목표는 성공 확률을 높이고 평가도 쉽게 만든다.

다만 Planner가 너무 세부 구현까지 미리 정하면 오히려 위험하다. Anthropic의 harness design 글은 Planner가 높은 수준의 범위와 성공 기준을 잡되, 세부 구현을 지나치게 단정하면 잘못된 가정이 Generator와 Evaluator에게 그대로 전달될 수 있다고 설명한다. 여행 계획으로 비유하면, “첫날은 숙소 체크인과 근처 식사까지 정한다”는 좋은 계획이지만, 아직 영업시간도 확인하지 않은 식당 이름과 이동 시간을 분 단위로 확정해 버리면 나중에 전체 일정이 흔들린다.

좋은 Planner는 **범위를 작게 자르고, 완료 기준을 분명히 하되, 구현 세부사항은 검증 가능한 형태로 남긴다**. 즉, 설계도를 그리되 현장의 실제 측정과 피드백을 받을 여지를 남겨야 한다.

## 9.5 Sprint contract

Sprint contract는 이번 반복의 약속이다. 무엇을 만들고, 무엇은 만들지 않으며, 어떤 기준을 통과해야 하는지 적는다.

```md
# Sprint Contract

## 이번 범위
사용자 검색 입력 UI와 빈 결과 상태 구현

## 제외 범위
고급 필터, 엑셀 다운로드, 권한 관리

## 완료 기준
- 검색어 입력 시 API 호출
- 결과 없음 메시지 표시
- 로딩 상태 표시
- 관련 테스트 통과
```

실전에서는 sprint contract도 한 번 쓰고 끝나는 문서가 아니다. Generator가 “이 범위라면 이렇게 만들 수 있다”고 초안을 제안하고, Evaluator가 “이 기준으로는 검증이 부족하다”거나 “이 항목은 이번 sprint 밖으로 빼야 한다”고 되묻는 과정이 필요하다. 두 역할이 범위와 완료 기준에 합의한 뒤 구현을 시작해야, 나중에 “나는 했다고 생각했는데 검토자는 아니라고 보는” 충돌이 줄어든다.

일상 비유로는 생일파티 준비 회의가 좋다. 기획 담당자가 “풍선 장식, 케이크, 초대장까지 오늘 하겠습니다”라고 말하면, 검토 담당자는 “오늘은 장소 예약과 초대 인원 확정까지만 하자. 케이크는 알레르기 확인 후 내일 정하자”라고 조정할 수 있다. 이 과정이 sprint contract 협상이다.

## 9.6 주관적 품질을 채점 가능하게 만들기

“디자인이 예쁜가?”는 주관적이다. 하지만 루브릭으로 바꾸면 평가할 수 있다.

|기준|질문|
|---|---|
|명확성|사용자가 무엇을 해야 하는지 바로 알 수 있는가|
|일관성|버튼, 색, 간격, 문구가 일관되는가|
|접근성|글자 크기와 대비가 충분한가|
|오류 처리|실패 상태가 친절하게 안내되는가|
|완성도|placeholder 느낌이 아니라 실제 제품 같은가|

## 9.7 디자인 품질 루브릭

디자인 평가용 루브릭 예시:

```md
0점: 기능만 있고 사용하기 어렵다.
1점: 기본 기능은 있으나 시각적 일관성이 부족하다.
2점: 사용 흐름이 명확하고 오류 상태가 있다.
3점: 실제 제품 수준의 완성도와 접근성을 갖춘다.
```

## 9.8 Playwright MCP와 브라우저 테스트

브라우저 테스트는 실제 사용자가 클릭하는 흐름을 검증한다. 로그인 버튼이 보이는지, 검색 결과가 나타나는지, 에러 메시지가 표시되는지 살핀다. 하네스 관점에서는 “AI가 만든 결과물을 AI가 실제 사용자처럼 써 보게 하는 일”이다.

Evaluator도 그냥 두면 항상 좋은 평가자가 되는 것은 아니다. 너무 관대하게 넘어가거나, 화면을 깊게 클릭하지 않고 표면만 보고 통과시킬 수 있다. 그래서 evaluator의 평가 로그를 읽고, “어떤 시나리오를 실제로 실행했는가?”, “어떤 실패를 재현했는가?”, “통과 기준을 어떻게 확인했는가?”를 계속 점검해야 한다.

좋은 평가자는 칭찬을 잘하는 사람이 아니라, **재현 가능한 결함을 찾아내는 사람**이다. 파티 검토 담당자가 “괜찮아 보여”라고만 말하면 도움이 적다. “아이 한 명이 견과류 알레르기가 있는데 케이크 재료 확인이 빠졌고, 초대장에는 시작 시간만 있고 종료 시간이 없다”처럼 구체적으로 말해야 다음 수정이 가능하다.

## 9.9 반복 개선 루프

Generator-Evaluator 구조의 핵심은 반복이다.

1. Planner가 작은 목표를 정한다.
2. Generator가 만든다.
3. Evaluator가 검사한다.
4. 실패하면 구체적 피드백을 준다.
5. Generator가 수정한다.
6. 통과하면 다음 sprint로 간다.

이 루프는 Self-Refine과 Reflexion 연구 흐름과도 연결된다. Self-Refine은 모델이 피드백과 개선을 반복해 품질을 올리는 접근이고, Reflexion은 언어적 피드백을 기억으로 남겨 다음 시도를 개선하는 접근이다.

Anthropic의 “Building effective agents” 글에서는 이와 가까운 구조를 **evaluator-optimizer workflow**로 설명한다. 한 LLM 호출이 결과를 만들고, 다른 LLM 호출이 평가와 피드백을 제공하며, 이 과정을 반복하는 방식이다. 책에서 말하는 Generator-Evaluator 하네스는 이 패턴을 업무 설계 언어로 풀어 쓴 것이다.

이때 evaluator는 단순히 “좋습니다”라고 말하는 역할이 아니다. 목표 기준과 실제 결과 사이의 차이를 찾아내고, 다음 수정에서 무엇을 바꿔야 하는지 구체적으로 알려 주어야 한다. 그래서 평가 기준, 실패 예시, 통과 조건이 없는 evaluator는 이름만 평가자일 뿐 하네스의 품질을 올리지 못한다.
