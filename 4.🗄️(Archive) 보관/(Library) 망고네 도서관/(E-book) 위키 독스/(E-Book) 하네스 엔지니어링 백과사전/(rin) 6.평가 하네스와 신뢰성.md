## 5.1 Eval이란 무엇인가

Eval은 AI 시스템의 품질을 측정하는 테스트다. OpenAI의 evals 문서는 모델 출력이 지정한 기준을 만족하는지 테스트하고, task description, test input 실행, 결과 분석과 반복 개선 과정을 제시한다. Anthropic의 evals 글은 evaluation harness가 지시와 도구를 제공하고, 작업을 실행하고, 단계를 기록하고, 결과를 채점하고, 집계하는 인프라라고 설명한다.

처음 배우는 사람에게 eval은 “AI용 시험지”다. 하지만 단순 객관식 시험지가 아니다. 때로는 실제 환경에서 예약이 생성됐는지, 파일이 수정됐는지, 고객에게 맞는 답변이 나갔는지 확인해야 한다.

## 5.3 Trial, grader, assertion

Trial은 같은 테스트를 한 번 실행한 결과다. LLM은 비결정적이기 때문에 같은 테스트를 여러 번 실행해야 할 수 있다. Grader는 점수를 매기는 함수나 모델이다. Assertion은 반드시 만족해야 하는 조건이다.

예시:

```text
Assertion 1: 이메일을 실제로 전송하지 않았는가?
Assertion 2: 환불 정책 문서를 인용했는가?
Assertion 3: 고객 개인정보를 노출하지 않았는가?
```
### 1. Trial (시험 치르기 / 시도)

- **의미:** AI에게 동일한 테스트를 **한 번 실행해 본 결과**를 뜻해요.
    
- **왜 중요할까요?:** 계산기는 1+1을 물어보면 언제나 2라고 답하지만, AI는 똑같은 질문을 해도 할 때마다 조금씩 다른 대답을 내놓는 특징(비결정적)이 있어요. 그래서 "우연히 한 번 정답을 맞힌 건지", 아니면 "진짜 실력이 좋아서 안정적으로 정답을 내는지" 확인하려면 같은 문제를 여러 번 풀게(다중 Trial) 시켜봐야 합니다.
    

### 2. Grader (채점관 / 채점기)

- **의미:** AI가 제출한 답안지를 보고 **점수를 매기는 주체**입니다.
    
- **특징:** 시험지를 채점하는 '선생님'이라고 생각하시면 됩니다. 이 채점관은 사람이 짠 기계적인 코드(함수)일 수도 있고, 우리가 앞서 이야기했던 '루브릭(채점 기준표)을 쥐고 있는 또 다른 AI 모델'이 될 수도 있어요.
    

### 3. Assertion (절대 조건 / 필수 확인 사항)

- **의미:** 테스트를 통과하기 위해 AI가 "반드시 만족시켜야만 하는 조건"이에요.
    
- **비유하자면:** 시험을 칠 때 "OMR 카드에 컴퓨터용 사인펜을 썼는가?", "이름을 제대로 적었는가?"처럼 타협할 수 없는 절대적인 규칙입니다.
    
- **문서 속 예시:** AI 에이전트가 일을 잘했는지 평가할 때, "테스트 중에 고객에게 진짜로 이메일을 발송해버리지 않았는가?", "고객의 개인정보를 노출하지 않았는가?"처럼 0과 1로 명확하게 떨어지는 아주 중요한 안전장치들이 바로 Assertion이 됩니다.
    

요약하자면, Trial(시험을 여러 번 쳐보고) → Grader(채점관이 점수를 매기는데) → Assertion(절대 규칙을 어기지 않았는지 깐깐하게 본다)는 흐름으로 이해하시면 완벽합니다!

## 5.5 루브릭 기반 평가

루브릭은 채점 기준표다. 예를 들어 고객 답변을 평가할 때 다음처럼 점수를 줄 수 있다.

|기준|0점|1점|2점|
|---|---|---|---|
|정확성|틀림|일부 맞음|정확함|
|친절함|무례함|보통|공감과 안내가 있음|
|근거|없음|애매함|문서 근거 있음|
|안전성|개인정보 노출|약간 위험|안전함|

루브릭은 개발자가 아닌 사람에게도 매우 강력하다. “좋은 답변”이라는 감을 구체적인 기준으로 바꾸기 때문이다.

## 5.6 LLM-as-judge의 장단점

LLM-as-judge는 AI가 다른 AI의 출력을 평가하게 하는 방식이다. 장점은 의미 판단이 가능하다는 점이고, 단점은 평가자도 실수할 수 있다는 점이다. Anthropic의 generator-evaluator 하네스 글은 자기평가만으로는 부족하고, 별도 evaluator를 회의적으로 튜닝하는 것이 더 낫다고 설명한다.

좋은 원칙은 “중요한 평가는 하나의 판단자에게 맡기지 않는다”이다. 결정적 테스트, 사람 검토, LLM judge를 조합해야 한다.

제품급 하네스에서는 검증 루프를 세 가지로 나누어 생각하면 이해하기 쉽다.

|검증 방식|예시|잘 잡는 문제|한계|
|---|---|---|---|
|규칙 기반 검증|테스트, 린터, 스키마 검사|형식 오류, 깨진 기능, 명확한 실패|의미 품질은 놓칠 수 있음|
|시각적·환경 검증|스크린샷, 브라우저 확인, DB 상태 확인|실제 화면과 실제 상태의 불일치|검증 도구 준비가 필요함|
|추론 기반 검증|LLM 평가자, 리뷰 에이전트|어조, 논리, 누락, 사용자 의도|지연시간과 비용이 늘고 평가자도 틀릴 수 있음|

Martin Fowler 사이트의 하네스 엔지니어링 글에서 설명하는 guides와 sensors로 바꾸어 읽으면 더 쉽다. 가이드는 작업 전에 좋은 행동을 유도하는 장치이고, 센서는 작업 후 실제 결과를 관찰하는 장치다. 평가 하네스는 이 두 가지를 함께 가져야 한다. 좋은 지시만 있고 센서가 없으면 결과를 믿기 어렵고, 센서만 있고 가이드가 없으면 매번 늦게 고치게 된다.

### 1. 세 가지 검증 루프 = AI를 감시하는 3단계 센서(Sensors)

문서에서 말하는 검증 루프는 AI가 사고를 치지 않게 작업 결과를 관찰하고 평가하는 장치, 즉 **센서(Sensors)** 역할을 합니다. 제품급 하네스는 이 센서를 3단계 필터로 구성합니다.

- **1단계: 규칙 기반 검증 (계산기/맞춤법 검사기)**
    
    - **무엇인가요?:** 0과 1로 명확하게 떨어지는 가장 기초적인 팩트 체크입니다.
        
    - **특징:** "AI가 지정된 JSON 양식을 정확히 지켰는가?", "출력물에 금칙어가 없는가?"처럼 기계적인 오류나 양식 파괴를 족집게처럼 빠르게 잡아냅니다. 단, 글의 '뉘앙스'나 '품질'은 평가할 수 없습니다.
        
- **2단계: 시각적·환경 검증 (현장 출동 요원)**
    
    - **무엇인가요?:** AI가 "다 했어요!"라고 말만 한 건지, **진짜로 현실(환경)을 바꿨는지 팩트 체크**를 하는 단계입니다.
        
    - **특징:** 예약 에이전트가 "캘린더에 일정 등록했습니다"라고 텍스트를 출력했을 때, 그 말을 곧이곧대로 믿지 않고 실제 데이터베이스(DB)나 캘린더 시스템에 일정이 진짜로 생성되었는지 교차 검증합니다.
        
- **3단계: 추론 기반 검증 (선생님의 서술형 채점)**
    
    - **무엇인가요?:** 기계적인 코드나 상태 확인으로는 잡을 수 없는 **의미와 맥락**을 다른 AI(LLM-as-judge)가 평가하는 단계입니다.
        
    - **특징:** "고객 응대 어조가 친절한가?", "사용자의 숨은 의도를 파악했는가?"를 평가합니다. 이전 질문에서 우려하셨던 것처럼 기준이 흔들릴 수 있으므로, 반드시 1·2단계를 거친 후 보조적으로만 사용해야 합니다.

### 2. 가이드(Guides)와 센서(Sensors)의 완벽한 앙상블

이 세 가지 검증 루프(센서)가 제대로 작동하려면 짝꿍인 가이드(Guides)가 반드시 필요합니다.

- **가이드 (Guides - 사전 예방):** AI가 작업을 시작하기 전에 "이렇게 해라", "이건 절대 하지 마라"라고 올바른 방향을 쥐어주는 내비게이션(표지판)입니다. (예: 시스템 프롬프트, 엄격한 도구 사용 설명서)
    
- **센서 (Sensors - 사후 검증):** 방금 살펴본 3단계 검증 루프로, AI가 가이드대로 잘 도착했는지 결과물을 검사하는 CCTV(관찰 장치)입니다.
    

**💡 왜 이 두 가지를 엮어서 설계해야 할까요?**

1. **가이드만 있고 센서가 없다면?:** AI에게 "친절하게 대답하고 DB에 저장해"라고 지시만 하고 결과 확인을 안 하는 셈입니다. AI가 특유의 환각 증세를 일으켜 아무것도 안 해놓고 "잘 저장했습니다!"라고 거짓말을 해도 눈치챌 수 없습니다. 결과를 절대 신뢰할 수 없게 됩니다.
    
2. **센서만 있고 가이드가 없다면?:** 명확한 룰도 안 알려주고 냅다 시험만 치게 한 뒤 틀리면 계속 혼내는 셈입니다. AI는 매번 엉뚱한 짓을 하고, 센서가 그걸 쳐내고 다시 시키느라 시스템이 지나치게 느려지고 비용만 낭비됩니다.
    

**결론적으로, 신뢰할 수 있는 에이전트 환경(하네스)이란:** 가이드(명확한 지시와 규칙)를 통해 AI가 처음부터 올바른 길을 가도록 확률을 높여주고, 그럼에도 발생할 수 있는 사고는 3단계 센서(기계적 룰 검사 → 실제 환경 상태 확인 → AI 추론 검사)로 촘촘하게 걸러내는 구조를 뜻합니다!

AI 평가 하네스도 같다.

|구분|하네스에서의 역할|일상 비유|예시|
|---|---|---|---|
|Feedforward|좋은 결과가 나오도록 미리 방향을 잡는다|요리 전 레시피와 재료 준비|`AGENTS.md`, `CLAUDE.md`, Skill, 출력 형식, 금지 규칙|
|Feedback|나온 결과를 관찰하고 다시 고치게 한다|맛보고 간 맞추기|테스트, 린터, 스크린샷 확인, LLM 리뷰, 사람 검토|

둘 중 하나만으로는 부족하다. Feedforward만 있으면 “규칙은 많지만 실제로 지켜졌는지 모르는 상태”가 된다. Feedback만 있으면 “매번 틀린 뒤에야 고치는 상태”가 된다. 좋은 하네스는 처음부터 덜 틀리게 만들고, 틀렸을 때는 스스로 고칠 수 있게 만든다.

평가를 설계할 때는 또 하나의 구분이 필요하다. 검사가 **계산형**인지 **추론형**인지 보는 일이다.

|검사 유형|쉬운 설명|장점|조심할 점|
|---|---|---|---|
|계산형 검사|정해진 규칙으로 빠르게 확인하는 검사|빠르고 반복 가능하며 결과가 안정적이다|의미와 의도는 놓칠 수 있다|
|추론형 검사|의미와 맥락을 읽고 판단하는 검사|어조, 논리, 누락, 사용자 의도 같은 것을 볼 수 있다|느리고 비싸며 판단이 흔들릴 수 있다|

계산형 검사는 맞춤법 검사기나 체온계에 가깝다. 빠르고 분명하다. 테스트, 린터, 타입 검사, JSON 스키마 검사가 여기에 속한다. 추론형 검사는 선생님의 서술형 채점에 가깝다. 문장의 설득력, 요구사항 누락, 과한 해결책 같은 것을 볼 수 있지만 항상 같은 답을 주지는 않는다.

기본 원칙은 분명하다. **계산형으로 잡을 수 있는 것은 계산형으로 먼저 잡고, 의미 판단이 필요한 부분에만 추론형 검사를 붙인다.** 모든 평가를 LLM-as-judge에 맡기면 비용과 지연시간이 늘고, 오히려 평가 자체가 흔들릴 수 있다.

## 5.9 회귀 평가와 실패 사례 축적

한 번 고친 버그가 다시 나타나는 것을 회귀라고 한다. AI 하네스도 회귀 평가가 필요하다. 사용자가 발견한 실패 사례는 버리지 말고 eval dataset에 추가해야 한다.

```text
실패 발생 → 원인 기록 → 테스트 케이스 추가 → 하네스 수정 → 재평가
```

이 루프가 있어야 AI 시스템이 시간이 지날수록 좋아진다.

### 하네스 힐클라이밍 - eval은 하네스의 훈련 데이터다

모델 학습에서는 좋은 데이터가 모델을 바꾼다. 하네스 엔지니어링에서는 좋은 eval이 하네스를 바꾼다. LangChain의 Better Harness 글은 eval을 하네스 엔지니어링의 “훈련 데이터”처럼 설명한다. 각 eval case는 “이 상황에서 에이전트가 올바른 행동을 했는가?”라는 신호를 제공하고, 그 신호가 다음 하네스 수정으로 이어진다.

운영 trace 수집
→ 실패 사례를 eval case로 변환
→ 실패 유형 태그 달기: 도구 선택 / 컨텍스트 누락 / 권한 문제 / 검증 부족
→ 하네스 수정: 프롬프트, 도구 설명, 권한, 검증 루프, 컨텍스트 구조
→ 재평가
→ holdout case로 과적합 확인
