# 2.2 분류 규칙의 유연성 및 Skill/Docs 관리 체계화

> **속기 원문**
> - *유동성을 정하자. 매뉴얼 쓸까. skill에 분류기준을 만들어 넣자. 애매하면 skill에 물어보고 skill 탓하기. 그럼 skill 고치면 되니까*
> - *docs / skill 이런 놈들을 잘 관리해보는걸로!*

---

## 📌 기존엔 왜 이렇게 관리했을까? (현행 사양의 이유)

* **1. `CLAUDE.md`와 `docs/`의 중앙 집중화**
  * 볼트의 규칙이 파편화되는 것을 막기 위해 최상위 입구 파일과 하위 `docs/` 가이드로 엄격히 체계화하여 일관된 룰을 강제함.
* **2. 지어내기(Hallucination) 방지 원칙**
  * 분류 규칙이 모호하거나 비어 있을 때 에이전트가 제멋대로 추측해서 속성을 채우지 못하도록 "모르면 사람에게 물어보라"는 안전장치를 유지함.

---

## 📌 핵심 분석

* **규칙의 경직성과 사람 간 감정적 소모:** 
  * "왜 이렇게 분류했냐"를 두고 사람끼리 따지게 되면 피로도가 급증함. 분류 책임을 사람이 아닌 **"규칙(Skill)"**에 귀속시키고 룰을 고치는 편이 훨씬 건강함.
* **Skill(실행 엔진)과 Docs(가이드 문서) 간의 정합성 문제:** 
  * 사람이 읽는 `docs/`와 실제 에이전트가 동작하는 `skills/`의 지침이 어긋나면 실행 시 오류가 발생하므로, 단일 관리 체계가 필요함.

---

## 🌐 참조 자료 및 모범 사례 (다른 곳은 어떻게 하는가?)

* **1. 소프트웨어 린터(Linter) & CI/CD 철학: "사람을 비난하지 말고 린터 룰을 고쳐라"**
  * 개발 문화에서는 코딩 스타일로 사람끼리 다투지 않고, 합의된 린터 규칙을 업데이트하여 기계가 검증하게 만듦.
* **2. 프롬프트 엔지니어링의 Few-Shot 예시 기반 룰 정의:**
  * 장황한 줄글 매뉴얼보다 "A 같은 글은 1.project로, B 같은 글은 3.resource로 보낸다"는 3~5개의 실제 예시를 `SKILL.md`에 넣어두는 것이 분류 정확도를 비약적으로 높임.
* **3. 에러 기반 규칙 진화 (Error-driven Refinement):**
  * 잘못 분류된 사례가 나올 때마다 이를 새로운 테스트 케이스로 삼아 스킬 규칙에 예외 조항으로 누적 반영함.

---

## ⚖️ 핵심 쟁점 (회의에서 답을 내려야 할 질문)

* **1. 분류 규칙의 정본(Single Source of Truth) 위치**
  * **[docs/ 우선]:** 사람이 읽고 관리하는 `docs/`를 정본으로 두고, 에이전트가 이를 읽게 할 것인가?
  * **[skills/ 우선 (권장)]:** 에이전트가 직접 실행하는 `skills/*/SKILL.md`를 정본으로 삼고, 수정 시 스킬 파일을 바로 고칠 것인가?

* **2. 애매한 경계선 문서의 기본 처리 정책**
  * 프로젝트인지 리소스인지 도무지 모호한 문서는 어떻게 처리할 것인가?
  * (선택지: '보류' 상태로 인박스에 남겨두기 vs 일단 `3.resource`로 기본 분류하기)
