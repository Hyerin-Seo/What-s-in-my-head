# 📋 [인수인계] 발언 유형별 전용 템플릿 산출 및 라우팅 가이드

> **핵심 원칙: "모든 발언을 하나의 템플릿에 억지로 구겨 넣지 마라."**  
> 회의 속기 분석 시 가장 흔히 저지르는 실수는 모든 항목을 똑같은 '의사결정 안건 카드(📌기존엔 왜 이렇게 관리했을까? / ⚖️핵심 쟁점)' 틀로 찍어내는 것입니다.  
> 발언의 본질적 유형을 먼저 식별하고, **그 유형에 정확히 최적화된 전용 템플릿으로 산출물을 렌더링**해야 회의와 실무가 겉돌지 않습니다.

---

## 1. 인수인계 배경: 5.1 안건의 시행착오와 교훈 (Case Study)

### 🚨 발생했던 시행착오
* **속기 원문:** *"노션에서 하고자 했던것 / 미로에서 하고자 했던것 이 리스트를 가져오세요. mem gpt 하 샤갈!"*
* **오류 1 (기계적 안건화):** "노션/미로에서 하고자 했던 것"이라는 발언을 보고, 있지도 않은 의사결정 쟁점(A vs B?)을 만들어 표준 안건 카드에 억지로 끼워 맞춤 ➔ *"이걸 왜 회의에서 토론하고 있지?"*라는 위화감 발생.
* **오류 2 (단순 파일 마이그레이션 오판):** "노션/미로에 있는 과거 노트를 볼트로 복사해 오라는 뜻인가?"로 곡해하여 단순 Todo 티켓으로 격하시킴.
* **진짜 의도 (기획 벤치마크 리스트):** 우리 서비스(문서 빌더 + 캔버스 시각화 + Agent 런타임)에 탑재하기 위해 과거에 치열하게 이야기했던 **3대 외부 벤치마크(노션의 블록, 미로의 캔버스 템플릿, MemGPT의 장기 기억)의 실제 기능 스펙 목록을 소환하여 정리하라는 것**이었음.

### 💡 핵심 교훈
1. **발언의 '목적'을 먼저 파악하라:** 토론용 안건인가, 과거 기획의 소환/스펙 정리인가, 작업 지시인가, 기술 검증인가?
2. **유형이 다르면 템플릿도 달라져야 한다:** 회의 안건 템플릿, 기획 벤치마크 템플릿, 실행 과제 템플릿, 기술 스파이크 템플릿을 분리 운영해야 합니다.

## 2. 발언 유형 판별 및 템플릿 라우팅 트리 (Routing Decision Tree)

속기 발언이나 인박스 노트를 마주했을 때, 다음 질문 순서대로 템플릿을 배정합니다:

```text
[속기 발언 분석 시작]
        │
        ├─▶ [질문 1] "참석자들이 회의에서 A vs B 중 하나를 선택/합의해야 하는 규칙/정책인가?"
        │      └─▶ [YES] ──▶ 템플릿 1: 【의사결정 안건 카드】 (Decision Agenda)
        │
        ├─▶ [질문 2] "과거 논의된 벤치마크, 레퍼런스, 기능 아이디어의 실제 목록을 복원/정리하는 것인가?"
        │      └─▶ [YES] ──▶ 템플릿 2: 【기획 벤치마크 스펙 리스트】 (Feature Spec)
        │
        ├─▶ [질문 3] "논의 없이 담당자가 정해져 손발을 움직여 산출물을 만드는 물리적 작업인가?"
        │      └─▶ [YES] ──▶ 템플릿 3: 【실행 과제 / Action Item】 (Task Ticket)
        │
        └─▶ [질문 4] "도입 가능성을 확인하기 위해 신기술/도구의 개념 검증(PoC)이 선행되어야 하는가?"
               └─▶ [YES] ──▶ 템플릿 4: 【기술 스파이크 / R&D 검증 카드】 (Tech Spike)
```

## 3. 4대 유형별 전용 템플릿 상세 스펙 (Template Library)

### 템플릿 1. 【의사결정 안건 카드 (Decision Agenda)】
* **용도:** 회의 테이블에 올려 1~2분 만에 결정을 내려야 하는 정책/규칙/프로세스 안건.
* **대표 사례:** 1.1(아카이빙 기준), 2.1(인박스 위임 룰), 3.1(에이전트 주도권 수준)
* **필수 섹션 아키텍처:**
  ```markdown
  # [번호] [안건 제목]
  > **속기 원문**
  ## 🎯 핵심 의사결정 포인트 (Decision Checkpoint)
  > **[결정 질문] 단 하나의 명확한 질문?**
  > - [ ] [선택지 A (권장)]: ...
  > - [ ] [선택지 B]: ...
  ## 📌 기존엔 왜 이렇게 관리했을까? (현행 사양의 이유 - 보호 가치 존중)
  ## 📌 핵심 분석 (현재 겪는 구체적 피로도)
  ## 🌐 참조 자료 및 모범 사례 (외부 도구/프레임워크 표준)
  ## ⚖️ 핵심 쟁점 (회의에서 답을 내려야 할 질문 1, 2)
  ## 💡 해결 방향 (회의에서 논의 후 결정 - 반드시 빈칸 유지!)
  ```

---

### 템플릿 2. 【기획 벤치마크 스펙 리스트 (Feature Benchmark Spec)】
* **용도:** 과거에 논의했던 외부 툴 벤치마크, 프로덕트 기능 목록, UX 스펙 자산을 실체화하여 정리할 때.
* **대표 사례:** 5.1(노션·미로·MemGPT 벤치마크 포인트 취합)
* **필수 섹션 아키텍처:**
  ```markdown
  # 📌 [기획 벤치마크] [서비스 도입용 벤치마크 명칭]
  > **속기 원문**
  ## 🎯 문서 개요 및 목적 (우리 서비스와의 연결 고리 명시)
  ## 1. 📝 [벤치마크 A]에서 가져올 핵심 포인트 리스트 (표/불릿 형태 스펙)
  ## 2. 🎨 [벤치마크 B]에서 가져올 핵심 포인트 리스트 (표/불릿 형태 스펙)
  ## 3. 🧠 [벤치마크 C]에서 가져올 핵심 포인트 리스트 (표/불릿 형태 스펙)
  ## 4. 🚀 우리 서비스 종합 융합 시나리오 (To-Be 통합 흐름)
  ## 📌 회의에서 활용할 핵심 체크포인트 (스프린트 우선순위 확정 등)
  ```

---

### 템플릿 3. 【실행 과제 및 작업 티켓 (Action Item / Task)】
* **용도:** 회의 결과로 도출되었거나, 논쟁할 필요 없이 담당자가 수행해야 하는 명확한 작업.
* **속성(Frontmatter):** `유형: 할일`, `상태: to do`
* **필수 섹션 아키텍처:**
  ```markdown
  # 🎯 [Action Item] [과제명]
  > **발주 배경 / 원문 인용**
  ## 📌 과제 개요 및 목적 (Why & What)
  ## 📋 세부 실행 과제 (Sub-Tasks)
  - [ ] 작업 단위 1
  - [ ] 작업 단위 2
  ## 🏁 완료 정의 (Definition of Done - 무엇이 나와야 끝인가?)
  ## 👥 R&R 및 협업 연결 (담당자, 마감일, 연계 프로젝트/노트)
  ```

---

### 템플릿 4. 【기술 스파이크 및 R&D 검증 (Tech Spike / Research)】
* **용도:** 회의에서 바로 결론을 낼 수 없어, 사전 조사가 필요한 신규 라이브러리, 오픈소스, 아키텍처 검증.
* **속성(Frontmatter):** `유형: 레퍼런스` 또는 `유형: 연구`, `상태: doing`
* **필수 섹션 아키텍처:**
  ```markdown
  # 🔬 [Tech Spike] [조사 기술명 및 검증 목적]
  ## 📌 탐색 배경 및 해결하려는 문제
  ## ❓ 검증할 핵심 가설 (Hypothesis to Test)
  ## 🧪 검증 방식 및 PoC 범위 (간이 테스트 시나리오)
  ## 📊 평가 기준 (Go / No-Go Decision Criteria)
  ## 📝 조사 결과 요약 (사후 기입)
  ```

## 4. 다음 작업 에이전트를 위한 운영 체크리스트 (Handover Checklist)

작업에 투입된 에이전트는 사용자의 속기 정비 요청을 받았을 때 다음 5단계를 엄수해야 합니다:

1. **[속기 맥락 심층 독해]:** 속기 속에 등장하는 툴 이름(노션, 미로 등)이 '데이터 저장소'인지 '서비스 벤치마크 대상'인지 프로젝트 도메인(`VibePatchNote`) 관점에서 먼저 해석할 것.
2. **[일률적 안건화 금지]:** "모든 항목을 의사결정 카드로 만들어라"는 지시가 아니라면, 템플릿 라우팅 트리를 거쳐 최적의 템플릿을 선정할 것.
3. **[의사결정 카드의 1초 원칙]:** 템플릿 1을 쓸 때는 상단에 반드시 **[1줄 결정 질문] + [선택지 체크박스]**를 배치하여 바쁜 사람이 10초 안에 결정을 내릴 수 있게 할 것.
4. **[해결 방향 비워두기]:** 템플릿 1의 `💡 해결 방향`은 에이전트가 단정 짓지 말고 사람이 회의에서 채우도록 반드시 비워둘 것.
5. **[히스토리 보존 원칙]:** 사용자가 기존 버전을 history로 보내라고 요구하면, 덮어쓰지 말고 기존 파일을 `history/`로 안전하게 이동한 뒤 새 버전을 생성할 것.
