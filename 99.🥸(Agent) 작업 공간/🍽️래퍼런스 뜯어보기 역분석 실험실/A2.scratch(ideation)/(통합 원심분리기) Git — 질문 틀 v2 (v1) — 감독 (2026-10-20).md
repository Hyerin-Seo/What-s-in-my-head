## 원본과 다른 답
- **되돌릴 수 있는 범위 (마지막 동작만 / 여러 단계 / 특정 시점 / 없음)** — 적힌 답: "커밋하지 않은 변경은 되돌릴 기록이 없음" → 원본: git add 로 담은 것은 index 에 남는다고 함. "This snapshot is now stored in a temporary staging area which Git calls the "index"" (gittutorial). 또 git checkout -- 파일 은 "Replace the specified files and/or directories with the version from the index." 라고 적혀 있음 (git-checkout 문서). 직접 써 보고 지워진 것은 add 하지 않은 변경뿐이라, 커밋하지 않은 변경 전체로 넓혀 적으면 원본과 다름.
- **사람 확인 없이 확정되는 것 (있으면 무엇)** — 적힌 답: "명령을 내리면 되묻지 않고 실행됨" → 원본: git clean 은 기본 설정에서 "will refuse to delete files or directories unless given -f" 라고 적혀 있음 (git-clean 문서). 직접 해 본 두 명령은 그대로 두고, 모든 명령으로 넓힌 말은 원본과 다름.
- **설치 · 가입 뒤 첫 결과물이 나오기까지 한 일 (차례대로)** — 적힌 답: "이름 설정 없이 commit 하면 "Author identity unknown" 으로 멈춤" (직접 사용) → 공식 문서: 설정이 없으면 "the environment variable EMAIL, or, if that is not set, system user name and the hostname used for outgoing mail" 에서 가져온다고 적혀 있음 (git-commit 문서 COMMIT INFORMATION). 직접 사용 결과와 공식 문서를 둘 다 적어야 함. 첫 단계인 git config 가 꼭 필요한 단계인지가 이 차이에 걸려 있음.
- **그 단계 수 (위 차례를 센 것)** — 적힌 답: "4" → 원본: 튜토리얼은 이미 파일이 있다는 가정에서 시작함. "Assume you have a tarball project.tar.gz with your initial work." (gittutorial). 검토 대상 7장에 적은 git status 안내도 "(create/copy files and use "git add" to track)" 로, git add 앞에 파일을 만들거나 넣는 일이 있음. 위 차례에 이 일이 빠져 있어 센 수가 원본의 흐름과 다름.
- **사용자가 마음대로 정하는 것** — 적힌 답: "브랜치 이름" → 원본: "Git imposes the following rules on how references are named" 뒤에 "They cannot have two consecutive dots .. anywhere." 같은 규칙이 이어짐 (git-check-ref-format 문서). 브랜치 이름은 정해 둔 규칙 안에서만 정할 수 있음.

## 판단이 섞인 답
- **스스로 검사하는 것 (맞춤법 · 형식 · 빠진 것 등 — 있으면)** — 적힌 말: "(Windows 기본 설정)" → 판단인 까닭: 경고가 나온 까닭을 사실처럼 적었는데, 붙인 출처(직접 사용, Hooks 안내서)는 그 까닭을 보여 주지 않음 → 대신 적을 것: 경고 문장만 남기거나, git config 로 본 core.autocrlf 값과 그 값이 어느 설정 파일에서 왔는지를 출처와 함께 적기

## 억지로 채웠거나 빈 칸
- **원본을 건드리지 않고 시험해 보는 공간 (있으면 무엇)** — git stash 를 넣었는데, 공식 문서는 stash 를 바뀐 것을 치워 두고 작업 폴더를 깨끗하게 돌리는 일로 적음. "want to go back to a clean working directory" (git-stash 문서). 시험해 보는 공간이 아니라 치워 두는 곳이라 질문과 어긋남.
- **그 결과를 보여 주는 방식 (바로 반영 / 제안으로 보여 줌 / 따로 파일 / 기타)** — 보기 중 하나를 고르지 않았고, 겹칠 때만 적음. 겹치지 않을 때는 9장에서 확인 못 한 것으로 남겼는데, 본 자료 목록에 있는 gittutorial 에 "If the changes don't conflict, you're done." 이 있음.
- **한 일을 마쳤을 때 보여 주는 것 (메시지 · 표시 · 결과 파일 · 없음)** — 적힌 답 "한두 줄 요약" 은 보기의 "메시지" 로 옮길 수 있는데 옮기지 않음.
- **단계를 나눠 보여 주는 방식 (탭 · 접기 · 구분선 · 단계 표시 · 없음)** — "해당 없음" 이라고 해 놓고 같은 칸에 "빈 줄로 덩어리를 나눔" 이라는 관찰을 적어, 해당 없음인지 답이 있는 것인지 갈리지 않음. 보기의 "없음" 이나 "구분선" 중 하나로 정해야 나란히 비교할 수 있음.
- **'선택'으로 미뤄 둔 설정이나 기능 (있으면)** — "찾지 못함" 으로 적어 '모름' 인지 '해당 없음' 인지 구분이 안 됨.

## 질문 틀에 알릴 것
- **원본을 건드리지 않고 시험해 보는 공간 (있으면 무엇)** — Git 에는 브랜치, 작업 폴더 추가, 치워 두기처럼 성격이 다른 장치가 여럿 있어서, 시험 공간이 아닌 것까지 이 칸에 들어옴.
- **단계를 나눠 보여 주는 방식 (탭 · 접기 · 구분선 · 단계 표시 · 없음)** — 보기가 화면 있는 도구를 전제로 해서, 화면 없는 도구는 해당 없음과 없음 사이에서 답이 흔들림.
- **가장 작은 단위의 이름 (예: 불릿 · 블록 · 카드 · 파일 · 커밋 · 행)** — 답은 커밋을 골랐지만 같은 답 안에 그보다 작은 트리와 블롭을 적음. Git 처럼 단위가 겹겹인 도구에서는 '가장 작은' 이 기록 단위인지 내용 단위인지 갈림.
- **계층 깊이 제한 (없음 / 몇 단계)** — 커밋은 그래프로 이어져 계층이 없고, 폴더(트리)에는 계층이 있어서 무엇의 깊이를 묻는지 갈림. 답도 9장에서 폴더 깊이로 바꿔 읽음.

## 감독 메모
- 계층 깊이 제한 칸은 "모름 — 문서에서 찾지 못함" 인데, 같은 git 2.52 문서의 git-config 에 core.maxTreeDepth 가 있음. 폴더를 따라 들어가는 깊이의 한계를 정하는 설정이고 기본값은 2048 (MSVC 로 만든 판은 512) 이라고 적혀 있음. 검토 대상이 목록에 올린 자료 밖의 문서라 고칠 답으로 세지 않았음. 모름이라고 적은 칸에 원본이 답을 가지고 있을 때 어디에 적을지 스킬에 없음.
- 출처가 없어도 되는 답으로 사실 확인 렌즈는 모름과 해당 없음만 듭니다. 질문 틀이 직접 정해 준 "밝힌 것 없음", "화면 없음" 은 같은 것으로 보고 출처를 묻지 않았지만, 스킬에 그렇게 적혀 있지는 않음.
- 직접 사용 출처는 따지지 말라고 하는데, 공식 문서와 어긋날 때만 적으라는 기준이 넓어서 판단이 갈렸음. 이번에는 문서가 다른 동작을 분명히 적은 곳(작성자 정보를 대신 가져오는 것, 되돌리기)만 적었음. 메시지 문장이 실행 파일 안에 있는지 본 것을 확인으로 쳐도 되는지는 스킬에 없음.
- 보기로 옮기지 않은 칸 같은 모양 문제와 원본과 다른 사실이 같은 무게로 세어져, 작은 모양 문제 하나만 있어도 결론이 고친 뒤 다시 보세요가 됨. 고칠 답을 질문 수로 세는지 지적 줄 수로 세는지도 정해져 있지 않음. 이번에는 질문 수로 셌음.
- 읽을 것 표는 볼트의 레퍼런스 노트를 원본으로 올리는데, 이번 노트는 Git 원문이 아니라 우리 쪽 해석 메모였음. 검토 대상도 같은 까닭으로 출처에서 뺐음. 이런 노트를 원본으로 볼지 스킬이 정해 주면 좋겠음.
- 질문과 다른 것을 답한 칸은 질문 틀에 알릴 것에도 적으라고 해서 두 절에 겹쳐 적었음. 보기로 옮기지 않은 칸은 겹쳐 적지 않았음.
