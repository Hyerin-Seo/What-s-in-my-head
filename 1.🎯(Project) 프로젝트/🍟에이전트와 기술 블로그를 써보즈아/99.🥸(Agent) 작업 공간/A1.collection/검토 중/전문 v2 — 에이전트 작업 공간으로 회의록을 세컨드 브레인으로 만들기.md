# 에이전트 작업 공간(agent workspace)으로 회의록을 세컨드 브레인으로 만들기

## 개요

팀 회의가 잦아지면서 회의록 정리를 에이전트에게 맡기는 일이 늘었습니다. 그런데 맡길수록, 에이전트가 쓴 노트가 사람이 쓴 노트와 같은 자리에 쌓이는 불편을 자주 겪었습니다.

예를 들어 "이 회의록 정리해줘" 라고 하면, 볼트 사정을 모르는 에이전트는 안건 카드와 할 일 후보를 다른 노트들 옆에 그대로 써 넣습니다. 그래서 정리를 시킬 때마다 이런 말을 덧붙여야 했습니다.

> 회의록 본문은 건드리지 말고
> 할 일은 바로 만들지 말고 후보로만 뽑고
> 네가 쓴 건 보드에 안 뜨게 따로 둬 줘

그래도 에이전트의 카드는 회의록 보드에 섞였습니다. 회의 한 번을 정리하려고 '덧붙이기, 섞인 것 골라내기, 다시 시키기' 를 매번 되풀이했습니다.

〔삽화 1〕

그래서 이런 생각이 들었습니다. '에이전트는 마음껏 쓰게 두고, 사람이 고른 것만 볼트에 들어오게 할 수는 없을까?'

개발에서는 이런 자리를 샌드박스라고 부릅니다. 우리는 옵시디언 볼트 안에 에이전트만 쓰는 샌드박스를 팠습니다. 이름은 `99.🥸(Agent) 작업 공간` 입니다. 이 글에서는 그 안의 폴더 다섯 개가 무엇을 하는지, 회의록이 거기서 어떻게 분류되고 사람 손을 거쳐 볼트로 올라가는지를 다룹니다. 그리고 그렇게 쌓인 기록이 뜻밖에 에이전트의 세컨드 브레인 노릇을 한 일까지 나눕니다.

## 작업 공간 / 스킬

회의 하나에 작업 공간 하나가 생깁니다. 구조는 이렇습니다.

```
99.🥸(Agent) 작업 공간/<회의록 이름>/
 ├ A1.collection
 ├ A2.scratch(ideation)
 ├ A3.working memory
 ├ A4.meta
 └ A5.outputs
```

| 폴더 | 누가 쓰나 | 역할 |
| --- | --- | --- |
| A1.collection | 에이전트 | 뽑은 카드를 모으는 곳 |
| A2.scratch(ideation) | 에이전트 | 지난 회의 점검표 |
| A3.working memory | 에이전트 | 작업 기억 |
| A4.meta | 에이전트 | 이 회의에만 쓰는 스킬 사본 |
| A5.outputs | **사람** | 사람이 고른 카드 |

폴더를 채우는 순서는 스킬이 정합니다. 작업 공간이 자리라면 스킬은 순서입니다.

## 작업 공간

작업 공간은 에이전트가 쓴 것이 볼트에 섞이지 않게 가둬 두는 자리입니다. 에이전트는 여기에만 쓰고, 볼트로 올리는 것은 사람만 합니다.

폴더마다 하는 일은 이렇습니다.

- **A1.collection** — 에이전트가 뽑은 카드가 처음 놓이는 곳입니다. 안에 `검토 중` · `paused` · `history` 가 있습니다. 새 카드는 `검토 중` 에 놓이고, 사람이 미룬 것은 `paused` 로, 끝내 안 고른 것은 `history` 로 갑니다.
- **A2.scratch(ideation)** — 다음 회의 전에 "지난번에 하기로 한 것이 됐나" 를 훑은 점검표가 놓입니다.
- **A3.working memory** — 에이전트의 작업 기억입니다. 세 줄 요약, 속기를 한 줄도 빼지 않고 번호 매긴 분류표, 고친 기록이 들어 있습니다. 다른 에이전트가 이어받아도 여기부터 읽으면 됩니다.
- **A4.meta** — 스킬의 사본입니다. 사람이 카드를 안 고르면 에이전트는 정본이 아니라 이 사본을 고쳐서 다시 뽑습니다. 회의 하나의 사정이 정본을 흔들지 않습니다.
- **A5.outputs** — 사람의 자리입니다. 마음에 드는 카드를 여기로 옮깁니다. 에이전트는 여기에 쓰지도 옮기지도 않습니다.

회의 하나를 돌리고 나면 안은 이렇게 됩니다.

```
2026.10.01 15분 공유회/
 ├ A1.collection/
 │   ├ 검토 중/     (비어 있음)
 │   ├ paused/
 │   └ history/     1.1_와꾸가_안_잡힌_사람_…   1.2_진심_펀치_테스트_…   1.3_…
 ├ A3.working memory/   2026.10.01 15분 공유회 — 작업 기억
 ├ A4.meta/         pre_meeting_agenda_preparer/   meeting_decision_recorder/
 └ A5.outputs/      D1_우리_도구는_시뮬레이터다_…
```

> Tip: 주목할 것은 옵시디언의 **"제외된 파일"** 입니다. 작업 공간 폴더를 통째로 제외해 두면 파일 탐색기에는 그대로 보이고, 보드 · 검색 · 그래프에는 안 뜹니다. 에이전트 노트마다 속성을 달아 하나씩 가리는 것이 아니라 폴더째로 가립니다.

이렇게 해 두면 에이전트가 카드를 몇 장을 쓰든 사람의 보드는 그대로입니다.

## Before / After 예시

차이는 회의록 보드를 열어 보면 가장 잘 보입니다.

### Before (작업 공간을 가리기 전)

에이전트가 쓴 카드의 속성은 보통 이렇게 생겼습니다.

```yaml
유형: 메모
분류:
  - 회의록
상태: 검토 중
작성자:
  - "[[Claude]]"
```

회의록 보드는 `분류: 회의록` 인 노트를 모읍니다. 주간 리뷰는 `상태: 검토 중` 인 노트를 모읍니다. 에이전트 카드는 속성만 보면 둘 다에 해당합니다. 그래서 둘 다에 떴습니다. 나중에 세어 보니 에이전트 노트 70장 가운데 약 30장이 `분류: 회의록` 이었습니다.

결국 보드를 열 때마다 "이건 에이전트 초안, 이건 우리가 정한 것" 을 눈으로 가르는 일이 되풀이됐습니다.

### After (폴더째 제외한 뒤)

고친 것은 설정 한 줄입니다.

```diff
  "userIgnoreFilters": [
    "skills/",
-   "/!\\(Template\\)/"
+   "/!\\(Template\\)/",
+   "99.🥸(Agent) 작업 공간/"
  ]
```

카드의 속성은 한 글자도 안 고쳤습니다. 그런데 보드에는 사람이 올린 것만 남았습니다.

## 작업 공간을 만들 때 고려했던 기준

작업 공간을 굴리면서 몇 가지 기준이 생겼습니다.

#### 에이전트는 작업 공간에만 쓴다

볼트의 노트를 직접 고치게 두면 무엇이 초안이고 무엇이 정한 것인지 흐려집니다. 에이전트가 볼트 쪽에 남기는 것은 회의록에 작업 공간으로 가는 링크 한두 줄뿐입니다.

#### 고르는 것은 사람이고, 고르는 자리는 하나다

- A1 `검토 중` = 에이전트가 낸 후보
- A5 `outputs` = 사람이 고른 것

사람은 마음에 드는 카드를 A5 로 옮기기만 합니다. 여기까지 오는 데 방식을 두 번 갈아엎었습니다 — 표에서 고르던 방식, 체크리스트 방식을 거쳐 지금의 카드 방식이 됐습니다.[^g5]

#### 안 고른 것도 지우지 않는다

안 고른 카드는 `history` 로 갑니다. 지우지 않습니다. 처음에는 그저 아까워서 둔 것인데, 이 기준이 나중에 뜻밖의 쓸모를 냈습니다 (아래 세컨드 브레인 패턴).

## 도입 후 느낀 변화

작업 공간을 쓴 뒤로 체감되는 변화가 몇 가지 있었습니다.

#### 보드에서 에이전트의 초안을 걸러 읽지 않아도 된다

회의록 보드와 주간 리뷰에는 사람이 올린 것만 뜹니다. 눈으로 가르던 일이 사라졌습니다.

#### 에이전트에게 덧붙이던 말이 사라졌다

"따로 둬 줘", "바로 만들지 마" 를 매번 말하지 않습니다. 어디에 쓰는지가 폴더로 정해져 있어서, 요청은 "정리해줘" 한마디로 줄었습니다.

#### 에이전트가 틀려도 치울 것이 없다

카드가 마음에 안 들면 안 고르면 됩니다. 볼트에는 아무것도 안 들어왔으니 되돌릴 것도 없습니다. 그래서 에이전트에게 후보를 넉넉히 내게 할 수 있습니다.

## 언제 작업 공간을 쓰면 좋은가

#### 에이전트가 쓴 것과 사람이 정한 것을 가려야 하는 경우

회의록 · 결정처럼 "누가 정했나" 가 중요한 기록을 에이전트와 같이 쓸 때 맞습니다.

#### 에이전트가 한 번에 여러 장을 쓰는 경우

후보를 많이 내게 할수록, 그 후보가 볼트에 안 섞이는 자리가 먼저 필요합니다.

## 스킬

작업 공간이 자리라면 스킬은 회의록을 그 자리에 채워 넣는 순서입니다. 사람이 하는 말은 이 정도입니다.

| 스킬 · 요청 | 하는 일 | 예시 요청 |
| --- | --- | --- |
| 회의 정리 | 속기를 읽고 작업 공간을 만들어 카드를 뽑음 | "이 회의록 정리해줘" |
| 안건 카드 | 아직 안 정한 것을 결정 질문과 쟁점으로 구조화 | (회의 정리가 부름) |
| 결정 카드 | 이미 정한 것을 결정 · 기한 · 이유로 기록 | (회의 정리가 부름) |
| 다시 뽑기 | 안 고른 카드의 이유로 스킬 사본을 고쳐 다시 뽑음 | "다시 뽑아줘" |
| 지난 회의 점검 | 지난번에 하기로 한 것이 됐는지 점검표를 깖 | "지난 회의 점검해줘" |

회의 정리는 속기를 요약하고 끝나지 않습니다. 사람이 하는 일은 녹음뿐이고, 그 뒤는 이런 순서로 흘러갑니다.[^g5]

```
녹음 · 전사 (발화자 번호와 시각)
       ↓
속기를 한 줄도 빼지 않고 번호 매기기
       ↓
세 갈래로 분류
  · 아직 안 정한 것      → 안건 카드
  · 이미 정한 것         → 결정 카드
  · 논의할 게 없는 것     → 카드 아님 목록 (단순 할 일 · 연락)
       ↓
A1 검토 중
       ↓
사람이 골라 A5 로, 사람 말로 다듬어 프로젝트의 회의 날짜 폴더로
       ↓
다음 회의 전에 점검
```

정한 것과 아직 안 정한 것을 다른 카드로 가르는 데는 까닭이 있습니다. 말하면서 이미 정한 것까지 안건으로 다시 묻지 않으려는 것입니다.[^b1]

물론 에이전트가 다 해 주는 것은 아닙니다. 9월 29일 회의는 녹음 전사 376발화였고, 에이전트는 안건 카드 여섯 장을 뽑았습니다. 우리가 고른 것은 세 장입니다. 고른 세 장도 그대로 쓰지 않았습니다. 카드 하나를 할 일 석 장으로 쪼갰고, 카드에 없던 내용을 더했습니다. 전사는 화자를 이름이 아니라 번호로만 적는다는 것도 아직 불편합니다.[^g5]

하지만 376발화를 읽고, 가르고, 근거 발화를 찾아 붙이는 일이 "정리해줘" 한마디로 줄었습니다. 사람은 고르고 더하는 데만 시간을 씁니다.

## 언제 스킬을 쓰면 좋은가

#### 순서가 늘 같은 일인 경우

회의는 매번 같은 차례로 정리됩니다 — 읽고, 가르고, 카드로 쓰고, 고르기를 기다립니다.

#### 노트 여러 장을 한 번에 만들어야 하는 경우

회의 하나에서 카드가 여러 장 나옵니다. 한 번에 다 시키면 서로 엉킵니다. 안건 카드와 결정 카드를 다른 스킬로 나눈 까닭입니다.

## 쌓인 회의록을 세컨드 브레인으로 쓰는 패턴

에이전트와 하는 일을 넓히다 보면 '에이전트가 우리 팀의 말을 못 알아듣는다' 는 한계에 부딪히기 쉽습니다.

우리 팀에는 "와꾸" 라는 말이 있습니다. 사전에 없고, 풀어서 정의하기도 어렵습니다. 에이전트에게 기획을 같이 보자고 하면서 이 말을 설명해도, 에이전트는 자기 식으로 알아듣고 보통 이런 답을 냈습니다.[^b1]

```
사업계획서 작성 지원을 위해 다음 세 모듈을 제안합니다.

1. Template Engine — 공고문 양식을 파싱해 섹션 트리를 생성
2. Reference Retriever — 벡터 DB 에서 유사 사업계획서를 검색 (top-k = 5)
3. Draft Generator — 섹션별 프롬프트 체인으로 초안을 생성
```

물은 것은 사람이 책상에서 하는 일인데, 돌아온 것은 만들 기능의 사양입니다. 결국 이 말을 다시 쳤습니다.

> 아니야 아니야 이런 것을 너에게 제시해달라는 것이 아니야. '행위'에 집중을 하라는 거야.

이럴 때 해 볼 수 있는 방법이 **설명하지 말고 가리키기**입니다. 길을 잃은 에이전트를 돌려놓는 것은 더 긴 프롬프트가 아니라 팀이 실제로 한 말이었습니다.[^g1] 그 말은 이미 작업 공간과 프로젝트 폴더에 쌓여 있었습니다.

〔삽화 3〕

### 예시: 에이전트에게 "와꾸가 안 잡혔다" 가 무슨 뜻인지 물을 때

앞의 긴 대화를 질문 하나로 줄이면 차이가 또렷해집니다.[^b2]

#### AS-IS: 말로 설명한다

```
질문  우리 팀에서 "와꾸가 안 잡혔다" 는 게 무슨 뜻이야?
  → 에이전트가 낱말 뜻으로 짐작
  → "양식이나 기준 문서가 없어서 틀이 안 잡힌 백지 상태를 말합니다."
```

틀렸습니다. 우리 팀에서는 기준 문서가 있어도 와꾸가 안 잡힐 수 있습니다.

#### TO-BE: 회의 폴더를 가리킨다

```
질문  discussions → 현재 이 내용을 본다면 우리 팀이 어떤 과정을 진행하는지를 알게 될거야.
  → 회의 날짜 폴더의 결정 카드
  → 링크된 안건 카드의 속기 원문
  → "80%는 양식(기준 문서)이 있어도, 20%의 모르는 칸이 나오면 와꾸가 안 잡힌 것이다." (속기 32:50)
```

실제 화면입니다. 에이전트는 1분 만에 회의에서 오간 말 셋을 시각과 함께 꺼내 왔습니다.

![[통쾌한 순간 2 — 에이전트의 답.png]]

#### 실제 전달 데이터 비교

AS-IS 의 오답은 그럴듯합니다. 회의에서 사람도 똑같이 알아들었습니다.[^b2]

```
발화자 2 (23:50)  기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?
발화자 2 (31:54)  … 레퍼런스가 있다는 거 자체가 와코가 잡힌 거지.
발화자 1 (32:50)  그러니까 와꾸가 안 잡혔다라는 것은 내가 80%는 나왔는데 20%는 몰라. 그럼 왔고 안 잡힌 거야.
```

사람 둘이 23:50 부터 32:50 까지 9분 동안 세 번 되물어 맞춘 말입니다. 에이전트가 가져온 것은 그 되물음이 끝난 자리였습니다.[^b1]

그렇다면 회의 전사를 통째로 읽히면 되지 않을까요. 전사는 "와꾸" 를 이렇게 받아 적었습니다.[^b2]

| 전사에 적힌 글자 | 횟수 |
| --- | --: |
| 와꾸 | 10 |
| 왔고 | 8 |
| 와코 | 2 |
| 와꼬 | 2 |
| 악구 | 1 |

스물세 번 가운데 "와꾸" 로 적힌 것은 열 번입니다. 에이전트가 읽은 것은 전사가 아니라 카드였습니다.

```markdown
# 1.1 와꾸가 안 잡힌 사람 — 첫 타겟을 어디에 그을까

> **속기 원문**
> - 발화자 2 (23:50) *… 기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?*
> - 발화자 1 (32:50) *그러니까 와꾸가 안 잡혔다라는 것은 내가 80%는 나왔는데 20%는 몰라. 그럼 왔고 안 잡힌 거야.*
```

카드는 제목에서 "와꾸" 한 가지로 묶고, 그 말이 오간 발화를 시각과 함께 옮겨 둡니다. 에이전트가 꺼내 온 말 셋은 전부 이 칸에 있던 것입니다.

두 답을 나란히 놓으면 이렇습니다.[^b2]

| 확인할 것 | AS-IS | TO-BE |
| --- | --- | --- |
| 뜻이 맞나 (기준 문서가 있어도 해당된다) | ✗ | ✓ |
| 팀이 실제로 한 말을 인용했나 | 0개 | 3개 |
| 인용에 시각이 붙어 있나 | 없음 | 32:50 · 15:04 · 16:23 |
| 확인하러 갈 곳이 있나 | 없음 | 회의록의 그 시각 |

그런데 이 카드는 우리가 **안 고른** 카드였습니다. 그 회의에서 고른 것은 결정 카드 한 장뿐이고, 안건 카드 석 장은 `history` 로 갔습니다. 고른 결정 카드가 그 석 장을 링크로 가리키고 있었고, 에이전트는 거기서 "와꾸" 를 찾았습니다. "안 고른 것도 지우지 않는다" 는 기준이 여기서 쓸모를 냈습니다.

**가리킬 수 있으려면 무엇이 있어야 하나요?**

전부 만들 필요는 없습니다. 그날 통한 것은 이 셋입니다.[^g1]

- 회의마다 폴더 하나.
- 안건마다 그 안건이 나온 발화 원문 몇 줄과 시각.
- 정한 것과 아직 안 정한 것을 따로.

안건 카드 스킬에는 카드의 틀이 이렇게 적혀 있습니다.[^b1]

```markdown
# [안건 번호] 안건 제목

> **속기 원문**
> - *<회의 속기에서 발췌한 날것의 발언 원문 그대로 인용>*

> **[결정 질문] <회의 참석자가 즉시 판단하고 결정할 단 하나의 핵심 질문>?**
```

**[참고] 회의 두 번의 크기**

| 회의 | 전사 전체 | 프로젝트 폴더에 올라간 것 | 줄어든 비율 |
| --- | --: | --: | --: |
| 09.29 (376발화) | 70,383 bytes | 16,394 bytes | 76.7% |
| 10.01 (175발화) | 35,913 bytes | 1,729 bytes | 95.2% |

안건 카드 한 장은 5,798 bytes 로, 그 회의 전사의 16% 입니다.

이 숫자에서 얻은 것은 크기보다 **찾을 수 있다는 것**입니다. 에이전트가 35분짜리 전사를 헤매지 않고 그 말이 오간 자리로 바로 갔고, 답에 시각이 붙어 있어서 우리도 원문을 열어 확인할 수 있었습니다. 실제로 열어 보니 에이전트가 꺼낸 말 셋 가운데 하나는 화자가 틀려 있었습니다. 뜻은 잡았고, 누가 말했는지는 놓쳤습니다.[^b2]

> 참고: 파일 크기이지 토큰이 아닙니다. 에이전트가 그날 실제로 얼마나 읽었는지를 잰 것도 아닙니다. 카드를 전부 합치면 줄지 않습니다 — 09.29 회의는 카드 전체가 67,390 bytes 로 전사와 거의 같습니다. 줄어드는 것은 한 번에 읽는 양입니다. 그리고 이것은 한 번 있었던 일입니다.

## 마무리

예전에는 에이전트에게 잘 시키고 잘 설명하는 것이 중요했다면, 지금은 에이전트가 쓴 것을 어디에 두고 누가 고를지를 먼저 정해 두는 것이 더 중요하다고 느꼈습니다.

처음에는 에이전트가 쓴 것을 볼트에서 떼어 놓으려고 폴더를 팠습니다. 그런데 그렇게 떼어 쌓은 기록이, 나중에는 에이전트에게 우리 팀을 설명해 주는 기억이 됐습니다. 팀의 말을 사전으로 만들려 하지 말고, 그 말이 맞춰진 회의를 남겨 보시기를 권합니다.[^b2]

여기서 한 걸음 더 가면, 사람이 안 고른 카드의 이유로 스킬이 회의마다 고쳐지고, 다음 회의 전에 지난 합의가 지켜졌는지 에이전트가 먼저 점검하는 데까지 넓힐 수 있습니다.

## 레퍼런스의 뉘앙스를 어디에 살렸나

레퍼런스의 예시는 로그인이 아니라 "user 조회 React Query 훅" 하나입니다. 그 글의 결은 **겪음 → 되풀이 → 깨달음 → 해결 → 숫자로 확인 → 다음 걸음**이고, 칸마다 이렇게 옮겼습니다.

| 레퍼런스가 쓰는 결 | 이 글에서 |
| --- | --- |
| 개요: 요청 하나를 예로 들어 불편을 보여 주고, 되풀이되는 과정에 이름을 붙임 | "이 회의록 정리해줘" → '덧붙이기, 섞인 것 골라내기, 다시 시키기' |
| 개요: 업계에 이미 있는 개념에 기대어 이름을 붙임 | 샌드박스 · 세컨드 브레인 |
| Before: "보통 이런 결과가 나온다" → 결국 되풀이된다 | 카드 속성 → 둘 다에 떴다 → "눈으로 가르는 일이 되풀이됐습니다" |
| After: 고친 것은 작다, 결과는 한 번에 | "설정 한 줄" · "속성은 한 글자도 안 고쳤습니다" |
| 기준 · 변화: "굴리다 보니 생겼다" 는 겪은 사람의 말투 | "몇 가지 기준이 생겼습니다" · "체감되는 변화" |
| 도구 2: "물론 다 해 주는 것은 아니다. 하지만 …" | 376발화 → 여섯 장 → 세 장, 그리고 "하지만 … 한마디로 줄었습니다" |
| 심화: "넓히다 보면 한계에 부딪힌다 → 이럴 때 해 볼 수 있는 방법" | 에이전트가 팀의 말을 못 알아듣는다 → 설명하지 말고 가리키기 |
| 심화: 숫자 뒤에 "이 숫자에서 얻은 것은" 과 단서 | "크기보다 찾을 수 있다는 것" · 참고 |
| 마무리: "예전에는 … 지금은 …" → 권유 → 한 걸음 더 | 그대로 |

## 지은 것과 확인할 것

- **지은 것 셋**: 개요의 인용 세 줄 · 심화의 모듈 사양 답 · AS-IS 의 답 한 줄. 새 대화에서 한 번씩 돌려 보면 실물로 바꿀 수 있습니다.
- TO-BE 의 질문은 실제로 한 말이지만 "와꾸의 뜻" 을 물은 것은 아니었습니다. 채점표의 TO-BE 열(인용 3개 · 시각 셋)은 실제 캡처에서 센 것입니다.
- "두 번 갈아엎었다" 는 `skills/meeting-notes/SKILL.md` 11절에 적힌 것입니다 (표 방식 → 09-23 체크리스트 → 09-28 지금 방식).
- "처음에는 그저 아까워서 둔 것" 은 **제가 붙인 말**입니다. 왜 안 지우기로 했는지는 문서에 "삭제는 사람이 한다" 로만 있습니다. 맞는 말로 고쳐 주세요.
- 밖에 내기 전에: 회의록 이름, "와꾸" · "진심 펀치", 카드 제목이 그대로 나옵니다.
