# 회의록 세컨드 브레인(second brain)으로 에이전트와 팀의 합의 맞추기

## 짝 맞춤 — 무엇을 무엇 자리에 놓았나

| 레퍼런스 | 우리 |
| --- | --- |
| 불편: AI 가 프로젝트 규칙을 몰라 매번 설명 | 불편: 에이전트가 팀이 합의한 것을 몰라 매번 설명 |
| 이름 붙인 개념: 하네스 엔지니어링 | 이름 붙인 개념: 세컨드 브레인 (회의록) |
| 도구 1 — Rules: 코드 작성 규칙 전달 | 도구 1 — 카드: 팀이 합의한 것 전달 |
| 도구 2 — Skills: 작업 자동화 | 도구 2 — 스킬: 회의를 카드로 만드는 일 자동화 |

| 심화: 원본 코드 대신 요약 JSON 을 읽힘 | 심화: 전사 전체 대신 카드를 읽힘 |

## 개요

`레퍼런스: 불편한 장면 → 매번 덧붙이던 말 (인용) → 삽화 → 질문 한 줄 → 개념 이름 → 이 글의 범위`

에이전트와 기획을 논의할 때, 에이전트가 팀에서 이미 합의한 방향을 몰라 같은 설명을 되풀이했습니다. 다른 참조를 먼저 읽은 뒤에는 무슨 요청을 해도 엉뚱한 아이디어와 모듈 사양만 돌아왔습니다.

원하는 답을 얻으려고 매번 이런 말을 덧붙였습니다.

> 아니야 아니야 이런 것을 너에게 제시해달라는 것이 아니야.
> '행위'에 집중을 하라는 거야.

〔삽화 1〕

그래서 이런 생각이 들었습니다. '에이전트가 우리 팀이 합의한 것을 처음부터 알고 있게 만들 수는 없을까?'

사람의 기억 밖에 두는 두 번째 기억을 세컨드 브레인이라고 부릅니다. 이 글은 옵시디언 볼트에서 회의를 카드와 스킬로 쌓아 에이전트가 읽는 기억으로 만든 과정과, 읽는 양을 줄여 본 사례를 다룹니다.

## 카드 / 스킬

`레퍼런스: 디렉터리 트리 → 역할 표 (두 줄)`

```
<프로젝트>/discussions/<회의 날짜>/     ← 카드
skills/meeting-notes/                  ← 스킬
```

| 구성 | 역할 |
| --- | --- |
| 카드 | 팀이 합의한 것 전달 |
| 스킬 | 회의를 카드로 만드는 작업 자동화 |

## 카드

`레퍼런스: 정의 → 설정 코드 → Tip 콜아웃 → 효과`

카드는 회의에서 오간 말을 안건 하나 단위로 잘라 에이전트에게 전하는 노트입니다. 그날 에이전트가 읽은 카드 한 장은 이렇게 생겼습니다.

```markdown
# 1.1 와꾸가 안 잡힌 사람 — 첫 타겟을 어디에 그을까

> **속기 원문** (속기 46–53 · 121–125 · 148–154)
> - 발화자 2 (23:50) *… 기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?*
> - 발화자 1 (32:02) *내가 방금 기준 문서 안에서도 와꾸가 안 나오는 항목들은 왕왕 등장해.*
> - 발화자 1 (32:50) *그러니까 와꾸가 안 잡혔다라는 것은 내가 80%는 나왔는데 20%는 몰라. 그럼 왔고 안 잡힌 거야.*

> **[결정 질문]** 첫 타겟 작업을 "기준 문서는 있는데 일부 항목을 모르는 작업" 으로 그을까, "기준 문서조차 없는 백지 작업" 으로 그을까?
```

> Tip: 주목할 것은 **회의 날짜 폴더**입니다. 모든 회의를 늘 읽히지 않습니다. `discussions/26.10.01` 처럼 그 회의만 가리키면 그 카드만 읽습니다.

이렇게 적어 두면 에이전트는 따로 설명을 듣지 않아도 팀이 그 말을 어떤 뜻으로 쓰는지를, 그 말이 오간 자리째로 가져옵니다.

## Before / After 예시

`레퍼런스: Before (먼저 필요했던 설명 → 요청 → 틀린 결과 → 되풀이) → After (요청 한 줄 → 맞는 결과) → 삽화`

### Before (카드를 읽히기 전)

%% Before 는 **만든 샘플**입니다 (Rin: "가라로 만들어 써라"). 실제 대화 원문이 아닙니다. 사람이 말한 상황("희한한 아이디어, 되지도 않는 모듈 사양")과 에이전트가 스스로 한 말("소프트웨어 기능 모듈 관점으로 빠졌던 실수")에 맞춰 지었습니다. After 는 실제 캡처입니다. %%

요청하기 전에 보통 이런 설명이 먼저 필요했습니다.

```
우리 도구는 문서를 대신 써 주는 게 아니라 같이 짜는 시뮬레이터입니다.
타깃은 무엇을 써야 할지부터 막막한 사람입니다.
기능 말고, 그 사람이 책상에서 실제로 하는 일을 봐 주세요.
```

그러고 나서 "사업계획서를 쓰는 사람이 실제로 무엇을 하는지 정리해 줘" 라고 요청해도, 에이전트는 보통 이런 답을 냈습니다.

```
사업계획서 작성 지원을 위해 다음 세 모듈을 제안합니다.

1. Template Engine — 공고문 양식을 파싱해 섹션 트리를 생성
2. Reference Retriever — 벡터 DB 에서 유사 사업계획서를 검색 (top-k = 5)
3. Draft Generator — 섹션별 프롬프트 체인으로 초안을 생성

추가 아이디어: 실시간 협업 커서, 버전 diff 뷰어, 평가위원 페르소나 채점 봇
```

물은 것은 사람이 하는 일인데, 돌아온 것은 만들 기능의 사양입니다. 결국 이 말을 다시 쳤습니다.

> 아니야 아니야 이런 것을 너에게 제시해달라는 것이 아니야. '행위'에 집중을 하라는 거야.

설명 → 답 → "아니야 아니야" → 다시 설명이 되풀이됐습니다.

### After (카드를 읽힌 뒤)

요청은 이것뿐이었습니다.

```
discussions → 현재 이 내용을 본다면 우리 팀이 어떤 과정을 진행하는지를 알게 될거야.
```

1분 뒤 에이전트는 회의에서 오간 말 셋을 시각과 함께 꺼내 방향을 고쳐 잡았습니다.

## 카드를 만들 때 고려했던 기준

`레퍼런스: 기준 세 개 (소제목이 결론 문장) — 넣지 않을 것 · 겹치지 않게 · 구조를 드러내게`

#### 요약하지 않고 발화 원문과 시각을 붙인다

결론은 "우리 도구는 시뮬레이터다" 한 줄입니다. 에이전트가 꺼내 온 것은 그 한 줄이 아니라 32:50 · 15:04 · 16:23 의 말이었고, 셋 다 카드의 `속기 원문` 칸에 있던 것입니다.

#### 정한 것과 아직 안 정한 것은 겹치지 않게 따로 둔다

- 결정 카드 = 이미 정한 것
- 안건 카드 = 아직 안 정한 것

#### 회의마다 폴더 하나, 카드끼리는 링크로 잇는다

에이전트가 볼트 전체를 뒤지면 관련 없는 노트를 읽습니다. 날짜 폴더와 링크가 길을 정해 줍니다 — 가리킨 결정 카드에서 안건 카드 `1.1` · `1.2` 로 링크가 이어져 있었습니다.

## 도입 후 느낀 변화

`레퍼런스: 변화 세 개 — 설명과 피로가 줄었다 · 누가 물어도 한결같다 · 첫 시도에 맞는다`

#### 다시 설명하지 않게 됐다

"아니야 아니야" 를 고쳐 쓰는 대신 폴더를 가리킵니다.

#### 누가 묻든 같은 합의에서 출발한다

그 말은 회의에서 사람 둘도 23:50 부터 32:50 까지 세 번 되물어 맞춘 말입니다. 에이전트는 그 되물음이 끝난 자리(32:50)를 첫 인용으로 골랐습니다.

#### 첫 답에서 방향이 맞았다

⚠ 한 번의 일입니다. "늘었다" 고 쓸 근거는 아직 없습니다.

## 언제 카드를 쓰면 좋은가

`레퍼런스: 경우 두 개`

#### 팀에만 통하는 말이 있는 경우

"와꾸" · "진심 펀치" 처럼 정의하기 어려운 말로 일하는 팀.

#### 사람과 에이전트가 같은 합의 위에서 일해야 하는 경우

회의에 없던 사람이나 에이전트가 그 뒤의 일을 이어받을 때.

## 스킬

`레퍼런스: 정의 → 스킬 표 (스킬 · 하는 일 · 예시 요청) → 파이프라인 → 한계 인정`

카드가 기록이라면 스킬은 그 기록을 만드는 순서입니다.

| 스킬 | 하는 일 | 예시 요청 |
| --- | --- | --- |
| 회의 정리 | 속기를 읽고 안건 카드 · 결정 카드를 뽑아 작업 공간에 둠 | "이 회의록 정리해줘" |
| 안건 카드 | 아직 안 정한 것을 결정 질문 · 쟁점으로 구조화 | (회의 정리가 부름) |
| 결정 카드 | 이미 정한 것을 결정 · 기한 · 이유로 기록 | (회의 정리가 부름) |
| 지난 회의 점검 | 지난번에 하기로 한 것이 됐는지 점검표를 깖 | "지난 회의 점검해줘" |
| 다시 뽑기 | 사람이 안 고른 카드의 이유로 스킬 사본을 고쳐 다시 뽑음 | "다시 뽑아줘" |

실제 스킬 폴더는 셋입니다 (`meeting-notes` · `pre_meeting_agenda_preparer` · `meeting_decision_recorder`). 점검과 다시 뽑기는 `meeting-notes` 가 받는 요청입니다. 레퍼런스의 표가 다섯 줄이라 요청 단위로 다섯 줄을 맞췄습니다.

회의 정리는 속기를 읽고 끝나지 않고 이런 순서로 돕니다.

```
녹음 · 전사
    ↓
안건 카드 · 결정 카드 뽑기
    ↓
사람이 고름
    ↓
프로젝트의 회의 날짜 폴더로
    ↓
다음 회의에서 점검
```

에이전트가 다 해 주는 것은 아닙니다. 그날 회의는 175발화에서 카드 넉 장이 나왔고 사람이 고른 것은 한 장입니다. 다만 받아 적고 쪼개는 일이 "정리해줘" 한마디로 줄고, 사람은 고르고 다듬는 데만 씁니다.

## 언제 스킬을 쓰면 좋은가

`레퍼런스: 경우 두 개`

#### 순서가 늘 같은 일인 경우

회의는 매번 같은 차례로 정리됩니다.

#### 노트 여러 장을 한 번에 만들어야 하는 경우

회의 하나에서 카드 여러 장이 나옵니다. 한 번에 한 가지 역할로 쪼개야 결과가 믿을 만해집니다.

## 카드를 활용한 컨텍스트 최적화 패턴

`레퍼런스: 한계 제기 → 해법 → 삽화 → 예시 (AS-IS 흐름 · TO-BE 흐름 · 실제 전달 데이터 비교) → 어떻게 구현했나 → [참고] 측정 표 → 수치의 단서`

회의를 쌓다 보면 "전사를 통째로 읽히면 되지 않나" 에 부딪힙니다. 전사는 길고, 안건과 상관없는 말이 섞여 있고, 같은 말을 여러 가지로 받아 적습니다.

그래서 전사 전체가 아니라, 안건에 닿는 발화만 뽑아 시각과 함께 적은 카드를 읽힙니다.

〔삽화 3〕

### 예시: "와꾸가 안 잡혔다" 가 무슨 뜻인지 에이전트가 찾을 때

#### AS-IS: 전사를 통째로

```
요청
  → 35분 53초짜리 전사 175발화를 처음부터 읽음
  → 안건과 상관없는 발화까지 컨텍스트에 들어감
  → 답
```

#### TO-BE: 카드로

```
요청
  → 회의 날짜 폴더의 결정 카드
  → 링크된 안건 카드의 속기 원문 (시각 포함)
  → 답
```

#### 실제 전달 데이터 비교

AS-IS: 전사 원문

```
발화자 2  (23:50)
아니 근데 레퍼런스를 일단 이렇게 이렇게 모았고 기준 문서를 갖고 있다는 거 자체가 왔고가 잡혔다는 거 아니야?
발화자 2  (25:42)
… 저거를 넣고 작업을 시작하는 거 자체가 나는 악구가 잡힌 거라고 얘기를 한다고 …
발화자 2  (31:54)
… 레퍼런스가 있다는 거 자체가 와코가 잡힌 거지.
```

전사는 "와꾸" 를 `왔고` · `악구` · `와코` · `와꼬` 네 가지로 적었습니다.

TO-BE: 카드 (위 `카드` 칸의 그 조각). 제목과 결정 질문에서 "와꾸" 한 가지로 묶여 있습니다.

**카드는 어떻게 만드나요?**

안건 카드 스킬이 속기에서 안건을 가르고, 카드 맨 위에 그 안건이 나온 발화를 옮겨 적습니다.

스킬 문서에 적힌 카드의 틀과 첫 단계입니다 (`skills/pre_meeting_agenda_preparer/SKILL.md` 그대로).

```markdown
# [안건 번호] 안건 제목

> **속기 원문**
> - *<회의 속기에서 발췌한 날것의 발언 원문 그대로 인용>*

## 🎯 핵심 의사결정 포인트 (Decision Checkpoint)
```

## 마무리

`레퍼런스: 관점 전환 한 문장 → 권유 → 다음에 넓힐 방향 → 참고 리소스 → 저자 소개`

예전에는 에이전트에게 잘 설명하는 것이 중요했다면, 지금은 팀이 한 말을 가리킬 수 있게 쌓아 두는 것이 더 중요하다고 느꼈습니다.

한 사람의 설명 솜씨에 기대지 말고, 팀의 합의가 남는 자리를 만들어 보시기를 권합니다.

여기서 한 걸음 더 가면, 다음 회의 전에 지난 합의가 지켜졌는지 에이전트가 먼저 점검하고, 사람이 안 고른 카드로 스킬이 스스로 고쳐지는 데까지 넓힐 수 있습니다.
