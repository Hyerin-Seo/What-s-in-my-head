### 1. 핵심 고민 배경 — "세 번 갈아엎는 작업의 불안감" vs "듀얼 줌 분할 뷰의 시각 피로도"

- **갈아엎기가 기본값인데 받쳐주는 장치 부재**:
  - 복잡한 문서 구조를 아웃라이너로 짤 때 한 번에 완성되는 법은 없으며, *"세 번은 디폴트로 다 갈아엎는"* 작업이 필수적임 (속기: "작업하다 보면 또 아니야. 그래서 이 버전 업 과정은 무조건 필요하더라")
  - 그러나 현재 아웃라이너 화면에는 이전 판을 임시 보관하거나 대조할 장치가 없어, 작업자가 마음 놓고 갈아엎지 못하고 불안해함
- **수동 듀얼 줌(Dual Zoom) 분할 화면의 극심한 피로도**:
  - 현재는 이전 버전(8·9번 노드)과 새 버전(2·3번 노드)을 비교하기 위해 화면을 반반 쪼개 각각 줌 인해 두고 사람 눈으로 대조하고 있음
  - 이는 작업 영역을 반토막 낼 뿐 아니라, *"바뀐 포인트를 찾기도 어렵고 전혀 편해졌다는 느낌을 받을 수가 없는"* 극심한 인지적 병목을 초래함 (발화자 2: "이걸 분할 뷰를 꼭 왜 해야 되는지도 모르겠어요")

### 2. 선택지 비교 및 쟁점 (A vs B vs C)

| 구분 | 선택지 A (권장: 줌 안 버전 탭 / EXP01) | 선택지 B (캔버스 플립 뷰 전환 / EXP02) | 선택지 C (전체 트리 Git Diff 비교) |
| :--- | :--- | :--- | :--- |
| **방식** | 특정 노드로 줌 인 진입 시 헤더 밑에 `[v1] [v2] [+]` 탭을 두고, `Alt + 1, 2` 단축키로 제자리에서 무지연 전환 대조 | 1차원 수직 아웃라인을 단축키(`Ctrl + Space`)로 2차원 캔버스(보드뷰)로 화면 플립 전환하여 여러 갈래를 사방으로 펼치고 가지치기 | 전체 문서 트리에 Git 스냅샷 엔진을 물려 초록줄(추가)·빨간줄(삭제) Diff 뷰어 제공 |
| **장점** | - 시선 분산 및 창 쪼개기 없음 (In-situ 대조)<br>- 개발 공수 최소 (가장 작은 걸음)<br>- 현재 손으로 하는 스테이징을 그대로 흡수 | - 1차원 트리의 답답함을 벗어나 전체 분기 조망<br>- 불필요한 브랜치를 시각적으로 뭉텅 잘라내는(Pruning) 손맛 우수 | - 완벽한 시계열 복구 및 롤백 보장<br>- 개발자에게 익숙한 정밀 추적 |
| **단점/부담** | - 3개 이상의 거대 분기를 한눈에 조망하기는 어려움<br>- 줌 인 상태에서만 동작 | - 캔버스 ↔ 아웃라인 양방향 동기화 사양 필요<br>- 보드뷰 카드 레이아웃 렌더링 부하 | - 개발 난이도가 너무 높고 사양이 꼬임 (이미 1차에서 걷어냄)<br>- 트리의 '이동'이 삭제+추가로 깨져 보임 |

### 3. 검증 실행 방향 및 집중 과제

- **사용성 프로토타입 검증 축 (Rin)**:
  - `EXP01`(줌 안 버전 탭)과 `EXP02`(캔버스 플립 뷰) 중 어느 인터랙션이 작업자의 "갈아엎기 피로도"를 더 획기적으로 낮추는지 프로토타입 사용성 테스트 진행
  - 노드 내 버전 전환 시 단축키(`Alt+1, 2`) 조작감 및 최종 1개 버전 채택 후 줌 아웃 시 부모 트리 반영 UX 플로우 점검
- **프론트엔드 에디터 엔진 축 (민규 서)**:
  - 아웃라이너 노드 데이터 스키마에 국소 서브트리 스테이징(`versions: { v1: [...], v2: [...] }`) 구조를 지원할 수 있는 최소 인터페이스 정의
  - 기존 스켈레톤 보드뷰(React Flow)와의 전환 브릿지 프로토타입 동작성 타진
