### 1. 핵심 고민 배경 — "에이전트의 구조 파괴" vs "인터페이스 병목과 강제 메커니즘"

- **에이전트 개입 시 트리 붕괴 문제**:
  - 사람이 정교하게 짠 위계 트리에 AI가 개입해 글을 쓰거나 수정하게 하면 뼈대와 본문을 섞어버리고 전체 구조를 박살냄 (속기: "입마가 다 깨... 얘가 끼면서부터는 다 박살이 나는 거")
  - 에이전트는 일반 마크다운 노트를 '글'로 읽고 '글'로 고치기 때문에, 어디까지가 뼈대(구조)이고 어디까지가 본문(내용)인지 구분하지 못함 ("이 텍스트랑 이 뼈대는 섞이면 안 되거든. AI가 뼈대로 인식하는 거랑 텍스트로 인식하는 건 작업 효율이 완전히 다름")
- **진짜 병목은 프롬프트가 아니라 편집 인터페이스**:
  - 위계 중심 프롬프팅으로 구조화 자체는 시킬 수 있으나, 인간과 AI가 함께 편집·수정하는 인터페이스가 부재한 것이 본질적 병목임
  - 옵시디언에서 프롬프트/자연어로 "아웃라인 수정해라" 하면 구조를 깨먹고 제대로 수행하지 못하지만, Workflowy의 전용 MCP 서버를 물려 노드 단위 API(`tree_patch`, `tree_seek` 등)로 통제했을 때는 엄격한 트리를 완벽히 유지하며 작동함을 실증함

### 2. 선택지 비교 및 쟁점 (A vs B vs C)

| 구분 | 선택지 A (권장: 볼트/온톨로지 MCP 서버) | 선택지 B (옵시디언 전용 커뮤니티 플러그인) | 선택지 C (프롬프트/스킬 기반 자연어 규칙 강제) |
| :--- | :--- | :--- | :--- |
| **방식** | Workflowy MCP처럼 노드 ID 기반 탐색(`tree_seek`) 및 패치(`tree_patch`) API를 제공하여 에이전트의 직접 텍스트 덮어쓰기 원천 차단 | 옵시디언 내부 UI(줌인, 아웃라인 접기)와 백단 로직을 결합한 독자 플러그인 제작 및 API 노출 | `CLAUDE.md`, 스킬, 린터 규칙 등으로 트리 들여쓰기 문법을 지키도록 자연어 지시 |
| **장점** | - 호스트/모델 비의존적 (어떤 에이전트든 동일 제어)<br>- 파일 직접 오염 완전 차단<br>- 검증된 Workflowy MCP 패턴 직결 | - 사람의 시각적 UI(줌/접기)와 에이전트 동작이 한 화면에서 일치<br>- 옵시디언 네이티브 UX 완성도 | - 개발 공수 최소 (문서/규칙만 작성)<br>- 즉시 실험 가능 |
| **단점/부담** | - 사람용 조작 UI는 별도 구현 필요<br>- MCP 통신 오버헤드 | - 옵시디언 API 의존도 증가<br>- 개발 난이도 및 유지보수 비용 큼 | - 에이전트의 환각/실수로 트리 붕괴 빈발 (실패 검증 완료)<br>- 작업 효율 급감 |

### 3. 검증 실행 방향 및 이번 주 집중 과제 (Decision 01 연계)

- **에이전트 하네스/MCP 축 (민규 서)**:
  - 이미 확보한 Workflowy MCP 13종 도구 명세(특히 `tree_patch`, `tree_seek`)를 분석하여, 옵시디언 볼트/온톨로지에 이식 가능한 최소 트리 조작 MCP 인터페이스 규격 도출
  - 에이전트가 노트를 통째로 overwrite하지 않고, 특정 노드 ID 하위에 '자식 노드 추가 / 이동 / 텍스트 수정'만 가능하도록 하는 경계 프로토콜 정의
- **사용성 및 콕핏 인터랙션 축 (Rin)**:
  - 작업자가 에이전트와 트리를 함께 수정할 때, 화면에서 트리 구조와 본문 텍스트가 어떻게 시각적으로 분리되어야 하는지 와꾸 정의
  - 에이전트에게 "이 노드 밑에 써줘", "이 구조는 손대지 마"라고 지시하는 콕핏형 인터랙션 플로우 구체화

### 4. 10월 09일 마일스톤 판정 기준 (DoD Checklist)

- [ ] Workflowy MCP(`tree_patch` 등) 핵심 패턴을 옵시디언 볼트에 접목할 최소 트리 제어 도구(MCP 또는 스크립트) 사양 정의
