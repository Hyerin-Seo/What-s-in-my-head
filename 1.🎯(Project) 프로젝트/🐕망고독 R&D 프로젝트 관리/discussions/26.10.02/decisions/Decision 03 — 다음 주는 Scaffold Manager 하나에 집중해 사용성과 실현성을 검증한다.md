# 🎯 Decision 03 — 다음 주는 "Scaffold Manager" 하나에 집중해 사용성과 실현성을 검증한다

## 1. 결정 내용 (What)

> [!check]
> - **단일 핵심 모듈 집중**: 문서 작업 프로세스를 '디깅(자료 조사)'과 '스토리라이닝(와꾸 짜기)'으로 양분하고, 이미 대안이 많은 디깅(Resource Manager)을 떼어내고 도움을 전혀 못 받는 **Scaffold Manager(SM) 하나에만 다음 주(10.05~10.09) 동안 집중**
> - **검증 축 분할 (역할 분담)**: Rin은 사용성(UX) 검증을 주도하고, 민규 서는 백단 구현 및 실현성(Feasibility) 검증을 메인으로 담당
> - **UI 배제 및 핵심 엔진 선행**: 복잡한 웹 UI 구축 없이 파일 디렉토리 객체화(레시피·아웃라인·세그먼트) + 옵시디언/안티그래비티 CLI 하네스 기반으로 즉시 조작감 검증

---

## 2. 결정 사유 (Why)

1. **진짜 병목 구간의 집중 돌파**: 자료 조사(디깅)는 사용자들이 이미 NotebookLM 등 기존 AI 도구로 80% 이상 해결하고 있으나, 전체 뼈대(와꾸)를 짜는 스토리라이닝 단계는 여전히 방치되어 있어 가장 혁신과 검증이 시급함
2. **단일 실패 리스크 조기 격파**: SM을 검증해 내면 제품 개발에서 가장 불확실성이 크고 위험한 마일스톤을 단숨에 통과할 수 있음
3. **불필요한 프론트 개발 공수 제거**: 파일 시스템 디렉토리 구조만으로도 SM 객체 조작의 본질을 검증할 수 있으므로, 껍데기(UI)를 만드는 데 시간을 쓰지 않고 다음 주 내에 승부를 봄

---

## 3. 실행 가이드라인 (Boundary & Criteria)

- **집중 대상 (Do)**:
  - 타깃 문서: 비문학, 보고서 형식, 정답이 정해진 규격 문서 (특허 문서, 법률 주장서, UI 사용 설명서 등)
  - 검증 방식: 파일 디렉토리 구조화 + 안티그래비티/클로드 연동 하네스 조작
  - 역할: 민규 서(하네스 구현 및 데이터 추출), Rin(실전 뉘앙스 전달 및 사용성 테스트)
- **제외 대상 (Don't)**:
  - Resource Manager(RM): 이번 스프린트 범위에서 제외 ("RM 떼고")
  - 복잡한 창작 영역: 단계와 뉘앙스 분기가 복잡하여 비문학 규격 문서 이후로 이관
  - 화려한 프론트엔드 UI: 파일 디렉토리 검증 완료 전까지 UI 작업 배제
- **완료 판단 기준 (DoD)**:
  - SM 하네스를 붙여 안티그래비티/클로드와 작업할 때, 사용자가 요구한 주제 안에서 탈선 없이 "문서 작업이 확실히 편해진다"고 체감하는 것 (10월 09일 마일스톤)
