## 1부. 이해한 것

### 1-1. 문서들의 관계

```
린 캔버스 01 (v1)      → 문제 정의 + Stage 1 조사 완료 + Stage 2 보완 조사 계획
      ↓ 문제를 다시 정의함
린 캔버스 01 v2        → "정보 처리의 늪" + Cursor 모델
      ↓ 9개 블록으로 펼침
린 캔버스 카드 01      → 린 캔버스 9블록 전체 (SSOT)
      ↓ 지표·리스크만 뽑음
Outcome 01 ver1       → 팀이 합의할 북극성 지표 + 4대 리스크
```

### 1-2. 지금 문서가 말하는 제품 (v2 · 카드 · Outcome 기준)

- **컨셉** — `Cursor for Document Building`. Cursor 가 코드베이스를 인덱싱하고 Composer 로 여러 파일을 한 번에 고치듯,
  백데이터 10~20개를 통째로 읽어 30~50장짜리 규격 문서(사업계획서 · R&D 계획서 · 입찰 제안서)를 한 번에 만든다.
- **문제** — 진짜 병목은 타이핑이 아니라 **자료를 읽고 · 찾고 · 대조하는 정보 처리 부담**.
  - 자료의 늪: RFP · 통계 · 논문을 오가며 수치를 찾느라 전략을 고민하기 전에 지친다
  - 떠넘기는 챗봇: ChatGPT · Copilot 은 사람이 읽고 발췌해 줘야 작동한다
  - 맥락 파편화: 창 30개를 오가다 "3장에서 무슨 주장을 하려 했지?" 를 잃는다
- **고객** — 30~50장 규격 문서를 쓰는 모든 작성자(Document Builders). 페르소나는 1인 창업가 · PM · 연구원.
- **해법 3가지**

  | Cursor | 문서 엔진 |
  | --- | --- |
  | `@Docs` · `@Codebase` | **@Reference 딥리딩** — 엔진이 자료를 다 읽고 슬롯별로 팩트 추출 |
  | Composer | **Document Composer** — 의도 한 줄로 30장 전체 슬롯을 한 번에 직조 |
  | 컴파일러 에러 검출 | **1:1 앵커** — 모든 수치·문장이 원본 쪽·줄에 연결, RFP 필수항목 누락 검출 |

- **북극성 지표** — 인덱싱 30초 · 문서 완성 3~4일 → 1시간 · 근거 결속 100% · 전환 의향 70% 이상.
- **4대 리스크** — 가치(1순위, 민규 서) · 사용성(Rin) · 실현 가능성(Antigravity) · 사업성(민규 서).
- **다음 단계** — 1주일 스파이크: PDF 5개 인덱싱 → 10장 계획서 직조 → 문장 클릭 시 원본으로 이동.
  마감이 있는 실사용자 5명에게 현장 테스트. 2D 캔버스 등 겉 UI 는 개발 중단.
- **수익 · 비용** — 월 $20~$50 구독 · 팀 · 엔터프라이즈 / 토큰 원가 · 파싱 인프라.

### 1-3. v1 → v2 에서 바뀐 것

| | v1 | v2 · 카드 |
| --- | --- | --- |
| 한마디로 | 에이전트와 **같이 일하기**가 괴롭다 | **자료 읽기**가 괴롭다 |
| 세 고통 | 새 자료 넣으면 컨셉 붕괴 · 다그침 반복 · 환각 검증 | 자료의 늪 · 떠넘기는 챗봇 · 맥락 파편화 |
| 고객 | 머릿속에 컨셉이 선 전문 작성자 | 자료에 짓눌린 모든 작성자 |
| 솔루션 | 레퍼런스(족보) 역공학 → 슬롯 고정 스캐폴딩 + 2D 캔버스 | Cursor 모델, 2D 캔버스 뺌 |
| 검증 | Stage 1 완료 + Stage 2(확증 편향 점검 · 지불 의향) 계획 | 조사 언급 없음 |

Outcome ver1 은 두 버전이 섞여 있습니다 — "컨텍스트 붕괴" 는 v1 의 고통, 나머지는 v2 입니다.
카드 파일 이름도 아직 v1 컨셉("레퍼런스 역공학 기반 무언의 스캐폴딩 엔진")입니다.

### 1-4. Rin 이 이해한 방향 — 민규 서와 맞는지 확인 필요

Rin 의 외주 개발 경험에서 나온 해석입니다.
외주 요청은 기능이 거기서 거기이고 튜닝 · 크기 · 용도 · 디자인만 조금씩 다릅니다. 그래서 예전 프로젝트를 찾아
인피니티 스크롤 같은 본체를 뜯어 와서 이식하고, 버그를 맞추고, CSS 를 맞추는 데 공수가 많이 들었습니다.
Cursor 는 **이식 · 버그 맞추기**는 크게 줄여 줬지만, **"예전에 어디서 짰더라"** 를 찾는 것은 여전히 사람 몫입니다.

문서도 같다고 봤습니다. 대부분의 업무 문서는 빈 종이에서 시작하지 않습니다.

| 새 문서의 덩어리 | 예시 | 하는 일 |
| --- | --- | --- |
| 물려받을 것 | 회사 템플릿 · 양식 · 목차 · 검증된 문단 | 가져다 씀 |
| 고칠 것 | 포트폴리오 성공사례 · 실적 수치 · 연도 | 최신으로 갱신 |
| 새로 찾을 것 | 이번 고객 · 공고에 맞는 새 자료 | 새 소스에서 찾아 넣음 |

정부과제만이 아니라 회사소개서 · 포트폴리오 · 제안서 · IR 덱처럼 **같은 종류를 반복해서 새로 쓰는 문서** 전부입니다.
이렇게 보면 "문서계의 Cursor" 는 **"백데이터를 대신 읽어 준다"(v2)가 아니라 "지난 문서를 출발점으로 새 문서를 만든다"** 입니다.
ChatGPT · Deep Research · NotebookLM 은 빈 문서에서 새로 쓰고, Cursor 는 있는 코드를 고칩니다.
"읽기" 는 세 번째 덩어리를 채우는 하위 기능이 됩니다.

### 1-5. 읽기 · 발췌 · 출처 — 캔버스를 버리면 어떻게 길을 안 잃나

**Heptabase · MarginNote** 가 여러 자료를 읽고 발췌하고 출처를 다는 일을 하는 도구입니다.
PDF 에서 하이라이트한 조각이 카드가 되고, 카드를 누르면 원문 위치로 돌아갑니다. **이 정도는 망고독도 당연히 지원해야 한다**고 봤습니다.

그런데 둘 다 **캔버스**입니다. 발췌를 **사람이 직접** 하니, 조각 수십 개를 공간에 펼쳐 놓고 공간 기억에 기댑니다.
v2 는 캔버스를 뺐는데, 엔진이 읽고 발췌한다면 사람에게 필요한 화면이 **탐색하는 화면에서 검토하는 화면**으로 바뀝니다.
Cursor 도 코드베이스를 캔버스에 펼치지 않습니다. 에이전트가 찾아오고, 사람은 결과(diff)를 받아들일지 버릴지만 정합니다.

캔버스 없이 길을 안 잃는 방법은 **길잡이를 "자료의 지도" 에서 "만들고 있는 문서의 목차" 로 바꾸는 것**입니다.

| 방식 | 어떻게 길을 안 잃나 | 참고할 도구 |
| --- | --- | --- |
| 목차가 지도 | 왼쪽에 새 문서의 목차(슬롯), 칸을 고르면 옆 패널에 **그 칸에 연결된 발췌만** | Scrivener (바인더 + 리서치 폴더 + 화면 분할) |
| 표(매트릭스) | 행 = 자료, 열 = 새 문서의 칸, 칸마다 출처 달린 발췌. 전체를 한 화면에 | Hebbia Matrix, Elicit |
| 자료 · 채팅 · 노트 3단 | 인용에 마우스를 올리면 원문 문단이 뜸 | NotebookLM |
| 옆에 쌓아 두기 | 본문은 두고 참고 페이지를 오른쪽 사이드바에 쌓음 | Roam Research 사이드바, VS Code Peek |
| 원문 왕복 | 발췌를 누르면 PDF 해당 쪽으로, 거기서 다시 원래 자리로 | Zotero (PDF 주석 → 노트), 옵시디언 PDF++ |

1-4 의 "지난 문서 + 갱신 + 새 자료" 와 맞물리는 것은 **목차가 지도 + 표** 조합입니다.

```
              │ 1. 회사 소개 │ 2. 문제 정의 │ 3. 시장 규모 │ 4. 성공사례 │
──────────────┼─────────────┼─────────────┼─────────────┼────────────┤
작년 계획서    │ ✅ 물려받음  │ ✏️ 고칠 것   │ ⚠️ 수치 낡음  │ ✏️ 갱신    │
이번 공고문    │             │ 📌 필수 항목 │             │            │
시장 리포트 A  │             │             │ 📎 p.12 표   │            │
```

- 열 = 새 문서의 목차 (길잡이) · 행 = 가져오는 소스 · 칸 = 엔진이 뽑은 발췌와 출처, 사람은 받아들일지 버릴지만
- 칸을 누르면 원문으로 가고, 돌아오면 다시 이 표

**짚을 점** — Heptabase · MarginNote 사용자는 **발췌하는 과정에서 생각을 정리**합니다. 엔진이 발췌를 대신하면 그 과정이 사라져
"빠르긴 한데 내가 쓴 것 같지 않다" 가 나올 수 있습니다. 사용성 리스크(Rin)의 핵심 질문이 될 것 같습니다.

### 1-6. 참고 도구 살펴본 것 — Hebbia · Elicit · Scrivener (2026-09-29)

1-5 의 "목차가 지도 + 표" 가 실제로 어떻게 생겼는지 사이트를 같이 봤습니다.

#### Hebbia Matrix — 자료 × 질문 표 (hebbia.com)

![[망고독 참고 — Hebbia Matrix.png]]

- 금융 분석가용. **행 = 회사**(회사마다 원본 파일 여러 개), **열 = 알고 싶은 질문**(재무 · 레버리지 · 신용등급 · 인수 · 리스크 · 추천 피치 앵글)
- **칸마다 AI 가 원본을 읽고 답을 채움** — 수치와 근거가 같이 들어감. 딜 단위 Project 로 파일 수천 개를 묶고, 결과는 표 · PowerPoint · 문서로
- **가져올 점** — 캔버스 없이 파일 수백 개를 한 화면에서 다루는 방법. 사람은 자료를 돌아다니지 않고 **질문(열)을 정하고 칸을 검토**. 망고독은 열을 "새 문서의 목차 칸" 으로
- **다른 점** — Hebbia 의 결과물은 분석 표. 우리는 정해진 양식의 **긴 문서 한 편**이라, 표는 중간 작업판이고 문서로 엮는 단계가 따로 필요

#### Elicit — 문장 단위 출처 · 표 · 라이브러리 (elicit.com)

![[망고독 참고 — Elicit 차별점.png]]

- 논문 연구용. 논문 최대 1,000편 · 데이터 포인트 20,000개를 한 번에 분석
- 스스로 내세우는 차별점이 우리와 겹침 — **문장 단위 인용**(Transparency), **채팅을 넘어선 표**(More than chat)
- **Library** — 찾은 자료를 쌓아 두고 다음 프로젝트에서 다시 씀 (2026-09-17 사람 · 에이전트 공유 허브로 바뀜)
- **가져올 점** — "발췌 + 출처" 는 이미 **표준 기능**. 이것만으로는 차별점이 못 됨. Library 는 "과거 자산 재사용" 의 연구판
- **다른 점** — 재료가 **외부 논문**. "지난번 **내** 계획서, **우리 회사** 템플릿" 은 안 다룸

#### Scrivener — 목차가 지도인 긴 글 편집기 (literatureandlatte.com)

![[망고독 참고 — Scrivener 자료를 원고 옆에.png]]

- 소설가 · 논문 저자 · 변호사가 쓰는 긴 글 편집기. AI 도구가 아님
- **바인더** — 원고를 조각(장면 · 챕터 · 논점)으로 나누고 목차에서 끌어서 순서를 바꿈
- **자료를 손 닿는 곳에** — PDF · 웹페이지 · 사진을 작업 중인 원고 **바로 옆에** 띄움 (위 그림)
- **Scrivenings** — 조각별로 쓰다가 여러 조각을 한 문서처럼 이어서 편집
- **Compile** — 쓰는 동안은 편한 서식, 내보낼 때 **제출 규정에 맞는 서식**(Word · PDF 등)으로.
  아래 그림은 같은 원고가 편집 화면 · 원고 제출용 · 책 조판 세 가지로 나오는 모습입니다 (overview 페이지의 "Getting it out there")

![[망고독 참고 — Scrivener Compile.png]]

- **가져올 점** — ① 캔버스 없이 긴 문서를 다루는 **"목차가 지도" 의 원조** ② Compile 이 **양식 문제의 힌트**: 내용은 칸 단위로 쓰고 공고 양식 · 회사 템플릿은 **내보낼 때 입힘**. 같은 내용을 A 공고 양식, B 회사 양식으로

#### 셋을 합치면

```
Scrivener 의 뼈대      목차(칸)가 지도, 자료는 옆에, 양식은 내보낼 때 입힘
  + Hebbia 의 작업판   자료 × 칸 표, AI 가 칸을 채우고 사람은 검토
  + Elicit 의 신뢰     문장 단위 출처, 쌓아 두고 다음에 다시 쓰는 라이브러리
```
