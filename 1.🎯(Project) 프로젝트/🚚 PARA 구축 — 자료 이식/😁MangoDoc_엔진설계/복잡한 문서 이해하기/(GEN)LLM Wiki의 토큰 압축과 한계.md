LLM 에이전트 시스템에 위키(Wiki) 형태의 아키텍처나 지식 그래프(Knowledge Graph, KG), 온톨로지를 결합한 RAG(검색 증강 생성)를 도입했을 때 토큰이 획기적으로 절약되고 정보가 압축되는 이유는, '정보의 밀도 최적화'와 '컨텍스트의 적시 로딩(Just-in-Time Loading)'으로 요약할 수 있습니다.

LLM이 모든 지식을 컨텍스트 윈도우에 우겨넣고 스스로 처리하게 만드는 대신, 외부의 구조화된 데이터베이스에 연산과 기억의 부담을 오프로딩(Offloading)하기 때문입니다. 구체적인 논거는 다음과 같습니다.

## 1. 자연어의 중복 제거와 '구조적 압축' (KG & 온톨로지)

우리가 사용하는 자연어(문서, 매뉴얼, 위키백과 텍스트 등)는 정보 전달 측면에서 보면 빈 공간이 아주 많습니다. 수식어, 조사, 맥락을 이어주기 위한 중복 문장 등 '토큰 낭비'가 심합니다.

지식 그래프와 온톨로지는 이 자연어를 **`(주어, 서술어, 목적어)` 형태의 트리플(Triple) 구조**로 압축합니다.

* **자연어 (수십 토큰):** "스티브 잡스는 1976년에 스티브 워즈니악과 함께 캘리포니아 쿠퍼티노에서 애플 컴퓨터를 창립했습니다."
* **지식 그래프 (최소 토큰):** `(Apple, FoundedBy, Steve Jobs)`, `(Apple, FoundedIn, 1976)`

에이전트가 특정 팩트를 조회할 때, 길고 장황한 텍스트 뭉치를 읽는 대신 고도로 압축된 JSON이나 트리플 형태의 그래프 데이터를 반환받게 됩니다. 이는 동일한 정보량을 훨씬 적은 프롬프트 토큰으로 LLM에 주입할 수 있음을 의미합니다.

## 2. '선택적 컨텍스트 주입'을 통한 윈도우 낭비 방지 (RAG + Wiki)

에이전트가 복잡한 문제를 해결할 때 전체 백그라운드 데이터를 프롬프트에 넣는 방식(Long-context 방식)은 토큰 비용을 기하급수적으로 증가시킵니다.

* **모노리틱(Monolithic) 접근:** 100페이지짜리 문서를 통째로 프롬프트에 넣고 "여기서 답을 찾아봐"라고 지시합니다. (수만 토큰 소모)
* **RAG / 위키 구조 접근:** 정보가 청크(Chunk) 단위나 위키의 '페이지' 단위로 쪼개져 있습니다. 에이전트는 현재 추론 단계에 정확히 필요한 특정 문서(또는 노드)만 검색(Retrieve)하여 읽어 들입니다. (수백~수천 토큰 소모)

위키 아키텍처는 문서 간의 하이퍼링크나 위계를 제공하므로, 에이전트가 백과사전을 찾듯 꼭 필요한 페이지만 '조회(Lookup)'하고 빠지는 식으로 토큰 사용량을 극도로 제한할 수 있습니다.

## 3. 온톨로지 기반 정밀 필터링 (쓰레기 토큰 유입 차단)

일반적인 벡터 임베딩 기반의 RAG는 단어의 '의미적 유사성'만 보기 때문에, 정답과 무관하지만 비슷한 단어가 들어간 문서들(Noise)까지 몽땅 가져와 프롬프트 토큰을 낭비하는 경우가 잦습니다.

반면, 온톨로지는 개념 간의 계층(Hierarchy)과 관계(Relationship)가 명확히 정의된 스키마를 가집니다.
에이전트가 "A 회사의 자회사 중 B 산업군에 속한 기업만 찾아줘"와 같이 그래프 쿼리(예: Cypher, SPARQL)를 날리면 데이터베이스 단에서 이미 필터링이 끝난 순도 100%의 데이터만 LLM에게 전달됩니다. 쓸데없는 컨텍스트가 섞여 들어오지 않으니 토큰이 절약되고 할루시네이션(환각)도 줄어듭니다.

## 4. 에이전트 메모리 오프로딩 및 캐싱 (다시 생각하지 않기)

'LLM Wiki' 아키텍처의 강력한 점은 단순히 읽기만 하는 것이 아니라 쓰기(Write/Update)가 가능하다는 점입니다.

에이전트가 복잡한 로우 데이터를 분석해 어떤 결론이나 요약을 도출했다면, 이를 즉시 위키 페이지나 KG의 새로운 노드로 기록(캐싱)해 둡니다. 다음번에 다른 에이전트나 사용자가 유사한 질문을 하면, 방대한 원본 데이터를 다시 읽고 분석하며 수천 토큰을 태우는 대신, **미리 압축해 둔 위키 페이지만 읽고 바로 답변**합니다. 연산 과정과 지식을 외부에 저장해 두고 재활용함으로써 누적 토큰 비용을 획기적으로 낮추는 것입니다.

---

> **요약하자면:** 온톨로지와 KG는 데이터 자체의 **포맷을 압축**하고, RAG와 위키 구조는 에이전트가 필요한 정보만 가져가도록 **검색 범위를 압축**하며, 업데이트된 지식 베이스는 **중복 추론 과정을 압축**합니다.



==============

정확한 지적입니다. 실무에서 LLM 에이전트나 구조화된 RAG 시스템을 구축해 본 엔지니어들이 가장 뼈저리게 느끼는 '이상과 현실의 괴리'가 바로 그 지점입니다.

이론적으로는 최단 경로로 정답을 찾아 토큰을 아껴야 하지만, 실제 환경에서는 말씀하신 이유들로 인해 오히려 '토큰 먹는 하마'가 되거나 단순 텍스트 검색(Vector Search)보다 못한 결과를 내는 경우가 많습니다. 구체적으로 어떤 상황에서 이런 역효과가 발생하는지 짚어보겠습니다.

## 1. 에이전트의 '탐색 루프(Navigation Loop)'에 빠짐

에이전트는 보통 "생각(Thought) -> 행동(Action/Search) -> 관찰(Observation)"의 사이클을 반복(ReAct 패턴)하며 답을 찾습니다. 문제는 에이전트가 위키나 지식 그래프에서 길을 잃었을 때 발생합니다.

* **히스토리 누적 폭발:** 에이전트가 엉뚱한 노드나 페이지를 검색하고 실패하면, 그 "실패한 과정" 자체가 컨텍스트 메모리에 누적됩니다.
* **비효율의 악순환:** 3~4번 연속으로 원하는 정보를 찾지 못하면, 실패한 검색 결과들이 프롬프트에 쌓여 결국 원본 문서를 통째로 넣는 것보다 훨씬 더 많은 토큰을 소모하게 됩니다. "압축된 정보"를 찾기 위해 "방대한 탐색 로그"를 LLM에게 계속 먹이는 모순이 발생합니다.

## 2. '풀스캔(Global Search)' 요청 시의 치명적 한계

지식 그래프나 위키 구조는 "모래사장 속 바늘 찾기(Targeted Lookup)"에 최적화되어 있습니다. 반대로 사용자가 "모래사장의 전체적인 성분 비율 분석(Global Aggregation)"을 요구하면 구조화된 시스템은 심각한 병목을 일으킵니다.

* **요약/통계 요청의 역설:** "이 회사의 10년 치 재무제표 전반의 흐름을 요약해 줘" 또는 "문서 전체에서 가장 많이 언급된 불만 사항 3가지는?" 같은 질문이 들어올 경우, 에이전트는 KG의 수많은 노드를 하나하나 탐색하려 들거나, 관련된 수백 개의 위키 페이지를 전부 열어보려 시도합니다.
* 이럴 때는 잘게 쪼개진 그래프 데이터를 순회하는 것보다, 차라리 롱 컨텍스트(Long-context) LLM에 전체 문서를 한 번에 때려 넣고 한 번의 추론으로 끝내는 것이 연산 시간(Latency)과 토큰 측면에서 훨씬 저렴하고 정확합니다.

## 3. 스키마(Schema) 주입과 쿼리 변환의 숨은 비용

자연어를 그래프 쿼리(Cypher 등)나 정형화된 API 호출로 변환하려면, LLM에게 "우리 시스템의 DB 구조(Schema)는 이렇게 생겼어"라고 먼저 알려주어야 합니다.

* **오버헤드 발생:** 지식 그래프의 엔티티 종류와 관계(Relationship) 정의가 복잡해질수록, 매 요청마다 시스템 프롬프트에 주입해야 하는 스키마의 토큰량 자체가 수천 토큰에 달하게 됩니다.
* 배보다 배꼽이 더 커지는 현상: 정작 꺼내올 정보는 50토큰인데, 쿼리를 제대로 생성하게 만들기 위해 2,000토큰짜리 가이드를 매번 읽혀야 하는 셈입니다.

## 4. 정보 파편화로 인한 문맥 상실 (Lost in Fragmentation)

자연어의 중복을 제거하고 핵심만 `(주어, 동사, 목적어)`로 압축하다 보면, 글이 가지는 미묘한 뉘앙스나 행간의 의미가 증발해 버립니다. 에이전트가 조각난 정보들을 가져와 퍼즐을 맞추더라도, 애초에 원본 텍스트가 주었던 자연스러운 문맥이 없기 때문에 엉뚱한 결론(할루시네이션)을 도출하는 경우가 생깁니다.

---

> **현실적인 해결책 (하이브리드 라우팅)**
> 결국 완벽한 단일 시스템은 없습니다. 최근의 아키텍처는 사용자의 의도를 먼저 파악하는 **라우터(Router) 에이전트**를 둡니다.
> * **특정 팩트 검색:** 지식 그래프 / 위키 검색 활용 (토큰 절약)
> * **전체 문맥 요약 / 풀스캔:** 전체 원본 문서 또는 대규모 문서 청크를 한 번에 주입 (탐색 비용 방지)
> 


=============

질문의 핵심을 아주 정확히 짚으셨습니다. 아무리 훌륭한 검색 도구와 지식 그래프를 갖춰도, 결국 사용자의 요청을 분석해 **'어떤 도구를 집어 들 것인가'를 결정하는 라우터(Router)의 쿼리 분류 능력**이 전체 시스템의 효율과 직결됩니다.

요청하신 4가지 단계에 따라, 쿼리를 어떤 카테고리로 나눌 수 있는지 체계적으로 분석해 보겠습니다.

---

## 1. 조사 및 탐색 방법론 수립

공신력 있는 기준을 찾기 위해, 저는 다음과 같은 두 가지 축을 기준으로 삼아 RAG와 에이전트 시스템 분야의 최신 문헌과 산업 표준을 탐색하는 방법론을 설정했습니다.

* **학술적 접근 (Information Retrieval & QA):** 정보 검색론과 기계 독해(MRC) 분야에서 전통적으로 사용자의 질문을 어떻게 분류해 왔는지 학술 논문과 벤치마크 데이터셋(예: HotpotQA, QASPER 등)의 분류 체계를 살핍니다.
* **산업적 접근 (RAG Frameworks):** 실무에서 가장 널리 쓰이는 프레임워크인 **LlamaIndex, LangChain**의 라우팅 설계 패턴과, 지식 그래프 검색의 최근 표준을 제시한 **마이크로소프트의 GraphRAG** 백서를 주요 근거 자료로 채택합니다.

## 2 & 3. 쿼리 분류의 논거(기준)와 공신력 있는 분류 체계

### 분류의 기준과 논거 (왜 이렇게 나누는가?)

쿼리를 분류하는 가장 핵심적인 논거는 데이터의 '공간적 범위(Scope)'와 추론의 '인지적 깊이(Depth)'입니다.
질문에 답하기 위해 단 하나의 문서만 찔러봐도 되는지(Local) 아니면 문서 전체를 뒤져야 하는지(Global), 단순한 사실의 추출인지(Single-step) A와 B의 관계를 엮어야 하는지(Multi-hop)에 따라 필요한 토큰과 파이프라인이 극명하게 갈리기 때문입니다.

이를 바탕으로 업계에서 대중적으로 인정받는 쿼리 유형은 크게 4가지로 분류됩니다.

| 쿼리 유형 (Category) | 특징 및 논거 | 적합한 탐색 라우팅 전략 |
| --- | --- | --- |
| **Factoid (단일 팩트 검색)** | "2023년 A회사의 영업이익은?"<br>

<br>특정 엔티티나 구체적인 수치, 사실을 묻는 질문. (단일 노드 탐색) | **Vector RAG / KG 직접 조회.**<br>

<br>연산이 필요 없으므로 가장 빠르고 토큰 소모가 적은 도구 사용. |
| **Multi-hop (다중 홉 추론)** | "A회사의 CEO가 이전에 창업했던 회사의 주력 제품은?"<br>

<br>꼬리에 꼬리를 무는 관계 탐색이 필요한 질문. | **Knowledge Graph / Wiki 구조.**<br>

<br>엔티티 간의 관계(Edge)를 따라가야 하므로 온톨로지 기반 검색이 압도적으로 유리. |
| **Comparison (비교 분석)** | "A문서의 1분기 전략과 B문서의 2분기 전략의 차이는?"<br>

<br>서로 다른 두 개 이상의 정보군을 동시에 올려두고 대조해야 함. | **병렬 검색 (Parallel Retrieval).**<br>

<br>에이전트가 쿼리를 2개로 쪼개어 각각 검색한 뒤, 결과를 모아 프롬프트에서 비교. |
| **Global/Aggregation (전체 스캔 및 요약)** | "이 100페이지 매뉴얼 전체에서 가장 많이 언급된 핵심 가치 3가지는?"<br>

<br>특정 지점이 아닌 데이터의 전체적인 흐름이나 통계적 요약 요구. | **문서 전체 주입 / Map-Reduce.**<br>

<br>마이크로소프트 GraphRAG의 'Global Search' 개념. 그래프를 타지 않고 커뮤니티 요약본이나 문서를 통째로 LLM에 넣는 풀스캔 진행. |

## 4. 조사 근거가 아닌 '내 생각' (실무적 한계와 제언)

학술적이고 산업적인 분류 기준은 논리적으로 매우 타당하지만, 실제 시스템으로 구동해 보면 완벽하게 맞아떨어지지 않는 경우가 많습니다. 제 관점에서 덧붙이고 싶은 현실적인 분류 기준과 생각은 다음과 같습니다.

**첫째, '의도 불명(Ambiguous) 쿼리'라는 독자적인 카테고리가 필수적입니다.**
위의 분류 체계는 사용자가 자신이 무엇을 원하는지 명확히 알고 논리적으로 질문했다는 것을 전제로 합니다. 하지만 현실의 사용자는 "이 회사 요즘 어때?", "저번에 말했던 그 문서 찾아봐"처럼 맥락이 생략된 질문을 훨씬 많이 던집니다. 시스템은 이를 억지로 팩트나 요약으로 분류하려다 실패 토큰을 낭비하기 일쑤입니다. 따라서 분류 체계 최상단에 "되묻기(Clarification)가 필요한 쿼리"를 배치하고, 섣불리 DB를 뒤지기 전에 사용자에게 의도를 명확히 해달라고 요청하는 것이 가장 확실한 토큰 절약 방법이라고 생각합니다.

**둘째, '예산 및 지연 시간(Budget & Latency)' 기반의 타협적 라우팅이 필요합니다.**
질문의 텍스트만 보고 "아, 이건 풀스캔 요약이네. 토큰 5만 개 태우자"라고 결정하는 것은 위험합니다. 질문의 성격과 별개로 **시스템의 한계**가 분류의 기준이 되어야 합니다.
예를 들어, 사용자가 풀스캔을 요구하더라도 현재 남은 API 크레딧이 부족하거나 3초 안에 응답해야 하는 제약이 있다면, 시스템은 스스로 쿼리 유형을 강등(Downgrade)하여 "가장 관련성 높은 상위 3개 페이지만 기반으로 요약함"이라는 타협적인 답변을 내놓을 수 있어야 합니다. 즉, 진정한 의미의 유능한 라우터는 쿼리의 의미적 유형뿐만 아니라 '물리적 실행 가능성'까지 동시에 판단해야 한다고 생각합니다.
