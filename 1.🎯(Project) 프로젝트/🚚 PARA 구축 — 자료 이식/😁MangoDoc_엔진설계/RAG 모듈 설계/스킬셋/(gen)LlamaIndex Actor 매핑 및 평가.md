2026년 7월 12일 기준의 최신 LlamaIndex 생태계를 바탕으로, 앞서 정리한 마인드맵의 5가지 카테고리가 실제 프레임워크 내에서 어떻게 구현되는지(액터/API)와 현업 전문가들의 냉혹한 평가를 분류해 드립니다.

단순 튜토리얼 수준을 넘어, 엔터프라이즈 프로덕션 환경에서 수천만 건의 문서를 다뤄본 고수들의 실증적 평가를 기준으로 정리했습니다.

---

## 1. LlamaIndex 프레임워크 지원 현황 (API / Actor 맵핑)

LlamaIndex는 사실상 '데이터와 LLM을 연결하는 가장 방대한 인터페이스'이므로 마인드맵의 대부분을 네이티브 객체(Actor)로 지원합니다. 하지만 프레임워크의 철학상 **'데이터 구조화'에는 압도적이지만 '복잡한 상태 관리'에는 한계**가 있습니다.

### ✅ LlamaIndex가 네이티브로 완벽히 지원하는 것들 (결정적 증거)

1. **표현 방식 (Representation)**
* **하이브리드 검색:** `QueryFusionRetriever` (Vector 검색과 BM25 검색 결과를 융합)
* **멀티 벡터/콜버트:** `ColBERTRetriever` (토큰 단위 지연 연산 인덱싱 지원)


2. **관계 및 구조 (Relational)**
* **GraphRAG:** `PropertyGraphIndex`, `GraphRAGRetriever` (2024년 말부터 대대적으로 개편되어 Neo4j 등과 연동, 엔티티 추출 및 커뮤니티 요약 기능 내장)


3. **계층형 및 맥락 (Hierarchical)**
* **Parent-Child (상위-하위):** `RecursiveRetriever` (검색은 하위 `Node`로, 반환은 상위 `Document`로 수행)
* **동적 병합:** `AutoMergingRetriever` (특정 비율 이상의 자식 청크가 검색되면 자동으로 부모 청크로 병합하여 맥락 반환)
* **요약 기반:** `DocumentSummaryIndex` (문서 전체 요약을 검색한 뒤 세부 탐색)


4. **에이전트 다단계 (Agentic)**
* **라우팅:** `RouterRetriever` (LLM이 질문의 의도를 파악해 Vector, Graph, SQL 중 어디로 갈지 분기)
* **서브 쿼리 분해:** `SubQuestionQueryEngine` (복잡한 질문을 여러 개의 하위 질문으로 쪼개어 병렬 검색)


5. **검색 후 최적화 (Post-Retrieval)**
* **리랭킹:** `CohereRerank`, `BGERerank` (Cross-encoder 기반 순위 재조정 노드)



### ❌ LlamaIndex만으로는 구축하기 어렵거나 지원하지 않는 것 (한계점)

* **초정밀 순환형(Cyclic) 에이전트 상태 제어:** LlamaIndex에도 `Workflows`나 `LlamaAgents`가 도입되었지만, 분기문이 수십 개에 달하고 에러 발생 시 특정 노드로 되돌아가는 복잡한 상태 머신(State-Machine) 설계는 경쟁사인 **LangGraph**에 비해 직관성과 제어력이 떨어집니다. (전문가들은 데이터 파이프라인은 LlamaIndex로 뚫고, 에이전트 오케스트레이션은 LangGraph를 섞어 쓰는 방식을 많이 취합니다.)
* **실시간 스트리밍 임베딩 제어:** 데이터가 초당 수만 건씩 쏟아지는 Kafka/Flink 기반의 실시간 스트리밍 인덱싱은 네이티브로 지원하지 않습니다. 배치(Batch) 기반 파이프라인(`IngestionPipeline`)에 최적화되어 있습니다.

## 2. 전문가/고수들의 실전 평가 (Pros & Cons)

2026년 현재, 논문에서의 성능(Benchmark)이 아닌 **실제 서버비용, 지연시간(Latency), 그리고 환각 제어** 관점에서 고수들이 내린 명확한 호불호 평가입니다.

### 🌟 압도적으로 좋았다고 평가받는 기술 (Must-Have)

**1. 하이브리드 검색 + Cross-Encoder 리랭킹 (`QueryFusionRetriever` + `BGERerank`)**

* **이유:** 고수들이 입을 모아 말하는 "RAG의 국룰 세팅"입니다. 벡터 검색만 쓰면 'SKU-8910' 같은 고유 품번이나 'B2B' 같은 줄임말을 맥락으로 뭉뚱그려버려 찾지 못합니다. BM25가 품번을 잡고 벡터가 맥락을 잡은 뒤, 가벼운 리랭커 모델이 순서를 교정하는 이 파이프라인은 비용 대비 성능이 가장 완벽합니다.

**2. Parent-Child 계층형 검색 (`RecursiveRetriever`)**

* **이유:** "청크 사이즈를 얼마로 해야 하나요?"라는 RAG 초보들의 영원한 난제를 박살낸 킬러 기능입니다. 검색은 정밀하게 200토큰으로 하되, LLM에게 읽힐 때는 1000토큰짜리 전체 문단을 줘서 맥락 단절(Lost in the middle)을 막습니다. 노이즈를 줄이면서도 설명력을 극대화해 실무 만족도가 압도적입니다.

**3. 서브 쿼리 분해 (`SubQuestionQueryEngine`)**

* **이유:** "A사 규정과 B사 규정의 2026년도 차이점"을 한 번에 검색하면 절대 제대로 된 문서가 안 나옵니다. 에이전트가 알아서 [A사 2026 규정], [B사 2026 규정]으로 쿼리를 2개로 쪼개서 병렬 검색하게 만드는 이 기능은 투명성(어느 문서를 참조했는지 추적 가능)이 확보되어 엔터프라이즈 환경에서 매우 선호됩니다.

---

### ⚠️ 실전에서 혹평을 받거나 주의가 필요한 기술 (Trap)

**1. 순진한 Multi-Hop 에이전트 탐색**

* **이유 (Latency & Cascading Error):** 에이전트에게 "알아서 검색 루프를 돌면서 정답을 찾아"라고 던져두는 방식입니다. 데모 영상에서는 멋있지만, 실서비스에서는 첫 번째 검색에서 엉뚱한 문서를 짚으면 그 뒤의 2, 3번째 검색이 모조리 '환각(Hallucination)'으로 빠지는 연쇄 붕괴가 일어납니다. 또한 응답 속도가 10~20초씩 걸려 사용자가 이탈합니다. 전문가들은 무한 루프 에이전트 대신, 라우팅(`Router`)을 통한 1-Depth 검색을 훨씬 선호합니다.

**2. LLM 기반 리랭킹 (`LLMRerank`)**

* **이유 (비용과 속도):** 수집된 문서 100개의 순위를 다시 매기기 위해 프롬프트로 묶어 LLM(GPT-4 등)에게 평가시키는 방식입니다. 성능 자체는 좋지만, 검색할 때마다 API 호출 비용이 미친 듯이 타들어가고 속도가 너무 느립니다. 고수들은 무조건 오픈소스 가중치 모델(Cross-encoder)을 로컬 서버에 띄워 리랭킹을 처리합니다.

**3. 원형 그대로의 GraphRAG (특정 유즈케이스 외 도입 시)**

* **이유 (인덱싱 파산):** LlamaIndex가 `PropertyGraphIndex`를 지원하면서 도입이 쉬워졌지만, 모든 문서에 무지성으로 GraphRAG를 걸면 안 됩니다. 문서를 쪼개서 노드(Entity)와 엣지(Relation)를 뽑아내는 과정 자체를 LLM이 수행해야 하므로 **문서 인덱싱 비용이 기존 벡터 임베딩 대비 수십~수백 배** 비쌉니다. "2026년 우리 회사의 전반적인 기술 부채 트렌드를 요약해 줘" 같은 거시적(Global) 질문에는 최고의 성능을 내지만, 단순 매뉴얼 검색에 쓰면 돈만 낭비하는 '토큰 버너(Token Burner)'라는 평가를 받습니다.
